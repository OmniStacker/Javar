# MySQL锁的分类

按粒度分：表锁、页锁、行锁。按性质分：读锁（共享锁S锁）、写锁（排他锁X锁）。按意向分：意向共享锁（IS）、意向排他锁（IX）。

- **表锁**：锁住整张表，并发度最低。MyISAM 默认表锁。
- **行锁**：锁住某行记录，并发度最高。InnoDB 默认行锁。
- **页锁**：锁住一页数据，介于表锁和行锁之间。

**读锁（S锁）**：允许多个事务同时读取，但阻塞写操作。
**写锁（X锁）**：阻塞其他事务的读和写。
**意向锁**：表级锁，用于快速判断表内是否有行锁，避免逐行检查。事务在加行锁前先加意向锁。

**间隙锁（Gap Lock）**：锁住索引记录之间的间隙，防止其他事务在间隙中插入数据，用于 RR 隔离级别防止幻读。
**临键锁（Next-Key Lock）**：行锁 + 间隙锁，锁住记录本身及其前面的间隙。

# MVCC机制

MVCC（多版本并发控制）通过维护数据的历史版本，让读操作读快照、写操作写最新版本，实现读写不阻塞。

**三个核心组件：**

1. **隐藏字段**：每行数据隐含 `DB_TRX_ID`（事务ID）、`DB_ROLL_PTR`（回滚指针指向Undo Log）、`DB_ROW_ID`（隐藏主键）。
2. **Undo Log**：旧数据拷贝到 Undo Log，通过 `DB_ROLL_PTR` 串成版本链。
3. **ReadView**：快照切片，决定能看到哪个版本。核心字段：`m_ids`（活跃事务ID列表）、`min_trx_id`（低水位）、`max_trx_id`（高水位）、`creator_trx_id`（当前事务ID）。

**可见性算法：**
- `TRX_ID == creator_trx_id`：自己改的，可见。
- `TRX_ID < min_trx_id`：已提交的旧事务，可见。
- `TRX_ID >= max_trx_id`：快照后才出现的事务，不可见。
- `min_trx_id <= TRX_ID < max_trx_id`：在 m_ids 中则不可见（活跃中），不在则可见（已提交）。

**RC vs RR 区别**：RC 每次 SELECT 生成新 ReadView；RR 在第一条快照读时生成 ReadView，之后复用。

# 深分页优化

`LIMIT 1000000, 10` 性能差：MySQL 需扫描并跳过前 100 万行。

**优化方案：**

1. **延迟关联（子查询+覆盖索引）**：
```sql
SELECT * FROM table t1
JOIN (SELECT id FROM table ORDER BY time LIMIT 1000000, 10) t2 ON t1.id = t2.id;
```
先在索引树上找 ID（覆盖索引不回表），再 JOIN 回表。

2. **ID 游标法**（仅适用于 ID 连续且按 ID 排序）：
```sql
SELECT * FROM table WHERE id > last_id ORDER BY id LIMIT 10;
```

3. **限制最大页数**：禁止用户访问过深分页。

# Online DDL

MySQL 5.6+ 支持 Online DDL，允许 DDL 与 DML 并发执行。

**执行三阶段：**
1. **初始化**：评估存储引擎能力，创建可升级的 MDL 读锁。
2. **执行**：短暂使用 MDL 写锁（准备阶段），降级为 MDL 读锁后执行 DDL（最耗时）。
3. **提交**：MDL 读锁升级为写锁，替换表定义，释放锁。

**ALGORITHM 参数：**
- `INPLACE`：原表修改，不生成临时表，不拷贝数据。
- `COPY`：通过临时表创建，需额外存储和 IO。

**LOCK 参数：**
- `NONE`：允许并发读写。
- `SHARED`：阻塞写，允许读。
- `EXCLUSIVE`：阻塞读写。

```sql
ALTER TABLE scores ADD INDEX idx_student_id (student_id), ALGORITHM=INPLACE, LOCK=NONE;
```

**注意**：不是所有 DDL 都支持 Online DDL。操作时尽量在业务低峰期，设置 `lock_wait_timeout` 避免长时间锁等待。

# 表设计经验15条

1. 优先选择 InnoDB 引擎（支持事务、行锁、外键）。
2. 字段尽量 NOT NULL，NULL 值处理麻烦且影响索引。
3. 整数类型选合适的：TINYINT < SMALLINT < INT < BIGINT。
4. 字符串定长用 CHAR，变长用 VARCHAR。
5. 时间类型：DATE、TIME、DATETIME、TIMESTAMP（TIMESTAMP 自动更新但范围有限）。
6. 金额用 DECIMAL，不用 FLOAT/DOUBLE。
7. 主键用自增 INT/BIGINT，避免 UUID 做主键（页分裂多）。
8. 单表字段不宜过多，建议不超过 50 个。
9. 大文本用 TEXT，大二进制用 BLOB，尽量拆分到扩展表。
10. 适当冗余，减少 JOIN。
11. 枚举值用 TINYINT 而非 VARCHAR。
12. 加索引遵循最左前缀原则。
13. 避免在索引列上做函数/运算操作。
14. 预估数据量，提前规划分库分表。
15. 表名、字段名用小写+下划线，避免使用保留字。

# 为什么MySQL默认RR隔离级别

1. **一致性保证**：RR 保证同一事务中相同 SELECT 结果一致，通过快照实现。
2. **防止幻读**：InnoDB 在 RR 下使用间隙锁（Next-Key Lock）防止幻读，比 SQL 标准的 RR 更强。
3. **性能权衡**：SERIALIZABLE 锁住读操作，并发度低；RR 允许更高并发。
4. **MVCC 优化**：读操作不被写操作阻塞，读写性能好。
5. **简化开发**：默认 RR 满足大多数 Web 应用的数据一致性需求。

# order by工作原理

MySQL 排序方式：
1. **全字段排序**：将所有字段放入 sort_buffer 排序。
2. **rowid 排序**：当单行数据过大时，只放入排序字段 + rowid，排序后回表取数据。

**sort_buffer 不够用时**：使用磁盘临时文件（外部排序，多路归并）。

**优化**：
- 为 ORDER BY 字段加索引，避免 filesort。
- 联合索引覆盖排序字段和查询字段，避免回表。

# MySQL索引数据结构

**为什么用 B+ 树：**
- 二叉树/红黑树：高度随数据量增长，磁盘 IO 多。
- B 树：非叶子节点也存数据，范围查询效率低。
- B+ 树：非叶子节点只存索引，叶子节点存数据且通过链表连接，范围查询高效，磁盘 IO 少。
- Hash 索引：等值查询 O(1)，但不支持范围查询。

**聚簇索引 vs 非聚簇索引：**
- **聚簇索引**：叶子节点直接存行数据，一个表只有一个（主键索引）。
- **非聚簇索引（二级索引）**：叶子节点存主键值，需回表查数据。

**InnoDB vs MyISAM：**
- InnoDB：聚簇索引，数据和主键索引在一起。
- MyISAM：非聚簇索引，索引和数据分开存储。

**索引下推（ICP）**：在联合索引中，将部分过滤条件下推到存储引擎层，减少回表次数。

**索引合并**：对多个索引的查询结果取交集/并集，减少全表扫描。

# Explain详解

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;
```

| 列 | 说明 |
|---|---|
| **id** | 查询序号，越大越先执行 |
| **select_type** | SIMPLE/PRIMARY/SUBQUERY/DERIVED/UNION |
| **table** | 表名 |
| **type** | 访问类型：system > const > eq_ref > ref > range > index > all |
| **possible_keys** | 可能使用的索引 |
| **key** | 实际使用的索引 |
| **key_len** | 索引使用的字节数（可判断联合索引用了几个列） |
| **ref** | 索引比较的列或常量 |
| **rows** | 估算扫描行数 |
| **filtered** | 过滤后剩余百分比 |
| **Extra** | 额外信息 |

**type 列详解：**
- `system`：表只有一行。
- `const`：通过主键或唯一索引等值查询，最多一条。
- `eq_ref`：JOIN 中使用主键或唯一索引等值匹配，最多一条。
- `ref`：通过普通索引等值匹配。
- `range`：索引范围扫描。
- `index`：全索引扫描。
- `all`：全表扫描。

**Extra 列详解：**
- `Using index`：覆盖索引，不回表。
- `Using where`：需在 Server 层过滤。
- `Using index condition`：索引下推。
- `Using temporary`：使用临时表。
- `Using filesort`：需要额外排序。
- `Select tables optimized away`：优化器已计算出结果，无需执行。

**key_len 计算规则**：CHAR(n)=n字节，VARCHAR(n)=n+1/2字节，INT=4，BIGINT=8，允许 NULL 额外+1。

# 索引优化最佳实践

1. **全值匹配**：查询条件覆盖联合索引所有列。
2. **最左前缀法则**：联合索引从最左列开始使用，不跳过中间列。
3. **不在索引列上做操作**：函数、运算、类型转换都会导致索引失效。
4. **范围查询右边的列失效**：联合索引中范围查询后的列无法使用索引。
5. **覆盖索引**：查询字段都在索引中，避免回表。
6. **不等空值 OR 优化**：`!=`、`IS NULL`、`OR` 可能导致索引失效。
7. **LIKE 百分号写最右**：`LIKE 'abc%'` 走索引，`LIKE '%abc'` 不走。
8. **字符串不加单引号**：隐式类型转换导致索引失效。

# SQL优化实战

```sql
-- 创建测试表
CREATE TABLE student (id INT AUTO_INCREMENT PRIMARY KEY, name VARCHAR(50), age INT);
CREATE TABLE scores (id INT AUTO_INCREMENT PRIMARY KEY, student_id INT, score INT);
```

**优化要点：**
1. **避免 SELECT \***：只查需要的列，减少 IO。
2. **小表驱动大表**：用小表做外层循环，如 `IN` 代替 `JOIN`（当子查询结果集小时）。
3. **用 JOIN 代替子查询**：子查询可能产生临时表。
4. **提升 GROUP BY 效率**：先 WHERE 过滤再 GROUP BY。
5. **批量操作**：`INSERT ... VALUES (...), (...), (...)` 代替逐条插入。
6. **LIMIT 优化**：百万级翻页用延迟关联。
7. **UNION ALL 代替 UNION**：UNION 需去重，UNION ALL 不去重。
8. **JOIN 表不宜过多**：建议不超过 3 张表。

# MySQL各种锁详解

**全局锁**：`FLUSH TABLES WITH READ LOCK`，整个数据库只读，用于备份。

**表级锁**：
- **表锁**：`LOCK TABLES ... READ/WRITE`。
- **MDL 锁（元数据锁）**：自动管理，DML 加 MDL 读锁，DDL 加 MDL 写锁。

**行级锁**：
- **记录锁（Record Lock）**：锁住索引记录。
- **间隙锁（Gap Lock）**：锁住记录间的间隙，防止插入。
- **临键锁（Next-Key Lock）**：记录锁 + 间隙锁。

**意向锁**：表级，加行锁前先加意向锁，快速判断表内是否有行锁。

**悲观锁 vs 乐观锁**：
- 悲观锁：`SELECT ... FOR UPDATE`，先锁再改。
- 乐观锁：版本号机制，`UPDATE ... SET version=version+1 WHERE version=?`。

**锁排查工具**：
```sql
SHOW ENGINE INNODB STATUS;  -- 查看锁信息
SELECT * FROM information_schema.INNODB_TRX;  -- 查看事务
SELECT * FROM performance_schema.data_locks;  -- MySQL 8.0 查看锁
```

**锁优化策略**：合理设计索引、缩短事务、降低隔离级别、按固定顺序加锁。

# NULL和NOT NULL是否走索引

**结论**：NULL 值是否走索引取决于 MySQL 版本和数据分布。

- MySQL 5.7：`IS NULL` 走 `ref`，`IS NOT NULL` 可能走 `range` 或 `ALL`。
- MySQL 8.0：组合条件中 NULL 的处理更优化，但大数据量下仍可能全表扫描。

**NULL 值分布影响**：如果 NULL 值占比很小，走索引收益高；如果占比大，优化器可能选择全表扫描。

**建议**：尽量用 NOT NULL + 默认值（如 0、空字符串），避免 NULL 的三值逻辑问题。

# 图解MySQL索引失效

**索引存储结构**：InnoDB 聚簇索引（数据+索引在一起），二级索引（存主键值，需回表）。

**6 种索引失效场景：**

1. **左模糊匹配**：`LIKE '%abc'` 不走索引（无法利用 B+ 树有序性）。
2. **对索引列使用函数**：`WHERE YEAR(date) = 2023` 不走索引。
3. **对索引列做表达式计算**：`WHERE price + 10 > 100` 不走索引，改为 `WHERE price > 90`。
4. **隐式类型转换**：`WHERE phone = 13800138000`（phone 是 VARCHAR）不走索引。
5. **联合索引非最左匹配**：索引 `(a,b,c)`，查 `WHERE b=1` 不走索引（MySQL 8.0 可能触发 Skip Scan）。
6. **OR 条件**：`WHERE a=1 OR b=2`，如果 b 无索引则全表扫描。

# MySQL自增ID用完怎么办

四种自增 ID：

1. **表定义自增 ID**：`AUTO_INCREMENT`，INT 最大约 21 亿，BIGINT 约 9.2×10^18。用完后插入报错，需改用 BIGINT 或分表。
2. **InnoDB row_id**：未定义主键时隐式生成，6 字节，最大 2^48。用完后循环覆盖，数据混乱。
3. **Xid**：事务 ID，由 server 层维护，8 字节。
4. **trx_id**：InnoDB 事务 ID，6 字节，循环使用。

**建议**：主键用 BIGINT UNSIGNED，最大 2^64-1，基本不会用完。

# NULL值5大致命陷阱

1. **COUNT 丢失**：`COUNT(column)` 不统计 NULL 值，`COUNT(*)` 统计所有行。
2. **比较结果未知**：`NULL = NULL` 结果为 NULL（非 TRUE），`WHERE column = NULL` 查不出数据，需用 `IS NULL`。
3. **运算结果为 NULL**：`NULL + 1 = NULL`，任何值与 NULL 运算结果都是 NULL。
4. **聚合函数空指针**：`AVG(column)` 忽略 NULL 行，可能导致结果偏差。
5. **GROUP BY 统计 NULL**：`GROUP BY` 将 NULL 视为一个分组，可能产生意外结果。

# 唯一索引+NULL导致重复数据

**问题**：唯一索引对 NULL 不生效，因为 `NULL != NULL`（三值逻辑）。可以插入多条 `column = NULL` 的记录。

**逻辑删除表加唯一索引的 3 种方案：**

1. **用 0/特殊值代替 NULL**：删除时设为 0 而非 NULL，唯一索引生效。
2. **联合唯一索引**：`(column, is_deleted)`，删除时 `is_deleted` 设为 ID。
3. **部分索引（MySQL 8.0）**：`CREATE UNIQUE INDEX ... WHERE is_deleted = 0`。

# 优化器选择非预期索引

**原因：**

1. **统计信息偏差**：采样页数不足导致基数估算错误。修复：`ANALYZE TABLE`。
2. **查询条件陷阱**：隐式类型转换、函数操作导致索引不可用。
3. **索引设计缺陷**：联合索引列顺序不合理、缺少覆盖索引、冗余索引干扰。
4. **成本计算模型局限**：基于估算而非实际耗时，SSD 环境仍用 HDD 默认成本参数。
5. **环境干扰**：Buffer Pool 未预热、optimizer_switch 设置不当。

**解决方案：**

```sql
-- 更新统计信息
ANALYZE TABLE orders;

-- 修正查询写法（避免函数/类型转换）
SELECT ... WHERE phone = '13800138000';
SELECT ... WHERE create_time >= '2023-01-01 00:00:00' AND create_time < '2023-01-02 00:00:00';

-- 重建复合索引（范围列前置）
CREATE INDEX idx_new ON orders(create_time, status);

-- 添加覆盖索引
CREATE INDEX idx_cover ON orders(user_id, status, amount);

-- SSD 优化参数
-- innodb_io_capacity=20000, optimizer_switch='index_merge=on'

-- 虚拟计算列 + 函数索引
ALTER TABLE orders ADD COLUMN create_date DATE AS (DATE(create_time)) VIRTUAL;
CREATE INDEX idx_func ON orders(create_date);
```

# count(1)、count(*)与count(列名)的区别

| 用法 | 统计内容 | NULL 处理 |
|------|----------|-----------|
| `COUNT(1)` | 所有行 | 不忽略 |
| `COUNT(*)` | 所有行 | 不忽略 |
| `COUNT(column)` | 该列非 NULL 的行数 | 忽略 NULL |

**性能**：`COUNT(*)` 和 `COUNT(1)` 基本相同，InnoDB 对 `COUNT(*)` 有优化。`COUNT(column)` 可能更慢（需检查 NULL）。

**选择建议**：统计总行数用 `COUNT(*)`，需忽略 NULL 用 `COUNT(column)`。

**COUNT(*) 慢的优化：**
1. 不需精确值时用 `EXPLAIN` 估算或查 `information_schema.tables`。
2. 走主键索引：加 `WHERE id > 0`。
3. 分批查询汇总。
4. 用缓存或单独的统计表维护计数。

# 为什么MySQL单表不要超过2000W数据

**B+ 树索引结构限制：**

- 页大小 16KB，主键 BIGINT 8 字节，指针 6 字节。
- 非叶子节点单页可存：16384 / (8+6) ≈ 1170 条。
- **高度为 3**：1170 × 1170 ≈ 1.37M 个叶子页，每页约 15 行（1KB/行）→ 约 2000 万行。
- **高度为 4**：查询需 4 次 IO，性能显著下降。

**2000 万是经验平衡点**：在 B+ 树高度从 3 变 4 的临界值附近，写入和范围查询效率骤降。

**其他因素**：行溢出（TEXT/BLOB）、碎片化、过多二级索引。

**优化建议**：冷热分离、分库分表、合理设计索引。

# 一次性查2000万数据，MySQL会OOM吗？

**结论：MySQL 服务端不会 OOM。**

MySQL 采用**流式协议（边读边发）**：
1. InnoDB 扫描一行数据。
2. 写入 `net_buffer`（默认 16KB）。
3. `net_buffer` 写满后通过网络发送。
4. 发送成功后清空 `net_buffer`，继续读下一行。

服务端内存占用始终只有 `net_buffer_length` 大小。真正可能 OOM 的是客户端（如 Java List 接不住）。

**真正的隐患——Buffer Pool 污染：**

全表扫描会将冷数据读入 Buffer Pool，朴素 LRU 会把热点数据挤出内存，导致磁盘 IO 飙升，系统雪崩。

**InnoDB 的防御——冷热分离 LRU：**

- LRU 链表按 5:3 分为 young 区和 old 区。
- 新数据默认插入 old 区头部（Midpoint Insertion）。
- `innodb_old_blocks_time`（默认 1000ms）：数据页在 old 区停留超过 1 秒才能晋升到 young 区。
- 全表扫描的数据页访问间隔极短（毫秒级），不满足晋升条件，只在冷区被淘汰，热点数据纹丝不动。

# 添加索引真的不会锁表吗？（OnlineDDL）

MySQL 5.6+ 的 Online DDL 允许加索引时不阻塞 DML。

- `ALGORITHM=INPLACE, LOCK=NONE`：不阻塞读写。
- `ALGORITHM=COPY, LOCK=EXCLUSIVE`：阻塞读写。

Online DDL 执行中两次获取 MDL 锁：准备阶段短暂 MDL 写锁 → 降级为 MDL 读锁 → 执行 DDL → 提交阶段升级为 MDL 写锁 → 释放。

**注意**：如果已有事务持有 MDL 锁，Online DDL 会等待。建议在业务低峰期操作，设置 `lock_wait_timeout`。

# 讲讲你对MVCC的理解

**核心思想**：通过维护数据多个历史版本，让读操作读快照、写操作写最新版本，实现读写并行互不阻塞。

**三驾马车：隐藏字段、Undo Log、ReadView。**

1. **隐藏字段**：`DB_TRX_ID`（事务ID）、`DB_ROLL_PTR`（回滚指针）、`DB_ROW_ID`（隐藏主键）。二级索引没有这些字段，但有 `PAGE_MAX_TRX_ID`，需回表到聚簇索引做版本判断。

2. **Undo Log（版本链）**：更新时旧数据拷贝到 Undo Log，`DB_ROLL_PTR` 串成版本链。

3. **ReadView**：`m_ids`（活跃事务列表）、`min_trx_id`（低水位）、`max_trx_id`（高水位）、`creator_trx_id`（当前事务）。

**可见性算法：**
- `TRX_ID == creator_trx_id`：可见（自己改的）。
- `TRX_ID < min_trx_id`：可见（已提交）。
- `TRX_ID >= max_trx_id`：不可见（快照后产生）。
- `min_trx_id <= TRX_ID < max_trx_id`：在 m_ids 中不可见，不在则可见。

**RC vs RR**：RC 每次 SELECT 生成新 ReadView；RR 在第一条快照读时生成，之后复用。

**面试避坑：**
1. **MVCC 能完全解决幻读吗？** 快照读解决了（ReadView 复用），当前读（`SELECT FOR UPDATE`）需 Next-Key Lock 解决。
2. **"看不见"的数据能 UPDATE 吗？** 能。UPDATE 是当前读，直接读最新数据。更新后 `TRX_ID` 变为自己的，再次 SELECT 就能看见。
3. **Undo Log 会无限膨胀吗？** 不会。Purge 线程自动清理不再需要的 Undo Log。长事务会导致 ReadView 不关闭，Undo Log 无法回收。

1. **EXPLAIN 诊断**：查看 type（目标 ref/range）、key、Extra。
2. **常见原因**：函数/表达式、左模糊 `LIKE '%abc'`、不等式 `<>`/`NOT IN`、复合索引范围条件后列失效、隐式类型转换。

6. **检查锁和事务**：锁争用、隔离级别可能影响索引使用。

8. **配置和硬件优化**：调整内存分配、连接池，使用 SSD。

# 我查这么多数据，会不会把数据库内存打爆？

**不会。** MySQL 采用"边读边发"策略：

1. 取一行写入 `net_buffer`（默认 16KB）。
2. 写满后发送，成功则清空继续取下一行。
3. 发送失败（socket buffer 满）则等待。

服务端内存占用最大就是 `net_buffer_length`，不会达到 200G。

**InnoDB Buffer Pool 影响**：全表扫描会读入数据页，但 InnoDB 的改进 LRU（冷热分离 + `innodb_old_blocks_time`）保证全表扫描的数据只在 old 区，不污染 young 区热点数据。

# MySQL8的索引跳跃扫描（Skip Scan）

MySQL 8.0.13+ 引入索引跳跃扫描。对于联合索引 `(a, b)`，查询 `WHERE b = 1`（跳过 a）：

- **传统**：不走索引（违反最左前缀）。
- **MySQL 8.0+**：如果 a 的区分度低（如枚举值），优化器将索引按 a 的唯一值分区，每个分区内扫描 `b = 1`，实现 Skip Scan。

适用于前导列基数低的场景。可通过 EXPLAIN 确认。

# 用了索引还是慢可能是什么原因

1. **索引不匹配查询**：前缀不匹配或联合索引顺序错误。
2. **数据分布不均**：索引选择性差。
3. **索引维护开销**：写多读少的表，索引拖慢写入。
4. **查询其他部分未优化**：大结果集排序/聚合。
5. **硬件资源限制**：IO/CPU/内存瓶颈。
6. **统计信息过期**：`ANALYZE TABLE` 更新。
7. **锁争用**：高并发写操作。
8. **表设计不合理**：字段类型过大、未规范化。

# 加密后的数据该如何支持模糊查询

**方案一：内存解密**（数据量少可用）
- 查出所有数据，内存中解密后匹配。缺点：数据量大时 OOM。

**方案二：映射查询**
- 建映射表（明文手机号 + 加密手机号 + userID），查映射表再查主表。缺点：明文仍存在。

**方案三：数据库加密函数**
- 用数据库加解密函数先解密再 LIKE。缺点：无法走索引。

**方案四：分片加密**（推荐）
- 将字段按 4 字符一组滑动分片，每片加密存储。查询时加密条件片段，`LIKE "%partial%"` 查库。

```java
String mobile = "12345678765";
int index = 0;
while (index + 4 <= mobile.length()) {
    String segment = mobile.substring(index, index + 4);
    // 加密 segment 并存储/查询
    index++;
}
```

# MySQL索引设计有哪些原则

1. **选择合适的列**：频繁查询条件、排序/分组、JOIN 连接字段。
2. **复合索引最左前缀**：最常用的列放前面。
3. **控制索引数量**：每个索引影响写性能。
4. **高选择性列优先**：基数高、区分度大的列。
5. **避免冗余索引**：定期清理不再使用的索引。
6. **覆盖索引**：索引包含查询所有列，避免回表。
7. **考虑写性能影响**：频繁更新的列慎加索引。
8. **大数据集考虑分区**：结合分区/分片设计。

# InnoDB存储引擎三大特性

### Buffer Pool

- 缓存数据页和索引页的内存区域，先查 Buffer Pool 再查磁盘。
- LRU 算法管理，改进版冷热分离（young/old 区按 5:3 划分）。
- `innodb_buffer_pool_size`：建议设为物理内存的 70%。

### Adaptive Hash Index（AHI）

- 自动监控索引使用，对频繁等值查询的索引建立哈希索引，加速查询。
- 仅支持等值比较（`=`、`<=>`、`IN`），不支持排序。
- `innodb_adaptive_hash_index`：默认启用，高并发 CPU 紧张时可禁用。

### Double Write

- 数据页先写入 Double Write Buffer，再写入数据文件。
- 崩溃时从 Double Write Buffer 恢复数据，保证数据完整性。
- `innodb_doublewrite`：默认启用。

# 哪些场景可以利用索引覆盖来优化SQL

1. **全表 COUNT 查询**：为统计列建索引，直接扫描索引。
2. **避免回表查询**：升级为联合索引覆盖所有查询列。
3. **分页查询**：联合索引覆盖排序和返回列。
4. **无 WHERE 条件查询**：索引覆盖查询列，避免全表扫描。
5. **WHERE 区分度低**：联合索引覆盖仍可减少数据访问。
6. **仅查主键**：辅助索引直接返回主键，无需回表。
7. **JOIN 和 ORDER BY**：覆盖索引减少表访问和排序开销。

**注意**：仅 B-Tree 索引支持覆盖；避免 SELECT *；权衡读写比例。

# 对索引的了解？哪些字段适合加索引，哪些不适合

**常见索引类型**：B树索引（默认，支持范围查询）、哈希索引（等值查询）、全文索引（大文本搜索）、复合索引（多字段联合）。

**适合加索引：**
1. 高基数字段（用户ID、订单号、手机号）。
2. 经常作为查询条件的字段（WHERE/JOIN/ORDER BY/GROUP BY）。
3. 外键和表连接字段。
4. 经常排序/分组的字段。

**不适合加索引：**
1. 低基数字段（性别、状态）。
2. 频繁更新的字段。
3. 超长文本/BLOB 字段。
4. 小表（全表扫描更快）。

**最佳实践**：合理设计复合索引、避免过多索引、覆盖索引优先、定期清理冗余索引、区分度高的列放前面。

# MySQL只操作同一条记录也会死锁吗

**会。** 可能的场景：

1. **索引导致锁竞争**：不同事务用不同索引查找同一行，锁顺序不同。
2. **自增锁**：并发自增列竞争。
3. **外键约束**：多表锁顺序不同。

**解决方法**：合理索引、缩短事务、统一加锁顺序、死锁重试机制（MySQL 死锁错误码 1213）。

```java
// 死锁重试示例
int attempts = 0;
while (attempts < MAX_RETRIES) {
    try {
        // 执行更新
        break;
    } catch (SQLException e) {
        if (e.getErrorCode() == 1213 && attempts < MAX_RETRIES - 1) {
            TimeUnit.SECONDS.sleep(RETRY_DELAY);
        } else throw e;
    }
}
```

**全链路优化思路：**

**1. 发现（监控）**：慢查询日志（阈值 1s）+ pt-query-digest 分析；Prometheus + Grafana 监控 QPS、锁等待、IO。

# 100W数据去重，该用distinct还是groupby

**功能上**：仅去重时两者等效，优化器生成相似执行计划。

**可读性**：`DISTINCT` 语义更直接（"返回唯一行"），优先推荐。`GROUP BY` 主要用于聚合，不带聚合函数时去重非其主要设计目的。

**性能**：关键在于是否有合适索引，而非 DISTINCT vs GROUP BY。无索引时两者都慢。

**需要聚合时**：用 `GROUP BY`（如 `COUNT(*)` 统计重复次数）。

**建议**：去重用 `DISTINCT`，性能靠索引，用 `EXPLAIN` 验证。

# SQL用了函数一定会索引失效吗

**不一定。**

**会失效**：在 WHERE 子句中对索引列使用函数（`LOWER(column)`）或计算表达式（`column + 1`），因为索引基于原始值构建。

**不会失效**：函数在 SELECT 列表、ORDER BY、GROUP BY 中使用，不影响 WHERE 的索引。

**优化建议**：
- 使用生成列（MySQL 5.7+）：`ADD COLUMN col_lower VARCHAR(255) GENERATED ALWAYS AS (LOWER(col)) STORED, ADD INDEX (col_lower)`。
- 在应用层处理函数转换。

# 为什么大厂不建议使用多表join

1. **性能**：多表 JOIN 计算复杂，占用大量内存和 CPU，依赖索引。
2. **可扩展性**：分布式数据库中跨节点 JOIN 传输大量数据，分片困难。
3. **维护复杂度**：复杂 SQL 难以理解和调试。
4. **架构设计**：微服务架构中数据去中心化，JOIN 违反服务数据自治。

**替代策略**：反范式化（适当冗余）、分而治之（应用层组合）、预先计算（ETL）、使用 NoSQL。

# where条件的顺序影响索引使用吗

**大多数情况不影响。** MySQL 优化器会重新排列 WHERE 条件以优化索引使用。

**关键点**：
1. 优化器可独立于条件书写顺序选择执行计划。
2. 复合索引遵循最左前缀原则（与 WHERE 顺序无关，与索引列顺序有关）。
3. 范围条件后的索引列失效（与条件位置无关，与索引列位置有关）。

**最佳实践**：为可读性让 WHERE 顺序与索引列顺序一致，用 EXPLAIN 验证。

---

# 为什么不推荐使用外键

1. **性能**：插入/删除需额外完整性检查，批量操作变慢。
2. **灵活性**：数据迁移和重构困难，表间依赖性强。
3. **事务复杂性**：多表级联操作管理复杂。
4. **分布式局限**：微服务/分布式数据库中跨服务外键难以实现。
5. **锁争用**：高并发写操作时外键约束增加锁争用。

**替代**：应用层通过业务逻辑维护数据一致性。

**适合用外键**：明确数据完整性需求、简单数据模型、开发效率优先的小项目。

---

# MySQL的行级锁锁的到底是什么

**行级锁锁的是索引记录**，而非物理行。

- 有索引时：锁住符合条件的索引项对应的行。
- 无索引时：退化为表锁（InnoDB 需要走隐式主键索引）。
- RR 隔离级别下还会加间隙锁/Next-Key Lock 防止幻读。

**要点**：合理设计索引，确保行锁精确加锁，避免锁升级。

---

# Mysql默认RR，大厂为啥要改成RC

1. **更高并发**：RC 读操作不持有间隙锁，减少锁争用。
2. **降低死锁概率**：无间隙锁，插入/更新时锁竞争减少。
3. **Web 应用适配**：对强一致性要求不如事务型应用，RC 足够。
4. **简化开发**：无需处理 RR 的复杂锁定问题。
5. **缓存协同**：外层缓存保证最终一致性，RC 降低数据库负担。
6. **减少事务开销**：事务提交/回滚更快。

---

# 区分度不高的字段建索引一定没用吗

**不一定。** 低选择性字段单独建索引收益有限，但在以下情况仍有价值：

1. **固定值查询**：状态标志字段频繁等值查询。
2. **与高选择性字段组合**：复合索引中作为非前导列。
3. **覆盖索引的一部分**：使查询成为覆盖索引。
4. **统计聚合**：分组操作可通过索引加速。

需结合具体场景权衡，用性能测试验证。

---

# 为什么不建议使用存储过程

1. **可移植性差**：绑定特定数据库，迁移需重写。
2. **调试困难**：缺乏良好的调试工具。
3. **版本控制挑战**：难以纳入代码库团队协作。
4. **复杂性和可读性**：业务逻辑分散到数据库，维护困难。
5. **性能问题**：执行计划限制或缓存策略不足时可能不如应用代码。

**适合场景**：高性能需求（减少网络往返）、复杂事务控制、多应用共享逻辑。

---

# 什么时候索引失效反而提升效率

1. **小表查询**：全表扫描比索引逐行查找更快。
2. **返回大部分行**（>30%）：索引回表开销大，全表扫描更有效。
3. **低选择性索引**：布尔字段等，索引过滤效果差。
4. **频繁更新的表**：减少索引降低写操作负担。
5. **复杂查询**：优化器选择不用某索引以提高整体效率。
6. **优化器误判**：手动禁用索引可能提升性能。

用 EXPLAIN 分析评估。

---

# MySQL中like模糊查询如何优化

1. **前缀匹配**：`LIKE 'prefix%'` 走索引。
2. **反向索引**：对后缀匹配 `LIKE '%suffix'`，创建反转字符串列并建索引。
```sql
ALTER TABLE users ADD reversed_username VARCHAR(255);
UPDATE users SET reversed_username = REVERSE(username);
CREATE INDEX idx_reversed ON users(reversed_username);
```
3. **限制扫描范围**：加其他条件缩小范围。
4. **缓存**：应用层缓存频繁查询。
5. **全文搜索引擎**：Elasticsearch/Solr 替代 LIKE。

---

# MySQL的深度分页如何优化

1. **主键游标法**：`WHERE id > last_id ORDER BY id LIMIT page_size`。
2. **子查询+JOIN**：先查 ID 再回表。
```sql
SELECT t.* FROM table t
JOIN (SELECT id FROM table ORDER BY id LIMIT offset, page_size) sub ON t.id = sub.id;
```
3. **覆盖索引**：分页查询字段被索引覆盖。
4. **缓存**：Redis 缓存分页结果。
5. **限制最大页数**：禁止过深翻页。

---

# Innodb加索引的时候会锁表吗

MySQL 5.6+ 支持 Online DDL，加索引时不锁表（`LOCK=NONE`）。

- 在线添加索引期间允许并发读写。
- 可能有短暂锁定（元数据更新），但不会长期锁表。
- 旧版本（5.5 及以前）加索引会锁表。

建议在低峰期操作，检查 MySQL 版本支持的功能。

---

# 为什么MySQL8.0要取消查询缓存

1. **全局锁定**：表修改时刷新缓存，全局锁影响并发。
2. **竞争争用**：高并发写环境下锁争用严重。
3. **命中率低**：动态数据频繁失效。
4. **维护复杂**：额外监控和刷新开销。
5. **替代方案**：Redis/Memcached 等外部缓存更高效。
6. **仅支持简单 SELECT**：复杂查询无法缓存。

MySQL 8.0 移除查询缓存，简化引擎设计，鼓励使用外部缓存。

# 一条SQL的执行过程是怎样的

1. **连接器**：建立连接，验证身份和权限。
2. **查询缓存**（MySQL 8.0 已移除）：命中则直接返回。
3. **分析器**：词法/语法分析，检查表、列、函数合法性。
4. **优化器**：生成执行计划，选择索引、连接顺序。
5. **执行器**：调用存储引擎接口执行查询。
6. **存储引擎**：从磁盘/内存读取或写入数据。
7. **返回结果**：结果经执行器、连接器返回客户端。

# 说下你对分库分表的理解

**水平切分（Sharding）**：同一表的记录拆分到多个结构相同的表，分散到不同节点。

**垂直切分**：按列拆分，常用列和不常用列分到不同表。

**面临问题和解决方案：**
1. **数据一致性**：跨节点事务用 2PC、最终一致性或分布式事务工具。
2. **跨分片查询**：分布式查询引擎、数据聚合、缓存。
3. **全局唯一 ID**：Snowflake 等分布式 ID 生成器。

---

# 高并发场景下，如何安全修改同一行数据

1. **乐观锁**：版本号/时间戳字段，更新时检查版本，冲突则重试。
2. **悲观锁**：`SELECT ... FOR UPDATE` 加锁，其他请求阻塞。
3. **分布式锁**：Redis SETNX 或 ZooKeeper 临时节点。
4. **事务**：数据库自动加行锁，串行化执行。

注意锁粒度、性能开销和死锁问题。

# 索引失效的情况有哪些

口诀"**模型数空运最快**"：

- **模**糊查询：`LIKE '%abc'` 左模糊失效。优化：覆盖索引或 `%` 放后面。
- **型**：数据类型不匹配，隐式转换失效。
- **数**（函数）：索引列做函数处理失效。
- **空**：NULL 值需慎重，唯一索引有 NULL 时 `NOT NULL & NULL` 可能失效。
- **运**算：索引列做运算失效。
- **最**左匹配：联合索引不满足最左前缀失效。
- **快**（扫描比）：索引检索值超过临界比例，全表扫描更快则不走索引。

# 为什么需要数据库连接池呢

1. **提高性能**：避免频繁创建/销毁连接的开销。
2. **资源管理**：复用连接，避免连接过多耗尽资源。
3. **并发处理**：多请求共享连接，提高并发能力。
4. **连接可靠性**：检测失效连接并重建。

# 分库分表下如何实现精准分页？

**跨分片**：记录游标分页，每个分片记录上一页/下一页最后一条记录的主键，根据游标定位。

**跨库**：
- **数据同步**：分片数据复制到统一主库，在主库分页。
- **查询路由**：将请求发送到各分片执行分页，合并结果返回。

需考虑数据一致性和容错性。

---

# 什么是最左前缀原则？

复合索引 `(A, B, C)` 的使用必须从最左列开始，不能跳过中间列：
- `WHERE A=1 AND B=2 AND C=3` ✅
- `WHERE A=1 AND B=2` ✅
- `WHERE A=1` ✅
- `WHERE B=2 AND C=3` ❌（跳过 A）
- `WHERE A=1 AND C=3`（只用 A，C 无法用索引）

好处：减少索引扫描数据量，节省磁盘空间和维护开销。

---

# 并发事务带来哪些问题

1. **脏读**：读到其他事务未提交的数据。
2. **不可重复读**：同一事务多次读取同一数据结果不同（其他事务修改/删除并提交）。
3. **幻读**：同一事务多次查询同一范围结果数量不同（其他事务插入并提交）。
4. **丢失修改**：多个事务同时修改同一数据，部分修改被覆盖。

**不可重复读 vs 幻读**：不可重复读重点是修改（列值变化），幻读重点是新增/删除（行数变化）。

---

# 数据库cpu飙升，你会如何处理

1. **查询性能问题**：慢查询日志 + EXPLAIN 分析，索引优化/重写 SQL。
2. **连接问题**：检查连接池配置、连接数限制、闲置连接。
3. **锁和死锁**：查看锁状态、死锁日志，调整事务并发控制。
4. **配置问题**：缓冲区大小、并发连接数、线程池大小。
5. **资源竞争**：监控内存/磁盘 IO，调整资源配置。

# B树和B+树的区别？

| 特性 | B树 | B+树 |
|------|-----|------|
| 数据存储 | 所有节点都存键和值 | 只有叶子节点存数据 |
| 数据检索 | 可在非叶子节点找到数据 | 必须到叶子节点 |
| 范围查询 | 需遍历多层级，效率低 | 叶子节点链表连接，效率高 |
| 适用场景 | 随机读写 | 范围查询和顺序访问 |

---

# MySQL索引底层结构为什么使用B+树

1. **良好的平衡性**：自平衡，快速定位数据。
2. **顺序访问性**：叶子节点有序且链表连接，范围查询高效，磁盘预读友好。
3. **存储效率**：非叶子节点只存索引值，节点更大，IO 次数少。
4. **支持高并发**：合适的锁/隔离级别下并发读写不严重阻塞。
5. **易于扩展和维护**：插入/删除只调整少数节点。

---

# MySQL为什么默认引擎是InnoDB

1. **支持事务**：ACID 特性。
2. **行级锁**：高并发下锁冲突少（MyISAM 只有表锁）。
3. **外键约束**：保证数据完整性。
4. **崩溃恢复**：自动恢复数据一致性。
5. **热备份**：在线备份不停止服务。

# where 1=1会不会影响性能？

- **MySQL < 5.7**：`WHERE 1=1` 可能影响性能，建议用 MyBatis `<where>` 标签。
- **MySQL >= 5.7**：常量折叠优化会在编译期消除 `1=1`，不影响性能。两种方式随便选。

可通过 `SHOW WARNINGS` 查看 `1=1` 被优化掉。

# 说下你对数据库事务的理解

事务是一系列数据库操作的逻辑单元，要么全部成功，要么全部回滚。

**ACID 特性：**
- **原子性（A）**：所有操作要么全执行，要么全回滚。
- **一致性（C）**：事务前后数据库保持一致状态（如转账前后总额不变）。
- **隔离性（I）**：并发事务互不干扰。
- **持久性（D）**：提交后数据永久保存。

# mysql中in和exists的区别

- **IN**：提供固定值列表，判断列值是否在列表中。适合子查询结果集小的情况。
  ```sql
  SELECT * FROM t WHERE col IN (v1, v2, v3);
  ```
- **EXISTS**：判断子查询是否返回至少一行。适合外表小、子查询关联的情况。
  ```sql
  SELECT * FROM t WHERE EXISTS (SELECT 1 FROM t2 WHERE t2.id = t.id);
  ```

**选择**：小表 IN，大表 EXISTS（"小表驱动大表"）。

---

# 数据库三大范式是什么

- **1NF**：每列不可再分（原子值）。
- **2NF**：在 1NF 基础上，非主键列完全依赖主键（消除部分依赖）。
- **3NF**：在 2NF 基础上，非主键列直接依赖主键（消除传递依赖）。

目的：减少冗余、提高一致性和可维护性。实际中可适度反范式化。

# MyISAM索引与InnoDB索引的区别？

| 特性 | MyISAM | InnoDB |
|------|--------|--------|
| 存储方式 | 非聚簇索引（索引和数据分开） | 聚簇索引（索引和数据一起） |
| 锁机制 | 表级锁 | 行级锁 |
| 事务 | 不支持 | 支持 ACID |
| 外键 | 不支持 | 支持 |
| 适用场景 | 读密集型 | 写密集型/需事务 |

# 如何解决MySQL死锁问题

1. **降低隔离级别**：RC 减少间隙锁，降低死锁概率（但可能引入不可重复读）。
2. **优化事务逻辑**：缩短持锁时间，按相同顺序加锁。
3. **使用行级锁**：合理索引确保行锁精确加锁。
4. **超时和重试**：设置 `innodb_lock_wait_timeout`，捕获死锁（错误码 1213）后重试。

# 创建索引时需要注意什么？

1. **选择适当的列**：查询条件、排序、聚合字段。
2. **避免过多索引**：影响写性能和存储。
3. **考虑联合索引**：多列查询用复合索引，遵循最左前缀。
4. **注意索引顺序**：最常用列放前面。
5. **合适的数据类型**：减小索引大小。

# MySQL记录货币用什么字段类型

推荐 **DECIMAL**，精确存储定点数，避免浮点精度问题。

```sql
CREATE TABLE my_table (amount DECIMAL(18, 2));  -- 18位总长，2位小数
```

优点：精确性、可控性、计算准确。缺点：存储空间较大。

# 什么时候不要使用索引？

1. **小型表**：全表扫描开销小，索引维护不划算。
2. **频繁插入/更新/删除的表**：索引维护成本可能超过查询收益。
3. **查询条件不常用**：字段很少用于查询。
4. **频繁大量写操作**：索引维护拖慢写入。

# 讲讲主从复制原理与延迟

**原理：**
1. 主库将变更写入 binlog。
2. 从库 IO 线程将主库 binlog 复制到本地中继日志（relay log）。
3. 从库 SQL 线程读取中继日志并执行。

**延迟原因：**
1. 从库太多，主库传输压力大。
2. 从库有慢查询。
3. 主库读写压力大，binlog 写入慢。

**优化：** 减少从库数量、优化慢查询、提升主库性能。

---

# 什么是索引？索引有哪些优缺点？

索引是排好序的数据结构，类似书籍目录，加速数据检索。

**优点：**
1. 提高查询性能（减少全表扫描）。
2. 唯一性约束（防止重复数据）。

**缺点：**
1. 占用存储空间。
2. 写操作时需维护索引，降低写入性能。

# 分表后非分片键的查询、排序怎么处理

1. **联合查询**：UNION/JOIN 合并各分表结果。
2. **扫描所有分表**：无法用分片键过滤时全分表扫描合并。
3. **手动分页排序**：各分表独立排序分页，应用层合并。
4. **全局索引**：在集群上创建非分片键的全局索引。

---

# Undolog是如何回滚事务的

1. 获取事务的回滚指针（Undo Log 起始位置）。
2. 从 Undo Log 末尾逆向扫描，按操作逆序处理：
   - INSERT → DELETE 撤销。
   - UPDATE → 用 Undo Log 中的旧值还原。
3. 跳过已提交的其他事务记录。
4. 处理完所有记录后，清除/标记已回滚的 Undo Log。

---

# 了解MySQL锁升级吗

锁升级：事务无法获取所需锁级别时，系统自动升级为更高级别锁。

**常见场景：**
1. 行锁冲突无法满足 → 升级为表锁。
2. 未走索引或非唯一索引记录数过多 → 升级为表锁。

**减少锁升级**：合理索引设计、适当隔离级别。

# MySQL索引分类

- **主键索引**：唯一标识记录，不可重复不可空，一个表只有一个。
- **唯一索引**：保证列值唯一，允许 NULL，可有多个。
- **普通索引**：无唯一性限制，最基本的索引。
- **组合索引**：多列联合索引，遵循最左前缀原则。

# 如何快速定位慢SQL

1. **启用慢查询日志**：记录超过阈值的 SQL。
2. **EXPLAIN 分析执行计划**：查看索引使用和性能瓶颈。
3. **检查索引使用情况**：`SHOW INDEX` 确认索引覆盖查询条件。
4. **分析查询语句**：冗余操作、重复子查询、不必要排序、大量 JOIN。

# UNION与UNION ALL的区别？

- **UNION**：合并结果集并**去重**，有额外排序开销。
- **UNION ALL**：合并结果集**不去重**，效率更高。

需要去重用 UNION，不需要去重或追求性能用 UNION ALL。要求列数和列类型一致。

# 事务的隔离级别有哪些

| 级别 | 说明 | 问题 |
|------|------|------|
| **读未提交** | 可读未提交数据 | 脏读、不可重复读、幻读 |
| **读已提交（RC）** | 只读已提交数据 | 不可重复读、幻读 |
| **可重复读（RR）** | 同事务内多次读结果一致（MySQL 默认） | 幻读（InnoDB 用间隙锁解决） |
| **串行化** | 事务串行执行 | 无，但并发性能差 |

# MySQL有哪些高可用方案

1. **主从复制**：主库写，从库复制 binlog，主库故障时从库提升为主库。
2. **集群**：共享无关架构，节点间自动分割和复制数据。
3. **MHA**：Master High Availability，自动故障切换。
4. **Orchestrator**：拓扑管理和自动故障恢复。

# CHAR和VARCHAR的区别？

| 特性 | CHAR | VARCHAR |
|------|------|---------|
| 存储方式 | 固定长度 | 可变长度 |
| 占用空间 | 固定分配 | 动态分配 |
| 尾随空格 | 填充到指定长度，检索时删除 | 不填充 |
| 访问效率 | 稍快 | 稍慢 |

CHAR 适合定长数据，VARCHAR 适合变长数据。

# 什么数据用hash存储

Hash 索引仅支持等值查找（O(1)），不支持范围查询。

**原因**：哈希将输入映射到固定大小哈希值，不保留数据顺序，`BETWEEN`、`>`、`<` 等范围操作无法利用哈希表。

**适用**：等值查询场景（如 KV 存储、内存表）。
