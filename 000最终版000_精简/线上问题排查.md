## 服务间通信超时问题怎么解决？

简答：先定位、分析问题，再按情况采取以下措施：

1. **优化服务性能**：减少不必要的逻辑，优化数据库。
2. **优化网络配置**：调整超时时间，选择合适的通信协议。
3. **采用容错机制**：熔断与重试。
4. **进行服务降级**：优先保障核心业务。
5. **优化服务架构**：异步通信、分批处理。
6. **监控和预警**：实时监控网络性能并设置预警。

下面展开细节并附关键源码。

### 一、优化服务性能

- **减少不必要的逻辑**：审查业务逻辑，去除冗余计算和无实际意义的转换。例如请求处理中做了大量数据转换，但其中部分对后续业务并无意义，可移除。

```java
public User getUserInfo(String userId) {
    return userDao.findById(userId);
}
```

- **优化算法**：用更高效的算法处理数据，如将时间复杂度较高的冒泡排序替换为快速排序。

```java
// 优化后：快速排序
public static void quickSort(int[] arr, int low, int high) {
    if (low >= high) {
        return;
    }
    int pivot = arr[low];
    int i = low, j = high;
    while (i < j) {
        while (i < j && arr[j] >= pivot) j--;
        if (i < j) arr[i++] = arr[j];
        while (i < j && arr[i] <= pivot) i++;
        if (i < j) arr[j--] = arr[i];
    }
    arr[i] = pivot;
    quickSort(arr, low, i - 1);
    quickSort(arr, i + 1, high);
}
```

- **数据库优化**
  - 添加索引：为高频查询字段建索引，加快检索。例如经常按手机号查用户，则在手机号字段上加索引。
  - 优化查询语句：避免复杂的嵌套查询与关联查询，可拆为多个简单查询后在应用层整合。

### 二、优化网络配置

- **调整超时时间**：根据服务实际响应时间和网络状况设置。例如通常响应 200ms 的服务，客户端超时设为 500ms–1000ms。
- **选择合适的通信协议**：使用轻量级协议，如 HTTP/2 或 gRPC。

API 工具包：

```java
@Data
public class Header {
    // sessionId, reqType, contextLen
    private long sessionId;
    private byte reqType;
    private int contextLen;
}

@Data
public class MessageRecord {
    private Header header;
    private Object body;
}

public enum OpCode {
    REQ((byte) 0), RES((byte) 1), PING((byte) 2), PONG((byte) 3);

    private final byte code;

    OpCode(byte code) {
        this.code = code;
    }

    public byte code() {
        return this.code;
    }
}

// 解码器
public class MessageRecordDecoder extends ByteToMessageDecoder {
    @Override
    protected void decode(ChannelHandlerContext ctx, ByteBuf byteBuf, List<Object> list) throws Exception {
        System.out.println(">>>>>>>>> 开始解码 >>>>>>>>>>>>");
        MessageRecord record = new MessageRecord();
        Header header = new Header();
        // 按消息协议顺序读取
        header.setSessionId(byteBuf.readLong());
        header.setReqType(byteBuf.readByte());
        header.setContextLen(byteBuf.readInt());
        record.setHeader(header);
        if (header.getContextLen() > 0) {
            byte[] contents = new byte[header.getContextLen()];
            byteBuf.readBytes(contents);
            ObjectInputStream ois = new ObjectInputStream(new ByteArrayInputStream(contents));
            record.setBody(ois.readObject()); // 反序列化用 IO 流
            System.out.println("反序列化的消息： " + record);
            list.add(record);
        } else {
            System.out.println("msg can't be null");
        }
    }
}

// 编码器
public class MessageRecordEncoder extends MessageToByteEncoder<MessageRecord> {
    @Override
    protected void encode(ChannelHandlerContext ctx, MessageRecord messageRecord, ByteBuf byteBuf) throws Exception {
        System.out.println(">>>>>>>>> 开始编码 >>>>>>>>>>");
        Header header = messageRecord.getHeader();
        byteBuf.writeLong(header.getSessionId());
        byteBuf.writeByte(header.getReqType());
        Object body = messageRecord.getBody();
        if (body != null) {
            ByteArrayOutputStream bos = new ByteArrayOutputStream();
            ObjectOutputStream oos = new ObjectOutputStream(bos);
            oos.writeObject(body);
            byte[] bytes = bos.toByteArray();
            byteBuf.writeInt(bytes.length); // 解码器读取 long、byte 之后读这里写入的长度
            byteBuf.writeBytes(bytes);
        } else {
            // 消息体为空，则长度为 0
            byteBuf.writeInt(0);
        }
    }
}
```

            }

            e.printStackTrace();
        } finally {

        }
    }
}

## OOM问题如何排查

OOM（OutOfMemoryError）意味着程序超出了可用内存，通常由内存泄漏或配置不足导致。排查步骤如下。

### 排查步骤

**1. 确认OOM错误类型**

- **java.lang.OutOfMemoryError: Java heap space**：堆内存不足。
- **java.lang.OutOfMemoryError: Metaspace**：元空间不足（JDK 8 及以上）。
- **java.lang.OutOfMemoryError: GC overhead limit exceeded**：GC 时间过长。

**2. 收集诊断信息**

- **Error 日志**：找到 OOM 发生时的日志片段。
- **Heap dump**：堆转储文件，可用 `-XX:+HeapDumpOnOutOfMemoryError` 自动生成。
- **GC 日志**：启用 GC 日志以分析垃圾回收活动。

```text
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dump -Xlog:gc*:file=gc.log:time
```

**3. 分析Heap Dump**

工具：Eclipse Memory Analyzer（MAT）。

1. 加载 Heap Dump。
2. 用 “Histogram” 视图查看占用内存最大的对象类型。
3. 用 “Leak Suspects Report” 自动分析可能的内存泄漏点。

例如通过 MAT 发现 `java.util.ArrayList` 实例占用大量内存，再深入查看其引用路径。

**4. 分析和识别问题代码**

- **大对象集合**：如 List、Map 等占用过大的集合。
- **长生命周期对象**：比预期存活更久的对象。

常见场景：自定义缓存没有过期/清理机制；把无限增长的请求数据存入集合。

**5. 优化代码和配置**

1. 优化数据结构，选择合适的数据结构与集合类。
2. 清理长生命周期对象，确保无用对象能被 GC 及时回收。
3. 应用确实需要更多内存时，适当调整堆大小。

问题代码：

```java
List<Object> largeList = new ArrayList<>();

public void processData(List<Object> data) {
    largeList.addAll(data); // 无限制增长
}
```

修复后：

```java
private static final int MAX_SIZE = 10000;

public void processData(List<Object> data) {
    if (largeList.size() + data.size() > MAX_SIZE) {
        largeList.clear(); // 清理，避免无限增长
    }
    largeList.addAll(data);
}
```

调优配置（合理前提下增大堆）：

```text
-Xmx4g -Xms2g
```

**6. 验证和监控**

- 运行负载测试，验证修改后的性能与内存使用。
- 持续监控内存使用，避免再次出现 OOM。

### 示例全面讲解

**场景**：一个 Java Web 应用在高负载测试中抛出 `java.lang.OutOfMemoryError: Java heap space`。

**步骤回顾**：

1. 配置 JVM 参数以捕捉 OOM。

```text
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dump -Xlog:gc*:file=gc.log:time
```

2. 收集 OOM 发生时的 Heap Dump。
3. 使用 MAT 分析：打开堆转储查看 Histogram，发现 Session 对象占用大量内存；通过 Dominator Tree 分析，发现 Session 没有及时失效。
4. 问题识别：自定义 Session 管理模块未正确释放过期 Session，永不过期的 Session 耗尽内存。
5. 代码优化：实现 Session 超时机制，定期或每次请求后清理过期 Session。

```java
public void cleanupSessions() {
    sessions.entrySet().removeIf(entry -> entry.getValue().isExpired());
}
```

6. 配置调整与测试：增加堆内存（如 `-Xmx512m` 提升到 `-Xmx1g`），执行负载测试验证。
7. 监控和告警：配置内存使用监控，设置内存使用率告警。

通过系统化地分析和优化内存管理，应用在高负载下运行稳定，未再出现内存溢出。

## Java进程突然挂了如何排查

进程突然挂掉可能由程序崩溃、资源限制、外部干扰等多种因素导致，需从日志、线程转储到系统资源全面分析。

### 排查步骤

1. **日志分析**
2. **生成和分析Heap Dump**
3. **检查系统资源**
4. **分析代码和依赖**
5. **环境配置检查**
6. **监控和验证**

### 详细过程

**1. 日志分析**

- **应用日志**：查看 application.log，搜索异常、错误信息和未处理的异常。
- **系统日志**：检查操作系统日志（如 `/var/log/syslog` 或 `/var/log/messages`）是否有突发事件记录。

共性问题：

- `java.lang.OutOfMemoryError`：内存不足。
- `java.lang.StackOverflowError`：栈溢出。
- `java.lang.NoClassDefFoundError`：类未找到。

**2. 生成和分析Heap Dump**

启动时设置 JVM 参数，崩溃时生成 Heap Dump：

```text
-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/dump
```

使用 MAT 分析 Heap Dump，识别内存泄漏和占用最多内存的对象。

**3. 检查系统资源**

- **CPU**：用 `top`/`htop` 监控 CPU 负载，查看是否有异常尖峰。
- **内存**：用 `free -m` 或 `vmstat` 检查内存使用，确认是否存在过度消耗。
- **磁盘**：用 `df -h` 检查磁盘空间，确认是否被写满。

**4. 分析代码和依赖**

- **代码审查**：检查最近的代码变更是否引入错误。
- **外部库**：确认是否使用不兼容或有漏洞的第三方库。

常见场景：未关闭的文件句柄或数据库连接；死锁或其他并发问题导致的资源占用。

**5. 环境配置检查**

- **JVM 参数**：确认 `-Xmx`（最大堆）和 `-Xms`（初始堆）设置是否合适。
- **环境依赖**：检查 Java 版本、操作系统版本及补丁更新等。

**6. 监控和验证**

- **监控加强**：用 Prometheus、Grafana 对系统和应用实时监控，设置合适报警阈值。
- **验证修复**：在接近生产的环境验证修复，并用自动化测试覆盖关键场景。

### 具体示例

**问题描述**：一个 Java Web 应用运行一段时间后突然挂掉。

**排查过程**：

1. **日志分析**：应用日志出现 `java.lang.StackOverflowError` 和反复递归调用；系统日志无内存溢出记录，但有 CPU 使用率高的记录。
2. **生成和分析 Heap Dump**：已配置 `-XX:+HeapDumpOnOutOfMemoryError` 但未找到堆转储，排除内存不足。
3. **检查系统资源**：`top` 发现进程占用 100% CPU，疑似死循环。
4. **分析代码和依赖**：递归函数缺少退出条件，导致无穷递归与栈溢出。

```java
public int computeFactorial(int n) {
    // 缺少 n == 0 的退出条件
    return n * computeFactorial(n - 1);
}
```

修复：添加递归基准条件。

```java
public int computeFactorial(int n) {
    if (n == 0) return 1;
    return n * computeFactorial(n - 1);
}
```

5. **环境配置检查**：确保 JVM 参数 `-Xms4g -Xmx4g` 符合资源需求。
6. **监控和验证**：测试环境负载测试验证修复效果；加强 Grafana 监控和 Prometheus 报警。

### 总结

Java 进程突然挂掉的原因包括代码错误、资源限制、环境配置或外部依赖问题。通过全面的检查与分析逐步定位并解决，配合现代化监控和报警工具可提前预警生产环境的潜在问题。

## MySQL数据库连接池爆满如何排查

连接池爆满会导致应用性能下降或请求被拒绝，需深入分析数据库连接管理。

### 确认问题

- 检查应用日志，查找与数据库连接相关的错误（如“无法获取连接”）。
- 查看连接池监控面板（如有）。
- 用数据库管理工具查看当前活跃连接数。

### 收集信息

连接池配置（最大/最小连接数、超时时间等）、当前活跃连接数、数据库与应用服务器的资源使用（CPU、内存、磁盘 I/O）、近期代码变更或流量激增。

### 分析连接使用情况

```sql
SHOW PROCESSLIST;
```

显示所有当前连接及其状态、执行的查询等。

### 检查慢查询

```sql
SHOW FULL PROCESSLIST;
```

关注 “Time” 列，看是否有查询执行时间过长、长期占用连接。

### 分析应用代码

检查连接使用方式：是否正确关闭连接、是否存在连接泄漏、是否有不必要的长连接。

可能导致连接泄漏的代码：

```java
public void leakyMethod() {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        // 使用连接进行操作
    } catch (SQLException e) {
        e.printStackTrace();
    }
    // 没有在 finally 块中关闭连接
}
```

正确做法：

```java
public void leakyMethod() {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        // 使用连接进行操作
    } catch (SQLException e) {
        e.printStackTrace();
    } finally {
        conn.close();
    }
}
```

### 检查连接池配置

以 HikariCP 为例：

```java
HikariConfig config = new HikariConfig();
config.setMaximumPoolSize(10);
config.setConnectionTimeout(30000);
config.setIdleTimeout(600000);
config.setMaxLifetime(1800000);
```

- `maximumPoolSize`：最大连接数。
- `connectionTimeout`：等待连接的最大毫秒数。
- `idleTimeout`：连接允许在池中闲置的最长时间。
- `maxLifetime`：连接最长生命周期。

### 使用监控工具

用 JConsole 或 VisualVM 观察连接池使用情况。

### 数据库性能分析

用 MySQL 的 Performance Schema 分析数据库性能：

```sql
SELECT * FROM performance_schema.events_waits_summary_global_by_event_name
WHERE event_name LIKE '%wait/synch/mutex/innodb/%'
ORDER BY sum_timer_wait DESC;
```

### 解决方案

根据分析结果，可能的方案包括：优化慢查询、增加连接池大小（资源允许时）、修复连接泄漏代码、读写分离或分库分表分散负载、添加连接池监控与告警。

### 实施和验证

实施后持续监控连接池使用情况。示例：某查询长时间运行导致连接无法释放。

1. 通过 `SHOW FULL PROCESSLIST` 发现长时间运行的查询：

```text
+----+------+-----------------+------+---------+------+--------------+------------------+
| Id | User | Host            | db   | Command | Time | State        | Info             |

| 1  | root | localhost:3306  | mydb | Query   | 3600 | Sending data | SELECT * FROM ...|
+----+------+-----------------+------+---------+------+--------------+------------------+
```

2. 分析发现是全表扫描的大查询：

```sql
SELECT * FROM large_table WHERE non_indexed_column = 'some_value';
```

3. 优化查询：添加索引、限制返回行数。

```sql
ALTER TABLE large_table ADD INDEX idx_non_indexed_column (non_indexed_column);
SELECT * FROM large_table WHERE non_indexed_column = 'some_value' LIMIT 1000;
```

4. 应用代码问题：

```java
public List<Data> fetchData(String value) {
    Connection conn = dataSource.getConnection();
    try {
        PreparedStatement stmt = conn.prepareStatement(
                "SELECT * FROM large_table WHERE non_indexed_column = ?");
        stmt.setString(1, value);
        ResultSet rs = stmt.executeQuery();
        // 处理结果集
    } catch (SQLException e) {
        e.printStackTrace();
    }
    // 连接未关闭
    return dataList;
}
```

5. 修改代码以正确管理连接：

```java
public List<Data> fetchData(String value) {
    List<Data> dataList = new ArrayList<>();
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        PreparedStatement stmt = conn.prepareStatement(
                "SELECT * FROM large_table WHERE non_indexed_column = ? LIMIT 1000");
        stmt.setString(1, value);
        try (ResultSet rs = stmt.executeQuery()) {
            while (rs.next()) {
                dataList.add(new Data(rs.getString("column1"), rs.getInt("column2")));
            }
        }
    } catch (SQLException e) {
        logger.error("Error fetching data", e);
    } finally {
        if (conn != null) {
            conn.close();
        }
    }
    return dataList;
}
```

6. 调整连接池配置：

```java
HikariConfig config = new HikariConfig();
config.setMaximumPoolSize(20); // 增加最大连接数
config.setConnectionTimeout(30000);
config.setIdleTimeout(600000);
config.setMaxLifetime(1800000);
```

7. 添加监控：用 Spring Actuator 或自定义监控跟踪连接池使用，连接使用率接近最大值时告警。

## 慢SQL问题如何排查

慢 SQL 是常见性能瓶颈，排查需要从识别问题到优化解决的系统过程。

### 排查过程

**1. 收集并识别慢SQL**

- 使用数据库慢查询日志。
- 在应用中添加 SQL 执行时间日志。
- 使用 APM 工具监控（如 New Relic、Dynatrace）。

开启 MySQL 慢查询日志：

```sql
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 2;  -- 慢查询阈值：2 秒
```

**2. 分析慢SQL语句**

- 从慢查询日志或应用日志中提取慢 SQL。
- 收集执行计划和执行时间。

```sql
SELECT orders.id, orders.date, customers.name FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE orders.date BETWEEN '2023-01-01' AND '2023-12-31'
ORDER BY orders.date DESC;
```

**3. 收集SQL执行计划**

- MySQL：`EXPLAIN`。
- Oracle：`AUTOTRACE` 或 `DBMS_XPLAN`。
- Postgres：`EXPLAIN ANALYZE`。

```sql
EXPLAIN SELECT orders.id, orders.date, customers.name FROM orders
JOIN customers ON orders.customer_id = customers.id
WHERE orders.date BETWEEN '2023-01-01' AND '2023-12-31'
ORDER BY orders.date DESC;
```

执行计划会显示表扫描类型（全表扫描、索引扫描）及各操作的数量、时间和可改进点。

**4. 检查表和索引**

- **索引使用情况**：确认过滤条件和连接条件是否已正确索引。
- **统计信息**：确保数据库统计信息最新，以优化查询计划。
- **数据量**：了解涉及表的数据量，评估查询复杂度。

```sql
CREATE INDEX idx_order_date ON orders(date);
CREATE INDEX idx_customer_id ON orders(customer_id);
```

**5. 优化SQL设计**

- 重构复杂查询：拆分复杂多表查询，分阶段进行。
- 减少返回数据量：只查必要列，避免 `SELECT *`。
- 使用合适聚合：确保聚合有效利用索引，避免全表扫描。

优化后：

```sql
SELECT o.id, o.date, c.name
FROM (SELECT id, date, customer_id FROM orders
      WHERE date BETWEEN '2023-01-01' AND '2023-12-31') AS o
JOIN customers c ON o.customer_id = c.id
ORDER BY o.date DESC;
```

**6. 配置和硬件观察**

调整内存缓存参数、连接池配置；检查 CPU 与内存瓶颈；了解负载峰值并做数据分片/分区优化。

**7. 验证和实现优化**

进行负载测试验证效果，并持续监控 SQL 执行性能。

### 排查示例

**场景**：某电商平台订单列表页加载缓慢，主要依赖一个慢 SQL。

1. **收集日志**：通过慢查询日志确认问题 SQL。

```sql
SELECT * FROM orders WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31';
```

2. **分析执行计划**：结果显示使用了全表扫描。

```sql
EXPLAIN SELECT * FROM orders ...
```

3. **检查索引**：发现 `order_date` 无索引，创建索引。

```sql
CREATE INDEX idx_order_date ON orders(order_date);
```

4. **优化查询结构**：

```sql
SELECT id, customer_id, order_date FROM orders
WHERE order_date BETWEEN '2023-01-01' AND '2023-12-31';
```

5. 用 `EXPLAIN` 确认新索引被使用，扫描时间大幅减少。
6. 检查并调整数据库缓存配置以提升读取效率。
7. 端到端性能测试，确认响应时间下降。
8. 部署上线并利用 APM 持续监控。

### 结论

通过系统化步骤快速识别并优化慢 SQL，既提升响应速度又改善用户体验；不同数据库可适当调整流程，但核心原则一致。

## 文件导入导出导致内存溢出如何排查

处理大文件时，程序试图在堆内存中加载过多数据会超过 JVM 限制，导致 OOM。

### 排查和优化步骤

**1. 确认内存溢出**

- **日志检查**：应用日志中存在 `java.lang.OutOfMemoryError: Java heap space`。
- **监控内存**：用 JConsole、VisualVM 观察内存使用。

**2. 生成和分析Heap Dump**

```bash
java -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/path/to/your/dumpfile -jar your-application.jar
```

用 MAT 或 JVisualVM 分析 Heap Dump，查找内存使用热点及占用最多的对象。

**3. 代码检查**

查看导入导出代码，找出一次性加载过多数据之处。

```java
public void importData(File file) throws IOException {
    BufferedReader reader = new BufferedReader(new FileReader(file));
    String line;
    List<String> data = new ArrayList<>();
    while ((line = reader.readLine()) != null) {
        data.add(line); // 将整个文件内容加载到内存
    }
    process(data);
    reader.close();
}
```

**4. 代码优化**

优化策略：

1. **逐行处理**：逐行读取处理，而非整体加载。
2. **合适的数据结构**：暂存数据时选择紧凑结构。
3. **流处理**：使用 Java 8 Streams 等流处理工具。
4. **临时存储机制**：用临时文件、数据库等外部存储处理临时数据。

优化后：

```java
public void importData(File file) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(file))) {
        String line;
        while ((line = reader.readLine()) != null) {
            processLine(line); // 逐行处理
        }
    }
}

private void processLine(String line) {
    // 处理每一行数据
}
```

**5. JVM和系统配置**

- 增加堆内存（结合硬件条件评估）：

```text
-Xmx4096m  # 最大内存调整为 4GB
```

- 根据应用需求调整垃圾回收器参数。

**6. 验证解决方案**

- 在开发/测试环境用较大文件验证。
- 观察内存使用是否保持稳定。

**7. 部署和持续监控**

- 实施改进后部署上线。
- 用 APM 工具（New Relic、Datadog）和 JVM 监控工具跟踪内存与性能。

### 具体示例

**问题描述**：应用导入大型 CSV 文件时抛出 OOM 导致崩溃。

1. **确认问题**：日志确定发生 OOM。
2. **生成 Heap Dump**：用 jmap 生成堆转储，并用 MAT 分析。
3. **分析结果**：MAT 显示 `java.util.ArrayList` 占用大量内存，所有文件内容都被加载到此集合。
4. **代码审查与优化**：以逐行处理替代整体加载。

```java
public void importData(File file) throws IOException {
    try (BufferedReader reader = new BufferedReader(new FileReader(file))) {
        String line;
        while ((line = reader.readLine()) != null) {
            processLine(line);
        }
    }
}

private void processLine(String line) {
    // 处理或立即存储每一行数据
}
```

5. **调整 JVM 设置**：通过增加 `-Xmx` 调整堆大小。
6. **验证和测试**：针对不同大小文件测试，确保内存稳定。
7. **上线和监控**：部署更新并配置监控警报。

### 总结

逐行处理文件、优化内存使用并调整 JVM 与系统内存设置，可有效解决文件导入导出的内存溢出问题。开发阶段充分测试、生产环境持续监控，并采用流处理方式减轻内存压力。

## 线上系统突然响应缓慢如何排查

### 1. 问题确认

- **用户反馈**：收集具体表现和时间点。
- **初步验证**：从不同客户端访问，确认问题是否普遍存在。

### 2. 检查系统资源

- **CPU**：用 `top` 或 `htop` 查看。
- **内存**：确认是否存在内存泄漏或不足。
- **磁盘 I/O**：用 `iostat` 或 `dstat` 检查读写性能。
- **网络流量**：用 `netstat`、`iftop` 检查带宽使用及异常流量。

### 3. 应用监控

- **APM 工具**：用 New Relic、Datadog 查看性能监控数据。
- **关键路径分析**：检查关键请求路径的响应时间，定位慢操作。
- **错误率分析**：检查错误日志，判断是否存在异常。

### 4. 数据库性能

- **慢查询日志**：发现耗时 SQL。
- **连接池使用率**：确认是否耗尽。
- **锁等待**：用数据库管理工具检查锁等待和事务阻塞。

### 5. 检查应用变更

- **代码变更**：查看最近代码/配置变更是否引入性能问题。
- **部署记录**：确认问题出现前是否有新版本部署。

### 6. 线程和进程分析

- **线程转储**：获取 Thread Dump，分析是否存在死锁或阻塞。
- **GC 分析**：检查 GC 日志，确认 Full GC 是否过于频繁。

### 7. 网络分析

- **延迟和丢包**：用 `ping` 或 `traceroute` 判断。
- **DNS 解析**：检查 DNS 设置和解析时间。

### 8. 压力测试和负载

- **请求负载**：确认当前请求量是否超过系统设计能力。
- **模拟测试**：在测试环境重现实际负载，看是否能复现。

### 9. 修复方案

- **问题定位后**：针对性实施修复，如优化查询、增加资源、回滚变更。
- **性能调优**：根据瓶颈进行代码和配置优化。

### 10. 验证和监控

- 测试修复效果，观察性能是否恢复。
- 持续监控性能指标，确保问题彻底解决。

### 实际案例

1. **确认问题**：首页加载时间从 200ms 增加到 5s。
2. **检查系统资源**：`top` 显示 CPU 占用接近 100%，主要是 Java 进程。
3. **应用监控**：APM 发现某 API 调用耗时过长，占用了大部分响应时间。
4. **数据库性能**：慢查询日志发现一个复杂 JOIN 查询耗时过长。
5. **检查应用变更**：最近上线的新功能涉及新增数据表但未建索引。
6. **修复方案**：优化 SQL 并添加必要索引。
7. **验证和监控**：部署后重新测试，响应时间恢复正常。

## Java死锁问题如何排查

死锁会导致线程永久阻塞，排查需要多线程调试技巧和工具。

### 排查步骤

1. **识别死锁现象**
2. **收集线程转储**
3. **分析线程转储**
4. **代码审查**
5. **重现问题**
6. **使用调试工具**
7. **优化和验证**

### 详细过程

**1. 识别死锁现象**

通常表现为应用挂起、不响应用户请求或 CPU 使用率下降。

**2. 收集线程转储**

- **JVM 命令**：Linux/Mac 用 `jstack`，Windows 用 `Ctrl+Break`。

```bash
jstack -l <pid> > threaddump.txt
```

- **IDE 支持**：用 Eclipse 或 IntelliJ 的调试功能生成线程转储。

**3. 分析线程转储**

从转储中寻找 “deadlock” 相关信息，Java 发现死锁时会显示类似内容：

```text
Found one Java-level deadlock:
=============================
"Thread-1":
waiting to lock monitor 0x000000000f8cba48 (object 0x00000000d66b4db0, a java.lang.Object),
which is held by "Thread-2"
"Thread-2":
waiting to lock monitor 0x000000000f8cba58 (object 0x00000000d66b4dc0, a java.lang.Object),
which is held by "Thread-1"

Java stack information for the threads listed above:
===================================================
"Thread-1":
at com.example.MyClass.methodA(MyClass.java:10)
- locked  (a java.lang.Object)
- waiting to lock  (a java.lang.Object)
"Thread-2":
at com.example.MyClass.methodB(MyClass.java:20)
- locked  (a java.lang.Object)
- waiting to lock  (a java.lang.Object)
```

**4. 代码审查**

根据线程转储审查出现死锁的代码段。

```java
public class DeadlockExample {
    private final Object lock1 = new Object();
    private final Object lock2 = new Object();

    public void methodA() {
        synchronized (lock1) {
            System.out.println("Method A: Holding lock 1...");
            try { Thread.sleep(100); } catch (InterruptedException e) {}
            synchronized (lock2) {
                System.out.println("Method A: Holding lock 2...");
            }
        }
    }

    public void methodB() {
        synchronized (lock2) {
            System.out.println("Method B: Holding lock 2...");
            try { Thread.sleep(100); } catch (InterruptedException e) {}
            synchronized (lock1) {
                System.out.println("Method B: Holding lock 1...");
            }
        }
    }
}
```

问题：methodA 与 methodB 之间存在循环锁定。

**5. 重现问题**

```java
public class DeadlockDemo {
    public static void main(String[] args) {
        DeadlockExample example = new DeadlockExample();

        Thread t1 = new Thread(() -> example.methodA(), "Thread-1");
        Thread t2 = new Thread(() -> example.methodB(), "Thread-2");

        t1.start();
        t2.start();
    }
}
```

**6. 使用调试工具**

用 Eclipse、IntelliJ 的线程调试功能进一步定位死锁位置。

**7. 优化和验证**

- **锁排序**：确保所有线程以相同顺序申请锁。

```java
public void methodA() {
    synchronized (lock1) {
        synchronized (lock2) {
            // 操作
        }
    }
}

public void methodB() {
    synchronized (lock1) { // 调整顺序
        synchronized (lock2) {
            // 操作
        }
    }
}
```

- **使用 Lock 接口**：用显式锁代替内置同步。

```java
private final Lock lock1 = new ReentrantLock();
private final Lock lock2 = new ReentrantLock();

public void methodA() {
    lock1.lock();
    try {
        lock2.lock();
        try {
            // 操作
        } finally {
            lock2.unlock();
        }
    } finally {
        lock1.unlock();
    }
}

public void methodB() {
    lock1.lock(); // 确保同样顺序锁定
    try {
        lock2.lock();
        try {
            // 操作
        } finally {
            lock2.unlock();
        }
    } finally {
        lock1.unlock();
    }
}
```

- **超时尝试**：利用 `tryLock` 的时间限制功能。

验证：实施改动后重新执行测试，确保死锁不再出现；强化单元测试覆盖多线程场景。

### 总结

死锁排查涉及识别现象、获取线程转储、分析代码、优化同步逻辑等步骤。良好的设计可避免大多数死锁；使用高层并发工具（如 `java.util.concurrent` 包）能显著简化并发编程，减少死锁可能。持续监控和测试是保证稳定性的关键。

## 高并发线程安全问题如何排查

### 排查思路和步骤

1. **问题识别**
2. **代码审查**
3. **日志分析**
4. **性能分析**
5. **线程转储分析**
6. **模拟和重现**
7. **使用专业工具**
8. **修复和验证**

### 详细步骤

**1. 问题识别**

- **症状识别**：确定具体表现，如数据不一致、死锁、性能下降等。
- **影响范围**：评估影响范围和严重程度。

**2. 代码审查**

- **并发控制检查**：是否正确使用 `synchronized`、`volatile`、`Lock` 等机制。
- **共享资源访问**：审查共享资源的访问模式，确保线程安全。
- **线程安全集合**：是否使用了合适的线程安全集合类。

**3. 日志分析**

- **错误日志**：查看系统日志中的错误和异常。
- **自定义日志**：分析并发操作日志，追踪问题上下文。

**4. 性能分析**

- **CPU 分析**：用 VisualVM 或 JProfiler 分析 CPU 使用，找出热点方法。
- **内存分析**：检查内存使用，是否存在内存泄漏或过度 GC。

**5. 线程转储分析**

- **获取线程转储**：用 `jstack` 或工具获取。
- **分析线程状态**：检查是否存在死锁、长时间等待等。

**6. 模拟和重现**

- **压力测试**：用 JMeter 等模拟高并发场景。
- **单元测试**：编写多线程单元测试重现问题。

**7. 使用专业工具**

- **Java Flight Recorder（JFR）**：分析运行时行为。
- **Java Mission Control（JMC）**：分析 JFR 数据，发现性能与并发问题。
- **FindBugs/SpotBugs**：静态代码分析，发现潜在并发问题。

**8. 修复和验证**

- **实施修复**：根据分析结果修改代码。
- **验证测试**：在模拟环境进行充分并发测试，验证修复效果。

### 实际案例

假设高并发订单处理系统中出现数据不一致：

1. **问题识别**：订单状态不一致，有时显示已支付，有时显示未支付，影响用户体验与系统可信度。
2. **代码审查**：订单状态更新方法没有恰当的同步机制。
3. **日志分析**：日志显示多个线程同时更新同一订单状态。
4. **性能分析**：VisualVM 发现订单处理方法是 CPU 热点。
5. **线程转储分析**：jstack 显示多个线程同时在订单处理方法中。
6. **模拟和重现**：用 JMeter 模拟高并发订单处理，成功复现。
7. **使用专业工具**：用 JFR 捕获详细线程行为。
8. **修复和验证**：为订单状态更新添加同步机制（如 `ReentrantLock`），重新并发测试确认问题解决。

```java
public class OrderService {
    private final ReentrantLock lock = new ReentrantLock();

    public void updateOrderStatus(Order order, String newStatus) {
        lock.lock();
        try {
            order.setStatus(newStatus);
            orderRepository.save(order);
        } finally {
            lock.unlock();
        }
    }
}
```

## MySQL死锁问题如何排查

下面通过一个模拟的死锁场景，逐步展示如何识别、分析和解决死锁。

### 场景描述

在线商店系统包含 `products`（产品表）和 `orders`（订单表），两个并发事务试图更新这些表导致死锁。

### 步骤1：复现死锁

```sql
-- 创建表
CREATE TABLE products (
    id INT PRIMARY KEY,
    name VARCHAR(100),
    stock INT
);

CREATE TABLE orders (
    id INT PRIMARY KEY,
    product_id INT,
    quantity INT
);

-- 插入初始数据
INSERT INTO products VALUES (1, 'Product A', 100);
INSERT INTO products VALUES (2, 'Product B', 200);
INSERT INTO orders VALUES (1, 1, 5);
INSERT INTO orders VALUES (2, 2, 10);
```

事务1：

```sql
START TRANSACTION;
UPDATE products SET stock = stock - 5 WHERE id = 1;
-- 模拟延迟
DO SLEEP(2);
UPDATE orders SET quantity = quantity + 5 WHERE id = 1;
COMMIT;
```

事务2：

```sql
START TRANSACTION;
UPDATE orders SET quantity = quantity - 5 WHERE id = 1;
-- 模拟延迟
DO SLEEP(2);
UPDATE products SET stock = stock + 5 WHERE id = 1;
COMMIT;
```

### 步骤2：识别死锁

死锁发生时，MySQL 会自动检测并回滚其中一个事务。

1. 检查应用日志，寻找类似 “Deadlock found when trying to get lock” 的错误。
2. 查看最近的死锁信息：

```sql
SHOW ENGINE INNODB STATUS;
```

在输出中找到 “LATEST DETECTED DEADLOCK” 部分。

### 步骤3：分析死锁

`SHOW ENGINE INNODB STATUS` 输出类似：

```text
------------------------
LATEST DETECTED DEADLOCK
------------------------
*** (1) TRANSACTION:
TRANSACTION 8-131, ACTIVE 6 sec starting index read
mysql tables in use 1, locked 1
LOCK WAIT 3 lock struct(s), heap size 1136, 2 row lock(s)
                                                       MySQL thread id 8, OS thread handle 140286124944128, query id 57 localhost root updating
UPDATE products SET stock = stock - 5 WHERE id = 1

*** (2) TRANSACTION:
TRANSACTION 8-132, ACTIVE 4 sec starting index read
mysql tables in use 1, locked 1
3 lock struct(s), heap size 1136, 2 row lock(s)
                                             MySQL thread id 9, OS thread handle 140286124680960, query id 58 localhost root updating
UPDATE orders SET quantity = quantity - 5 WHERE id = 1

*** WE ROLL BACK TRANSACTION (1)
```

说明：事务1 正在更新 `products`，事务2 正在更新 `orders`，MySQL 选择回滚事务1 来解决死锁。

### 步骤4：解决死锁

1. **保持一致的访问顺序**：修改应用代码，确保所有事务按相同顺序访问表（例如总是先 `products` 再 `orders`）。
2. **减少事务范围**：尽可能缩小事务范围，减少持锁时间。
3. **使用乐观锁**：

```sql
ALTER TABLE products ADD COLUMN version INT DEFAULT 0;

-- 更新时检查版本号
UPDATE products
SET stock = stock - 5, version = version + 1
WHERE id = 1 AND version = 0;
```

4. **添加适当的索引**：确保 `products.id` 和 `orders.id` 有合适索引。
5. **使用行级锁而非表级锁**：InnoDB 默认行级锁，避免使用会导致表级锁的操作（如 `LOCK TABLES`）。

### 步骤5：监控和预防

1. 设置死锁监控：

```sql
SET GLOBAL innodb_print_all_deadlocks = 1;
```

将所有死锁信息记录到 MySQL 错误日志。

2. 定期检查当前执行的事务：

```sql
SELECT * FROM information_schema.INNODB_TRX;
```

3. 用 Performance Schema 监控锁等待：

```sql
SELECT * FROM performance_schema.events_waits_current
WHERE EVENT_NAME LIKE 'wait/synch/mutex/innodb%';
```

### 结论

预防死锁的关键在于合理设计数据库结构和事务逻辑，以及持续监控和优化。

## 频繁FullGC问题如何排查

频繁 Full GC 通常表明内存管理存在问题，会导致性能下降。

### 排查步骤

1. **收集GC日志**
2. **分析GC日志**
3. **监控JVM内存使用情况**
4. **分析堆内存**
5. **检查代码中的内存使用**
6. **调整JVM参数**
7. **优化代码**
8. **验证改进**

### 详细示例

假设某大型电商网站用户反馈系统响应变慢，运维发现服务器频繁 Full GC。

**1. 收集GC日志**

在 JVM 参数中添加：

```text
-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:/path/to/gc.log
```

**2. 分析GC日志**

用 GCViewer 等工具分析，发现：

- Full GC 频率：每 10 分钟一次
- 每次 Full GC 平均耗时：3 秒
- Old Gen 使用情况：每次 GC 后仍保持在 80% 以上

GC 日志片段：

```text
2023-05-15T14:30:45.123+0800: [Full GC (Ergonomics) [PSYoungGen: 20M->0M(60M)] [ParOldGen: 180M->175M(200M)] 200M->175M(260M), [Metaspace: 30M->30M(1024M)], 3.2345678 secs] [Times: user=10.23 sys=0.25, real=3.23 secs]
```

**3. 监控JVM内存使用情况**

用 VisualVM 或 JConsole 实时监控，观察到：

- Eden 区：频繁被填满后触发 Minor GC
- Survivor 区：经常接近满载
- Old Gen：持续增长，Full GC 后也难以下降

**4. 分析堆内存**

```bash
jmap -dump:format=b,file=heap_dump.hprof
```

用 MAT 分析堆转储，发现：大量 `com.example.Order` 对象占用 Old Gen 大部分空间，且包含大量历史订单数据。

**5. 检查代码中的内存使用**

```java
public class OrderService {
    private static final List<Order> allOrders = new ArrayList<>();

    public void processOrder(Order order) {
        // 处理订单
        allOrders.add(order);  // 问题所在：持续添加订单到静态列表
    }
}
```

**6. 调整JVM参数**

临时缓解问题：

```text
-Xms4g -Xmx4g -XX:NewRatio=2 -XX:SurvivorRatio=8
```

**7. 优化代码**

```java
public class OrderService {
    private static final int MAX_ORDERS = 10000;
    private static final Queue<Order> recentOrders = new LinkedList<>();

    public void processOrder(Order order) {
        recentOrders.offer(order);
        if (recentOrders.size() > MAX_ORDERS) {
            recentOrders.poll();  // 移除最旧的订单
        }
    }
}
```

同时实现定时任务，将处理过的订单持久化到数据库并从内存中清除。

**8. 验证改进**

重新部署、监控 GC 活动与内存使用、负载测试。结果：

- Full GC 频率降低到每小时 1–2 次
- 每次 Full GC 耗时减少到 1 秒以内
- Old Gen 使用率稳定在 60% 左右

### 总结

本例通过 GC 日志和监控工具识别问题，通过堆内存分析找到内存泄漏根源，优化代码中的内存使用模式，调整 JVM 参数适应应用特性，并验证优化效果。实际问题的形态可能更复杂，但该方法论可作为处理各类 GC 性能问题的基础框架。

## 线上系统接口响应很慢如何排查

- 验证是所有用户、特定用户还是某个环境下出现。

### 2. 系统资源检查

用 `top`、`htop`、`vmstat` 检查 CPU、内存和 I/O 使用情况。

### 3. 应用监控

用 SkyWalking 或 Prometheus 等 APM 工具查看接口响应时间、吞吐量和错误率，并查看具体请求的分布式追踪结果，识别耗时操作。

### 4. 日志分析

在请求进入接口时记录开始和结束时间，计算处理时长。

```java
@RestController
public class ExampleController {

    @GetMapping("/example")
    public ResponseEntity<String> exampleEndpoint() {
        long startTime = System.currentTimeMillis();

        simulateSlowOperation();

        long duration = System.currentTimeMillis() - startTime;
        Logger.getLogger(ExampleController.class.getName())
                .info("exampleEndpoint processed in " + duration + " ms");

        return ResponseEntity.ok("Response");
    }

    private void simulateSlowOperation() {
        try {
            Thread.sleep(3000); // 模拟慢操作
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

### 5. 数据库性能

用慢查询日志分析 SQL 性能，检查索引是否缺失、查询是否可优化。

```sql
-- 检查 MySQL 慢查询配置
SHOW VARIABLES LIKE 'slow_query_log%';
SHOW VARIABLES LIKE 'long_query_time';
SHOW VARIABLES LIKE 'log_output';

-- 测试用开启（生产环境须评估后再操作）
SET GLOBAL slow_query_log = 'ON';
SET GLOBAL long_query_time = 1;  -- 秒
```

### 6. 外部依赖分析

对所有外部调用添加超时控制，并记录开始和结束时间。

```java
public void callExternalAPI() {
    try {
        URL url = new URL("http://external-service/api");
        HttpURLConnection connection = (HttpURLConnection) url.openConnection();
        connection.setConnectTimeout(3000); // 3 秒连接超时
        connection.setReadTimeout(5000);    // 5 秒读取超时

        // 处理响应
    } catch (IOException e) {
        Logger.getLogger(ExampleController.class.getName())
                .severe("External API call failed: " + e.getMessage());
    }
}
```

### 7. 调整应用程序

确保线程池大小合理，避免过小导致请求排队，可用配置文件调整：

```java
@Configuration
public class AsyncConfiguration {

    @Bean(name = "taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(5);
        executor.setMaxPoolSize(10);
        executor.setQueueCapacity(500);
        executor.setThreadNamePrefix("CoreExecutor-");
        executor.initialize();
        return executor;
    }
}
```

### 8. 监控和验证

用 JMeter 或 Gatling 对修复后的接口做压力测试，确认响应时间符合预期且负载下运行正常。

### 9. 经验分享与知识积累

记录问题排查、分析和解决过程，供团队参考；定期回顾线上问题处理流程，持续改进。

## 线上偶发性问题如何处理和跟踪

### 1. 问题识别

- **收集信息**：记录发生时间、频率、涉及功能模块及用户反馈。
- **症状描述**：清晰描述问题表现，如错误信息、影响用户群、错误码等。

### 2. 日志收集与分析

- **启用详细日志**：确保问题模块有足够日志便于诊断。
- **日志分析**：用 ELK Stack、Splunk 等查看异常前后的日志。
- **异常聚类**：分析日志中是否有共同特征、模式或错误信息。

### 3. 监控与预警

- **设置监控指标**：对问题模块设置关键性能指标（如响应时间、错误率）。
- **配置预警**：设定阈值，达到即告警，便于及时响应。
- **使用分布式跟踪**：用 Jaeger、Zipkin 等监控问题请求的全路径。

### 4. 回溯分析

- **回顾近期变更**：检查问题前后的代码、配置或基础设施变更记录，找潜在关联。
- **系统健康检查**：确保涉及模块的基础设施（服务器、网络、数据库）无资源瓶颈或异常。

### 5. 重现问题

- **收集线索**：根据已有信息和日志提炼固定重现步骤。
- **模拟环境测试**：在测试环境按步骤验证，尽量模拟生产条件（流量、数据）。

### 6. 根因分析

- **深入分析**：借助调试和分析工具对代码行为做细粒度分析。
- **团队讨论**：召集相关开发运维人员集体分析，寻找不同视角。

### 7. 制定解决方案

- **短期措施**：找出临时方案缓解影响。
- **长期解决方案**：根因明确后制定彻底修复计划，可能涉及代码更改、架构调整或配置优化。

### 8. 实施和验证

- **实施修复**：在受控安全的情况下实施。
- **回归测试**：对修改功能回归测试，确保不引入新问题。
- **用户反馈**：阶段性用户检查与反馈，确认问题解决。

### 9. 监控和跟踪

- **持续监控**：修复后密切监视相关指标，防止反弹。
- **建立跟踪文档**：记录详细信息、分析过程和解决办法，作为知识库案例。

### 10. 复盘与经验总结

- **故障复盘**：团队复盘，总结原因及应对措施。
- **改进措施**：提出系统与流程改进建议，如提升监控、增强日志、改善预警。
- **知识共享**：将复盘结果和经验教训分享给更广泛的团队。

关键在于不断总结经验教训，并将其转化为更完善的技术和流程改进。

## CPU飙高问题如何排查

线上系统 CPU 飙高可按以下步骤排查。

**1. 确定问题进程**

用 `top` 找出占用 CPU 较高的 Java 进程，找到对应 PID。

```bash
top
```

![1724650124042-4d8e6da5-a32e-4174-8669-68f40a29a8e8.png](images/1724650124042-4d8e6da5-a32e-4174-8669-68f40a29a8e8.png)

**2. 获取线程信息**

用 `top -Hp <pid>` 查看该进程内各线程的 CPU 占用，记录占用较高的线程 ID。

```bash
top -Hp <pid>
```

![1724650133740-e843164e-93a9-4cfa-b66a-b5e2dab8514a.png](images/1724650133740-e843164e-93a9-4cfa-b66a-b5e2dab8514a.png)

**3. 转换线程ID为十六进制**

用 `printf` 将线程 ID `19664` 转换为十六进制，结果为 `0x4cd0`。

```bash
printf "%x\n" 19664
```

**4. 获取线程堆栈**

```bash
# 得到线程堆栈中 4cd0 这个线程所在行的后面 10 行，从中可发现导致 CPU 飙高的调用方法
jstack 19663 | grep -A 10 4cd0
```

![1724650226761-875a7f47-019d-4909-8a6f-53209cb9b083.png](images/1724650226761-875a7f47-019d-4909-8a6f-53209cb9b083.png)

**5. 代码分析**

根据堆栈信息查看相关 Java 代码。可能导致 CPU 飙高的示例：

死循环：

```java
while (true) {
    // 耗 CPU 的操作
}
```

频繁的垃圾回收：

```java
List<Object> list = new ArrayList<>();
while (true) {
    list.add(new Object());
    if (list.size() > 10000) {
        list.clear();
    }
}
```

不当的线程同步：

```java
public class BadSynchronization {
    private static final Object lock1 = new Object();
    private static final Object lock2 = new Object();

    public static void method1() {
        synchronized (lock1) {
            synchronized (lock2) {
                // 操作
            }
        }
    }

    public static void method2() {
        synchronized (lock2) {
            synchronized (lock1) {
                // 操作
            }
        }
    }
}
```

密集的计算操作：

```java
public long fibonacci(long n) {
    if (n < 2) return n;
    return fibonacci(n - 1) + fibonacci(n - 2);
}
```

**6. 检查系统资源**

用 `vmstat`、`iostat` 等命令检查系统资源使用情况，排除系统资源问题。

通过以上步骤可定位导致 CPU 飙高的具体代码位置，再进行相应优化。常见优化方法包括：优化算法、增加缓存、调整线程池参数、优化数据库查询等。优化后要充分测试，确保不引入新问题。
