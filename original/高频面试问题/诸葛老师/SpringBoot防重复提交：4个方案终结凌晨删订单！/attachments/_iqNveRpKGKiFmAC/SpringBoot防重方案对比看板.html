SpringBoot 防重复提交：4大核心方案对决

从单体到分布式架构，彻底告别重复订单

方案一：本地锁 单体应用

核心组件

AOP + 自定义注解
ConcurrentHashMap (本地缓存)

核心原理

请求 → AOP拦截 → 生成Key → 检查本地缓存 → [ 存在? 拦截 : 放行并存入 ]
优点
  • 实现简单，无外部依赖
  • 性能高，内存操作
缺点
  • 仅限单体应用
  • 服务重启后失效

方案二：分布式锁 分布式

核心组件

Redis / Zookeeper
Lua 脚本 (保证原子性)

核心原理

请求 → Redis SETNX(key, val, EX) → [ 失败? 拦截 : 成功? 执行业务 ]
优点
  • 通用性强，适用分布式
  • 高性能，官方推荐方案
缺点
  • 引入外部依赖 (Redis)
  • 需处理锁失效、续期等问题

方案三：数据库约束 分布式

核心组件

业务幂等表
唯一索引 (Unique Index)

核心原理

请求 → 组装唯一业务ID → INSERT幂等表 → [ 唯一键冲突? 拦截 : 成功? 执行业务 ]
优点
  • 实现简单，无需额外中间件
  • 可靠性高，最终防线
缺点
  • 对数据库有性能压力
  • 业务侵入性较强

方案四：令牌机制 分布式

核心组件

服务端 Token 生成/校验
前端请求携带 Token

核心原理

页面加载时获取Token → 提交时携带Token → 后端校验Token → [ 校验成功? 删除Token并执行 : 失败? 拦截 ]
优点
  • 控制粒度最细，最灵活
  • 可与业务逻辑解耦
缺点
  • 流程最复杂，需要前后端配合
  • Token 的存储与管理是关键
