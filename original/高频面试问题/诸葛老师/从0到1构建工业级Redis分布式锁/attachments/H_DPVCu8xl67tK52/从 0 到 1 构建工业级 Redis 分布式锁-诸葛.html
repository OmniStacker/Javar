V2.0避免死锁：引入过期

问题：死锁

如果持有锁的客户端宕机，没有执行 DEL，锁将永远无法释放。

方案：原子化加锁与过期

单独执行SETNX和EXPIRE两步操作并非原子，存在风险。

正确姿势: 使用 SET lock_key <val> EX <seconds> NX 一条命令完成。

V3.0防止误删：校验所有权

问题：误删锁

客户端A因耗时过长，锁自动过期。此时客户端B获取了锁。随后A执行完毕，执行DEL，误删了B的锁。

方案：原子化校验与删除

1. 加锁时，value存入唯一ID（如UUID）。SET lock_key <uuid> ...

2. 解锁时，使用 Lua脚本 原子地“获取key -> 对比uuid -> 删除key”。

V4.0自动续期：看门狗机制

问题：过期时间两难

时间设太短，业务没执行完锁就没了；设太长，宕机后锁要等很久才释放。

方案：Watchdog

1. 加一个稍短的过期时间（如30s）。

2. 启动一个后台守护线程（看门狗）。

3. 看门狗每隔 1/3 过期时间（如10s）就为锁续期。

4. 业务线程宕机，守护线程自动终止，不再续期，锁最终释放。

V5.0高级特性：可重入性

问题：不可重入

一个线程在持有锁的情况下，再次请求同一个锁会失败（死锁）。

方案：Hash + 计数

使用 Redis Hash 结构。Key是锁名，Field是客户端ID，Value是重入次数。利用 HINCRBY 原子地增加计数值。

HINCRBY my_lock uuid_client_1 1

↓

Redis Hash: { my_lock: { "uuid_client_1": 2 } } (表示已重入2次)

V6.0高级特性：阻塞与唤醒

问题：无效轮询

抢锁失败的客户端通过 while(true) + sleep() 自旋，浪费CPU和Redis资源。

方案：发布/订阅 (Pub/Sub)

抢锁失败的客户端订阅一个频道并“休眠”，当锁被释放时，通过发布消息来“唤醒”它们，避免了空转。

V7.0高可用：Redlock

问题：主从架构锁丢失

客户端在Master加锁成功，但锁信息未同步到Slave时Master宕机。新Master上没有锁，导致其他客户端也能加锁成功。

方案：Redlock

部署N个（奇数个）独立的Redis Master。客户端必须在 超过半数 (N/2 + 1) 的节点上加锁成功，才算真正获取锁。
