方案一: `scroll` 快照游标

为海量数据导出而生，通过“冻结”快照与游标ID实现高效顺序读取。

1. 发起首次查询

创建带1分钟时效的滚动查询。

POST /_search?scroll=1m
{ 
"size": 1000, 
"query": { ... } 
}

2. 创建快照 & 返回游标

返回首页数据和“滚动钥匙”。

_scroll_id: "DXF1Z...",
hits: [ ... Page 1 data ... ]

3. 使用游标滚动读取

POST /_search/scroll
{ 
"scroll": "1m", 
"scroll_id": "DXF1Z..."
}

优点

  • 性能极高，是大数据量导出的不二之选。
  • 对协调节点内存压力小。

缺点

  • 数据非实时，操作的是“历史”快照。
  • 无法自由跳页，只能一页一页向后翻。
  • 快照会持续占用堆内存和文件句柄资源。

方案二: `search_after` 实时书签

通过传递上一页的“书签”，实现高性能、无状态的实时滚动翻页。

1. 首次请求

带上一个唯一的排序规则。

GET /_search
{ 
"size": 10,
"sort": ["timestamp", "_id"]
}

实时数据流

2. 返回第1页 & 书签

在最后一条数据中包含“书签”值。

Document 1
...
Document 10
🔖
"sort": [
1668142800, 
"doc_123"
]

3. 使用书签请求第2页

将“书签”放入`search_after`。

GET /_search
{
...
"search_after": [
    1668142800, 
    "doc_123"
]
}

获取下一页数据...

优点

  • 数据实时：每次都是一次新的、独立的查询。
  • 无状态：服务器不保存任何游标信息，扩展性好。

缺点

  • 只能向后翻，无法直接跳转到指定页码。
  • 必须使用一个全局唯一的字段组合进行排序。

实战演练：混合分页方案

在用户体验和系统性能之间找到最佳平衡。

1. 用户发起分页请求

2. 判断请求深度

请求页码 > 100 页?

(或 from + size > 10,000)

否 (浅层分页)

使用 `from` + `size`

✓ 性能开销小

✓ 支持任意跳页

是 (深度分页)

切换为 `search_after`

✓ 保证服务性能

✗ 限制为“上一页/下一页”

总结：分页策略的智慧抉择

没有银弹，只有最适合场景的解决方案。

from + size

浅层分页的首选

  • 用户体验佳，支持任意跳页。
  • 深分页时性能急剧下降。

适用：普通的用户界面分页 (< 10k 条)。

search_after

深层分页的利器

  • 性能恒定，资源消耗低。
  • 不支持跳页，实现稍复杂。

适用：无限滚动、深度数据探索。

scroll

海量数据导出专用

  • 最高效的批量数据拉取方式。
  • 非实时快照，不适用于实时 UI。

适用：数据迁移、离线分析处理。

核心思想：动态切换，智能分页

将 from+size 和 search_after 结合，以用户请求的深度为阈值动态切换策略，是兼顾用户体验与系统性能的最佳实战方案。
