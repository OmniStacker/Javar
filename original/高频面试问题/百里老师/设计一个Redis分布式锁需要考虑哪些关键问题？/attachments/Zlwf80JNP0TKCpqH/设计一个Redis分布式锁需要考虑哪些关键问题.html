问题一：死锁问题

线程崩溃后，锁无法释放

解决方案

1. 设置过期时间
SET lock_key value NX EX 30

即使线程崩溃，锁也会在30秒后自动释放

2. Redisson看门狗机制

自动续期机制，防止业务执行时间超过过期时间

每10秒检查 自动续期至30秒

过期时间设置原则：业务最大耗时 + 50%-100%冗余
示例：业务20秒 → 设置30秒

问题四：不可重入问题

同一线程无法重复获取已持有的锁

递归调用场景

businessMethod()

第1次加锁 ✓

lock.lock();  // 成功
try {
    // 业务逻辑...
    recursiveMethod();
} finally {
    lock.unlock();
}
调用

recursiveMethod()

第2次加锁 ✗

lock.lock();  // 失败! 死锁
try {
    // 递归逻辑...
} finally {
    lock.unlock();
}

线程被自己持有的锁阻塞，陷入死锁

Redisson可重入锁

Hash结构 + 计数器

问题五：原子性问题

多步操作被其他命令打断导致竞态条件

错误：非原子操作

加锁场景

// 步骤1: 判断
if (jedis.exists("lock_key") == false) {
    // ⚠️ 危险窗口：可能被打断
    // 步骤2: 设置
    jedis.set("lock_key", "value");
    jedis.expire("lock_key", 30);
}
竞态条件时序
线程A: EXISTS → false
线程B: EXISTS → false
线程A: SET lock_key A
线程B: SET lock_key B (覆盖!)

互斥性被破坏

解锁场景

// 步骤1: 查询
String value = jedis.get("lock_key");
// ⚠️ 危险窗口：锁可能过期
// 步骤2: 删除
if (myValue.equals(value)) {
    jedis.del("lock_key"); // 可能误删
}

正确：原子操作

加锁：SET NX EX

SET lock_key unique_value NX EX 30

NX: 仅当key不存在时设置

EX 30: 同时设置30秒过期

原子性: 一条命令完成三件事

解锁：Lua脚本

if redis.call('get', KEYS[1]) == ARGV[1] then
    return redis.call('del', KEYS[1])
else
    return 0
end

查询 + 校验 + 删除 原子执行

Redis单线程保证不被打断

非原子

步骤1
⚡ 可被打断
步骤2

原子操作

一次性完成
