热点Key瓶颈

根源：集群也无解的“单点宿命”

集群模式下，一个Key的哈希槽位是固定的，导致所有压力仍由单一主节点承担。

所有请求

主节点A (空闲)
主节点B (过载)
主节点C (空闲)

方案：化整为零第一步 · 拆分

核心思路：将一个热点大Key，化整为零，拆分成N个小Key。

coupon:stock

coupon:stock:0
coupon:stock:1
...
coupon:stock:N

方案：化整为零第二步 · 散列

利用CRC16哈希，将不同的小Key自动散列到集群中的不同物理节点。

coupon:stock:1

小Key

CRC16(key) % 16384

映射到某主节点

方案：化整为零第三步 · 路由

客户端根据UserID等信息进行路由，将请求均匀地分发到不同的小Key上。

User A
User B
User C

业务逻辑分发

userID.hashCode() % N

Node1 decr(key:0)
Node2 decr(key:1)
Node3 decr(key:2)

权衡：没有银弹，只有取舍

优点

  • 吞吐量提升: 将压力分散到多节点，系统总QPS成倍增长。
  • 负载均衡: 有效避免单点过载，提升系统整体稳定性。

缺点

  • 系统复杂性: 需引入客户端路由逻辑，增加开发心智负担。
  • 维护开销: Key数量调整、数据聚合、集群扩容等操作更复杂。

总结：从“一点引爆”到“雨露均沾”
