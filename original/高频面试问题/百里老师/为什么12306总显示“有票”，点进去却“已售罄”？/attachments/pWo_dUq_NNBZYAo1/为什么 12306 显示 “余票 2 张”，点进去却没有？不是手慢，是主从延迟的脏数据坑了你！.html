点进去却没有？

不是你手慢，是主从延迟的脏数据坑了你！

查票: 余票2张
光速点击
主从延迟
数据不同步
结果: 已售罄

是什么：主从延迟与脏数据

写操作 (下单) 票数 - 1
主库 (Master) 票数 = 1 (新)
延迟 ⚡️
从库 (Slave) 票数 = 2 (旧)
你的读操作 (查票) 读到脏数据！

你查了“过去”的数据，当然买不到“现在”的票！

为什么：探究主从复制的“作案现场”

主库 (Master)
Binlog 写入
从库 I/O 线程
拉取 Binlog
主要延迟点
从库 (Slave)
Relay Log 写入
SQL 线程重放

网络、磁盘I/O、大事务...任何一环的“慢动作”都会造成延迟！

怎么做：半同步复制

异步复制 (默认)

Client 提交
Master 写 Binlog & 立即返回 OK
(异步)
Slave 拉取数据

半同步复制 (更可靠)

Client 提交
Master 写 Binlog
等待...
Slave 确认收到 & 返回 ACK
Master 向 Client 返回 OK

用写入性能的轻微牺牲，换取更高的数据一致性保障。

怎么做：强制读主库

用户请求
请求路由器 判断请求类型
普通读 (如浏览)
Slave 1
Slave 2
关键读 (如查库存)
Master

简单粗暴，效果拔群。适用于金融、交易等零容忍场景。

怎么做：延迟双删

线程 A (写操作)

线程 B (读操作)

1. 更新 Master DB
2. 删除 Redis 缓存
3. 读 Redis (Miss)
4. 读 Slave DB (读到旧值 v1)
5. 写 Redis (缓存了旧值 v1)
延迟 N 秒 ( > 主从延迟)
6. 再次删除 Redis 缓存
(清除脏数据 v1)

这颗“定时炸弹”，精准清除了主从延迟产生的缓存脏数据！

方案对比：没有银弹，只有取舍

每种方案都是在一致性、性能、复杂度之间的权衡。

总结：面试“高分回答”

1. 分场景讨论: 不存在银弹，根据业务对一致性的容忍度选择方案。

2. 强一致场景: 采用 强制读主库，确保数据绝对准确（如交易、金融）。

3. 最终一致场景: 采用 延迟双删 策略，保证性能和最终一致性（如商品详情）。

4. 基础设施保障: 开启 半同步复制，提高集群整体的数据可靠性。
