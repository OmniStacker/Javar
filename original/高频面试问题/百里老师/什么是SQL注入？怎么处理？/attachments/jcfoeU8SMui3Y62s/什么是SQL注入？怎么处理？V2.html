什么是SQL注入？怎么处理？

从根源剖析到最佳防御实践

SQL注入是通过在输入中注入恶意SQL代码，
使数据库执行未授权操作的攻击方式

正常用户

输入合法数据
执行预期查询

攻击者

注入恶意SQL
篡改查询逻辑

数据库沦陷

数据泄露/篡改
甚至完全控制

典型攻击场景：从正常到危险

同一个登录接口，两种截然不同的命运

正常查询流程

用户输入: admin

// 拼接后的SQL
SELECT * FROM users
WHERE username = 'admin'

✓ 正常返回用户数据

SQL注入攻击

恶意输入: admin'; DROP TABLE users; --

// 拼接后的SQL（被篡改！）
SELECT * FROM users
WHERE username = 'admin';
DROP TABLE users;
-- '

✗ 用户表被删除！

攻击原理解析

  • ' 提前闭合了原SQL的字符串
  • ; 结束当前语句，开始新的恶意语句
  • -- 注释掉后续内容，使SQL语法完整

根源：数据与代码的边界崩塌

当用户输入侵入SQL结构，灾难就此开始

理想状态：边界清晰

数据区

用户输入

代码区

SQL逻辑

危险状态：边界消失

数据侵入

代码被篡改

字符串拼接导致边界消失

历史根源：JDBC Statement时代

  • 完全依赖字符串拼接：SQL结构由开发者手动拼接决定
  • 参数不可控：用户输入直接融入SQL，无隔离机制
  • SQL格式动态变化：数据库无法预判和优化

开发者的认知盲区

  • 框架屏蔽细节：ORM默认使用参数化查询
  • 缺乏底层经验：未接触过原始JDBC拼接
  • 过度信任框架：误以为"用了框架就绝对安全"

核心解决方案：PreparedStatement

通过预编译和参数化，重建数据与代码的边界

工作原理：三步走

1

定义SQL模板

使用 ? 作为参数占位符

2

预编译SQL结构

数据库解析并锁定SQL逻辑，此时结构不可变

3

安全传递参数

参数作为纯数据独立发送，无法篡改SQL结构

关键转变：从“拼接”到“分离”

Statement (旧方式)

代码 + 数据 = 危险的SQL

PreparedStatement (新方式)

SQL模板(代码) + 参数(数据) = 安全的执行

不安全的写法

String sql = "SELECT * FROM users WHERE username = '" + username + "'";
Statement stmt = conn.createStatement();
ResultSet rs = stmt.executeQuery(sql);

安全的写法

String sql = "SELECT * FROM users WHERE username = ?";
PreparedStatement pstmt = conn.prepareStatement(sql);
pstmt.setString(1, username);
ResultSet rs = pstmt.executeQuery();

MyBatis核心实践：认准 `#{}`

一个符号决定安全，覆盖99%的场景

安全卫士: #{ }

  • 原理: PreparedStatement
  • 效果: 解析为 `?`，参数被安全处理
  • 场景: 所有动态参数传递
<foreach collection="ids" item="id" open="(" separator="," close=")">
  #{id}
</foreach>

双刃剑: ${ }

  • 原理: 字符串拼接
  • 效果: 直接文本替换，有注入风险
  • 特殊场景: 动态表名/列名/排序
ORDER BY ${columnName}

最终裁决：使用原则

默认，永远，必须使用 `#{}`

无论是简单参数还是动态SQL（如 ``, ``），它都能保证安全。

仅在必要时，谨慎使用 `${}`

仅用于无法参数化的场景（如`ORDER BY`），且必须配合严格的白名单校验，绝不能直接使用前端传入的值。

总结：从核心到体系

掌握核心，构建体系，告别注入

核心回顾

根源：边界崩塌

字符串拼接，导致用户输入的数据侵入了SQL代码的结构。

核心方案：参数化查询

使用 `PreparedStatement` (MyBatis中的 `#{}` )，将SQL结构和数据分离。

框架实践：认准`#{}`

始终用 `#{}`，仅在`ORDER BY`等场景严格校验后用 `${}`。

构建防御体系

纵深防御：不止于代码

单一防御点可能被绕过，建立多层防御是专业做法。

参数化查询 + 输入验证 + 最小权限

面试直通车

Q: `#{}` 和 `${}` 的区别？
A: `#{}` 是预编译，防注入；`${}` 是拼接，有风险。

永远不要信任用户输入，
参数化查询是你的第一道、也是最重要的一道防线。
