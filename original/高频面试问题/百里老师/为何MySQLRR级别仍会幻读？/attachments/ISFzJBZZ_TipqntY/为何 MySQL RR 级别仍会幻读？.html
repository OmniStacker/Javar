幻读现象

同一事务中两次查询结果不一致，出现"幻影"数据

RR 隔离级别的幻读防御机制

MySQL 通过 MVCC 和 Next-Key Lock 两种机制防御幻读

Next-Key Lock 机制

记录锁 + 间隙锁

id=100

id=+∞

加锁读取 范围锁定 阻止插入

两种机制对比

MVCC 适用场景
  • 纯查询操作（SELECT）
  • 不需要修改数据的场景
  • 高并发读取需求
  • 数据分析和报表生成
Next-Key Lock 适用场景
  • 读后写入操作（SELECT + INSERT/UPDATE）
  • 需要保证数据强一致性
  • 防止并发插入导致的幻读
  • 关键业务逻辑（如库存扣减）

问题场景：快照读与当前读的混合使用

当事务内混合使用两种读取模式时，MVCC 的保护机制将失效

并发执行时间线

事务 A

1
快照读 MVCC
SELECT * FROM products
WHERE id > 100;
返回: 0 行

基于事务开始时的快照

3
尝试插入
INSERT INTO products
VALUES (101, 'Product A', 99.99);
错误: Duplicate entry '101'

主键冲突 - 但快照读时明明没有数据？

4
当前读验证 Next-Key Lock
SELECT * FROM products
WHERE id = 101 FOR UPDATE;
返回: 1 行 (幻读！)

幻读现象

步骤1查询为空，步骤4却查到数据

事务 B

事务B尚未开始

2
并发插入并提交

开始事务

BEGIN;

插入数据

INSERT INTO products
VALUES (101, 'Product B', 88.88);

提交事务

COMMIT;
成功提交 (id=101 已存在)

此时事务A的快照读无法看到此数据

问题根源分析

快照读的局限

步骤1使用MVCC快照读，只能看到事务开始时的数据，无法感知事务B的插入

写入操作的真实性

步骤3的INSERT检查的是当前最新数据，发现id=101已存在，导致主键冲突

当前读的"惊喜"

步骤4使用当前读，读取到最新数据，与步骤1的结果不一致，形成幻读

关键结论

在同一事务中混合使用快照读和当前读会导致数据不一致，RR隔离级别无法防御这种场景下的幻读。

解决方案：统一使用当前读模式

将首次检查升级为当前读，通过 Next-Key Lock 锁定范围防止幻读

核心解决思路

将快照读 (SELECT) 改为 当前读 (SELECT ... FOR UPDATE)，在首次查询时就锁定范围，阻止其他事务插入数据。

事务 B

由于事务A已锁定 (100, +∞) 间隙

阻塞原因:

• 事务A持有 Next-Key Lock

• 锁定范围包含 id=101

• 必须等待事务A提交或回滚

问题场景 (混合读)
步骤1: 快照读

✗ 不加锁，无法阻止并发插入

步骤2: 事务B插入

✓ 成功插入 (没有锁阻止)

步骤3-4: 幻读发生
INSERT 失败 → SELECT FOR UPDATE 查到数据

✗ 数据不一致，幻读出现

解决方案 (统一当前读)
步骤1: 当前读加锁
SELECT ... FOR UPDATE

✓ 锁定范围 (100, +∞)

步骤2: 事务B尝试插入
INSERT ... (阻塞)

⏳ 等待锁释放 (被阻止)

步骤3-4: 一致性保证
INSERT 成功 → COMMIT

✓ 数据一致，无幻读

最佳实践建议

读后写场景使用当前读

如果查询后需要基于结果进行写操作，首次查询就应使用 FOR UPDATE

保持读模式一致性

同一事务中避免混合使用快照读和当前读

关键业务逻辑加锁

库存扣减、账户余额等关键操作必须使用当前读

纯查询可用快照读

报表、数据分析等只读场景，快照读性能更优
