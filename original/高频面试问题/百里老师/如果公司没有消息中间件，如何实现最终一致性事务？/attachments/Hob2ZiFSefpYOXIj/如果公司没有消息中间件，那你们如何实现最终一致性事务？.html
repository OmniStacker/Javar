如果公司没有消息中间件

如何实现最终一致性事务？

在深入探讨解决方案前，我们必须先理解构建分布式系统的两大理论基石：CAP 与 BASE。

CAP 理论：不可能三角

一致性 (Consistency)

所有节点在同一时间具有相同的数据。

可用性 (Availability)

每个请求都能收到一个（非错误）响应。

分区容错性 (Partition Tolerance)

系统在网络分区后仍能继续运行。

BASE 理论：现实的选择

在现代分布式系统中，P 是必须项。因此我们通常选择 AP，牺牲强一致性(C)，追求最终一致性。

Basically Available, Soft state, Eventually consistent

方案一：本地消息表（最推荐）

利用数据库事务保证原子性，定时任务异步发送

1

事务写入

业务数据 + 消息记录
在同一事务中完成

2

定时扫描

独立任务轮询数据库
查找待发送消息

3

发送确认

调用下游服务
成功后更新消息状态

优点

  • 实现简单：只需数据库和定时任务，无额外依赖。
  • 可靠性高：利用数据库事务保证消息必不丢失。
  • 易于排查：消息状态持久化，方便追溯问题。

缺点

  • 实时性差：存在5-10秒的轮询延迟。
  • 数据库压力：对消息表频繁读写，需定期清理。

方案二：消息表 + 定时对账

双重保障：实时推送 + 异步兜底

金融级双重保障机制

通过实时消息推送保证快速响应， 配合定时对账机制确保数据最终一致性。

1

实时消息推送

本地事务保证

订单数据和消息记录在同一事务中

准实时响应

通常在 5-10 秒内完成数据同步

覆盖率: 99.9%+

2

定时对账补偿

数据比对

定期比较上下游数据状态

差异修复

自动或人工处理数据不一致

兜底保障: 100%

行业标准

此方案以极高的可靠性， 成为金融、支付、电商等领域的 事实标准。

方案三：Saga 模式

为长事务设计的编排模式，每个子事务都有对应的补偿操作

核心理念

将一个大的分布式事务拆分成多个本地事务，通过事务编排器协调执行。 如果任一步骤失败，则按相反顺序执行补偿操作。

正向执行流程

1

创建订单

生成订单记录

2

扣减库存

减少商品数量

3

处理支付

扣减账户余额

如果第3步失败

补偿回滚流程

2

恢复库存

增加商品数量

1

取消订单

标记订单已取消

适用场景

  • 长业务流程：涉及多个服务的复杂业务链
  • 可补偿操作：每个步骤都有明确的逆向操作

注意事项

  • 补偿复杂性：需要为每个步骤设计补偿逻辑
  • 状态管理：需要可靠的事务状态跟踪机制

方案四：TCC 模式

Try (预留) → Confirm (确认) → Cancel (取消)

二阶段提交的业务层实现

TCC 是应用层的二阶段提交协议，通过业务逻辑来保证事务的一致性。 相比 Saga 的最终一致性，TCC 提供强一致性保证。

TCC 执行流程

成功路径

T

Try 阶段

检查并预留业务资源

账户余额: ¥1000
冻结金额: ¥100
C

Confirm 阶段

确认执行，扣减冻结资源

账户余额: ¥900
冻结金额: ¥0

失败路径

T

Try 阶段

部分服务预留失败

库存服务预留失败
C

Cancel 阶段

取消执行，释放冻结资源

账户余额: ¥1000
状态: 已回滚

谨慎使用

TCC 模式开发成本极高，维护复杂，仅建议在对数据一致性要求苛刻的核心金融业务中使用。 大多数场景下，Saga 模式已经足够。

四大核心实施要点

1. 幂等性

确保重复消息不产生副作用，是所有方案的基石。

2. 重试退避

应对网络抖动，通过指数退避算法优雅地重试。

3. 监控告警

监控消息堆积、失败率，让你比用户更早发现问题。

4. 数据清理

定期归档或删除历史消息，防止数据库性能下降。
