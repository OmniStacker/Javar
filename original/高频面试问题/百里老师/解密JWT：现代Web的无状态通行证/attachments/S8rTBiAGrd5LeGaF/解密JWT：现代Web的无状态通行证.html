JWT 结构分解

一个令牌，三个部分，一条清晰的装配流水线。

STEP 1: 将 Header 和 Payload 分别进行 Base64Url 编码

Header (JSON)

{\n  "alg": "HS256",\n  "typ": "JWT"\n}
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9
明文可见!

Payload (JSON)

{\n  "sub": "12345",\n  "role": "admin"\n}
eyJzdWIiOiIxMjM0NSIsInJvbGUiOiJhZG1pbiJ9

STEP 2: 将编码后的两部分用 '.' 拼接，并使用密钥进行签名

Secret Key

eyJhbGci...CIn0.eyJzdWIi...pbiJ9

HMACSHA256 Processor

TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ

STEP 3: 将三部分用 '.' 拼接成最终的 JWT

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxMjM0NSIsInJvbGUiOiJhZG1pbiJ9.TJVA95OrM7E2cBab30RMHrHDcEfxjoYZgeFONFh7HgQ

总结：JWT vs Session

在无状态的现代架构中，JWT是更优解。

特性JWT传统 Session
状态存储无状态 (客户端存)有状态 (服务端存)
扩展性极佳差 (需状态同步)
安全性依赖签名和HTTPS依赖Cookie安全策略
跨域支持天生支持需CORS等额外配置
主动失效困难 (需黑名单策略)简单 (服务端删除即可)
适用场景微服务、分布式、API网关单体应用、后台管理系统
