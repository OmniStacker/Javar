简陋方案：高并发下的“竞态条件”

线程A (消息M1)

1. SELECT * WHERE id=X

▶️ 结果: null

2. INSERT ... (执行业务)

线程B (消息M1-重复)

1. SELECT * WHERE id=X

▶️ 结果: null

2. INSERT ... (重复执行!)

两条消息同时“穿透”了检查防线！

方案一：悲观锁 (Select for Update)

线程A (消息M1)

SELECT ... FOR UPDATE

▶️ 成功锁定，执行业务

COMMIT (释放锁)

线程B (消息M1-重复)

SELECT ... FOR UPDATE

等待锁释放...

▶️ 获得锁, 发现已处理, 跳过

缺点：锁住业务表，严重影响性能和吞吐量。

方案二：本地消息表 + 事务

消费请求
→

同一数据库事务

① 插入消息记录表
+
② 更新业务表

优点

利用事务保证了“记录消费”和“执行业务”的原子性，实现了“Exactly Once”。

局限性

强依赖单库事务，无法覆盖含RPC、跨库操作等复杂场景。

方案三：终极演进 - “状态机”幂等方案

① 新消息到达

查询幂等记录
无记录?
插入(状态:消费中) + 设置超时
执行业务逻辑...

② 重复消息到达

查询幂等记录
状态:消费中?
延迟重试
状态:已完成?
直接ACK

③ 业务执行后

成功

更新状态:已完成

失败

删除记录

关键：超时机制

自动删除过期的“消费中”记录，防止死锁和消息丢失。

方案四：存储媒介的选择

MySQL

优点: 数据可靠性、一致性高。

缺点: 性能相对较低，实现超时TTL需额外开发定时任务。

Redis

优点: 性能极高，原生支持TTL，完美契合超时需求。

缺点: 数据可靠性相对较低，需业务自行权衡。

这套方案是“银弹”吗？

✅ 价值巨大：解决99%重复问题

解耦、通用、高效

❌ 无法解决：中途失败的副作用

1锁库存(RPC)
服务崩溃!
1'锁库存(RPC) (再次执行!)
2'插订单(DB)

总结：构建完整的幂等性“防御体系”

1

核心: 采用“状态机”幂等方案，解决绝大部分问题。

2

接口: 关键下游服务(RPC)自身也要实现幂等。

3

补偿: 消费失败时，提供回滚/补偿机制。

4

运维: 做好优雅停机与死信队列监控。
