核心痛点

  • 服务器被动

    无法主动向客户端推送数据，只能等待被“临幸”。

  • 连接与头部开销

    每次请求都需携带完整的HTTP头部，造成带宽和性能的浪费。

方案一：定时轮询 (暴力破解)

客户端不知疲倦地重复询问，直到服务器“不堪其扰”地给出答案。

资源消耗

服务器

优点

  • 实现简单：逻辑清晰，前端一个 `setInterval` 即可搞定，无需复杂配置。

缺点

  • 性能瓶颈：绝大多数都是无效请求，极大浪费了客户端和服务器的宝贵资源。
  • 延迟明显：数据的实时性完全取决于轮询间隔。间隔太短则费资源，太长则体验差。

方案二：长轮询 (The "Patient Waiter")

对轮询的智能优化：服务器学会了“憋大招”，有货才发。

客户端

状态: 发送请求 / 处理数据

1. 发起请求

2. 连接挂起 (Holding)

3. 立即响应

服务器

状态: 保持连接

新数据!

4. 客户端处理完数据后，立即发起新一轮长轮询

优点

  • 减少无效请求：只有在数据更新时才响应，极大提升了效率，减少了大部分轮询的资源浪费。

缺点

  • 服务器压力：需要为每个客户端维持一个挂起的连接，当客户端数量庞大时，对服务器是考验。
  • 仍有连接开销：每次响应和超时后都需要重新建立连接，并非真正的“长连接”。

终极方案：WebSocket 全双工革命

一次握手，持久连接，真正的双向奔赴。

2. 建立持久化双向通道

服务器

优点

  • 真·实时，低延迟：连接一旦建立，数据可立即双向传输，无须等待请求。
  • 开销极小：握手后，数据帧头部信息很少，极大减少了网络开销。
  • 原生双向通信：完美支持服务器主动推送和客户端上报，是为实时交互而生的协议。

权衡

  • 实现稍复杂：相比无状态的HTTP，WebSocket是状态化的，对服务器后端设计有更高要求。
  • 兼容性：需要考虑旧的浏览器或特定的网络代理/防火墙环境。
