核心禁忌: Rebase公共分支的灾难

黄金法则：永远不要 rebase 一个团队共享的远程分支！

开发者 A

"为了干净，我 rebase 了公共分支并强推！"

git push --force

"我准备推送我的代码...嗯？历史分叉了？！"

后果：团队其他成员的本地仓库与远程仓库产生严重冲突，需要花费大量时间手动修复。

实战指南：合并策略选择器

根据不同场景，选择最合适的合并策略。

优先使用 Git Merge

合入公共分支

如 `master`, `release`，确保历史稳定。

团队新人较多

操作简单，不易出错，降低协作门槛。

谨慎使用 Git Rebase

整理个人分支

合并前清理提交，保持历史线性、整洁。

追求极致历史

适合对代码历史有洁癖的资深开发者。

最佳实践：用 `rebase` 整理过程，用 `merge` 记录结果。

最终总结：一张表看懂所有差异

掌握决策矩阵，自信应对任何合并场景。

对比维度 Git Merge Git Rebase
历史记录 非线性，保留分叉 线性，整洁干净
可读性 真实反映并发，但复杂 清晰易追溯，像故事线
安全性 安全，不改历史 危险，重写历史
合并提交 会产生合并提交 不产生（快进时）
核心用途 将功能安全地【合入】公共分支 在合并前【整理】个人分支
