方案一：旁路缓存模式

最经典通用，写操作后【删除缓存】是精髓。

写请求

1. 更新MySQL

2. 删除Redis缓存

性价比之王
逻辑简单

易于理解和实现，适用绝大多数场景。

数据可靠

删除缓存保证了下次读取时能从DB加载最新数据。

方案二：MQ异步更新

追求极致写性能，接受【最终一致性】。

写请求

1. 更新Redis

2. 发送MQ消息

3. 消费者

4. 更新MySQL

高吞吐量

写操作无需等待数据库，响应极快。

最终一致性

存在短暂数据不一致，需保证消息幂等性。

方案三：双写方案 (TCC)

金融级强一致性保障，不容丝毫差池。

TCC 分布式事务边界

TCC协调器

更新 Redis

Try Confirm/Cancel

更新 MySQL

强一致性

提供原子性保证，数据绝对可靠。

高复杂度 & 低性能

引入分布式事务，系统开销巨大，性能下降。

方案四：数据回写方案

超高频聚合写，牺牲一致性换取极致性能。

多个写请求

Redis 聚合计数

INCR article:1:likes -> 1001

INCR article:1:likes -> 1002

... ...

INCR article:1:likes -> 2000

阈值 / 定时
触发器

批量更新MySQL

极致写性能

将大量DB写操作合并为一次，极大降低DB压力。

弱一致性

数据延迟非常高，只适用于非核心指标统计。
