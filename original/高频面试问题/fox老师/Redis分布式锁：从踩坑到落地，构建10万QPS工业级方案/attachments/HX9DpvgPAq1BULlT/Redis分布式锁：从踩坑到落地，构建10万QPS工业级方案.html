return 0

生产环境的“天坑”与对策

坑1

锁过期但业务没完成

业务执行时间超过锁的过期时间，导致其他线程提前进入。

问题场景：并发执行

线程 A 加锁成功 (30s 过期)

线程 A 执行业务 (耗时 > 30s)

锁自动过期释放！

线程 B 加锁成功

线程 A 和 B 并发执行，数据错乱！

解决方案：引入“看门狗”(Watchdog)

启动一个后台线程，在业务执行期间，周期性地为锁“续命”。业务执行完毕，看门狗停止续期，然后释放锁。

// 启动看门狗线程
watchDogPool.submit(() -> {
while (isBusinessRunning) {
  // 1. 休眠一段时间
  Thread.sleep(renewInterval);
  // 2. 用 Lua 脚本原子性地给自己的锁续期
  jedis.eval(renewScript, ...);
}
});

坑2

主从切换，导致锁丢失

主节点加锁后宕机，锁信息未同步到从节点，导致新主节点上可以重复加锁。

问题场景：真实电商惨案

1. 线程A加锁

Master

2. 同步延迟

Slave

3. Master宕机

CRASH!

4. Slave变新主

New Master

5. 线程B加锁成功

New Master

结果：两个线程同时持有锁，5分钟内1200笔订单重复创建！

解决方案：3 种方案按业务选择

方案核心逻辑优点缺点适用场景
主从延迟释放 加锁后休眠100ms，等待同步 实现简单，性能损耗低 无法100%避免 普通业务（商品库存）
Redis Cluster 分片锁 Key分片到不同节点，分散压力 高可用，无锁丢失风险 需处理跨分片锁 高并发场景（秒杀）
红锁 (Redlock) 超过半数独立节点加锁成功 强一致性 运维成本高，性能低 金融级场景（支付）

避坑提示：90% 的业务用 Redis Cluster 分片锁足够，不要盲目用红锁！

坑3

自旋等待，导致 CPU 飙升

加锁失败后，使用`while(true)`循环不断重试，造成CPU资源浪费。

问题：无效的“忙等”

100%

CPU 使用率

// 抢不到锁，就一直循环尝试
while (!tryLock(lockKey)) {
// CPU 空转，浪费资源
}

解决方案：发布/订阅 (Pub/Sub)

线程B:加锁失败订阅并休眠
线程A:解锁发布消息
线程B:收到消息被唤醒重新尝试加锁

变“忙等”为“通知”，极大降低CPU消耗。再配合短暂的自旋作为兜底，防止消息丢失。

坑4

自研可重入锁，逻辑复杂易出错

自己实现可重入、公平锁、看门狗等高级功能，费时费力且容易出错。

终极解决方案：拥抱 Redisson

一个功能强大且生产级的 Redis Java 客户端

Redisson 内置的核心功能：

可重入

同一线程可重复加锁，不会死锁。

看门狗

自动续期，彻底解决锁过期问题。

公平锁

默认按请求顺序分配锁，避免线程饥饿。

主从安全

内置重试机制，解决主从切换锁丢失。

生产级代码范例

// 1. 初始化 Redisson 客户端 (生产推荐 Cluster 模式)
Config config = new Config();
config.useClusterServers()
    .addNodeAddress(
        "redis://192.168.1.101:6379", "redis://192.168.1.102:6379",
        "redis://192.168.1.103:6379", "redis://192.168.1.104:6379",
        "redis://192.168.1.105:6379", "redis://192.168.1.106:6379"
    )
    // 集群状态扫描间隔，自动感知拓扑变化
    .setScanInterval(2000) 
    // 超高并发场景下，扩大公平锁竞争队列 (默认32)
    .setLockFairPoolSize(64);

// 2. 创建客户端 (Spring Boot 环境可通过 Starter 自动注入)
RedissonClient redisson = Redisson.create(config);

// 3. 获取可重入锁 (锁Key按业务粒度设计)
RLock lock = redisson.getLock("lock:order:20240520001");

// 4. 加锁 (默认30秒过期，自动启动看门狗续期)
lock.lock();
try {
  log.info("订单锁加锁成功，开始创建订单...");
  createOrder(20240520001);
  // 子方法中再次加锁 (可重入特性，无需担心死锁)
  updateOrderStatus(20240520001);
} catch (Exception e) {
  log.error("订单处理异常，锁Key：{}", lock.getName(), e);
  throw e;
} finally {
  // 5. 解锁 (自动处理重入计数，为0时才删锁)
  if (lock.isHeldByCurrentThread()) {
      lock.unlock();
      log.info("订单处理完成，已释放锁");
  }
}

Redisson 如何解决核心痛点？

解决主从锁丢失：自动重试

加锁后若主节点宕机，Redisson 能自动感知，并重新向新主节点发起加锁请求，从根本上避免“锁双持”。

Master 宕机

感知拓扑变化

自动重试新主

公平锁与高并发调优

默认采用公平锁，按请求顺序分配，避免线程饥饿。超高并发下可通过 `setLockFairPoolSize` 扩大竞争队列。

线程排队

依次获取锁

TPS > 5万? 调大队列

生产环境避坑指南

不要为了追求所谓的极致性能而使用 **“不公平锁”** (`getFairLock`)。它可能导致某些线程长时间无法获取到锁（线程饥饿），给系统带来巨大的稳定性风险。在绝大多数场景下，Redisson 默认公平锁的性能损耗完全可以忽略不计。
