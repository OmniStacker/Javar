字节一面：库存超卖我只答了“加锁”...

7层方案｜性能 vs 一致性｜场景驱动｜技术权衡

1. 数据库无符号

最后的防线

库存: 1
→
UPDATE
→
库存: 0

🚫

再次 UPDATE (失败)
👍 兜底保证
👎 被动防御

2. 悲观锁

串行执行，性能杀手

请求1
请求2
请求3
SELECT ... FOR UPDATE
👍 强一致性
👎 吞吐量极低

3. 乐观锁 (CAS)

先斩后奏，冲突重试

请求A: 读V1
请求B: 读V1
→
A: 成功✅
B: 失败❌
→
B重试
👍 性能提升
👎 冲突时CPU空转

4. Redis 队列

削峰填谷，异步处理

🌊
→
队列
→
💧
→
👍 扛瞬时流量
👎 逻辑复杂/有风险

5. Redis LUA 脚本

打包命令，保证原子

1. GET stock
2. IF stock > 0
3.   DECR stock
4. END

→
原子
👍 Redis层面原子性
👎 脚本维护难

6. 分布式锁

宁慢勿错，强一致

服务A →
服务B 🚫
服务C 🚫
👍 分布式强一致
👎 性能瓶颈

7. 分段锁

分而治之，并发倍增

总库存 = 100
段1(10)
段2(10)
...
请求A→段1
请求B→段2
👍 并发能力倍增
👎 实现复杂/库存碎片

8. 总结：没有银弹，只有取舍

技术选型的艺术

性能 / 并发
一致性 / 简单性
业务场景
根据业务对性能、一致性和成本的要求，选择最适合的方案组合。
