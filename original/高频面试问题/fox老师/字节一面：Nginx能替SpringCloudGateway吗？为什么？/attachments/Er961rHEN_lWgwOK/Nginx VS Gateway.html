Nginx 能替 Gateway 吗？

一张图讲透：定位、差异与最佳实践

核心破题：搞懂“定位”就不纠结

保安 (Nginx)

守好园区大门，管“南北向流量”

核心诉求：稳、快、高并发

挡黑客、抗DDoS

做负载均衡

管家 (Gateway)

协调大楼内部，管“东西向流量”

核心诉求：灵活、精准、懂业务

做身份校验

做精细流控

场景PK ①：动态路由 (服务扩容)

“库存服务”从1台扩容到3台，会发生什么？

Spring Cloud Gateway: 自动、无感知

1. 实时拉取服务列表

服务实例列表

192.168.1.10 192.168.1.11 新增 192.168.1.12 新增

2. 自动转发新流量

零配置、零重启

Nginx: 手动、高风险

1. 手动修改配置文件

upstream stock_service {
  server 192.168.1.10;
  server 192.168.1.11; # add new
  server 192.168.1.12; # add new
}

2. 执行 reload 使其生效

$ nginx -s reload
易出错、效率低

场景PK ②：精细化流控

需求：“VIP用户每秒100次，普通用户10次”

Spring Cloud Gateway: 简单、贴合业务

请求

自定义 Filter

响应
class AuthFilter implements GlobalFilter {
  // 1. 获取用户身份 (VIP/Normal)
  // 2. 调用 Sentinel/Resilience4j 限流
  // 3. 业务逻辑清晰...
}
工程师易维护

Nginx: 复杂、性能损耗

请求

Lua 脚本

响应
local user_role = get_user_role(ngx.req)
if user_role == "VIP" then
  -- ... 复杂的限流逻辑 ...
else
  -- ... 另一套限流逻辑 ...
end
学习成本高，拖慢转发

最佳实践：不是“二选一”，而是“强强联合”

外部请求

Nginx (流量防火墙)

  • 全局负载均衡
  • DDoS/CC 防护
  • 静态资源缓存
  • SSL 卸载

Gateway (业务总管)

  • 动态服务发现
  • 身份认证 & 鉴权
  • 精细化流控熔断
  • 日志 & 监控

微服务集群

面试高分回答逻辑

1. 定位 (保安 vs 管家)
2. 差异 (两大场景PK)

结论：它们是“分工伙伴”，不是“竞争对手”
