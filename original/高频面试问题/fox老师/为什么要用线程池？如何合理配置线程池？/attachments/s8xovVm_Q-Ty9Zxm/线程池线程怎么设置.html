第一幕：告别 `new Thread()` 的三大痛点

💸降低资源开销

  • 痛点: 线程是重量级资源，频繁创建和销毁，成本极高。
  • 解决: 通过复用已有线程，避免了内核态切换和资源消耗。

🚧控制并发风险

  • 痛点: 无限制创建线程，会导致CPU上下文切换和内存溢出(OOM)。
  • 解决: 限制并发线程数，像一个“阀门”保护系统不被冲垮。

📊提供管理能力

  • 痛点: 线程状态黑盒，难以监控和管理。
  • 解决: 提供任务排队、拒绝策略、状态监控等高级功能。

第二幕：科学配置四步落地法

1

分析任务类型：量化核心特征

🧠 CPU 密集型

大量计算，CPU繁忙。线程数不宜过多，避免切换开销。

线程数 ≈ CPU核心数

🌐 IO 密集型

大量等待，CPU空闲。可配置更多线程，提升吞吐。

核心数 / (1 - IO等待占比)

🔎 用 Arthas 等工具量化，拒绝拍脑袋！

↓
2

确定目标并约束资源

📈 结合业务目标反推

配置要服务于业务，从 QPS 和 响应时间(RT) 出发。

理论线程数 = QPS × RT(秒)

💻 考虑机器资源限制

理论值不能脱离实际，必须关注两大约束：

  • CPU约束: 利用率建议 < 80%
  • 内存约束: 警惕队列和线程栈导致的OOM
↓
3

配置队列与拒绝策略：应对过载

🚫 阻塞队列

  • ArrayBlockingQueue (有界): 在线业务首选，防止OOM。
  • LinkedBlockingQueue (无界): 慎用！易耗尽内存。
  • SynchronousQueue: 不存储任务，要求快速响应。

🛡️ 拒绝策略

  • AbortPolicy (默认): 抛异常，核心业务感知失败。
  • CallerRunsPolicy: 调用者执行，非核心业务防丢失。
  • DiscardPolicy: 直接丢弃，用于不重要数据。

🔮场景一：队列积压，响应变慢

  • 症状: 队列长度持续增长，但活跃线程数未达到最大值。
  • 诊断: 线程处理能力不足，或队列设置不当。
  • 药方: 适当调大 maximumPoolSize 和队列容量。

🔥场景二：CPU利用率过高

  • 症状: CPU利用率持续高于80%，系统整体变慢。
  • 诊断: 线程数过多，导致大量时间用于上下文切换。
  • 药方: 适当调小 maximumPoolSize。
