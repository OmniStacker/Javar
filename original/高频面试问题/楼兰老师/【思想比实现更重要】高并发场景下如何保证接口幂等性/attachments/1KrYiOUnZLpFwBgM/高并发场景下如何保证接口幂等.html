幂等性：锦上添花 vs. 生死存亡

新手的困境

查询 + 插入 (错误示范)

具体方案

最朴素的想法：先 `SELECT` 查一下数据是否存在，如果不存在，再执行 `INSERT` 操作。

优势

无。逻辑看似简单，但实则是高并发场景下的致命陷阱。

局限性

存在致命的并发安全问题，多个请求可能同时通过检查，导致数据重复插入。

悲观锁

具体方案

在查询时就利用数据库行锁，锁住数据，防止其他事务操作。例如：`SELECT ... FOR UPDATE`

优势

简单粗暴，能绝对保证数据安全，有效防止并发下的数据冲突。

局限性

性能杀手！将高效的并行处理强行变为低效的串行排队，在高并发场景下会造成大量请求阻塞。

乐观锁

具体方案

增加 `version` 字段，更新时验证版本号。`UPDATE ... SET version = version + 1 WHERE id = ? AND version = ?`

优势

性能极高，不产生实际的锁竞争，是一种非常优雅的无锁并发控制手段。

局限性

需额外修改表结构。主要防止更新操作的重复，对于防止插入操作的重复无能为力。

唯一索引

具体方案

利用数据库的唯一约束。给订单号、流水号等天然唯一的字段加上 `UNIQUE KEY`。

优势

最高效、最可靠的防重手段。由数据库层面保证唯一性，代码实现简单、性能极佳。

局限性

需要业务上有明确的唯一标识。在分库分表的架构下，全局唯一索引的实现会变得复杂。

防重表

具体方案

建立一张独立的防重表，仅包含唯一业务ID，并设置唯一索引。通过 `INSERT` 这张表来判断是否重复。

优势

将防重逻辑与业务逻辑解耦，不侵入主业务表，方案灵活，可复用性强。

局限性

增加了一次数据库 `INSERT` 操作，会带来额外的性能开销和数据一致性维护成本。

状态机

具体方案

利用业务状态的单向流转特性。`UPDATE ... SET status='PAID' WHERE id=? AND status='UNPAID'`

优势

与业务逻辑结合紧密，实现非常自然且优雅，代码可读性好，不易出错。

局限性

适用场景有限，仅适用于那些具有明确、单向状态流转的业务流程。

分布式锁

具体方案

利用 Redis 的 `SETNX` 命令。`SET lock:order:xxx '1' NX EX 60`，原子性地尝试获取一个全局唯一的锁。

优势

分布式环境下的标准解法，通用性强，是解决跨服务、跨节点幂等问题的核心利器。

局限性

引入了外部依赖 (如Redis)，增加了系统复杂度和潜在的故障点。锁的可靠性需要精细设计。

Token 令牌

具体方案

前端在进入页面时先获取一次性令牌，提交时携带。后端通过原子操作（如 Redis `DEL`）校验并销毁令牌。

优势

方案灵活，将防重前置到网关或代码层，能有效防止用户重复点击、网络重试等多种场景。

局限性

需要前后端配合改造，一次业务操作需要两次网络请求（获取、使用），增加了交互复杂性。
