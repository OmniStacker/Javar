并发陷阱：先删缓存，再更新DB

sequenceDiagram
  participant RA as Request A (Write)
  participant RB as Request B (Read)
  participant C as Cache
  participant DB as Database
  RA->>C: 1. Delete cache(key)
  Note right of C: Cache is empty
  RB->>C: 2. Read cache(key) - Miss
  RB->>DB: 3. Read DB (gets v1)
  Note right of DB: DB has old data v1
  RB->>C: 4. Write cache(key, v1)
  Note right of C: Cache now has old data v1
  RA->>DB: 5. Write DB (sets v2)
  Note right of DB: DB now has new data v2
  Note over RA,DB: ❌ Inconsistency!
Cache has v1, DB has v2

结论：导致缓存与数据库数据永久不一致，方案不可取！

4 / 9

并发风险：先更新DB，再删缓存

sequenceDiagram
  participant RA as Request A (Write)
  participant RB as Request B (Read)
  participant C as Cache
  participant DB as Database
  RA->>DB: 1. Write DB (sets v2)
  Note right of DB: DB has new data v2
  RB->>C: 2. Read cache(key) - Hit (gets v1)
  Note right of C: User gets old data v1 (briefly)
  RA->>C: 3. Delete cache(key)
  Note right of C: Cache is empty
  Note over RA,C: Next read will miss, fetch v2 from DB,
and write v2 to cache.
  Note over RA,C: ✅ System self-corrects.

结论：可能发生短暂不一致，但系统可自动修复。相对安全。

方案二：延迟双删 (Cache-Aside 变种)

1
更新缓存

不推荐！成本高，且有并发问题

↓
1
删除缓存
↓
2
更新数据库
↓
3
延时 500ms (估算业务读库+写缓存时间)
↓
4
再次删除缓存

优点:

大大降低不一致概率。

缺点:

延时难以精确评估，增加了写请求耗时。

方案三：消息队列（最终一致性）

👨‍💻
写请求
→
1. 更新数据库
2. 发送消息到 MQ
→
🚀
消息队列
(RabbitMQ/Kafka)
→
⚙️
消费者服务
→
3. 删除缓存

优点:

业务解耦，主流程性能高，可靠性强（支持重试）。

缺点:

架构变重，存在短暂的数据不一致。

7 / 9

终极方案：订阅 Binlog（异步解耦）

👨‍💻
写请求
→
1. 更新数据库
→
🗃️
MySQL
产生 Binlog
→
📡
订阅服务
(Canal/Maxwell)
→
2. 删除缓存

业务代码只需关心数据库，缓存同步完全分离！

优点:

完全解耦，对业务代码无侵入，可靠性极高。

缺点:

架构最重，需要引入和维护额外组件。
