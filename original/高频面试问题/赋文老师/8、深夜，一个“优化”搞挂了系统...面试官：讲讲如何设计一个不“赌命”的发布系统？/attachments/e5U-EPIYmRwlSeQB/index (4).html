不“赌命”的发布系统？

灰度发布 & A/B 测试核心架构

痛点：发布 = 赌命

  ↓
💻 上线“优化”代码
  ↓
💥 罕见BUG，服务雪崩
  ↓
🚨 P0 故障！
  ↓
😰 紧急回滚，一身冷汗
  • ❓ 灵魂拷问：如果只让 1% 的用户先用，是不是就能避免灾难？
  • 🎯 面试官真正想考察的，是你能否设计一个稳定、可控、可观测的发布系统。

核心思路：流量染色 & 全链路灰度

1. 流量染色 (Dyeing)

↓
在入口处，根据规则给请求打上特殊标记。
↓
Header: x-gray-version: v2

2. 全链路灰度 (Tracing)

↓
确保这个标记在整个微服务调用链中不丢失。
↓
A → B(v2) → C(v2)

第一层：流量染色 (入口层)

  • 📍 地点: API 网关 (e.g., Spring Cloud Gateway)
  • ⚙️ 动作:
    1. 获取用户画像 (UID, Location, Device...)
    2. 匹配动态灰度规则
    3. 生成灰度标记
  • 🏷️ 载体: 将标记放入...
    - HTTP Header
    - RPC Attachment
    - MQ Message Property 
  请求  → [ API 网关 ] → 染色后的请求
           ┌─────────┐
 User ────▶│  Rules  │
 (UID:123) │(北京,VIP)│
           └─────────┘
                 ↓
           [ 添加 Header ]
      x-gray-version: v2

第二层：全链路透传 (核心)

// 目标：灰度标记像接力棒一样传递

1. HTTP 调用 (Gateway 路由 & Feign 拦截器)
   Request → Gateway(加Header) → ServiceA → Feign(传Header) → ServiceB

2. RPC 调用 (Dubbo Filter)
   ServiceB → Consumer Filter(塞Attachment) → Provider Filter(取Attachment) → ServiceC

3. 异步调用 (RocketMQ AOP)
   ServiceC → AOP(加消息属性) → [ MQ ] → AOP(取消息属性) → ServiceD

第三层：A/B 测试 (决策)

  • 🤔 不是简单的流量路由，而是业务逻辑分流。
  • 🆚 灰度发布: 验证新版【稳不稳定】。
  • 📈 A/B 测试: 对比 A、B方案【哪个更好】。
  • 🔧 实现: 业务代码中，通过“特性开关”或“实验平台”来决策。
// 推荐服务 RecommendService
public List getRec(userId) {
  // 询问实验平台，我该走哪个分支？
  group = experimentClient.getGroup(userId);

  switch(group) {
    case "Plan-A": return newAlgorithmA();
    case "Plan-B": return newAlgorithmB();
    default:     return legacyAlgorithm();
  }
}

第四层：统一管控平台

🕹️ [ 灰度发布与A/B实验平台 ]
↓
📜
动态规则配置
📊
实时指标监控
⏪
一键发布/回滚

让发布过程安全、可控、可观测

总结：完美回答 = 3步 + 2个锦囊

1. 核心架构： 流量染色 → 全链路透传 (HTTP/RPC/MQ) → A/B测试 (特性开关) → 管控平台

2. 展现经验 (锦囊1 - 缓存)：
为了防止缓存污染，缓存 Key 必须带上灰度标记。 Key = "user:" + uid + ":v2"

3. 展现经验 (锦囊2 - 数据库)：
灰度期间，DB变更必须向前/向后兼容（只加字段，不删/改字段）。
