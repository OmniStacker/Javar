面试官：双十一1亿人下单，你的购物车怎么不崩？

高手都懂：这题考的不是CRUD，是架构思维

购物车的核心矛盾：“冰”与“火”

🔥

火焰: 极度写压力

零点前疯狂加购、改数量
写操作是读的数倍

🧊

冰山: 临时非核心

下单前随时被清空
无需昂贵的强一致性

面试官的3层恐惧

1. 存储雪崩：无脑MySQL，行锁打满，瞬间崩溃
2. 设计缺陷：读写竞争，数据覆盖，用户抓狂
3. 业务漏洞：登录丢数据，合并出Bug，客诉爆炸

破局第一步：选对主战场

❌ MySQL: 锁地狱

U1 ↘️ U2 → [ DB LOCK 🔒 ]
U3 ↗️ U4 → [ DB LOCK 🔒 ]

串行操作，性能瓶颈

✅ Redis: 并发天堂

U1 → [ Hash A ]
U2 → [ Hash B ]
U3 → [ Hash C ]

独立空间，无锁竞争

制胜武器：Redis Hash 结构

Key: cart:user_10086

{
  "prod_8801": "{'qty': 2}", // HSET (新增/覆盖)
  "prod_8802": "{'qty': 1}", // HINCRBY (原子增减)
  "prod_8803": "{'qty': 5}" // HDEL (删除)
}

O(1) 复杂度 | 原子操作 | 完美匹配

破局第二步：性能与一致性的权衡

❌ 同步写: 阻塞

⚡️

极致体验与最终一致
