问题：一个请求，为啥这么慢？🤔

用户下单，主流程就一个：创建订单 (50ms)

但还要同步做一堆“附加动作”：

  • 通知库存中心 (100ms)
  • 发短信通知 (200ms)
  • 增加用户积分 (80ms)
  • 记录操作日志 (20ms)

同步总耗时: 450ms = 用户感觉“卡顿” 😡

解法：异步化！把非核心操作丢出去！

方案一：线程池 (进程内异步)

用户线程

(创建订单)

→

应用内线程池

(执行发短信、加积分...)

优点 👍

  • 简单、快: 同一进程
  • 零延迟: 瞬时执行

硬伤 👎

  • 数据丢失: 宕机=白给
  • 强耦合: 代码全耦合
  • 无削峰: 流量大就爆

总结：一种“战术级”的性能优化手段。

方案二：消息队列 (分布式异步)

订单服务
(生产者)

→

MQ 中间件

消息持久化

→

下游服务
(消费者)

解决线程池三大硬伤！

1. 持久化 + ACK → 数据不丢失
挂了也能重试，保证任务执行。
2. 发布/订阅 → 系统解耦
生产者和消费者互不影响，自由增减。
3. 消息积压 → 削峰填谷
从容应对流量洪峰，保护下游系统。

总结：一种“战略级”的系统架构设计。

终极答案：如何选择？

“面试官您好，我会从这 4 个维度评估：”

1. 可靠性

允许丢失? → 线程池

绝不能丢? → 必须 MQ

2. 耦合度

应用内消费? → 线程池

跨服务消费? → 必须 MQ

3. 性能延迟

要毫秒级? → 线程池

可容忍秒级? → MQ

4. 流量削峰

流量平稳? → 线程池

有秒杀洪峰? → 必须 MQ

线程池是战术，MQ是战略。优先考虑可靠性与扩展性！
