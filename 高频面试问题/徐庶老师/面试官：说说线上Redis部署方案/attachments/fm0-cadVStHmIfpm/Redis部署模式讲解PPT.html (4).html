面试官：聊聊Redis部署模式？

从单机到集群，这5种生产级架构你必须懂！

1. 单实例模式 (Single Instance)

最简单、最基础的部署方式，一切开始的地方

Client
➔
Redis Server
(Single Process)

要点

  • 优点简单（部署、配置、维护）。
  • 缺点无高可用，服务器宕机则服务完全不可用。
  • 缺点内存大小受限于单个服务器。
  • 风险数据有丢失风险（RDB/AOF也无法完全避免）。

2. 主从 + 哨兵 (Master-Slave + Sentinel)

高可用性的基石，实现自动故障转移

Slave 1
Slave 2

要点

  • 优点通过数据备份和自动主从切换，保障高可用。
  • 优点读写分离，从节点可分担读请求，提升性能。
  • 缺点写操作仍然存在单点瓶颈。
  • 缺点无法解决海量数据存储问题。

3. 分片集群 + 一致性Hash

应对海量数据的水平扩展方案

Client
➔
0 ~ 2³²-1
在环上顺时针找到最近的节点进行路由
Redis-1
Redis-2
Redis-3
...

要点

  • 优点通过增加节点实现集群的线性扩展。
  • 优点一致性哈希算法在增删节点时，只影响少量数据。
  • 缺点基础模式下每个分片是单点，需要结合主从+哨兵保障分片高可用。
  • 缺点数据迁移和扩容相对复杂。

4. 分片集群 + 预分配 (Slots)

Codis核心思想，为平滑扩容设计

Client → hash(key) % 1024 = slot
↓
0-255
256-511
512-767
768-1023
↓
Shard 0
Shard 1
Shard 2
Shard 3

要点

  • 优点保留分片集群的可扩展优势。
  • 优点通过预分配槽位，数据迁移更平滑、可控。
  • 缺点数据迁移过程仍非常考验架构师功底。
  • 缺点需要中间件（如Codis Proxy）或定制客户端支持。

5. 官方 Redis Cluster

功能趋于完美的官方最终形态

Smart
Client
16384 Slots
M1 (0-5500)
M2 (5501-11000)
M3 (11001-16383)
S1 (from M1)
节点间通过Gossip协议通信

要点

  • 优点完全去中心化，多主多从。
  • 优点无需哨兵，通过Gossip协议探测健康并自动切换。
  • 优点官方SDK支持，客户端无感知路由和扩缩容。
  • 缺点配置和运维相对复杂。
  • 缺点复杂的多键操作（如MSET）可能受限。

总结：真的有银弹吗？

No Silver Bullet

  • 没有一种方案是完美的银弹。
  • 每种模式都有其适用场景和局限性。
  • 理解业务需求，权衡性能、扩展性和运维成本，才能做出最佳的选择。
