1. 单实例模式 (Single Instance)

最简单、最基础的部署方式，一切开始的地方

要点

  • 优点简单（部署、配置、维护）。
  • 缺点无高可用，服务器宕机则服务完全不可用。
  • 缺点内存大小受限于单个服务器。
  • 风险数据有丢失风险（RDB/AOF也无法完全避免）。

故障转移: Gossip协议 & 选举

M1 (Fail)
S1 (Slave of M1)
M2
M3
1. M2通过Gossip发现M1疑似下线 (PFAIL).
2. M2向其他节点广播此信息，收集到足够确认后将M1标记为下线 (FAIL).
3. S1发起选举，获得多数Master投票后，晋升为新Master.

核心机制

  • 去中心化路由

    客户端可向任意节点发请求。若目标Slot不在此节点，则收到`MOVED`重定向响应，告知正确节点地址。客户端会缓存该映射，实现自动路由。

  • Gossip协议

    节点间持续交换PING/PONG包，携带各自状态和对其他节点状态的认知。这种“闲聊”机制使集群状态信息快速传播，实现最终一致。

  • 故障发现与转移

    节点通过Gossip发现某节点失联(PFAIL)，当多数主节点都认为其失联时，状态变为FAIL。其从节点将发起选举，获得多数选票后晋升为新的主节点，接管Slot。

总结：如何选择？

没有最好的架构，只有最适合的场景

架构模式 高可用 可扩展性 适用场景
单实例 无 差 开发测试、小型应用

Redis Cluster 高 高 海量数据、高并发、官方推荐
