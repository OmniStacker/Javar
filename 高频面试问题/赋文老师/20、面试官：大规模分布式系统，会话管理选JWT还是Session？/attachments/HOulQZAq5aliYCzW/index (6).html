冲突2：JWT无状态很香，为什么大厂还在用Session？
JWT核心：加密Token存客户端，服务端无状态验证
// JWT工具类（核心逻辑） public class Jwt工具 { 密钥=32位密钥; 过期=2小时; // 生成Token 生成Token(用户) { 明文={用户ID:用户.ID, 过期:当前+过期}; 签名=HMAC-SHA256(明文,密钥); 返回 Base64(明文)+"."+Base64(签名); } // 验证Token 验证Token(Token) { [明文B64,签名B64] = Token.split("."); 明文=解密B64(明文B64); if(明文.过期 < 当前) 抛 过期异常; 验签=HMAC-SHA256(明文,密钥); if(Base64(验签)!=签名B64) 抛 签名异常; 返回 明文.用户ID; } } // 核心流程：登录→生成→携带→验证→放行

JWT结构：Header(算法) + Payload(数据) + Signature(签名)
JWT的4个致命坑点（大厂慎选的原因）
❌ 无法主动失效
登出/冻结后，未过期Token仍可用
⚠️ Payload不加密
仅Base64编码，不可存敏感信息
🔑 密钥泄露风险
密钥泄露=伪造Token；更换=旧Token失效
⏳ 过期时间固定
生成后无法修改，需重新登录

// 黑名单工具（核心逻辑） public class Jwt黑名单 { 注入 Redis模板; // 登出/冻结时加入黑名单 加入黑名单(Token) { 剩余时间=Jwt工具.获取剩余过期(Token); Redis.set("jwt:black:"+Token, "1", 剩余时间, 秒); } // 验证时查黑名单 是否失效(Token) { return Redis.exists("jwt:black:"+Token); } } // 完整验证流程 public 验证结果 验证流程(Token) { if(黑名单.是否失效(Token)) return 401; try { Jwt工具.验证Token(Token); return 200; } catch { return 401; } }
面试标准应答
1. 选型核心看场景：分布式会话是「一致性、安全性、扩展性」的平衡；

2. 安全优先选 Session+Redis：支持主动失效，适合支付、后台；

3. 高并发跨域选 JWT：无状态、性能高，适合APP、API网关；

4. 混合场景选 JWT+黑名单：兼顾无状态和主动失效。
