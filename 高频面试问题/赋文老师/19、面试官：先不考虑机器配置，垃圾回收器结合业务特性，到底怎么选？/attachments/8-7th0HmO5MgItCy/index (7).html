抛开机器配置，只看业务特性！

“结合你的业务，到底怎么选垃圾回收器？”

高级工程师 vs 初级工程师的核心差距：业务→技术的翻译能力

核心考核意图：不是“参数背诵机”，而是“业务决策者”

核心逻辑链：

业务特性
↓

↓
GC选型

3大GC的核心设计目标：

Parallel GC（并行GC）：

追求高吞吐量 → 单位时间处理最多任务，允许短停顿（200ms+）

G1 GC（垃圾优先）：

追求低延迟 → 响应时间稳定，控制停顿在50ms内

ZGC（新一代GC）：

追求高并发低停顿 → 毫秒级停顿（<10ms），支撑高QPS

场景→诉求→选型 对应表（面试直接背）

1

批处理/数据同步

每天凌晨跑数、报表生成、数据迁移

诉求：高吞吐

选型：Parallel GC

停顿容忍：200ms+

2

支付/实时接口

电商支付、金融交易、实时查询接口

诉求：低延迟

选型：G1 GC

停顿要求：<50ms

3

秒杀/高并发API

电商秒杀、直播互动、高频下单接口

诉求：高并发低停顿

选型：ZGC

停顿要求：<10ms

场景1

高吞吐优先：批处理/数据同步/报表生成

业务核心信息

  • • 数据量：1000万+条
  • • 对象特征：批量创建、批量回收（短生命周期）
  • • 核心诉求：总处理时间越短越好
  • • 痛点：用G1会因增量回收耗CPU，降低吞吐

核心代码（简化版）

// 批量创建1000万短生命周期对象
List dataList = new ArrayList<>(10_000_000);
for (int i = 0; i < 10_000_000; i++) {
  dataList.add(new UserData("用户" + i, 18+i%30, "余额" + (i%10000)));
}
// 批量处理：数据转换、入库
processData(dataList);
// 释放引用，让GC批量回收
dataList.clear();

Parallel GC 工作原理

新生代：Parallel Scavenge

多线程并行标记+清理，无并发开销

↓

老年代：Parallel Old

多线程并行Full GC，最大化CPU利用率

核心优势

1. 利用多CPU核心，回收效率最高

2. 无并发回收的CPU消耗，总吞吐最优

3. 配置简单，无需复杂调优

场景2

低延迟优先：支付/金融交易/实时接口

G1 GC 工作原理

1. 堆内存划分为多个Region（2MB-32MB）

新生代、老年代不再物理隔离

2. Young GC：回收新生代Region

快速回收短生命周期对象

3. Mixed GC：增量回收老年代Region

优先回收垃圾多的Region，控制停顿时间

核心优势

1. 停顿时间可预测（默认<200ms，可调至<50ms）

2. 平衡吞吐和延迟，适合高并发接口

业务核心信息

  • • QPS：1000+ 每秒
  • • 对象特征：每个请求创建多个临时对象（校验、订单、日志）
  • • 核心诉求：响应时间稳定（<50ms）
  • • 痛点：用Parallel会触发长Full GC，导致接口超时

核心代码（简化版）

// 支付接口：每个请求创建临时对象
@PostMapping("/api/pay")
public PayResponse doPayment(@RequestBody PayRequest req) {
  // 1. 参数校验（临时对象）
  ValidateResult validate = validateRequest(req);
  if (!validate.isSuccess()) return 参数错误;
  // 2. 创建订单/支付记录（临时对象）
  PayResult result = processPayment(req);
  // 3. 异步日志（临时对象）
  CompletableFuture.runAsync(() -> logPayment(result));
  return new PayResponse(result.isSuccess());
}
场景3

高并发低停顿：秒杀/直播互动/高频API

业务核心信息

  • • 峰值QPS：1万+ 每秒
  • • 对象特征：海量短生命周期对象（请求、临时订单、缓存Key）
  • • 核心诉求：极致低停顿（<10ms）
  • • 痛点：G1的Mixed GC仍有50ms+停顿，导致抢购异常

核心代码（简化版）

// 秒杀接口：海量短生命周期对象
@PostMapping("/api/seckill")
public SecKillResponse seckill(@RequestBody SecKillReq req) {
  // 临时缓存Key
  String cacheKey = "seckill:user:" + req.getUserId();
  if (boughtCache.containsKey(cacheKey)) return 重复抢购;
  // 高并发扣减库存
  int remain = stock.decrementAndGet();
  if (remain < 0) return 库存售罄;
  // 创建临时订单对象
  SecKillOrder order = new SecKillOrder(UUID.randomUUID().toString());
  // 异步保存（对象后续回收）
  asyncSaveOrder(order);
  return 抢购成功;
}

ZGC 工作原理（核心：并发回收）

初始标记（<1ms）

仅标记根对象

并发标记（不暂停应用）

遍历所有可达对象

重新标记（<1ms）

修正并发标记遗漏

并发清理+重定位（不暂停）

回收垃圾+移动存活对象

核心优势

1. 停顿时间稳定在1ms左右，<10ms

2. 支持TB级堆内存，高并发下无压力

3. 基于着色指针+读屏障，无需STW长时间停顿

面试直接套用：GC选型3步决策法

1

抓核心诉求（最关键）

→ 业务是要高吞吐、低延迟还是高并发低停顿？

2

辅助判断对象生命周期

→ 短对象多：G1/ZGC更高效 | 长对象多：Parallel更省CPU

3

匹配GC选型

→ 高吞吐→Parallel | 低延迟→G1 | 高并发低停顿→ZGC

记住：面试官要的不是“选对”，而是“说清为什么这么选”
