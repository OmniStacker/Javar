面试官真正想考什么？
基础认知
是否懂JWT有效性依赖「签名+过期时间」，与用户状态无关
场景思维
能否根据并发量、架构（单体/分布式）选方案
工程能力
是否考虑性能、安全性（如黑名单查询效率）
关键：不是背方案，是「场景匹配能力」！
冲突本质：为什么注销后仍生效？
JWT有效性判断逻辑
签名正确？
→
未过期？
→
默认有效
核心结论：
JWT只认「技术层面」（签名+过期），
不认「业务层面」（注销/封号）！ 
// JWT核心特性（伪代码）
JWT验证(token) {
  return 签名通过 && 未过期; // 不关心业务状态
}
方案1：黑名单机制（中小规模首选）
适用场景
QPS<1万、单体/小型分布式、需立即失效（金融/隐私接口）
核心逻辑
用户注销
→
Token存Redis黑名单
→
接口校验黑名单
→
拒绝访问
// 极简伪代码
注销(token) {
  Redis.set("黑名单:"+token, 1, 过期时间);
}

验证(token) {
  return JWT验证(token) && !Redis.exists("黑名单:"+token);
}
核心优势：实现简单、成本低，支持立即失效
方案2：双Token（高并发首选）
适用场景
QPS>1万、分布式系统、允许5分钟短窗口有效
Access Token（访问令牌）
• 短期有效：5分钟
• 用途：接口请求
• 特点：有效期短，风险低
Refresh Token（刷新令牌）
• 长期有效：7天
• 用途：刷新Access Token
• 特点：仅存Redis，安全性高
核心流程
登录：服务器返回双Token，Refresh Token存入Redis
接口请求：用Access Token访问，过期则发起刷新
注销：删除Redis中Refresh Token，旧Token过期后无法续期
// 极简伪代码
刷新Token(刷新Token, 用户ID) {
  if (Redis.get("刷新:"+用户ID) == 刷新Token) {
    return 生成新访问Token;
  }
  return 失效;
}

注销(用户ID) {
  Redis.delete("刷新:"+用户ID); // 无法再刷新
}
核心优势：性能优、无黑名单查询开销，扩展性强
方案3：令牌撤销中心（大规模微服务）
适用场景
• 大规模微服务架构
• 核心需求：统一管理Token注销、封号、批量失效
• 并发量：QPS>5万、多服务协同场景
架构逻辑
业务服务A/B/C
→
Feign调用
→
撤销中心
→
Redis集群
核心伪代码
// 撤销中心接口
撤销Token(token) {
  Redis.set("已撤销:"+token, 1, 过期时间);
}

// 微服务验证
验证Token(token) {
  return JWT验证(token) && !撤销中心.是否已撤销(token);
}

// 批量撤销（封号）
批量撤销(用户IDs) {
  用户IDs.forEach(ID => Redis.set("用户禁用:"+ID, 1));
}
核心优势：集中管理、支持跨服务批量操作、适配微服务架构
方案4：自定义声明（批量失效场景）
适用场景
• 批量失效某类用户Token（如违规用户、离职员工）
• 核心需求：一键禁用、快速失效、操作简单
• 场景举例：平台封号、部门权限变更
核心逻辑
生成Token：加入version自定义声明（如version=1）
存储版本：服务器Redis存储用户最新version
触发失效：注销/封号时，更新version（如1→2）
接口校验：Token version ≠ 服务器version → 拒绝访问
核心伪代码
// 生成Token
生成Token(用户ID) {
  版本 = Redis.get("版本:"+用户ID) || 1;
  return JWT签名({用户ID, 版本});
}

// 验证Token
验证Token(token) {
  载荷 = JWT解析(token);
  当前版本 = Redis.get("版本:"+载荷.用户ID);
  return 载荷.版本 == 当前版本 && JWT未过期;
}

// 批量失效
批量失效(用户ID) {
  Redis.incr("版本:"+用户ID); // 版本+1，旧Token失效
}
核心优势：操作简单、无黑名单存储、支持批量快速失效
