## <font style="color:rgba(0, 0, 0, 0.96);">【问题拆解 - 第2页】</font>
<font style="color:rgba(0, 0, 0, 0.96);">好，我们先来看看API网关到底是个什么样的场景。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">首先，流量洪峰</font>**<font style="color:rgba(0, 0, 0, 0.96);">！作为所有外部请求的入口，QPS可能达到数十万级别，这压力可想而知。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">其次，对象朝生夕死</font>**<font style="color:rgba(0, 0, 0, 0.96);">！每个HTTP请求进来，网关会创建一堆临时对象：Request、Response、Token、Context……处理完马上就变成垃圾。</font>

<font style="color:rgba(0, 0, 0, 0.96);">你看这张图，典型的"用完即扔"模式，对吧？</font>

**<font style="color:rgba(0, 0, 0, 0.96);">所以核心矛盾在哪？</font>**<font style="color:rgba(0, 0, 0, 0.96);">频繁的Young GC会产生STW停顿，也就是Stop-The-World，整个应用暂停！如果这个停顿时间不可控，TP99直接爆表！</font>

<font style="color:rgba(0, 0, 0, 0.96);">这就是第一个致命冲突点。</font>

## <font style="color:rgba(0, 0, 0, 0.96);">【深挖问题 - 第3页】</font>
<font style="color:rgba(0, 0, 0, 0.96);">很多同学第一反应："JDK 11之后默认是G1，那就用G1呗！"</font>

**<font style="color:rgba(0, 0, 0, 0.96);">但问题来了，G1真的靠谱吗？</font>**

<font style="color:rgba(0, 0, 0, 0.96);">G1有个核心参数叫MaxGCPauseMillis，你可以告诉它："每次停顿别超过20毫秒。"</font>

<font style="color:rgba(0, 0, 0, 0.96);">听起来很美好对吧？但现实是残酷的！</font>

**<font style="color:rgba(0, 0, 0, 0.96);">你看这个真实的GC表现：</font>**

+ <font style="color:rgba(0, 0, 0, 0.96);">正常情况下，Young GC确实只要20毫秒</font>
+ <font style="color:rgba(0, 0, 0, 0.96);">但流量一突增，Mixed GC就飙到150毫秒</font>
+ <font style="color:rgba(0, 0, 0, 0.96);">更可怕的是，老年代一旦填满，Full GC直接2.3秒！</font>

**<font style="color:rgba(0, 0, 0, 0.96);">为什么会这样？</font>**<font style="color:rgba(0, 0, 0, 0.96);">因为G1的"可预测"只是"尽力而为"，不是一定能做到！</font>

<font style="color:rgba(0, 0, 0, 0.96);">在高并发场景下，对象晋升速度超过老年代回收速度，G1就会失控，从而触发灾难性的Full GC！</font>

<font style="color:rgba(0, 0, 0, 0.96);">这就是第二个冲突点：</font>**<font style="color:rgba(0, 0, 0, 0.96);">G1在极端场景下会击穿你的TP99目标！</font>**

## <font style="color:rgba(0, 0, 0, 0.96);">【解决方案1 - 第4页】</font>
<font style="color:rgba(0, 0, 0, 0.96);">那怎么办？我给你两套方案。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">第一套：驯服G1，让它不要失控！</font>**

<font style="color:rgba(0, 0, 0, 0.96);">核心策略就一句话：</font>**<font style="color:rgba(0, 0, 0, 0.96);">让对象尽可能死在年轻代！</font>**

<font style="color:rgba(0, 0, 0, 0.96);">具体怎么做？三步走：</font>

**<font style="color:rgba(0, 0, 0, 0.96);">第一，加大堆内存！</font>**<font style="color:rgba(0, 0, 0, 0.96);">不要吝啬，给8个G甚至10个G。更大的堆意味着更低的GC频率，能缓冲流量波动。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">第二，调整新生代比例！</font>**<font style="color:rgba(0, 0, 0, 0.96);">用G1MaxNewSizePercent参数，给年轻对象更多空间，减少晋升到老年代的机会。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">第三，调整Region大小！</font>**<font style="color:rgba(0, 0, 0, 0.96);">防止大对象直接进入老年代，把Region从2MB调到4MB。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">还有最关键的第四点：持续监控GC日志！</font>**<font style="color:rgba(0, 0, 0, 0.96);">这是调优的出发点！你必须知道对象晋升速率、Mixed GC频率，才能针对性优化。</font>

## <font style="color:rgba(0, 0, 0, 0.96);">【解决方案2 - 第5页】</font>
**<font style="color:rgba(0, 0, 0, 0.96);">第二套方案：拥抱ZGC，终极核武器！</font>**

<font style="color:rgba(0, 0, 0, 0.96);">如果你的团队技术实力强、服务器资源充足，能用JDK 15以上，那ZGC就是你的神！</font>

**<font style="color:rgba(0, 0, 0, 0.96);">ZGC的杀手级特性：STW停顿时间小于1毫秒，而且不随堆大小增长！</font>**

<font style="color:rgba(0, 0, 0, 0.96);">无论你的堆是4个G还是400个G，ZGC的停顿时间都稳如磐石！</font>

<font style="color:rgba(0, 0, 0, 0.96);">你看这个对比：</font>

+ <font style="color:rgba(0, 0, 0, 0.96);">G1的停顿是15到150毫秒，TP99不稳定</font>
+ <font style="color:rgba(0, 0, 0, 0.96);">ZGC的停顿始终小于1毫秒，TP99稳如狗！</font>

<font style="color:rgba(0, 0, 0, 0.96);">**但ZGC也有代价：**更高的CPU和内存开销。所以你要权衡。</font>

**<font style="color:rgba(0, 0, 0, 0.96);">我的建议是：</font>**

+ <font style="color:rgba(0, 0, 0, 0.96);">如果是核心业务，对延迟零容忍，果断上ZGC</font>
+ <font style="color:rgba(0, 0, 0, 0.96);">如果还在发展阶段，先用好G1，积累经验后再平滑迁移</font>
