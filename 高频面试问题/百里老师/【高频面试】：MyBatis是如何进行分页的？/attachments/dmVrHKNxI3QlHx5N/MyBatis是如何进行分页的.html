超·高频面试：MyBatis是如何进行分页的？

从“暴力拉取”到“精准查询”的性能进化之路

MyBatis

核心问题：如何高效地从海量数据中只取一页？

逻辑分页

一次性全量加载，内存中分页，
数据量大时 100% OOM

物理分页

利用数据库原生分页查询，
性能卓越，生产必备

分页的核心思想：逻辑 vs 物理

一个天上，一个地下。

逻辑分页 (内存分页)

返回【全部】1,000,000条数据

应用内存

筛选第1页的10条

物理分页 (SQL分页)

`... LIMIT 0, 10`

发送分页SQL

数据库

仅返回【10条】数据

方式一：XML中的“硬核手写”

最直接的方式：在Mapper.xml中手动拼接物理分页SQL。

<select id="selectUsers" resultType="User">
  SELECT * FROM user
  LIMIT #{offset}, #{limit}
</select>

优点

  • 简单直观：所见即所得，易于理解。
  • 无依赖：无需任何额外配置。

缺点

  • 数据库耦合：SQL与特定数据库强绑定。
  • 代码重复：每个分页查询都需重复编写。

方式二：RowBounds的“内存陷阱”

看似优雅的背后，是逻辑分页的本质，是性能的噩梦。

mapper.selectAll(new RowBounds(0, 10));

开发者以为：只查10条数据

MyBatis实际执行：

SELECT * FROM user;

背后真相：查询了全部数据！

应用内存 OOM!

BOOM!

在内存中对百万数据进行截取，导致崩溃

方式三：Interceptor的“偷天换日”

通过拦截器在SQL执行前动态改写，实现真正的物理分页。

1. 原始调用

SELECT * FROM user

2. Interceptor 魔法

动态拼接SQL

`原始SQL` + `LIMIT ?, ?`

3. 最终执行的SQL

SELECT * FROM user LIMIT 0, 10

优点：性能好，逻辑统一。缺点：手写复杂，门槛高。

方式四：分页插件的“一键化”革命

将复杂的拦截器逻辑封装为黑盒，开发者只需享受成果。

开发者

PageHelper.startPage(1, 10);

只需一行代码，开启分页

PageHelper 插件

  • 基于ThreadLocal传递参数
  • 内置强大Interceptor
  • 自动拼接物理分页SQL
  • 自动执行Count查询
  • 自动封装PageInfo结果

收获成果

PageInfo<User>

  • .getList() // 当前页数据
  • .getTotal() // 总记录数
  • .getPages() // 总页数
  • ...

得到包含一切分页信息的对象
