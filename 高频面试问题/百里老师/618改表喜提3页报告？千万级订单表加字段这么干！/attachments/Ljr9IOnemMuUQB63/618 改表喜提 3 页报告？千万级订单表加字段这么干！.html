方案三：业务扩展新表

从应用架构层面解耦，避免直接修改。

应用层

通过代码逻辑 `JOIN` 两张表

`orders` (原表)

id, amount...

+

`order_extension` (新表)

order_id, new_field...

优点：完全解耦

不修改核心表，风险低。

缺点：查询复杂化

引入JOIN，可能影响性能，增加技术债。

上上策：预留JSON扩展字段

拥抱变化，预见未来。用一个字段的“不变”，应对万变的业务需求。

架构之基石

一次定义，长期稳定

// orders 表结构

id: BIGINT,

amount: DECIMAL,

user_id: BIGINT,

ext_attributes: JSON

数据之弹性

随需而变，无需变更

// 之前: 只有来源字段

{ "source": "web" }

新增“是否来自直播”需求

// 之后: 直接增加新Key

{ "source": "web", "is_live": true }

无需 `ALTER TABLE`，业务迭代如丝般顺滑。
