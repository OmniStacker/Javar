## 一、什么是云计算：定义与关键特性

本节给出云计算的权威定义和它必须具备的特征，先建立整体印象，再进入后面的服务模型、部署模型等细节。判断一个"云"到底算不算云，依据就是这些特征。

### 定义

美国国家标准与技术研究院（NIST，National Institute of Standards and Technology）在 SP 800-145（2011 年）中给出的定义是：云计算是一种模型，它可以实现对可配置计算资源池（网络、服务器、存储、应用和服务等）的泛在、便捷、按需的网络访问，这些资源能以最少的管理工作或服务提供商交互被快速供应和释放。该模型由五个必要特征、三种服务模型和四种部署模型组成。

对 Java 开发者更直观的理解是：以前上线一个系统要自己买服务器、装系统、拉网线；现在这些资源由云厂商以控制台和接口的形式提供，用多少申请多少，用完释放。可以把云计算理解成"用电"：不必自己建发电厂，插上插座就能取电，按用电量付费。

### 五个必要特征

NIST 把云计算的必要特征归纳为五条，缺一条严格来说就不算"云"：

| 特征 | 含义 | 对开发者的体现 |
| --- | --- | --- |
| 按需自助服务（On-demand self-service） | 用户可自行申请计算、存储等资源，无需人工审批 | 控制台或接口一键开出一台服务器 |
| 广泛网络访问（Broad network access） | 资源通过网络、以标准方式访问，终端不限 | 笔记本、手机、服务器都能访问同一服务 |
| 资源池化（Resource pooling） | 厂商把资源集中成池，按多租户方式动态分配 | 你通常不需要知道自己的虚拟机落在哪台物理机上 |
| 快速弹性（Rapid elasticity） | 容量可快速伸缩，对用户而言近似"按需无限" | 大促前扩容、活动结束缩容 |
| 可度量服务（Measured service） | 使用量可计量、可监控、可按量计费 | 账单能按实例时长、流量、调用次数拆分 |

### 实践中常被提到的其他特性

原始资料还列了若干"特性"（虚拟化、动态可扩展、按需部署、高可靠性、通用性、按需服务、成本低）。这些说法在工程实践中很常见，但它们不是 NIST 定义里的必要特征，措辞也需要收一收：

- **虚拟化与动态可扩展**：属于实现手段而非特征本身，见第四节。规模能否动态伸缩，取决于厂商的配额、库存与你的架构设计。
- **按需部署**：用户可按需部署和运行应用，不必先采购硬件、先买软件许可。这一条成立，属于按需自助服务的延伸。
- **高可靠性**：云厂商通常通过多可用区部署、数据多副本、故障自动迁移等手段提升可用性，但最终能达到多少取决于所选服务等级与架构设计，不能一概而论。
- **通用性**：同一资源池可以承载不同类型的应用，这一点成立；但不同工作负载对实例规格、网络和存储的要求差异很大，实际选型仍要具体分析。
- **成本更低**：规模化共享通常能降低单位资源成本，但总成本取决于使用方式与计费模型；资源长期闲置时，云上成本完全可能高于自建机房。原文"极其廉价"属于绝对化表述，已按上述方式修正。

## 二、服务模型：IaaS、PaaS、SaaS

本节讲云服务按"厂商帮你管到哪一层"划分的三种模型。理解这条分层线，既能判断一个云产品属于哪一类，也能判断出了问题该由谁负责。

### 用一个比喻理解三者

把"运行一个应用"想象成"住"：IaaS 相当于租毛坯房，水电到户，墙和地自己装修；PaaS 相当于租精装公寓，水电家具齐全，你只管把自己的东西搬进去；SaaS 相当于住酒店，拎包入住，连床单都不用自己换。

### IaaS（Infrastructure as a Service，基础设施即服务）

IaaS 提供最基础的计算资源，包括虚拟化的硬件、存储和网络。用户可以自由配置和管理操作系统、应用程序与中间件。

- **控制**：用户对操作系统、存储、应用程序、选定的网络组件拥有最大控制权。
- **管理责任**：用户负责操作系统的安装与管理、安全配置、应用部署。
- **灵活性**：自定义能力最强，适合需要对基础设施做精细控制的场景。
- **常见产品**：AWS EC2、Azure 虚拟机、Google Compute Engine，以及各厂商的云服务器产品。

### PaaS（Platform as a Service，平台即服务）

PaaS 提供一整套应用开发与部署环境，包括操作系统、编程语言执行环境、数据库和 Web 服务器等。用户把自己的代码或制品交上去，平台负责运行。

- **控制**：用户主要控制应用程序和数据库，底层操作系统与基础设施由厂商管理。
- **管理责任**：不需要管理底层基础设施和操作系统，管理负担明显减轻。
- **效率**：简化开发与部署过程，开发者可以专注业务逻辑而不是基础设施。
- **常见产品**：Google App Engine、Azure App Service、AWS Elastic Beanstalk 等。

### SaaS（Software as a Service，软件即服务）

SaaS 提供完整的软件解决方案，用户通过网络访问软件，通常按订阅方式付费。

- **控制**：用户通常只负责软件的配置和使用，管理与维护全部由厂商负责。
- **管理责任**：更新、维护、安全等由厂商承担，用户不接触底层系统。
- **使用便捷**：无需安装和配置即可使用，适合希望快速落地解决方案的场景。
- **常见产品**：Google Workspace、Microsoft 365、Salesforce 等。

### 三者对比

| 对比项 | IaaS | PaaS | SaaS |
| --- | --- | --- | --- |
| 用户管理范围 | 操作系统及以上 | 应用与数据 | 仅配置和使用 |
| 厂商管理范围 | 虚拟化、硬件、机房 | 操作系统、运行时、中间件 | 全部，含应用本身 |
| 控制粒度 | 最大 | 中等 | 最小 |
| 管理复杂度 | 最高 | 中等 | 最低 |
| 典型场景 | 需要自定义运行环境、迁移遗留系统 | 专注业务开发、快速上线 | 办公协同、CRM 等标准软件 |
| 上手速度 | 慢 | 较快 | 最快 |

### 怎么选

选择的核心是平衡"控制力"与"管理成本"：需要自己掌控内核参数、中间件版本、特殊网络配置时选 IaaS；只想写业务代码、不愿维护服务器时选 PaaS；需求本身就是标准软件能力时选 SaaS。Java 应用常见的两种落法是：把 Spring Boot 打成可执行 jar 交给 PaaS 运行，或把应用做成容器镜像跑在 IaaS 的虚拟机上。

## 三、部署模型：公有云、私有云与混合云

本节讲"这套云给谁用"的问题。NIST 定义的四种部署模型是私有云、社区云、公有云和混合云；日常讨论最多的是公有云、私有云和混合云。

### 公有云

由第三方厂商建设并运营，向公众开放，任何个人或组织都可以按需购买使用。硬件、软件和日常运维全部由厂商负责，用户只需把自己的应用部署上去。

可以类比为公共健身房：器械齐全、随到随用，但你无法决定器械的品牌，也要和其他人共享场地。

### 私有云

为单一组织构建和使用的云环境，资源不与其他组织共享。它能提供对数据、安全性和服务质量最强的控制力，代价是硬件、软件和日常维护都要自己（或委托第三方）负责。

### 混合云

公有云与私有云的结合：把核心数据、强合规要求的系统放在私有云，把弹性需求大、波动明显的业务放在公有云，两者之间打通网络与身份体系。由于安全和控制方面的考虑，并非所有企业信息都适合放在公有云上，因此混合云在实践中相当常见。

### 社区云（补充）

由若干具有共同诉求（如同一行业、同一合规要求）的组织共同建设和使用，介于公有云与私有云之间。它属于 NIST 定义的四种部署模型之一，日常讨论中出现频率较低。

### 对比

| 对比项 | 公有云 | 私有云 | 混合云 |
| --- | --- | --- | --- |
| 资源归属 | 厂商 | 组织自己 | 两者兼有 |
| 开放程度 | 对公众开放 | 内部专用 | 部分开放 |
| 初始投入 | 低，按量付费 | 高，需自建机房 | 中等 |
| 可控性 | 受厂商产品能力约束 | 最高 | 核心系统可控 |
| 运维责任 | 厂商 | 自己或托管方 | 分担 |
| 典型场景 | 互联网业务、弹性需求大 | 金融核心、强合规数据 | 核心自持 + 弹性外溢 |

三种模式的区别可以概括为开放性、私有性和混合程度的不同，选择时主要看合规要求、数据敏感度与成本结构。

## 四、虚拟化：云计算的底层技术

本节讲云计算最底层的一环：一台物理机如何变成多台"看起来彼此独立"的机器。后面要讲的热迁移、弹性伸缩、多租户，都建立在虚拟化之上。

### 是什么

云端的虚拟化技术把物理硬件资源抽象成多个逻辑资源，使多个操作系统和应用程序可以共享同一台物理计算机。负责切分和调度这些资源的软件叫 Hypervisor（虚拟机监控器，也称 VMM，Virtual Machine Monitor），它创建的每个运行单元就是虚拟机（VM，Virtual Machine），每台虚拟机都可以运行各自的操作系统。

一个生活化的比喻：把一整块蛋糕切成多份，每份单独装盘、单独打包，看起来就像好几块独立的蛋糕，但原料来自同一块。

### 为什么需要

- **提升资源利用率**：物理服务器的 CPU、内存常年处于低负载，虚拟化后可以让多个业务共享同一台机器。
- **隔离故障**：一台虚拟机崩溃或被攻击，通常不会波及其他虚拟机。
- **便于交付**：创建、克隆、删除虚拟机只需分钟级操作，不必等采购和上架。
- **降低成本**：减少硬件采购、机房空间和电力消耗。

### Hypervisor 的两种类型

| 类型 | 运行位置 | 特点 | 常见实现 |
| --- | --- | --- | --- |
| 类型 1（裸金属型，bare-metal） | 直接运行在物理硬件上，取代宿主操作系统 | 直接访问硬件，效率高、攻击面小；通常需要独立的管理端 | KVM、Microsoft Hyper-V、VMware ESXi 等常被归入此类 |
| 类型 2（宿主型，hosted） | 作为普通应用运行在宿主操作系统之上 | 安装方便，适合个人桌面；需经宿主系统转发资源，多一层开销 | VirtualBox、VMware Workstation 等常被归入此类 |

云厂商的数据中心基本使用类型 1，因为它的资源开销和性能损失更小。

### 一次资源请求的处理流程

1. Hypervisor 在物理计算机上创建一个或多个虚拟机。
2. 每台虚拟机拥有自己的操作系统和应用程序，同时共享物理机的 CPU、内存和存储。
3. 虚拟机需要资源时，通过虚拟化层向物理机发出请求。
4. 虚拟化层把这些请求映射到物理机的实际资源上。
5. 虚拟机之间可以通过网络通信，从而组成一个虚拟的分布式系统。

### 虚拟化与容器（补充对比）

容器是另一种资源隔离方式，常与虚拟机一起出现。二者的关键差别在于是否各自携带操作系统内核：

| 对比项 | 虚拟机 | 容器 |
| --- | --- | --- |
| 操作系统 | 运行完整操作系统，包含自己的内核 | 共享宿主操作系统的内核，只包含应用和必要的用户态组件 |
| 隔离强度 | 与宿主及其他虚拟机完全隔离，安全边界更强 | 轻量隔离，安全边界弱于虚拟机；需要更强隔离时可借助轻量虚拟机方案 |
| 资源开销 | 较大，需为每台虚拟机分配独立内核与系统进程 | 较小，启动更快、密度更高 |
| 兼容性 | 可在其中运行几乎任意操作系统 | 通常需与宿主操作系统版本一致 |
| 典型场景 | 需要强隔离的多租户环境、遗留系统 | 微服务、快速扩缩容、持续交付 |

### 在云计算中的作用

虚拟化是构建云基础架构的关键技术之一：它让一个物理平台虚拟出多个虚拟平台，每个都可以作为独立节点加入云端的分布式系统，从而使云具备灵活扩展能力。同时，虚拟机可以整体迁移和备份，配合快照与多副本，为云端服务提供可靠性与数据保护能力；集中管理多个虚拟机也简化了运维工作。

## 五、虚拟机迁移：冷迁移与热迁移

本节讲运维中最常见的两个动作：把一台虚拟机从一台宿主机挪到另一台宿主机。迁移能力直接决定了硬件维护、机房搬迁、容量调整时业务是否要中断。

### 冷迁移

冷迁移指把虚拟机从一台主机迁移到另一台主机，迁移过程中虚拟机需要关机。因此它会带来业务中断，适用于可以安排停机窗口的维护、搬迁或换机场景。

**优点**

- 可以把虚拟机完整迁移到新环境，包括虚拟机实例、存储卷等。
- 迁移完成后重新启动虚拟机即可恢复业务。
- 实现简单，不需要在运行状态下同步内存。

**缺点**

- 迁移期间业务中断，对在线应用有直接影响。
- 通常需要停机窗口与人工确认，流程较长。

### 热迁移

热迁移（Live Migration，实时迁移）指在虚拟机持续运行的情况下，把它从一个计算节点迁移到另一个计算节点，迁移过程对使用者基本无感知。它适用于不允许中断的高可用场景。

**优点**

- 迁移过程中无需关机，运行中的应用基本不受影响。
- 可以实现接近零停机的业务连续性，便于硬件维护和容量均衡。

**缺点**

- 对虚拟机状态与资源占用有要求，并非所有虚拟机都能热迁移。
- 通常还需要共享存储或存储迁移、足够的网络带宽、源与目标主机之间兼容的 CPU 特性等条件。
- 操作相对复杂，需要选择合适的迁移时机与目标主机。

### 对比

| 对比项 | 冷迁移 | 热迁移 |
| --- | --- | --- |
| 业务影响 | 中断，需停机窗口 | 基本无感知 |
| 实现复杂度 | 低 | 高 |
| 前置条件 | 关机即可 | 共享存储/存储迁移、带宽、CPU 兼容性等 |
| 适用场景 | 计划内维护、机房搬迁、离线系统 | 在线业务、硬件维护、负载均衡 |

### 实践注意点

- **先确认依赖**：应用是否有本地会话、内存缓存、机器绑定授权，这些在迁移后可能需要重新处理。
- **批量迁移看带宽**：一次迁太多虚拟机会打满存储与网络，通常在业务低峰分批执行。
- **迁移不等于高可用**：迁移解决的是"换地方"，故障自动切换要靠集群与容灾设计，见下一节。

## 六、容灾与业务连续性

本节讲"出事之后还能不能继续提供服务"。迁移关注的是"搬家"，容灾关注的是"房子塌了怎么办"，它是业务连续性的最后一道防线。

### 是什么

容灾（Disaster Recovery）指在硬件故障、自然灾害、机房断电等重大事件发生时，通过备份与恢复机制、冗余部署和切换流程，保证业务能够继续运行或快速恢复。它通常用两个指标衡量：

- **RTO（Recovery Time Objective，恢复时间目标）**：能容忍业务中断多久。
- **RPO（Recovery Point Objective，恢复点目标）**：能容忍丢失多长时间的数据。

比喻：重要文件在家里和办公室各放一份，家里进水了还能用办公室那份继续干活；放几份决定 RPO，多久能拿到决定 RTO。

### 常见容灾形态

**双活容灾**：在两个不同区域分别部署应用与数据库，并通过数据同步保证两侧数据基本一致。一侧故障时由另一侧继续提供服务。成本最高，但对连续性要求高的系统是常见选择。

**备份容灾**：把备份数据存放在多个存储位置（例如不同厂商的对象存储桶），配合版本控制保证备份的正确性与一致性，并预先准备好可执行的恢复流程。它恢复得慢，但成本低，适合作为兜底。

**迁移容灾**：迁移期间把业务数据同时同步到云端与本地数据中心，迁移过程中若出现故障，可以回退到本地继续提供服务。

### 优点与代价

**优点**

- 重大事件发生时业务仍可继续运行，减少中断带来的损失。
- 具备数据备份与恢复能力，保证数据的完整性与可靠性。

**缺点**

- 需要持续投入资源与成本，包括冗余环境、备份存储和恢复机制的建设与维护。
- 恢复或切换过程本身可能影响业务，需要合理规划策略与流程，并定期演练。

### 设计要点

- 先定 RTO/RPO，再选技术方案。要求秒级切换和能接受小时级恢复，成本相差很大。
- 明确单点：数据库、注册中心、证书、专线都可能是单点，逐项确认冗余方式。
- 备份要能恢复：只备份不演练，等于没有备份；恢复流程应定期实测。
- 切换要有决策与回滚路径，避免故障时临时判断。

## 七、弹性伸缩

本节讲云计算最有代表性的能力：资源随负载自动增减。它同时影响可用性和账单，是上云后最先被用到的机制之一。

### 是什么

弹性伸缩（Auto Scaling）是一种动态资源调度机制：根据应用负载自动调整计算资源的数量和类型。简单说，它在访问量上涨时自动加机器，在访问量回落后自动减机器。

比喻：餐厅按客流临时加桌、撤桌，服务员和厨房产能跟着调整，而不必常年按最高峰配置桌椅。

### 为什么需要

- **对使用者**：业务有明显的峰谷（如电商大促、工作日与周末），固定容量要么浪费要么扛不住。
- **对厂商**：把资源池中的空闲容量调度给需要的租户，整体利用率更高。
- **对成本**：只为实际使用的容量付费，减少长期闲置。

### 怎么实现

弹性伸缩通常由两部分配合完成：虚拟化技术把物理服务器切分为多个虚拟服务器，自动化调度技术按预设条件触发资源的增减。落地时一般配置三类参数：

| 参数 | 作用 |
| --- | --- |
| 最小容量 | 下限，保证基础流量始终有机器承载 |
| 期望容量 | 当前希望维持的实例数，可由策略动态调整 |
| 最大容量 | 上限，防止异常流量或配置错误导致费用失控 |

触发方式常见有三种：基于指标的动态策略（如 CPU 使用率、请求数、队列长度超过阈值）、定时策略（如每天 9 点扩容）、预测式策略（按历史规律提前扩容）。主流平台都提供对应能力，例如 AWS 的 Auto Scaling 组、Kubernetes 的 Horizontal Pod Autoscaler。以 AWS 为例，Auto Scaling 服务本身不额外收费，费用来自被创建出来的实例、存储和监控资源。

### 典型应用场景

1. **互联网服务**：随流量变化动态调整服务器资源以保证服务质量，负载过高时自动扩容缓解压力。
2. **大型企业**：业务量较大，需要按时间、流量等因素灵活调度资源，兼顾效率与可靠性。
3. **新兴行业**：如人工智能、自动驾驶等需要大量算力做训练和模拟的场景，可按需快速调整资源。

### 使用注意点

- **扩容有延迟**：新实例启动、应用预热、JVM 与连接池初始化都需要时间，指标阈值要留出提前量。
- **有状态服务难伸缩**：无状态应用最适合水平扩容；有状态服务需要配合会话共享、分片或读写分离。
- **缩容要谨慎**：缩容过快会引发抖动，通常设置冷却时间与逐步缩容。
- **成本护栏**：务必设置最大容量与预算告警，避免策略失效或流量异常造成意外账单。

### 发展趋势

弹性伸缩整体朝着更智能（预测式、基于业务指标）、更高性能、更多功能形态和更标准化的方向演进，以适应不断增长的云计算需求。

## 八、多租户技术

本节讲云平台如何在共享资源的前提下，让不同客户互不干扰。它既是厂商侧的架构问题，也是你设计 SaaS 时必须面对的设计题。

### 是什么

多租户技术指在单一系统内同时为多个租户提供服务，让不同租户在共享硬件、数据库等资源的同时，保持各自数据与应用的独立性。这里"租户"通常指一家客户组织，一家组织内的多个用户属于同一租户。

比喻：一栋写字楼里有很多公司，租户之间共用电梯、空调和保安，但各自的门锁、办公区和档案柜互不相通。

### 隔离的几个层次

多租户的关键是隔离，而隔离可以发生在不同层级，成本与强度差别很大：

| 隔离方式 | 做法 | 隔离强度 | 成本 |
| --- | --- | --- | --- |
| 独立数据库 | 每个租户一套库 | 最强 | 最高，运维对象多 |
| 共享数据库、独立 schema | 同一实例内按租户分 schema | 较强 | 中等 |
| 共享表、带租户标识 | 所有租户数据同表，用租户 ID 区分 | 最弱，依赖代码与权限控制 | 最低，扩展性最好 |

原文提到"将不同租户的数据存储在独立的数据库中"，这只是其中一种做法；实践中更多系统会根据数据敏感度和规模，在不同模块选用不同层级。

### 在云环境中的应用

1. **数据隔离**：按上述层级隔离租户数据，保证数据安全与隐私。
2. **服务隔离**：把不同服务运行在独立的虚拟机或容器中，避免互相影响。
3. **负载均衡**：按租户需求分配计算资源，提升整体利用率。
4. **定制化服务**：按客户需求提供不同配置与支持级别。

### 注意点

- 每个请求都要能识别租户身份，且所有查询都必须带租户条件，否则容易越权。
- 需要防止"吵闹邻居"：单个租户的流量突增不应拖垮其他租户，可用配额与限流隔离。
- 租户级配额、审计日志和计费口径要提前设计，事后补非常麻烦。

多租户技术提高了资源利用率、降低了成本，同时提供灵活的服务形态，是云计算中很基础的一项能力。

## 九、计费模式：按需付费与预留实例

本节讲云上花钱的两种基本方式。选错计费方式，架构不变而成本可能相差数倍，因此它是上云必须掌握的知识。

### 常见计费维度

云资源通常按实际使用的量计费，常见维度包括计算（实例运行时长）、存储（容量与请求次数）、网络（出网流量）以及函数调用次数等。计费粒度多为按秒或按小时，具体以厂商文档为准。

### 按需付费

按需付费（On-Demand）指按实际使用的资源量实时计费，用多少付多少。它灵活、弹性好，适合临时、短期或用量不确定的工作负载：不必提前预购，可随需求动态调整，避免资源浪费。

需要注意，账单金额与使用量大致同向变化，但并非严格线性：不同规格的单价不同，流量、存储请求等还有各自的计费规则，实际费用要以账单明细为准。

### 预留实例

预留实例（Reserved Instance，RI）指用户承诺一段时期（常见为 1 年或 3 年）的资源使用，以换取比按需价格更低的单价，适合长期稳定的工作负载。

需要澄清一个常见误解：以 AWS 为例，预留实例并不是"一台提前买好、随时可用的物理机器"，而是一种**账单折扣**，它会自动抵扣属性匹配的按需实例用量；折扣力度通常较大（官方文档提到最高可省约 72% 的按需费用），但到期后不会自动续订，届时会回落到按需价。此外，预留实例本身通常不保证容量，需要容量保障时要用容量预留等专门机制。不同厂商的规则不同，使用前应查对应文档。

### 对比

| 对比项 | 按需付费 | 预留实例 |
| --- | --- | --- |
| 付费方式 | 按实际用量实时计费 | 承诺期限，换取折扣单价 |
| 单价水平 | 基准价 | 通常明显更低，承诺越久折扣越大 |
| 灵活性 | 最高，随时调整 | 较低，绑定实例属性或用量承诺 |
| 适用负载 | 临时、短期、波动大 | 长期稳定、可预测 |
| 主要风险 | 用量大时总价高 | 承诺后闲置仍要付费 |

### 怎么选

先看负载曲线：常年稳定运行的部分用预留或承诺型折扣覆盖，波动部分用按需，临时可中断的任务还可以考虑竞价类实例。AWS 官方目前更推荐 Savings Plans 而非预留实例，因为它只承诺消费金额、不绑定具体实例规格，灵活性更好。实际选型时建议以"基线用量 + 峰值用量"两段式拆分，并定期复核覆盖率。

## 十、无服务器计算（Serverless）与 FaaS

本节讲一种"完全不用管服务器"的运行方式。它是云原生里比较新的一层抽象，理解它的边界比记住概念更重要。

### 是什么

无服务器计算（Serverless Computing）是一种云计算执行模型：开发者编写并部署代码，无需管理底层服务器。它通常是事件驱动的——代码在特定事件（HTTP 请求、消息到达、定时任务、文件上传）触发时由平台自动运行，运行完即释放资源。

FaaS（Function as a Service，函数即服务）是无服务器最常见的形态：你上传一个函数，平台负责调度、扩缩容和运行。

比喻：打车。你不必买车、买保险、找车位，需要时叫车，按里程付费，用完就走；代价是不能像自己开车那样随意改装。

### 为什么需要

- **不承担运维**：不需要关心操作系统补丁、服务器配置与容量规划。
- **按需扩展**：请求量上来时平台自动并发扩容，无需提前压测容量。
- **按使用付费**：计费通常基于调用次数与执行消耗（执行时长与分配内存的组合），空闲时不产生计算费用。
- **加快交付**：开发者只关注业务逻辑，迭代更快。

### 怎么用

以函数为例，典型流程是：编写处理函数 → 配置触发源（网关、消息队列、对象存储事件、定时器）→ 部署 → 平台按事件调用。Java 场景下通常用平台提供的运行时，把逻辑写成一个处理方法，再交给平台打包。

使用前要了解平台限制，例如 AWS Lambda 的单次调用执行时长上限为 900 秒（15 分钟）、函数内存可选 128 MB～10 240 MB，具体数值以官方配额文档为准。这类限制意味着无服务器更适合短时、无状态的任务。

### 冷启动

平台在没有请求时通常会把实例缩容到零，下一个请求到来时需要重新初始化运行环境，因此首个请求的延迟会明显高于后续请求，这叫冷启动（cold start）。缓解手段包括：保留最小实例数/预置并发、减小包体积与依赖、缩短初始化逻辑。Java 应用因启动较慢，冷启动问题通常更明显。

### 适用与不适用

| 适合 | 不适合 |
| --- | --- |
| 事件驱动、调用稀疏的接口或定时任务 | 长时间运行的计算（受执行时长上限约束） |
| 需要快速迭代、流量波动大的业务 | 强依赖本地状态、常驻连接的服务 |
| 图片处理、日志清洗等短任务 | 对启动延迟极敏感的接口（除非预置实例） |

### 常见平台

AWS Lambda、Azure Functions、Google Cloud Functions 等。

无服务器计算简化了应用的开发、部署和管理，提高了迭代效率，但它并不是所有场景的最优解，选型时仍要结合调用特征与延迟要求判断。

## 十一、服务网格（Service Mesh）

本节讲微服务之间"通信"这件事如何从业务代码里剥离出来。当服务数量变多，重试、超时、加密、限流、追踪这些横切逻辑会在每个服务里重复出现，服务网格就是为此而生的基础设施层。

### 是什么

服务网格是一种处理服务间通信的基础设施层，为应用提供流量管理、安全、可观测性等能力，而不需要修改业务代码。它通常通过对服务间网络流量做透明代理来实现，因此业务代码对它是无感知的。

比喻：老式电话总机。所有通话都要经过总机转接，总机负责接通、录音、限制通话时长，而打电话的人不需要改造自己的电话机。

### 为什么需要

微服务把系统拆成很多小服务后，网络调用变成了常态，于是每个服务都要处理服务发现、负载均衡、超时重试、熔断、加密传输、链路追踪。把这些逻辑写进每个服务的代码里，既重复又难以统一升级；服务网格把它们下沉到基础设施层，由平台统一配置和治理。

### 核心能力

| 能力 | 说明 |
| --- | --- |
| 流量管理 | 支持复杂路由规则、流量切分（灰度、A/B 测试）、负载均衡 |
| 安全 | 服务间加密通信与身份认证，可实现零信任式的访问控制 |
| 可观测性 | 提供请求级别的指标、日志与调用链，便于定位问题 |
| 故障恢复 | 提供重试、超时、熔断等机制，提高系统弹性 |

### 怎么落地

常见实现方式是给每个服务实例配一个边车代理（sidecar），由代理接管进出流量；较新的实现（如 Istio 的 ambient 模式）尝试减少 sidecar 带来的资源开销。主流实现包括 Istio、Linkerd、Consul Connect 等，其中 Istio 基于 Envoy 代理构建。

### 代价与适用边界

服务网格不是免费的：多一层代理会带来额外延迟与资源消耗，控制面本身也需要运维，配置错误的影响面很大。服务数量较少（比如十几个以内）时，用框架内的重试与网关层的治理往往更划算；服务规模大、多语言混布、需要统一安全策略时，服务网格的价值才明显。

## 十二、云环境中的性能测试与安全测试

本节讲上线前后必须做的两类验证。云环境的弹性与按量计费会放大测试的影响：压测既可能打满自己的额度，也可能影响同租户的其他系统，因此方法要更讲究。

### 性能测试的五种类型

| 类型 | 关注点 |
| --- | --- |
| 负载测试 | 模拟不同数量的用户请求，测系统的响应能力与处理能力 |
| 压力测试 | 在高负载下测系统的稳定性与可靠性，找出崩溃点 |
| 尖峰测试 | 测系统面对突发流量（瞬时尖峰）时的表现 |
| 持久性测试 | 测系统在长时间高负载下的表现，暴露内存泄漏、连接泄漏等问题 |
| 可扩展性测试 | 测系统在增加或减少部署资源时的性能变化 |

### 安全测试的六类动作

1. **端口扫描与应用扫描**：扫描设备端口与部署的应用，发现暴露的服务和已知漏洞。
2. **漏洞分析与评估**：集中收集扫描结果，判断哪些漏洞真正可被利用、影响多大，排出修复优先级。
3. **验证访问控制与身份认证**：测试认证与授权机制能否有效阻止未授权访问和越权操作。
4. **测试数据保护与加密**：验证传输和存储环节的保护措施，包括加密算法与密钥管理机制。
5. **模拟攻击与恶意代码测试**：模拟攻击者行为，检测系统的抵御能力与恢复能力。
6. **安全审计与日志分析**：审查系统与应用日志，发现异常行为并修复。

### 云上测试的注意点

- **压测前评估资源与费用**：弹性扩容会在压测期间真实产生实例和流量费用，需设置上限。
- **遵守厂商规则**：部分厂商对压测来源、速率有明确要求，必要时提前报备，避免被判定为攻击。
- **使用独立环境与脱敏数据**：压测与安全扫描不要在承载真实用户数据的环境里做。
- **关注云侧指标**：除了应用指标，还要看带宽、连接数、存储 IOPS 等云资源配额是否先成为瓶颈。

## 十三、云环境中的典型挑战与应对

本节用一个具体场景把前面的能力串起来：流量高峰导致响应变慢，这类问题在云上非常常见，解决思路也比较典型。

### 场景

某应用在高峰期需要处理大量请求，响应明显变慢，影响用户体验。这类问题的根因通常是资源不足、数据库成为瓶颈，或流量集中在少数节点上。

### 应对一：弹性伸缩

设置伸缩规则，按系统负载自动增减实例数量，覆盖峰谷变化。这是最直接的手段，但要注意扩容延迟与应用启动时间，指标阈值要留提前量。

### 应对二：引入缓存

把热点数据放进缓存（如 Redis 等内存存储），减少对数据库的重复查询，避免数据库成为瓶颈。需要同时考虑缓存与数据库的一致性、缓存穿透与失效风暴等问题。

### 应对三：负载均衡

把流量分发到多个实例，提高整体吞吐并避免单点过载，同时配合健康检查摘除异常节点。

### 应对四：安全与配置治理

- 用防火墙、入侵检测等手段保护边界与主机安全。
- 特别注意配置错误：对象存储权限过宽、数据库对公网开放、密钥写进代码仓库，都是云上高频事故来源。
- 定期做安全审计与漏洞扫描，及时发现并修复风险。

### 小结

弹性伸缩解决"容量"，缓存与负载均衡解决"效率"，安全治理解决"底线"。三者叠加，才能在高峰期保持性能与安全。

## 十四、云环境中的数据一致性

本节讲分布式环境下最容易被低估的问题：同一份数据出现在多个节点上时，如何保证各节点看到的内容一致。云环境的网络延迟、节点故障与并发访问，会让这件事比单机复杂得多。

### 为什么在云上更难

数据往往存在多个副本、多个可用区甚至多个区域；节点之间通过网络通信，可能超时、乱序、分区；并发请求来自不同实例，没有单机锁可以依赖。一致性方案的选择，本质上是在一致性、可用性和延迟之间做取舍。

### 六种常见手段

| 手段 | 做法 | 适用场景 |
| --- | --- | --- |
| 分布式事务 | 用两阶段提交、TCC、Saga 等协议协调多个参与方，保证操作整体成功或整体回滚 | 跨服务、跨库的强一致需求 |
| 时间戳 | 给每次操作打上时间戳，据此判定先后顺序、解决写冲突 | 需要确定操作时序的场景 |
| 版本控制 | 为数据维护版本号，更新时校验版本（类似 CAS），冲突则重试 | 并发更新同一行数据的场景 |
| 消息队列 | 把需要异步处理的任务通过消息投递，按顺序消费，避免并发竞争 | 最终一致、可接受延迟的场景 |
| 数据库复制 | 把数据复制到多个节点，按复制策略保持一致（同步或异步） | 读多写多、需要高可用与读扩展 |
| 快照与备份 | 定期对数据做快照与备份 | 防误删、防损坏，作为兜底 |

需要注意，原文中"时间戳能确保同一时间只有一个操作成功""版本号能确保同一时刻只有一个操作拥有最新版本"这类表述过于绝对：时间戳与版本号本身只是判定依据，真正的一致要靠冲突检测与重试逻辑实现，且不同数据库的实现方式不同。

### 代码示例：用版本号做乐观并发控制

下面的示例用版本号实现乐观锁：只有当数据库里的版本号与读取时一致，更新才会生效，否则说明有人先改了数据。

```java
// 读取时拿到 version，更新时把它作为条件
int updated = jdbc.update(
        "UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?",
        newBalance, accountId, expectedVersion);

if (updated == 0) {
    // 版本冲突：重新读取最新数据，再决定是否重试
    Account latest = load(accountId);
    // 业务判断后重试或返回冲突提示
}
```

这类方案实现简单、无锁等待，适合冲突不频繁的场景；冲突频繁时应改用悲观锁、串行化队列或分片，避免大量重试拖垮数据库。

### 选型思路

先判断业务能接受"强一致"还是"最终一致"，再决定用分布式事务还是消息队列；跨库、跨服务的强一致代价很高，多数互联网业务采用"核心链路强一致 + 外围链路最终一致"的混合策略。同时要结合网络延迟与故障恢复预案一起考虑，因为一致性方案在故障时的行为往往才是关键。

## 十五、云环境中的用户数据安全

本节从工程落地角度讲数据安全的常规做法。云上安全的基本前提是"责任共担"：厂商负责基础设施安全，配置、身份、数据加密通常由使用者负责。

### 身份与访问控制

- **使用强密码策略**：要求足够的长度与复杂度，避免被猜测或撞库。
- **启用多因素认证（MFA，Multi-Factor Authentication）**：在密码之外再增加一种验证因素，如动态口令、硬件密钥、短信或邮件验证码。
- **最小权限**：按角色授权，避免使用超级账号跑应用；程序使用独立的服务账号与临时凭证。

### 数据加密

- **传输加密**：服务间、客户端到服务端都使用加密通道。
- **存储加密**：对敏感字段或整卷加密，密钥交给专门的密钥管理服务保管，不要写进代码或配置文件。
- **脱敏与分级**：日志、测试数据中的手机号、身份证号等应脱敏，按数据敏感级别决定存储位置与访问审批。

### 备份与恢复

定期备份数据并保存在安全、隔离的位置，防止误删、勒索软件与区域性故障。备份要验证可恢复性，并明确保留周期与销毁策略。

### 运维与审计

- **及时更新软件与操作系统**，修复已知漏洞。
- **制定并执行安全策略**，包括访问控制、加密要求、变更流程。
- **开启审计日志**并集中留存，便于事后追溯；对异常登录、批量导出等行为设置告警。
- **了解厂商提供的安全能力**，如加密、访问控制、态势感知等，并把属于自己的那部分责任落实到位。

## 十六、企业上云迁移建议

本节把前面的知识收敛成一份可执行的清单。迁移不是"把机器搬上去"，而是应用、数据、流程和成本管理的一次整体调整。

1. **制定详细的迁移计划**：明确迁移范围、时间窗口、目标架构、验证方式与回滚方案。
2. **评估云服务提供商的可靠性**：考察其可用性承诺、服务等级协议、合规资质与技术支持响应能力。
3. **优化应用性能**：迁移前先做瘦身与优化，例如引入缓存、压缩传输、减少不必要的远程调用，避免把原有问题一起搬上云。
4. **管理成本**：按业务线打标签做成本归集，结合预留/按需组合控制支出，定期复核闲置资源。
5. **确保数据安全**：迁移链路加密、访问最小化、密钥集中管理，敏感数据评估是否需要留在本地。
6. **进行测试与验证**：功能、性能、容灾切换都要在云上环境验证，而不是只验证"能启动"。
7. **考虑多云策略**：把不同应用部署在不同厂商，可降低单一厂商风险，也会带来运维复杂度与网络成本的上升，需要权衡。

迁移通常建议分阶段推进：先迁无状态、低风险的边缘系统，再迁核心系统；每一步都保留回退能力。规划得越细，迁移过程越可控。
