## 索引基础

索引是 MySQL 性能话题的起点。这一章先回答"索引是什么、有哪些种类、底层为什么是 B+ 树"，把地基打牢，后面讨论"为什么走索引/为什么不走"才有依据。

### 什么是索引？索引有哪些优缺点

索引（index）是数据库按某种规则排好序的辅助数据结构，作用是让查询不必逐行比对整张表。

可以把它想成一本字典的拼音目录：正文按页码排，目录按拼音排，查字时先翻目录定位页码，再翻到那一页。目录本身占纸张、需要在改版时同步更新，这就是索引的代价。

优点：

1. 提高查询效率，把"全表扫描"变成"按索引定位"，减少磁盘 IO。
2. 唯一索引、主键索引天然带唯一性约束，可以防止重复数据。

缺点：

1. 占用额外存储空间（二级索引本质上是"索引列 + 主键"的一份副本）。
2. 写入变慢：`INSERT`、`UPDATE`、`DELETE` 都要同步维护索引，索引越多写放大越明显。

结论：索引不是越多越好，而是"为高频、高选择性的查询条件建最少的索引"。

### MySQL 索引分类

按实现方式与用途，常见分类如下。

| 类型 | 说明 | 典型场景 |
|---|---|---|
| 主键索引 | 唯一且非空，一张表只有一个，InnoDB 中它就是聚簇索引 | `id` |
| 唯一索引 | 列值唯一，允许 NULL（多个 NULL 不冲突） | 手机号、订单号 |
| 普通索引（二级索引） | 无唯一性约束，最常见的索引 | 状态、时间 |
| 组合索引（联合索引） | 多列联合排序，遵循最左前缀 | `(user_id, create_time)` |
| 全文索引 | 面向大文本的分词检索，InnoDB 5.6+ 支持 | 文章内容 |
| 前缀索引 | 只索引字符串前 N 个字符，节省空间 | 长 URL |

按数据结构还可以分为 B+ 树索引（默认，支持范围查询与排序）、哈希索引（等值查询 O(1)，InnoDB 只在自适应哈希索引等内部场景使用）、空间索引（`SPATIAL`，用于地理数据）。

### MySQL 索引数据结构

InnoDB 的索引是一棵 B+ 树。理解它要抓住两个概念：聚簇索引（clustered index）和二级索引（secondary index）。

- **聚簇索引**：叶子节点直接存放整行数据。InnoDB 一定会有聚簇索引：有主键就用主键；没有主键就用第一个"所有列都 NOT NULL 的唯一索引"；两者都没有时，InnoDB 会生成一个隐藏的 6 字节行号列并建立名为 `GEN_CLUST_INDEX` 的隐藏聚簇索引。
- **二级索引（非聚簇索引）**：叶子节点存放"索引列的值 + 主键值"。用二级索引查到主键后，还要再回聚簇索引取整行，这一步叫**回表**。

因此主键越短越好：主键值会跟着每一个二级索引一起存，主键过长会让所有二级索引一起变胖。

同一条 SQL 还可能遇到两个优化：

- **索引下推（ICP，Index Condition Pushdown）**：联合索引上，把能在索引里判断的条件下推到存储引擎层先过滤，减少回表次数。`EXPLAIN` 的 Extra 显示 `Using index condition`。
- **索引合并（index merge）**：一条 SQL 用到多个索引，把各自的结果取交集或并集。`EXPLAIN` 的 type 显示 `index_merge`。它通常不如一个设计良好的联合索引，属于"补救"手段。

### 为什么索引用 B+ 树

先看几种候选结构为什么被淘汰，再看 B+ 树赢在哪。

- 二叉搜索树 / 红黑树：每个节点只有两个孩子，树高随数据量快速增长。2000 万行数据树高约 24 层，意味着最多 24 次磁盘 IO，不可接受。
- B 树：非叶子节点也存整行数据，单页能放的键更少，树更高；范围查询要在层间来回跳。
- 哈希表：等值查询 O(1)，但哈希值不保留顺序，范围查询、排序、最左前缀全部失效。
- B+ 树：非叶子节点只存键和指针，单页能放上千个键，树高只有 3~4 层；叶子节点按序双向链表相连，范围查询只需顺着链表扫。

一句话：B+ 树用"矮胖 + 叶子有序链表"同时满足了"少 IO"和"范围扫描快"这两个磁盘数据库最核心的诉求。

### B 树和 B+ 树的区别

| 特性 | B 树 | B+ 树 |
|---|---|---|
| 数据存放位置 | 所有节点都存键和值 | 只有叶子节点存数据（或行指针） |
| 查找路径 | 可能在非叶子节点提前命中 | 一定走到叶子节点，路径长度稳定 |
| 范围查询 | 需要在层间回溯遍历 | 叶子节点链表顺序扫描 |
| 单页扇出 | 较小，树更高 | 较大，树更矮 |
| 适用场景 | 随机读写为主 | 范围查询、顺序访问、排序 |

### 什么数据用哈希存储

哈希索引把键经过哈希函数映射到固定位置，等值查找平均 O(1)。

不适合的范围场景：哈希值不保留原值的顺序，所以 `BETWEEN`、`>`、`<`、`ORDER BY`、`LIKE 'abc%'` 都无法利用哈希索引，只能全表扫描。
也不支持最左前缀：`(a, b)` 的哈希索引必须同时给出 a 和 b 才能算哈希值。

适合的场景：纯等值查询，例如 KV 型访问、内存表（`MEMORY` 引擎默认哈希索引）、以及 InnoDB 内部的自适应哈希索引。

MySQL 的 B+ 树索引也支持等值查询，所以业务表通常不需要显式哈希索引；如果要自己实现，常见做法是额外存一列"哈希值"（如 `CRC32(url)`）并对它建唯一索引，用等值匹配代替长字符串比较。

### MyISAM 索引与 InnoDB 索引的区别

| 特性 | MyISAM | InnoDB |
|---|---|---|
| 索引组织方式 | 非聚簇：索引文件与数据文件分离，叶子存行地址 | 聚簇：主键索引叶子存整行，二级索引叶子存主键值 |
| 主键查询 | 先查索引再按地址取行 | 一次索引查找即得整行 |
| 二级索引查询 | 按地址回表 | 按主键回表（多一次主键查找） |
| 锁粒度 | 表级锁 | 行级锁 |
| 事务 / 外键 | 不支持 | 支持 |
| 崩溃恢复 | 弱 | 依赖 redo log 与 double write |

结论：需要事务与高并发写入时选 InnoDB；MyISAM 已不适合作为新项目的默认选择（MySQL 5.5 起默认引擎就是 InnoDB）。

## 索引设计与使用

知道索引是什么之后，真正难的是"给哪几列建、按什么顺序建、什么时候不该建"。这一章围绕最左前缀原则展开，把设计原则、覆盖索引、跳跃扫描和 NULL 相关的取舍讲清楚。

### 什么是最左前缀原则

组合索引 `(A, B, C)` 在 B+ 树中是按 A、再按 B、再按 C 排序的。因此查询必须从最左边开始、并且不能跳过中间的列，才能利用"有序性"做范围定位。

| 查询条件 | 能否用上索引 | 说明 |
|---|---|---|
| `WHERE A=1 AND B=2 AND C=3` | 三列全用 | 全值匹配 |
| `WHERE A=1 AND B=2` | 用 A、B | 前缀匹配 |
| `WHERE A=1` | 只用 A | 最短可用前缀 |
| `WHERE A=1 AND C=3` | 只用 A | C 被 B 隔断，无法定位 |
| `WHERE B=2 AND C=3` | 用不上（8.0.13+ 可能走跳跃扫描） | 缺少最左列 |
| `WHERE A=1 AND B>2 AND C=3` | A、B 用于定位，C 只能做索引下推过滤 | 范围列之后的列无法继续缩小扫描区间 |

生活化理解：电话簿按"姓 + 名"排序，你可以查"姓张且名三"的人，也可以查"所有姓张"的人，但没法高效查"名字叫三"的所有人。

好处是显著的：索引列顺序设计得好，一个组合索引可以顶多个单列索引，既省空间又省写入开销；设计得不好，则会出现"建了索引却用不上"的浪费。

### 哪些字段适合加索引，哪些不适合

**适合加索引：**

1. 高基数字段：用户 ID、订单号、手机号这类取值几乎不重复的列。
2. 经常出现在查询条件里的列：`WHERE`、`JOIN ... ON`、`ORDER BY`、`GROUP BY`。
3. 表连接用的外键列（即使不建外键约束，也建议建索引）。
4. 需要唯一性约束的业务字段（用唯一索引顺带解决查询）。

**不适合加索引：**

1. 低基数字段单独建索引：性别、是否删除这类只有两三个取值的列，命中率再高也要回表，优化器往往直接放弃。
2. 频繁更新的列：每次更新都要改索引，写放大严重。
3. 超长文本、`TEXT`、`BLOB`：索引体积大，通常改用前缀索引或全文索引。
4. 很小的表：几百行的表全表扫描比走索引更快。
5. 从不参与查询、排序、连接的列。

**落地建议**：优先设计能覆盖高频查询的组合索引；控制单表索引数量（经验上 5 个以内比较好维护）；区分度高的列放前面；定期用 `performance_schema.table_io_waits_summary_by_index_usage` 找出从未被使用的索引并清理。

### MySQL 索引设计有哪些原则

1. **按查询设计，不按字段设计**：先收集高频 SQL，再决定索引，而不是给每个"看起来重要"的字段都建一个索引。
2. **组合索引优先**：把同一张表上高频一起出现的条件合并成一个组合索引，最常用的列放最左。
3. **控制数量**：每个索引都会拖慢写入，一般单表 3~5 个索引为宜，具体看读写比。
4. **高选择性列优先**：基数高、区分度大的列放左边，能更快缩小扫描范围。
5. **避免冗余索引**：已有 `(a, b)` 时，再建 `(a)` 就是冗余；`(a, b)` 与 `(b, a)` 也往往只需要一个。
6. **尽量做覆盖索引**：让查询需要的列都在索引里，省掉回表。
7. **考虑写性能**：写多读少的表要克制建索引。
8. **超大数据量配合分区/分片**：索引解决不了单表过大的问题，需要配合分区键或分片键设计。

### 创建索引时需要注意什么

1. **选对列**：查询条件、排序、聚合、连接字段优先。
2. **选对顺序**：组合索引中区分度高、等值查询的列放前面，范围查询列放后面。
3. **选对类型**：索引列尽量小而固定，例如用 `INT` 而不是 `VARCHAR(64)` 存状态码；字符集统一，避免隐式转换。
4. **注意长度**：长字符串用前缀索引，例如 `INDEX idx_url (url(32))`；但前缀索引无法做覆盖索引，也无法用于 `ORDER BY`。
5. **避免给可空列建唯一索引**：唯一索引允许多个 NULL，业务上的"唯一"会被打破。
6. **在线变更要评估**：大表加索引优先用 Online DDL（`ALGORITHM=INPLACE, LOCK=NONE`），并在低峰期执行。
7. **命名规范**：`idx_列名`、`uk_列名`，便于排查与清理。

### 什么时候不要使用索引

1. **小表**：全表扫描只需读少量页，走索引反而多一次回表。
2. **写多读少的表**：索引维护成本可能超过查询收益。
3. **查询会命中大部分行**：当条件能过滤掉的行很少（经验上返回超过全表 20%~30%），全表扫描的顺序 IO 更划算。
4. **区分度极低的列且单独使用**：如"是否删除"，索引用不上。
5. **列很少被查询**：纯粹占空间。
6. **报表类大批量导出**：一次读全表时索引没有意义。

判断依据不要凭感觉，用 `EXPLAIN` 对比 `rows` 与 `type`，必要时用真实数据做压测。

### 区分度不高的字段建索引一定没用吗

不一定。低选择性（low cardinality）字段单独建索引收益有限，但在下面这些场景仍然有价值。

1. **等值查询 + 结果集小**：例如"待支付订单"这类状态，虽然取值少，但占比极小（比如 0.1%），索引依然高效。
2. **作为组合索引的非前导列**：`(user_id, status)` 中 `status` 用来在索引内过滤，配合索引下推能减少回表。
3. **作为覆盖索引的一部分**：查询只需要索引里已有的列，不回表，扫描索引页比扫描数据页便宜。
4. **支撑分组统计**：`GROUP BY status` 可以走索引有序性，避免临时表和排序。
5. **支撑排序**：`ORDER BY status, id` 与索引顺序一致时可免排序。

结论：区分度决定"单独使用时"的收益，而组合索引、覆盖索引、排序分组会改变结论，必须结合具体 SQL 判断。

### 哪些场景可以利用索引覆盖来优化 SQL

覆盖索引（covering index）指查询需要的所有列都在索引里，存储引擎返回索引即可，不需要回表。`EXPLAIN` 的 Extra 显示 `Using index`。

典型可用场景：

1. **统计总数**：`SELECT COUNT(*) FROM t WHERE status=1`，在 `(status)` 索引上扫描即可。
2. **只查主键**：`SELECT id FROM t WHERE name='x'`，二级索引叶子本身就有主键。
3. **列表页只取少量列**：把 `SELECT *` 改成需要的列，再让这些列进组合索引。
4. **深分页的延迟关联**：先在索引里取出 10 个主键，再回表取整行（见"深分页"小节）。
5. **无 WHERE 的覆盖扫描**：需要遍历全表但只取少数列时，扫索引比扫数据页便宜。
6. **JOIN 的连接列 + 过滤列**：被驱动表的连接列与返回列都在同一索引中。
7. **ORDER BY + LIMIT**：索引天然有序，取前 N 行即可停止扫描。

注意事项：`SELECT *` 会直接破坏覆盖；`TEXT`/`BLOB` 不能进索引（前缀索引也不算覆盖）；索引列越多，索引越大，写入越慢，需要权衡。

### 索引跳跃扫描（Skip Scan，MySQL 8.0.13+）

组合索引 `(a, b)`，查询 `WHERE b = 1` 缺少最左列 a，传统上只能全索引扫描或全表扫描。

MySQL 8.0.13 引入索引跳跃扫描（Index Skip Scan）：优化器先枚举 a 的每个不同值，再对每个 a 值构造 `a=常量 AND b=1` 的子区间做范围扫描，从而"跳过"没有条件的最左列。

它属于成本优化，不是无条件的。官方文档给出的适用条件包括：

- 只有一张表，且查询只用到索引里的列（相当于覆盖索引）；
- 不能有 `GROUP BY`、`DISTINCT`；
- 最左列上必须是等值条件（可以是 `IN`），且最右列上必须存在范围条件；
- 是否启用由优化器开关 `optimizer_switch` 中的 `skip_scan` 控制（默认 on）。

因此原文"前导列区分度低就会自动跳跃扫描"的说法过于绝对：真正决定的是成本——如果 a 的取值非常多，枚举成本可能高于全索引扫描，优化器就不会选它。
验证方式：`EXPLAIN` 的 Extra 出现 `Using index for skip scan`，`EXPLAIN FORMAT=TREE` 或 `optimizer_trace` 中能看到 `skip_scan_range`。

```sql
CREATE TABLE t1 (f1 INT NOT NULL, f2 INT NOT NULL, PRIMARY KEY (f1, f2));
EXPLAIN SELECT f1, f2 FROM t1 WHERE f2 > 40;
-- Extra: Using index for skip scan
```

### NULL 和 NOT NULL 是否走索引

**结论**：`IS NULL` 与 `IS NOT NULL` 本身都可以用索引，是否真正使用由优化器按成本决定，与 MySQL 版本关系不大。

官方文档明确说明：`col IS NULL` 可以像 `col = 常量` 一样使用索引和范围扫描，典型 `type` 是 `ref` 或 `range`；`col = 常量 OR col IS NULL` 这种形式会显示 `ref_or_null`。另外，如果列本身声明为 `NOT NULL`，优化器会直接把 `col IS NULL` 化简掉。

需要注意的两点：

1. 数据分布影响选择：如果 NULL 占绝大多数，`IS NULL` 会命中大部分行，优化器可能改成全表扫描；反之占比很小时索引收益明显。
2. 可空列会让索引变"胖"：`key_len` 会多 1 字节，且 NULL 在索引中的排序位置在最前，业务上的 `ORDER BY` 语义容易出错。

实践建议：业务字段尽量 `NOT NULL DEFAULT ...`（数值用 0，字符串用空串，时间用固定值或 `1970-01-01`），把"是否为空"变成独立的布尔列，避免三值逻辑带来的坑。

### 索引优化最佳实践

1. **全值匹配**：条件把组合索引的列都用上，`key_len` 会显示完整长度。
2. **遵守最左前缀**：不在组合索引中间"跳列"。
3. **不在索引列上做运算/函数/类型转换**：`WHERE id+1=10`、`WHERE DATE(create_time)='2023-01-01'` 都会让索引失效，改写为范围条件。
4. **范围查询列放最后**：`(a, b)` 中 `a>10 AND b=1`，b 无法继续缩小扫描区间，只能靠索引下推过滤。
5. **优先覆盖索引**：能回表少一次就少一次。
6. **少用 `!=`、`NOT IN`、`OR` 跨列**：这类条件容易退化为全表扫描，能改写就改写（`OR` 拆成 `UNION ALL`，`NOT IN` 改 `LEFT JOIN ... IS NULL` 并注意 NULL 语义）。
7. **LIKE 通配符放右边**：`LIKE 'abc%'` 可用索引，`LIKE '%abc'` 不行。
8. **字符串条件加引号**：`WHERE phone = 13800138000` 会触发隐式类型转换，索引失效。
9. **用 `EXPLAIN` 验证**：优化前后对比 `type`、`key`、`rows`、`filtered`，不要凭直觉。

## 索引失效与查询写法

建了索引却没用上，是业务里最常见的性能问题。这一章把"索引失效"的典型场景、排查路径，以及容易误判的写法（函数、条件顺序、`1=1`）集中讲清。

### 索引失效的常见场景

先把最常见的六类列出来，再补一个便于记忆的口诀。

1. **左模糊匹配**：`LIKE '%abc'` 或 `LIKE '%abc%'`。B+ 树按前缀有序，无法从中间定位；只有 `LIKE 'abc%'` 能用索引做范围扫描。
2. **在索引列上使用函数**：`WHERE YEAR(create_time)=2023`、`WHERE UPPER(name)='ABC'`。索引里存的是原始值，函数结果没有索引，只能逐行算。
3. **在索引列上做表达式运算**：`WHERE price+10>100` 改写为 `WHERE price>90` 即可走索引。
4. **隐式类型转换**：列是 `VARCHAR` 而条件是数字（`WHERE phone=13800138000`），MySQL 会把列转成数字再比较，索引失效。反过来，列是数值而条件是字符串通常仍可用索引。
5. **组合索引不满足最左前缀**：`(a,b,c)` 上查 `WHERE b=1` 用不上（8.0.13+ 在满足成本与条件时可能走跳跃扫描）。
6. **`OR` 连接了无索引列**：`WHERE a=1 OR b=2`，若 `b` 无索引，整条语句退化为全表扫描。

其余常见情况：`!=`、`<>`、`NOT IN`、`NOT LIKE` 这类否定条件选择性差；对可空列使用 `IS NOT NULL` 且 NULL 占比高；联合索引列顺序与查询不匹配；对索引列做排序方向相反的 `ORDER BY`（无降序索引时）。

记忆口诀（六字）：**模、型、数、空、运、最**。

- 模：模糊查询以 `%` 开头。
- 型：类型不匹配导致隐式转换。
- 数：索引列上套了函数。
- 空：NULL 相关的判断与可空列。
- 运：索引列参与运算。
- 最：不满足最左前缀。

### 索引失效的问题如何排查

1. **先看执行计划**：`EXPLAIN` 关注 `type`（目标是 `ref`/`range`，出现 `ALL` 或 `index` 要警惕）、`key`（是否为空、是否非预期）、`rows`（估算扫描行数）、`Extra`（是否 `Using filesort`、`Using temporary`）。
2. **对比 `possible_keys` 与 `key`**：有候选索引却没用，说明成本估算不划算，通常是数据分布或统计信息的问题。
3. **检查 SQL 写法**：函数、运算、隐式转换、左模糊、`OR`、`NOT IN`。
4. **检查索引本身**：组合索引列顺序是否匹配查询；前缀索引是否无法覆盖；索引是否因字符集/排序规则不一致而不可用。
5. **更新统计信息**：`ANALYZE TABLE t;` 之后重新 `EXPLAIN`。
6. **看优化器为什么不选**：MySQL 8.0 可用 `EXPLAIN FORMAT=JSON` 或 `SET optimizer_trace='enabled=on'` 查看代价计算过程。
7. **确认没有锁或长事务干扰**：`performance_schema.data_locks` 与 `information_schema.innodb_trx` 能看到阻塞来源。

### SQL 用了函数一定会索引失效吗

不一定，要看函数作用在哪个位置。

- **失效**：函数作用在 `WHERE` 的索引列上（`WHERE LOWER(name)='abc'`），因为要对每一行求值后才能比较，索引的有序性用不上。
- **不失效**：函数作用在常量侧（`WHERE create_time >= NOW() - INTERVAL 1 DAY`），或出现在 `SELECT` 列表、`HAVING` 中，都不影响 `WHERE` 的索引选择。

如果业务确实需要"按函数结果查询"，有两条正规做法。

1. **生成列 + 索引**（MySQL 5.7+，8.0 完善）：

```sql
ALTER TABLE users
  ADD COLUMN name_lower VARCHAR(64) GENERATED ALWAYS AS (LOWER(name)) STORED,
  ADD INDEX idx_name_lower (name_lower);

SELECT * FROM users WHERE name_lower = 'abc';
```

2. **MySQL 8.0.13+ 函数索引（functional index）**：本质也是隐藏的生成列。

```sql
ALTER TABLE orders ADD INDEX idx_date ((DATE(create_time)));
```

3. **在应用层转换**：写入时就把规范化后的值存一列，查询时用规范化值匹配。

### where 条件的顺序影响索引使用吗

大多数情况不影响，但有两个例外。

1. **优化器会重排条件**：`WHERE` 中条件的书写顺序与执行顺序无关，优化器按代价选择用哪个索引、以什么顺序访问表，范围条件下推的顺序也不依赖书写顺序。这点在官方文档的"范围优化"一节中有明确说明：范围条件的提取结果与条件在 `WHERE` 中出现的顺序无关。
2. **真正决定成败的是索引列顺序**：组合索引 `(a,b)` 上写 `WHERE b=1 AND a=2` 与 `WHERE a=2 AND b=1` 完全等价，都能用上；写成 `WHERE b=1` 才用不上。

例外与注意点：

- `AND` 与 `OR` 混用时，括号会改变语义，进而改变能否使用索引；
- 某些带副作用的表达式（如自定义函数、`RAND()`）求值顺序可能有影响，但这类写法本身不建议出现在 `WHERE` 中。

实践建议：为了可读性，让 `WHERE` 的书写顺序与索引列顺序保持一致，最终以 `EXPLAIN` 为准。

### 什么时候索引失效反而提升效率

"走索引"不等于"更快"。下面这些情况下，优化器主动放弃索引是正确决策。

1. **小表**：数据量只有几页，全表扫描一次顺序 IO 就够。
2. **返回大部分行**：条件过滤性差（经验上超过 20%~30%），走索引要大量随机回表，反而不如顺序扫全表。
3. **低选择性索引**：如布尔列，几乎每行都命中。
4. **写密集表**：少一个索引就少一份维护成本，读稍慢但整体吞吐更高。
5. **需要排序的大结果集**：`ORDER BY` 无可用索引时走 filesort，有时配合覆盖索引反而更慢。
6. **优化器估算偏差**：统计信息过期导致选错索引，可用 `FORCE INDEX` 或 `ANALYZE TABLE` 纠正。

结论：是否走索引应由优化器的成本模型决定，人的工作是把"统计信息、SQL 写法、索引设计"这三件事做对。

### where 1=1 会不会影响性能

**结论：在现代版本上基本没有影响。**

`WHERE 1=1` 常被用来拼接动态 SQL（后面统一追加 `AND ...`）。优化器在准备阶段会做常量折叠与条件化简，恒真条件会被消除，不会进入执行阶段。

验证方式：

```sql
EXPLAIN SELECT * FROM users WHERE 1=1 AND status = 1;
SHOW WARNINGS;  -- 查看优化器改写后的语句
```

早期版本（5.5 及更早）优化器能力有限，社区里因此流传"`1=1` 影响性能"的说法；在 5.7 / 8.0 / 8.4 上，实测执行计划与去掉 `1=1` 时一致。

真正需要注意的是别的点：`WHERE 1=1` 会让"忘记加条件"这类低级错误不再报错，从而放大全表扫描的风险。使用 MyBatis 时用 `<where>` 标签能自动处理首尾 `AND`，比手写 `1=1` 更稳。

## 执行计划与优化器

`EXPLAIN` 是排查性能问题的第一手工具。这一章先把它的每一列讲透，再解释"优化器为什么会选错索引"以及"排序为什么慢"，最后说明查询缓存为什么被移除。

### EXPLAIN 详解

`EXPLAIN` 输出的是优化器选定的执行计划，不是真实耗时；想看真实耗时要用 `EXPLAIN ANALYZE`（MySQL 8.0.18+）。

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;
EXPLAIN FORMAT=JSON SELECT * FROM users WHERE id = 1;   -- 信息更全
EXPLAIN ANALYZE SELECT * FROM users WHERE id = 1;        -- 8.0.18+，输出实际执行统计
```

| 列 | 含义 | 关注点 |
|---|---|---|
| `id` | 查询序号，同一个 `SELECT` 内越大越先执行；`UNION` 结果行可能为 `NULL` | 判断子查询/联合的层次 |
| `select_type` | `SIMPLE`、`PRIMARY`、`SUBQUERY`、`DEPENDENT SUBQUERY`、`DERIVED`、`UNION`、`UNION RESULT`、`MATERIALIZED` 等 | 有无物化、相关子查询 |
| `table` | 该行对应的表；也可能是 `<derived N>`、`<union M,N>`、`<subquery N>` | 派生表是否被物化 |
| `partitions` | 命中哪些分区，非分区表为 `NULL` | 分区裁剪是否生效 |
| `type` | 访问类型，从好到差：`system` > `const` > `eq_ref` > `ref` > `fulltext` > `ref_or_null` > `index_merge` > `unique_subquery` > `index_subquery` > `range` > `index` > `ALL` | 出现 `ALL`/`index` 要重点看 |
| `possible_keys` | 理论上可选的索引 | 为 `NULL` 说明没有可用索引 |
| `key` | 实际使用的索引；可能不在 `possible_keys` 中（覆盖索引场景） | 是否符合预期 |
| `key_len` | 实际使用的索引字节数，可推断用了组合索引的几列 | 比预期短说明有列没用上 |
| `ref` | 与索引比较的列或常量，`func` 表示用了函数结果 | 是否出现意外的函数比较 |
| `rows` | 估算需要扫描的行数（InnoDB 是估算值） | 与真实行数偏差大说明统计信息过期 |
| `filtered` | 按表条件过滤后剩余行数百分比，最大 100 | `rows × filtered` 约等于传给下一张表的行数 |
| `Extra` | 额外信息，见下表 | 优先消除 filesort 与 temporary |

**type 常见值解释：**

- `system`：表只有一行（系统表），`const` 的特例。
- `const`：主键或唯一索引与常量等值比较，最多一行，优化阶段就能读出。
- `eq_ref`：JOIN 中被驱动表用主键或唯一非空索引等值匹配，每次一行。
- `ref`：用普通索引（或唯一索引的最左前缀）等值匹配，可能多行。
- `range`：索引范围扫描，`>`、`<`、`BETWEEN`、`IN`、`LIKE 'abc%'` 等。
- `index`：全索引扫描；若 `Extra` 是 `Using index` 则是覆盖索引扫描。
- `ALL`：全表扫描。

**Extra 常见值解释：**

| Extra | 含义 | 处理建议 |
|---|---|---|
| `Using index` | 覆盖索引，不回表 | 理想状态 |
| `Using index condition` | 索引下推（ICP） | 正常，说明过滤在存储引擎层做了 |
| `Using where` | 需要在 Server 层再过滤 | 结合 `rows` 看过滤量 |
| `Using filesort` | 需要额外排序 | 考虑让 `ORDER BY` 走索引 |
| `Using temporary` | 使用了临时表 | 常见于 `GROUP BY` 与 `ORDER BY` 列不一致 |
| `Using join buffer (...)` | 用了 join buffer（BNL/BKA/hash join） | 被驱动表缺索引 |
| `Using index for skip scan` | 走了跳跃扫描 | 8.0.13+ 特性 |
| `Select tables optimized away` | 优化阶段即可得出结果（如 MyISAM 的 `COUNT(*)`） | 正常 |
| `Impossible WHERE` | 条件恒假 | 检查逻辑 |

**`key_len` 的计算规则**（容易算错，务必注意字符集）：

| 列类型 | 占用的 key_len |
|---|---|
| `TINYINT` / `SMALLINT` / `MEDIUMINT` / `INT` / `BIGINT` | 1 / 2 / 3 / 4 / 8 字节 |
| `CHAR(n)` | 字符集最大字节数 × n（utf8mb4 为 4n，utf8 为 3n，latin1 为 n） |
| `VARCHAR(n)` | 字符集最大字节数 × n + 1（长度 ≤255）或 +2（长度 >255） |
| 可空列 | 再 +1 字节 |

原文"`CHAR(n)=n` 字节"只在 `latin1` 下成立，utf8mb4 下应为 4n，这是最常见的 `key_len` 误判来源。

**看执行计划的顺序**：先看 `type` 有没有 `ALL`，再看 `key` 是否为空或非预期，然后看 `rows` 的量级，最后看 `Extra` 有没有 `filesort`/`temporary`。三张表以上的 JOIN 还要注意驱动表选择是否合理。

### 优化器选择非预期索引

优化器基于**成本估算**选择索引，估算偏差就会选错。常见原因与处理办法：

| 原因 | 表现 | 处理 |
|---|---|---|
| 统计信息偏差 | `rows` 与真实值差很多，采样页数不足 | `ANALYZE TABLE t;`；8.0 可调 `innodb_stats_persistent_sample_pages` |
| 隐式类型转换 / 函数 | `possible_keys` 有值但 `key` 为空 | 改写 SQL，让条件与列类型一致 |
| 索引设计不合理 | 组合索引列顺序与查询不匹配、缺覆盖索引 | 重建索引，范围列后置 |
| 冗余索引干扰 | 多个相似索引，优化器选到较差的 | 删除冗余索引 |
| 成本模型与环境不匹配 | SSD 上仍按传统磁盘参数估算随机 IO | 调整 `innodb_io_capacity`，必要时用 `FORCE INDEX` |
| Buffer Pool 未预热 | 冷启动时随机读代价被高估 | 预热或使用 `innodb_buffer_pool_load_at_startup` |
| 优化器开关 | `optimizer_switch` 关闭了某些优化 | 检查 `index_merge`、`skip_scan`、`mrr` 等开关 |

```sql
ANALYZE TABLE orders;

-- 让条件与列类型一致
SELECT * FROM orders WHERE phone = '13800138000';

-- 时间范围用半开区间，避免函数
SELECT * FROM orders
 WHERE create_time >= '2023-01-01 00:00:00'
   AND create_time <  '2023-01-02 00:00:00';

-- 组合索引：等值列在前，范围列在后
CREATE INDEX idx_status_time ON orders(status, create_time);

-- 覆盖索引
CREATE INDEX idx_cover ON orders(user_id, status, amount);
```

必要时才用 `FORCE INDEX` / `USE INDEX`：它是"绕过优化器"，一旦数据分布变化就可能变成新的性能问题，应作为临时手段并记录原因。

### 用了索引还是慢可能是什么原因

1. **索引与查询不匹配**：组合索引少了最左列，或者范围条件之后的列用不上。
2. **回表太多**：命中行数过多，随机 IO 成为瓶颈，此时覆盖索引才有意义。
3. **索引选择性差**：列区分度低，等于"扫了索引还要扫表"。
4. **排序/聚合开销**：`ORDER BY` 无法用索引导致 filesort，`GROUP BY` 产生临时表。
5. **统计信息过期**：优化器低估行数，选错驱动表。
6. **锁等待**：高并发写导致行锁/间隙锁等待，SQL 本身很快但响应很慢。
7. **Buffer Pool 命中率低**：数据量超过内存，频繁读盘。
8. **返回数据量过大**：网络传输与客户端反序列化成为瓶颈（`SELECT *` 一次取几十万行）。
9. **硬件或配置限制**：磁盘 IOPS、CPU、连接数打满。

定位方法：先看 `EXPLAIN`，再看 `performance_schema` 的等待事件，最后用 `SHOW PROFILE`（已废弃，8.0 建议用 `performance_schema`）或 `EXPLAIN ANALYZE` 区分"执行慢"还是"等待慢"。

### 为什么 MySQL 单表不要超过 2000 万行

**先说明：2000 万不是 MySQL 的硬限制，而是一个基于 B+ 树高度的经验参考值。**

推算过程（假设 InnoDB 默认页大小 16KB、主键 `BIGINT` 8 字节、页内指针 6 字节）：

- 非叶子节点每个键占 8 + 6 = 14 字节，一页约能放 16384 / 14 ≈ 1170 个键，即扇出约 1170。
- 树高为 3（根 + 一层分支 + 叶子）时，叶子页数量约 1170 × 1170 ≈ 137 万页。
- 若每行约 1KB，一页放约 15 行，则总行数约 137 万 × 15 ≈ 2000 万。

也就是说：**数据量到 2000 万行附近，B+ 树可能从 3 层涨到 4 层，一次主键查询的磁盘 IO 从 3 次变成 4 次**，同时 Buffer Pool 更难全部装下，命中率下降。

需要强调的是，这个数字非常依赖假设：

- 行宽越小，一页放的行越多，临界值就越高；行宽大（含 `VARCHAR`、`TEXT`）则临界值更低。
- `innodb_page_size` 可以设为 4/8/16/32/64KB（5.7/8.0/8.4 均支持），页越大临界值越高。
- 二级索引越多，实际占用空间与维护成本越大，但主键索引的高度不变。

除树高之外，还要考虑：行溢出（`TEXT`/`BLOB` 走溢出页）、表空间碎片、DDL 变更成本、备份恢复时间、`ALTER TABLE` 耗时。

结论与做法：把 2000 万当作"该考虑治理了"的信号，而不是"不能超过"的红线。到达这个量级时优先做归档与冷热分离、按时间分区、优化索引；确实无法控制增长再考虑分库分表。

### order by 工作原理

MySQL 的排序有两种执行路径。

1. **索引有序则免排序**：`ORDER BY` 的列与索引顺序一致（且方向一致），直接按索引顺序读即可，`Extra` 不会出现 `Using filesort`。
2. **无法用索引时走 filesort**：
   - **全字段排序**：把查询需要的所有列放进 `sort_buffer` 排序，排完直接返回，只读一次表。
   - **rowid 排序**：当单行太大（超过 `max_length_for_sort_data`）时，只把"排序键 + 主键"放进 `sort_buffer`，排序后再按主键回表取其余列，多一次回表但内存占用小。

`sort_buffer` 不够时，MySQL 会把数据分块写入磁盘临时文件，再做多路归并（外部排序），这就是"排序慢"的根因。相关参数：`sort_buffer_size`（每个连接独占，不宜过大）、`max_length_for_sort_data`、`tmp_table_size`。

优化手段：

- 给 `ORDER BY` 的列建索引，最好与 `WHERE` 组合成 `(过滤列, 排序列)` 形式；
- 让 `ORDER BY` 与索引顺序、方向完全一致，避免混用升降序（MySQL 8.0 支持降序索引）；
- 只取需要的列，争取覆盖索引；
- 深分页场景配合延迟关联或游标法。

### 为什么 MySQL 8.0 要取消查询缓存

查询缓存（query cache）以"SQL 文本的哈希"为键缓存结果集，命中则直接返回。它在 8.0 被彻底移除（5.7.20 起标记废弃），原因是它带来的问题远大于收益。

1. **失效粒度粗**：只要表上有一条 `UPDATE`，该表相关的所有缓存条目全部失效，写多的库命中率极低。
2. **全局锁竞争**：缓存的读写需要全局互斥量，高并发下成为瓶颈。
3. **额外内存与碎片**：缓存占用大量内存，且频繁失效产生碎片。
4. **只对完全相同的 SQL 生效**：多一个空格、大小写不同都无法命中，且不能缓存复杂查询。
5. **更好的替代品**：Redis / 本地缓存可以按业务 key 精细失效，命中率与可控性都更高。

实践结论：用应用层缓存（Redis）缓存热点数据，用 `SQL_CACHE`/`query_cache_type` 这类老配置在 8.0 中已不可用。

## 事务与并发

事务解决"多条语句要么全做、要么全不做"的问题，隔离级别解决"并发事务互相看到什么"的问题，MVCC 则是 MySQL 在"隔离"与"并发"之间找到的平衡点。这一章按这三个层次展开。

### 说下你对数据库事务的理解

事务（transaction）是一组数据库操作的逻辑单元：要么全部提交，要么全部回滚。

用转账举例：A 账户扣 100、B 账户加 100，这两步必须同生共死，否则钱会凭空消失或凭空出现。事务就是保证这件事的机制。

ACID 四个特性：

- **原子性（Atomicity）**：靠 Undo Log 实现，回滚时按反向操作撤销。
- **一致性（Consistency）**：事务前后数据满足业务约束（总额不变、外键有效），这是目的，由 A、I、D 共同保障。
- **隔离性（Isolation）**：并发事务互不干扰，靠锁与 MVCC 实现。
- **持久性（Durability）**：提交后即使断电也不丢，靠 redo log 的刷盘策略实现。

InnoDB 中事务的边界由 `BEGIN`/`START TRANSACTION` 开始，`COMMIT` 或 `ROLLBACK` 结束；默认 `autocommit=1`，单条语句自成一个事务。

### 并发事务带来哪些问题

| 问题 | 现象 | 根因 |
|---|---|---|
| 脏读（dirty read） | 读到别的事务**未提交**的数据，对方回滚后数据"从未存在" | 读不加锁、不判可见性 |
| 不可重复读（non-repeatable read） | 同一事务内两次读同一行，值不一样 | 别的事务在两次读之间提交了 `UPDATE`/`DELETE` |
| 幻读（phantom read） | 同一事务内两次按同一条件查询，行数变了 | 别的事务在两次读之间 `INSERT` 并提交 |
| 丢失修改（lost update） | 两个事务读同一行再各自写回，后写的覆盖先写的 | 读与写之间没有互斥 |

**不可重复读与幻读的区别**：前者关注"同一行的值变了"，后者关注"结果集的行数变了"。

需要强调：在 InnoDB 的可重复读下，**快照读**通过 MVCC 已经能保证同一事务多次查询结果一致（不会出现不可重复读，也不会出现幻读）；**当前读**（`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE`）则依靠临键锁阻止别的事务插入，从而避免幻读。这两条路径要分开理解。

### 事务的隔离级别有哪些

SQL 标准定义四个级别，隔离性从弱到强：

| 级别 | 能避免 | 仍可能出现 | InnoDB 默认 |
|---|---|---|---|
| 读未提交（READ UNCOMMITTED） | 无 | 脏读、不可重复读、幻读 | 否 |
| 读已提交（READ COMMITTED，RC） | 脏读 | 不可重复读、幻读 | 否 |
| 可重复读（REPEATABLE READ，RR） | 脏读、不可重复读 | 当前读场景下的幻读由临键锁阻止 | **是（5.7/8.0/8.4）** |
| 串行化（SERIALIZABLE） | 全部 | 无 | 否 |

几点说明：

- `SELECT @@transaction_isolation;` 可查看当前级别；`SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;` 可修改（8.0 起变量名为 `transaction_isolation`，5.7 兼容 `tx_isolation`）。
- 串行化在 InnoDB 中会把普通 `SELECT` 隐式转成加共享锁的读，事务之间实质串行，并发能力最差。
- RC 下 InnoDB 会关闭间隙锁（外键检查与唯一性检查除外），这也是很多互联网业务把隔离级别降到 RC 的主要原因。

### 为什么 MySQL 默认 RR 隔离级别

1. **主从复制的一致性**：早期 statement 格式的 binlog 在 RC 下可能出现"主库执行顺序与从库不一致"的问题，RR 下更安全。这是历史原因，binlog 默认改为 ROW 后该顾虑已大幅减弱。
2. **快照读开销低**：RR 只在事务第一次快照读时生成一次 ReadView，之后复用，比 RC 每次查询都创建更省。
3. **语义更符合直觉**：同一事务内重复查询结果稳定，减少业务代码里的"读到变化"的意外。
4. **幻读有兜底**：当前读用临键锁阻止插入，比 SQL 标准要求的 RR 更强。
5. **兼容性**：默认值改动会影响大量存量应用，官方一直保持 RR。

### MySQL 默认 RR，为什么很多公司改成 RC

1. **减少锁范围**：RC 关闭间隙锁，`UPDATE`/`DELETE` 只锁命中行，锁冲突显著下降。
2. **降低死锁概率**：没有间隙锁，插入与范围更新之间的交叉等待大幅减少。
3. **适配互联网业务**：多数 Web 业务对"同一事务内多次读一致"要求不高，RC 足够，且更接近 Oracle/PostgreSQL 的默认行为。
4. **配合缓存与最终一致**：业务层用缓存与补偿保证最终一致，数据库不必承担强一致压力。
5. **提升并发吞吐**：锁持有时间短，事务提交更快。

代价也要清楚：RC 下同一事务内两次查询可能读到不同结果；依赖"RR 防幻读"的逻辑（例如"先查后插"防重复）必须改成唯一索引或显式加锁。

### MVCC 机制

MVCC（Multi-Version Concurrency Control，多版本并发控制）让"读"不阻塞"写"、"写"也不阻塞"读"：读操作读历史快照，写操作写最新版本。

可以把它想成文档的"修订记录"：每次修改都留一个旧版本，读者按自己打开文档的时间点看到对应版本，作者继续改自己的，互不干扰。

**三个核心组件：**

1. **隐藏字段**：InnoDB 每行都有 `DB_TRX_ID`（最后修改该行的事务 ID，6 字节）、`DB_ROLL_PTR`（指向 Undo Log 中旧版本的回滚指针，7 字节）、`DB_ROW_ID`（无主键时用的隐藏行号，6 字节）。
2. **Undo Log（版本链）**：每次更新都把旧值写入 Undo Log，`DB_ROLL_PTR` 把各版本串成链表，链表头是最新版本。
3. **ReadView（读视图）**：事务做快照读时生成，决定"能看到哪个版本"。核心字段：
   - `m_ids`：生成时仍活跃（未提交）的事务 ID 列表；
   - `min_trx_id`：`m_ids` 中的最小值（低水位）；
   - `max_trx_id`：生成时系统将要分配的下一个事务 ID（高水位）；
   - `creator_trx_id`：创建该 ReadView 的事务 ID。

**可见性判断（沿版本链从新到旧找第一个可见版本）：**

- `TRX_ID == creator_trx_id`：自己改的，可见。
- `TRX_ID < min_trx_id`：在 ReadView 之前就已提交，可见。
- `TRX_ID >= max_trx_id`：ReadView 生成后才开启的事务，不可见。
- `min_trx_id <= TRX_ID < max_trx_id`：若在 `m_ids` 中说明当时还活跃，不可见；否则已提交，可见。

**RC 与 RR 的唯一区别**：RC 每次快照读都新建 ReadView；RR 只在事务内第一次快照读时创建，之后复用。这也是"RR 能可重复读、RC 不能"的根本原因。

几个常见追问：

- **二级索引没有隐藏事务字段**：二级索引页上有 `PAGE_MAX_TRX_ID`，若它小于 ReadView 的 `min_trx_id` 说明整页都可见；否则需要回表到聚簇索引做版本判断（所以二级索引查询在 RR 下可能比预期多一次回表判断）。
- **"看不见"的行能改吗**：能。`UPDATE` 是当前读，读最新版本；改完后该行的事务 ID 变成自己，再查就可见了。
- **Undo Log 会无限涨吗**：不会，purge 线程会清理不再被任何 ReadView 需要的旧版本；但长事务会让 ReadView 一直不释放，Undo 无法回收，这是"长事务危险"的核心原因之一。

### Undo Log 是如何回滚事务的

Undo Log 记录的是"如何撤销这次修改"，回滚就是沿着它反向执行。

1. 每个事务有一条 Undo 链，事务开始时确定起点（回滚段中的 undo 记录位置）。
2. 回滚时从最新记录开始**逆序**处理：
   - `INSERT` 的 undo 记录对应"删除该行"；
   - `DELETE` 的 undo 记录保存了被删行的完整内容，对应"重新插入"；
   - `UPDATE` 的 undo 记录保存了被修改列的旧值，对应"写回旧值"。
3. 只回滚本事务自己的修改，其他事务的记录跳过。
4. 回滚完成后，这些 undo 记录被标记为可清理，由 purge 线程回收。

注意两点：Undo Log 属于逻辑日志（记录"反向操作"而不是物理页镜像），因此回滚是按逻辑重放；回滚本身也要写 redo log，保证"回滚"这个动作在崩溃后可以重做。

## 锁

锁是隔离性的执行手段。这一章从分类讲到"行锁到底锁什么"，再纠正一个流传很广的错误说法（锁升级），最后给出死锁与高并发更新的处理办法。

### MySQL 锁的分类

按粒度分：全局锁、表锁、页锁、行锁。按性质分：共享锁（S 锁）、排他锁（X 锁）。按思想分：悲观锁、乐观锁。

- **全局锁**：`FLUSH TABLES WITH READ LOCK`，整库只读，用于全库逻辑备份（现在更常用 `mysqldump --single-transaction` 或 xtrabackup 替代）。
- **表锁**：锁整张表，并发度最低；MyISAM 只有表锁。
- **页锁**：BDB 引擎使用，粒度介于表锁与行锁之间；InnoDB 不支持页锁。
- **行锁**：锁索引记录，并发度最高；InnoDB 默认行锁。

- **共享锁（S 锁）**：`SELECT ... FOR SHARE`（8.0 语法，5.7 为 `LOCK IN SHARE MODE`），多个事务可同时持有，阻塞写。
- **排他锁（X 锁）**：`SELECT ... FOR UPDATE`、`UPDATE`、`DELETE` 自动加，阻塞其他事务的读写。

InnoDB 的行锁有三种形态：**记录锁（Record Lock）** 锁单条索引记录；**间隙锁（Gap Lock）** 锁两条索引记录之间的空隙，阻止插入；**临键锁（Next-Key Lock）** 是"记录锁 + 记录之前的间隙锁"，InnoDB 在 RR 下默认用临键锁，这也是它能阻止幻读的原因。

### MySQL 各种锁详解

**表级锁**

- `LOCK TABLES t READ/WRITE`：显式表锁，MyISAM 常用；InnoDB 也支持但一般不用。
- **MDL（metadata lock，元数据锁）**：MySQL 5.5 引入，自动加。DML 加 MDL 读锁，DDL 加 MDL 写锁；读写互斥，因此"长事务不提交"会让后续 `ALTER TABLE` 一直等待，进而阻塞后面所有查询。

**行级锁**

| 锁类型 | 作用 | 加锁条件 |
|---|---|---|
| 记录锁 | 锁住某条索引记录 | 唯一索引等值命中且记录存在 |
| 间隙锁 | 锁住索引记录之间的空隙，阻止插入 | 范围查询、非唯一索引等值查询（RR 下） |
| 临键锁 | 记录锁 + 前面的间隙锁 | RR 下的范围扫描默认形态 |
| 插入意向锁 | 插入前对目标间隙加的意向锁，多个插入不同位置可并行 | `INSERT` |

**意向锁（IS/IX）**：表级锁，用来"声明我打算在表里锁某些行"。有了它，判断"表里有没有行锁"只需看表上的意向锁，不用逐行扫描；意向锁之间互相兼容，只与全表请求（如 `LOCK TABLES ... WRITE`）冲突。

**悲观锁与乐观锁**

- 悲观锁：先锁后改，`SELECT ... FOR UPDATE`。适合冲突频繁、重试代价高的场景。
- 乐观锁：不改锁，用版本号或条件更新。`UPDATE t SET version=version+1, ... WHERE id=? AND version=?`，影响行数为 0 说明被改过，由业务重试。

**查看锁与事务**

```sql
SHOW ENGINE INNODB STATUS;                       -- 最近一次死锁、锁等待概览
SELECT * FROM information_schema.innodb_trx;     -- 正在运行的事务
SELECT * FROM performance_schema.data_locks;     -- 8.0+ 当前持有的锁
SELECT * FROM performance_schema.data_lock_waits;-- 8.0+ 锁等待关系
```

5.7 及更早用 `information_schema.innodb_locks` 与 `innodb_lock_waits`，这两个表在 8.0 已被移除。

**锁优化策略**：让每条 DML 都能走索引（避免扫全表加锁）、缩短事务、按固定顺序访问资源、必要时降低隔离级别。

### MySQL 的行级锁锁的到底是什么

**锁的是索引记录，不是物理行。**

官方文档说得很直接：记录锁总是加在索引记录上；即使表上没有任何索引，InnoDB 也会创建隐藏的聚簇索引（`GEN_CLUST_INDEX`）来加锁。

由此推出几条实践结论：

1. **有合适索引时**：只锁命中的索引记录（RR 下还会锁相邻间隙），并发度高。
2. **没有索引时**：InnoDB 需要全表扫描，会给扫描到的每一条记录都加上锁（RR 下是临键锁），效果上相当于"锁住整张表"，其他事务几乎无法写入。这不是"锁升级"，而是"锁得太多"。
3. **不同索引会锁不同记录**：同一条数据若通过不同索引访问，可能锁住不同的索引记录，这也是死锁的常见来源。
4. **主键更新会同时锁二级索引**：修改被索引的列时，旧二级索引项与新索引项都会被锁定。

实践建议：所有 `UPDATE`/`DELETE` 都必须能走索引；能用主键就用主键；批量更新控制单次行数。

### 了解 MySQL 的锁升级吗

**先纠正一个常见误解：InnoDB 没有"锁升级"（lock escalation）机制。**

锁升级是指"行锁数量超过阈值时自动升级为表锁"，这是 SQL Server 等数据库的行为。InnoDB 的锁是逐条记录申请的，不会因为行锁太多而改成表锁；锁数量受内存限制，极端情况下会报错而不是升级。

那"感觉像锁升级"的现象从哪来？

1. **SQL 没走索引**：全表扫描给所有记录加锁，效果等于锁表（原因见上一节）。
2. **间隙锁范围过大**：范围条件过宽，临键锁覆盖了大量间隙，插入全部被阻塞。
3. **MDL 写锁**：DDL 需要 MDL 写锁，会把整张表的读写全部挡住，看起来像"表被锁了"。
4. **显式表锁**：`LOCK TABLES` 或备份工具加的锁。

所以正确的表述是：**InnoDB 通过"索引 + 锁粒度"控制锁范围，不存在自动升级；要减少锁冲突，应优化索引与事务，而不是期待"锁升级"的开关。**

### MySQL 只操作同一条记录也会死锁吗

**会。** 死锁的本质是"两个事务以相反顺序申请锁"，即使目标只有一行，也可能因为索引、间隙、外键等原因产生不同顺序。

常见场景：

1. **不同索引访问同一行**：事务 A 用二级索引定位再回表，事务 B 用主键定位，加锁顺序不同。
2. **唯一键冲突**：两个事务同时插入相同唯一键，其中一个等待对方的 S 锁，形成环。
3. **间隙锁交叉**：两个事务各持有一段间隙锁，又都要插入对方区间。
4. **外键检查**：插入子表时需要对父表记录加共享锁，顺序不当会互相等待。
5. **自增锁**：批量插入持有 AUTO-INC 锁期间又去申请其他锁。

处理办法：

- 统一访问顺序（先按主键升序处理，再处理关联表）；
- 缩短事务，把非数据库操作（RPC、发消息）移到事务外；
- 保证 DML 走索引，减少锁范围；
- 捕获死锁错误码 **1213**（`Deadlock found when trying to get lock`）并重试，锁等待超时是 **1205**。

```java
int attempts = 0;
while (true) {
    try {
        // 执行更新
        break;
    } catch (SQLException e) {
        if (e.getErrorCode() == 1213 && ++attempts < MAX_RETRIES) {
            Thread.sleep(RETRY_DELAY_MS);
        } else {
            throw e;
        }
    }
}
```

重试要加随机退避，避免两个事务同步重试再次撞车。

### 如何解决 MySQL 死锁问题

1. **先看现场**：`SHOW ENGINE INNODB STATUS` 的 `LATEST DETECTED DEADLOCK` 段会给出两个事务的 SQL、持有锁与等待锁；8.0 还可用 `performance_schema.data_lock_waits`。生产环境建议开启 `innodb_print_all_deadlocks=ON`，把所有死锁写入 error log。
2. **降低隔离级别到 RC**：间隙锁关闭后，插入类死锁大幅减少，代价是可能读到不可重复的数据。
3. **优化事务**：缩短持锁时间、按固定顺序加锁、避免大事务与批量更新。
4. **优化索引**：让 DML 精确加锁，避免扫全表加锁。
5. **调参数**：`innodb_lock_wait_timeout`（默认 50 秒）控制等待上限；`innodb_deadlock_detect`（默认 ON）决定是否主动检测死锁——关闭后靠超时回滚，高并发下可减少检测开销，但故障恢复变慢。
6. **应用层兜底**：对 1213/1205 做有限次重试，并把重试做成幂等。

### 高并发场景下，如何安全修改同一行数据

同一行被并发更新时，核心是"让修改串行化"，常见四种做法。

| 方案 | 实现 | 优点 | 代价 |
|---|---|---|---|
| 原子更新 | `UPDATE t SET stock=stock-1 WHERE id=? AND stock>=1` | 简单、无锁等待、天然幂等 | 只能做简单运算 |
| 乐观锁 | 版本号/时间戳：`UPDATE ... WHERE id=? AND version=?` | 无长事务、吞吐高 | 冲突时需重试 |
| 悲观锁 | `SELECT ... FOR UPDATE` 后更新 | 逻辑直观、强一致 | 锁等待、易死锁 |
| 分布式锁 | Redis `SET key val NX PX`、ZooKeeper 临时节点 | 跨服务、跨库 | 引入外部依赖与锁超时问题 |

实践建议：

- 能用一条原子 SQL 解决的，优先用原子更新（如扣库存必须带 `stock>=1` 条件，用影响行数判断是否成功）；
- 需要"读-算-写"的业务用乐观锁，重试次数控制在 3 次以内；
- 悲观锁与分布式锁只用于真正冲突频繁且必须强一致的场景，并注意锁超时、锁续期与死锁；
- 无论哪种方案，都要保证操作幂等，避免重试造成重复扣减。

## 日志、内存与存储引擎

MySQL 的可靠性建立在三类日志上，性能则很大程度上取决于内存里的 Buffer Pool。这一章讲清"三种日志各管什么、刷盘参数怎么影响安全与速度"，以及"查大量数据会不会把内存打爆"这类高频疑问。

### 三种日志的分工：redo、undo、binlog

先把三种日志摆在一起对比，后面各小节再展开细节。

| 日志 | 层次 | 内容 | 作用 | 写入方式 |
|---|---|---|---|---|
| redo log | InnoDB | 物理页的修改（"在某页某偏移写了什么"） | 崩溃恢复（crash-safe），保证已提交事务不丢 | 循环写，容量固定 |
| undo log | InnoDB | 逻辑反向操作（旧值） | 事务回滚、MVCC 版本链 | 按 undo 表空间增长，purge 回收 |
| binlog | Server 层 | 逻辑变更（语句或行） | 主从复制、数据恢复（按时间点） | 追加写，按文件滚动 |

生活化比喻：redo log 像"操作流水账"，记下每一步要写哪里，断电后照着补；undo log 像"撤销记录"，允许把做过的操作撤回；binlog 像"对外发布的变更公告"，从库和备份工具照着它重放。

**两阶段提交**：为了让 redo log 与 binlog 保持一致，InnoDB 提交时会先写 redo（prepare 状态），再写 binlog，最后把 redo 置为 commit。这样崩溃恢复时可以用 binlog 是否完整来判断该提交还是回滚。

**刷盘参数（安全与性能的权衡）：**

| 参数 | 取值 | 含义 | 默认 |
|---|---|---|---|
| `innodb_flush_log_at_trx_commit` | 1 | 每次提交都把 redo 刷到磁盘 | **1**（5.7/8.0/8.4） |
| | 0 | 每秒刷一次，崩溃可能丢 1 秒事务 | |
| | 2 | 提交时只写 OS 缓存，每秒刷盘；MySQL 崩溃不丢，主机断电可能丢 | |
| `sync_binlog` | 1 | 每次提交都 fsync binlog | **1**（8.0/8.4） |
| | 0 | 由操作系统决定，性能最好但可能丢日志 | |
| | N | 每 N 个事务 fsync 一次 | |

生产环境常用"双 1"（`innodb_flush_log_at_trx_commit=1` + `sync_binlog=1`）保证不丢数据；允许少量丢失的日志类业务可以调成 0 或 2 换取吞吐。改完之后要用压测确认收益，不要直接照抄网上的配置。

### Binlog 三种格式

binlog（二进制日志）记录所有会修改数据的语句或行变更，用于主从复制与按时间点恢复。

| 格式 | 记录内容 | 优点 | 缺点 |
|---|---|---|---|
| `STATEMENT` | 原始 SQL 语句 | 日志量小，可读性好 | 非确定函数（`NOW()`、`UUID()`、`RAND()`）、自增、`LIMIT` 无排序等场景可能主从不一致 |
| `ROW` | 每一行变更前后的镜像 | 一致性强，可精确恢复；行锁冲突少 | 日志量大（批量更新尤甚），可读性差 |
| `MIXED` | 默认 STATEMENT，遇到不确定语句自动切 ROW | 折中 | 行为不够直观，排查困难 |

版本差异（重要）：

- MySQL 5.7.7 起 `binlog_format` 默认值为 `ROW`，8.0 保持 `ROW`。
- 8.4 中 `binlog_format` 已被标记**废弃**，官方建议只使用 `ROW`，其他格式未来可能被移除。
- 8.4 起二进制日志**默认开启**（5.7/8.0 需要显式配置 `log_bin`）。
- `binlog_expire_logs_seconds` 默认 2592000 秒（30 天），到期自动清理；也可用 `PURGE BINARY LOGS` 手动清理。

相关参数还有 `binlog_row_image`（默认 `full`，可设 `minimal` 减少日志量）、`max_binlog_size`（单个文件大小上限，事务超大会被拆到下一个文件）。

### InnoDB 存储引擎三大特性

InnoDB 的性能与可靠性主要由三块机制支撑：Buffer Pool 负责"少读盘"，自适应哈希索引负责"更快等值查找"，Double Write 负责"写坏页也能恢复"。

#### Buffer Pool

- 作用：在内存中缓存数据页与索引页，读写先经过 Buffer Pool，未命中才访问磁盘。
- 管理：改进版 LRU，链表分为 young（热）与 old（冷）两个区，默认 old 区占 3/8（`innodb_old_blocks_pct=37`）；新页插入 old 区头部（中点插入），在 `innodb_old_blocks_time`（默认 1000 毫秒）之后再次被访问才会晋升到 young 区。
- 大小：`innodb_buffer_pool_size`。官方文档提到，专用服务器上常把最多约 80% 的物理内存分配给 Buffer Pool；实践中常用 60%~75%，给连接、排序缓冲和操作系统留余量。
- 监控：`SHOW ENGINE INNODB STATUS` 的 `BUFFER POOL AND MEMORY` 段可看命中率；`information_schema.innodb_buffer_pool_stats` 也有对应指标。

#### 自适应哈希索引（AHI）

- 作用：InnoDB 自动监控索引访问模式，对频繁使用的等值查询在内存中建立哈希索引，把 B+ 树的多层查找变成一次哈希定位。
- 限制：只支持等值比较（`=`、`<=>`、`IN`），不支持范围查询与排序；由 InnoDB 自己维护，用户不能指定列。
- 参数：`innodb_adaptive_hash_index`。**注意版本差异：8.0 及以前默认开启，8.4 起默认关闭**（高并发下 AHI 的锁竞争可能反而拖慢性能，官方因此调整了默认值）。
- 建议：读写分离、点查为主的负载可以尝试开启并压测；高并发写场景保持默认关闭，或按需开启后观察 CPU 与 `INNODB STATUS` 中的 `Hash table size`。

#### Double Write

- 问题：InnoDB 页大小 16KB，而文件系统/磁盘的一次原子写通常只有 512B 或 4KB，断电时可能写出"半页"，这种页无法用 redo 恢复。
- 方案：刷脏页前先把页写到 double write buffer（内存 + 磁盘上的双写区），再写到数据文件；崩溃恢复时先用双写区里的完整副本修复坏页，再重放 redo。
- 参数：`innodb_doublewrite`，8.0 默认开启（`ON`）；对数据安全性要求极高时不要关闭，SSD 上关闭可减少约一半写入量，但需要自行承担风险。

### 一次性查 2000 万数据，MySQL 会 OOM 吗

**结论：服务端不会因为结果集大而 OOM，客户端很可能会。**

原因是 MySQL 采用"边读边发"的流式协议：存储引擎每取一行，就写入 `net_buffer`（默认 `net_buffer_length` 16KB），缓冲写满就通过 socket 发给客户端，发送成功后再清空继续取下一行。所以服务端的内存占用与结果集大小无关，只与网络缓冲有关；如果客户端读得慢，服务端会阻塞在发送上，而不是把数据堆在内存里。

真正会 OOM 的地方：

1. **客户端一次性把结果读进 `List`**：2000 万行对象在 JVM 里通常是几个 GB，堆溢出。
2. **排序/分组/去重**：`ORDER BY`、`GROUP BY`、`DISTINCT`、`UNION` 需要 `sort_buffer` 或临时表；内存不够会落磁盘（`Using filesort`/`Using temporary`），极端情况下写满 `tmpdir`，这是"服务端变慢甚至报错"的常见原因。
3. **大事务**：一次 `UPDATE` 几百万行，undo 与 binlog 都会膨胀。

正确做法：分页或游标分批读取（每批几千行）、导出用 `SELECT ... INTO OUTFILE` 或 `mysqldump`、给排序字段建索引避免临时表、客户端用流式查询（如 JDBC 的 `setFetchSize` + 只进结果集）。

### 我查这么多数据，会不会把数据库内存打爆

不会，原因同上：结果是流式返回的，不占大块服务端内存。但有两个副作用需要了解。

1. **Buffer Pool 被污染**：全表扫描会把大量冷数据页读进 Buffer Pool，如果按朴素 LRU 淘汰，热点页会被挤出去，随后业务查询全部落盘，出现"越查越慢"的雪崩。InnoDB 用中点插入 + `innodb_old_blocks_time`（默认 1000ms）应对：扫描读入的页先放 old 区，1000ms 内被重复访问才晋升，而全表扫描对同一页的访问间隔通常远小于 1 秒，因此这些页只在 old 区被淘汰，热数据不受影响。
2. **IO 与网络压力**：大量顺序读会打满磁盘带宽，影响同实例的其他查询；必要时把大查询放到只读从库或离线库执行。

### MySQL 为什么默认引擎是 InnoDB

1. **支持事务**：完整 ACID，业务能放心用事务保证一致性（MyISAM 不支持）。
2. **行级锁**：高并发写入时锁冲突远小于 MyISAM 的表锁。
3. **崩溃恢复**：依靠 redo log 与 double write，异常断电后能自动恢复到一致状态。
4. **外键约束**：可以在数据库层保证引用完整性（虽然互联网业务常不用，但能力在）。
5. **聚簇索引**：主键查询只需一次索引查找，效率高。
6. **在线热备**：配合 xtrabackup 等工具可在不停机的情况下做物理备份。
7. **社区与生态**：官方持续投入，8.0 起新增降序索引、Hash Join、原子 DDL 等能力。

MyISAM 的优势（表级锁、计数快、占用空间小）在现代硬件与业务形态下已不构成选择理由；除极少数只读归档场景，新项目都应使用 InnoDB。

## SQL 调优实战

调优不是"背优化技巧"，而是一条链路：先能发现慢 SQL，再能诊断它为什么慢，最后才是改写与治理。这一章按这个顺序组织，并集中处理计数、分页、JOIN、模糊查询等高频场景。

### 如何快速定位慢 SQL

1. **打开慢查询日志**：`slow_query_log=ON`，`long_query_time` 按业务设定（常用 0.5~1 秒），`log_queries_not_using_indexes` 可辅助发现无索引查询。
2. **聚合分析**：用 `pt-query-digest` 按"总耗时 = 单次耗时 × 次数"排序，优先治理总耗时最高的 SQL，而不是单次最慢的那条。
3. **看实时会话**：`SHOW PROCESSLIST` 或 `information_schema.processlist` 找长时间 `Sending data`/`Waiting for lock` 的线程。
4. **看等待事件**：`performance_schema.events_statements_summary_by_digest` 按 `SUM_TIMER_WAIT` 排序；`sys.statement_analysis` 是它的易读视图。
5. **看执行计划**：对可疑 SQL 做 `EXPLAIN`，必要时 `EXPLAIN ANALYZE` 看真实行数与耗时。
6. **看索引使用情况**：`sys.schema_unused_indexes` 找从未使用的索引，`sys.schema_redundant_indexes` 找冗余索引。

### 慢 SQL 你是怎么优化的

一条完整的优化链路，可以按"发现 → 诊断 → 治理"三步走。

**1. 发现（监控）**

- 慢查询日志 + `pt-query-digest` 做 TOP N 分析；
- Prometheus + Grafana 监控 QPS、连接数、锁等待、磁盘 IO、Buffer Pool 命中率；
- 应用侧埋点记录 SQL 耗时，按接口维度报警。

**2. 诊断（分析）**

- `EXPLAIN`：看 `type`（目标 `ref`/`range`）、`key`（是否符合预期）、`rows`（扫描量）、`Extra`（有无 `filesort`/`temporary`）。
- `performance_schema` / `sys` schema：`SHOW PROFILE` 已废弃，用 `events_stages_history` 或 `sys.session` 看各阶段耗时。
- `optimizer_trace`：看优化器为什么放弃某个索引，代价是多少。
- `EXPLAIN ANALYZE`（8.0.18+）：直接给真实执行时间与行数，能发现"估算 1 行实际 100 万行"这类问题。

**3. 治理（战术与战略）**

- 战术：改写 SQL（去掉函数、拆 `OR`、消除隐式转换）、加合适索引（含覆盖索引）、用延迟关联优化深分页、用 `UNION ALL` 替代 `UNION`。
- 战略：冷热分离、读写分离、分库分表、把复杂检索交给 Elasticsearch、把热点数据放 Redis。

核心原则：**看投入产出比**。一条每天执行 3 次、耗时 2 秒的报表 SQL，优先级远低于一条每天执行 300 万次、耗时 50ms 的列表查询。

### 如何进行 SQL 调优

1. **先定位再动手**：用 `EXPLAIN` 与慢日志确认瓶颈在"扫描行数多""回表多""排序/临时表"还是"锁等待"，不同原因对应不同手段。
2. **合理使用索引**：为 `WHERE`、`JOIN`、`ORDER BY`、`GROUP BY` 建索引；组合索引遵守最左前缀；控制索引数量。
3. **改写 SQL**：避免 `SELECT *`；用 JOIN 代替相关子查询（或反之，视数据量）；把 `OR` 拆成 `UNION ALL`；批量插入代替逐条插入；`LIMIT` 分页用延迟关联或游标。
4. **优化数据模型**：选择更小的数据类型；适度反范式冗余以减少 JOIN；大字段拆到扩展表。
5. **加缓存与批量化**：热点数据放 Redis；合并小事务；用 `INSERT ... VALUES (...),(...)` 批量写。
6. **维护统计信息**：定期 `ANALYZE TABLE`，避免优化器估算偏差；碎片严重的表考虑 `OPTIMIZE TABLE`（或在线重建）。
7. **架构层手段**：读写分离、分区、分库分表、冷热分离。
8. **配置与硬件**：合理设置 `innodb_buffer_pool_size`、连接池大小、`tmp_table_size`；使用 SSD。

### 数据库 CPU 飙升，你会如何处理

按"先定位来源，再对症处理"的顺序：

1. **看是查询还是锁**：`SHOW PROCESSLIST` 找大量 `Sending data` 的语句（慢查询）；若大量线程处于 `Waiting for ... lock`，说明是锁等待引发的连锁反应。
2. **看是否有突发流量**：QPS 曲线与业务发布、定时任务、爬虫是否对得上；必要时限流或降级。
3. **看执行计划退化**：统计信息变化导致索引选择变化，`EXPLAIN` 对比历史计划；用 `ANALYZE TABLE` 或 `FORCE INDEX` 临时止血。
4. **看连接数**：连接池配置过大导致线程争抢，`Threads_running` 远高于 CPU 核数时通常是并发过高。
5. **看慢 SQL 与全表扫描**：`Handler_read_rnd_next` 飙高说明大量全表扫描。
6. **看 InnoDB 内部**：`SHOW ENGINE INNODB STATUS` 的 `SEMAPHORES` 段若出现大量等待，可能是热点页竞争或 AHI 争用（8.4 已默认关闭 AHI）。
7. **看配置**：`tmp_table_size`、`sort_buffer_size` 过小导致磁盘临时表；过大导致内存换页。
8. **兜底**：kill 掉异常长事务/长查询（注意会回滚），把读流量切到从库。

### SQL 优化实战

先准备两张测试表：

```sql
CREATE TABLE student (
  id   INT AUTO_INCREMENT PRIMARY KEY,
  name VARCHAR(50),
  age  INT
);

CREATE TABLE scores (
  id         INT AUTO_INCREMENT PRIMARY KEY,
  student_id INT,
  score      INT,
  KEY idx_student_id (student_id)
);
```

优化要点：

1. **避免 `SELECT *`**：只取需要的列，减少 IO 与网络传输，也更容易做覆盖索引。
2. **小表驱动大表**：JOIN 时让结果集小的表做驱动表；子查询结果集小时用 `IN` 往往比 `EXISTS` 更合适。
3. **用 JOIN 代替相关子查询**：相关子查询可能对外层每一行都执行一次，JOIN 通常只需一次扫描。
4. **先过滤再聚合**：`WHERE` 尽可能缩小数据范围，再 `GROUP BY`，减少临时表数据量。
5. **批量操作**：多条 `INSERT` 合成一条（注意 `max_allowed_packet` 限制），批量 `UPDATE` 用 `CASE WHEN` 或分批执行。
6. **深分页用延迟关联或游标**（见后文）。
7. **`UNION ALL` 代替 `UNION`**：不需要去重时省掉排序去重开销。
8. **控制 JOIN 表数量**：经验上不超过 3 张，超过时考虑在应用层组合或冗余字段。

### count(1)、count(*) 与 count(列名) 的区别

| 用法 | 统计内容 | 是否忽略 NULL | 说明 |
|---|---|---|---|
| `COUNT(*)` | 行数 | 不忽略 | 标准写法，优化器会选最小的索引扫描 |
| `COUNT(1)` | 行数 | 不忽略 | 与 `COUNT(*)` 执行计划通常完全相同 |
| `COUNT(column)` | 该列非 NULL 的行数 | 忽略 | 需要判断每行该列是否为 NULL |
| `COUNT(DISTINCT column)` | 该列不同非 NULL 值的个数 | 忽略 | 需要去重，开销更大 |

性能说明：

- `COUNT(*)` 与 `COUNT(1)` 在 InnoDB 上基本等价，都会选择一棵较小的索引做全索引扫描（InnoDB 不保存精确行数）。
- `COUNT(column)` 若该列可空，需要额外判断 NULL；若列上有索引且非空，开销接近 `COUNT(*)`。
- 官方文档提到，只有像 MyISAM 这样维护精确行数的引擎，才可能对无 `WHERE` 的 `COUNT(*)` 直接返回结果（`Extra: Select tables optimized away`）；InnoDB 不行。

`COUNT(*)` 慢时的优化：

1. 不要求精确值时，用 `EXPLAIN` 的 `rows` 估算，或维护一张计数表/Redis 计数器。
2. 让计数走最小的二级索引（`SELECT COUNT(*) FROM t` 会自动选，但带 `WHERE` 时要保证条件列有索引）。
3. 分批统计后汇总，避免一次扫描过多行。
4. 业务上改用"近似值 + 定时校准"。

### 深分页优化

`LIMIT 1000000, 10` 的代价不是"返回 10 行"，而是"扫描并丢弃前 100 万行"，还要回表取整行。

三种常用优化：

**1. 延迟关联（子查询 + 覆盖索引）**：先在索引上取出主键，再回表只取 10 行。

```sql
SELECT t1.*
  FROM orders t1
  JOIN (SELECT id FROM orders ORDER BY create_time LIMIT 1000000, 10) t2
    ON t1.id = t2.id;
```

**2. 游标法（推荐）**：记住上一页最后一条记录的主键或排序键，下一页从它之后开始。它要求排序键唯一（或组合唯一），不支持跳页。

```sql
SELECT * FROM orders WHERE id > 1000000 ORDER BY id LIMIT 10;
-- 复合排序键写法
SELECT * FROM orders
 WHERE (create_time, id) > ('2023-01-01 00:00:00', 1000000)
 ORDER BY create_time, id LIMIT 10;
```

**3. 限制最大页数 / 换交互方式**：产品层禁止翻到第 1000 页，或改为"加载更多"。

补充手段：分页查询列被索引覆盖可以减少回表；缓存热门页结果；导出场景直接走 `mysqldump` 或 `SELECT ... INTO OUTFILE`。

### MySQL 中 like 模糊查询如何优化

1. **前缀匹配**：`LIKE 'abc%'` 可以走索引范围扫描；`LIKE '%abc'` 不行。
2. **反转字符串 + 索引**：对"后缀匹配"的需求，额外存一列反转后的值并建索引。

```sql
ALTER TABLE users ADD COLUMN reversed_username VARCHAR(64);
UPDATE users SET reversed_username = REVERSE(username);
CREATE INDEX idx_reversed ON users(reversed_username);

-- 查以 abc 结尾：反转后变成前缀匹配
SELECT * FROM users WHERE reversed_username LIKE CONCAT(REVERSE('abc'), '%');
```

3. **缩小范围**：先加时间、状态等条件把数据量降下来，再模糊匹配。
4. **全文索引**：InnoDB 5.6+ 支持 `FULLTEXT`，适合分词检索；中文需要 `ngram` 分词器。
5. **外部检索**：数据量大、需要相关性排序时用 Elasticsearch 等搜索引擎。
6. **应用层缓存**：把高频搜索词的结果缓存起来。

### 加密后的数据如何支持模糊查询

数据加密后无法直接用 `LIKE` 匹配明文，常见四种方案，各有代价。

**方案一：内存解密**（仅适合小数据量）

查出候选数据，在应用内存中解密后匹配。缺点：数据量大时内存与 CPU 都扛不住，且无法分页。

**方案二：映射表**

单独建一张映射表（明文片段 + 密文 + 业务 ID），先查映射表拿到 ID 再查主表。缺点：明文仍然落库，加密的意义被削弱，需要单独加固这张表。

**方案三：数据库加解密函数**

用 `AES_DECRYPT` 等函数在 SQL 里解密再 `LIKE`。缺点：无法走索引，每行都要解密，数据量大时性能不可接受。

**方案四：分片加密（推荐）**

把字段按固定长度滑窗切片，每片单独加密存储（例如手机号按 4 位切分），查询时把查询片段同样加密后做等值匹配。

```java
String mobile = "13800138000";
List<String> segments = new ArrayList<>();
for (int i = 0; i + 4 <= mobile.length(); i++) {
    segments.add(encrypt(mobile.substring(i, i + 4)));  // 加密后存入检索表
}
// 查询 "1380"：加密后与 segments 做 IN 匹配，命中即候选
```

优点是仍然可以走索引、支持任意位置的片段匹配；代价是存储膨胀（约为原文的 N 倍）、需要维护检索表、长度小于窗口的查询无法命中。

选型建议：合规要求高且查询简单（如"按手机号后四位"）时，用"分片加密 + 精确后缀列"；需要复杂模糊搜索时，把检索需求交给搜索引擎，并在搜索引擎侧做脱敏。

### 100 万数据去重，用 distinct 还是 group by

**功能上**：只做去重时两者等价，优化器通常会生成相似的计划（都可能用到 `Using temporary` 或索引）。

**可读性**：`DISTINCT` 语义直接表达"返回唯一行"，推荐优先使用；`GROUP BY` 的设计目的是聚合，不带聚合函数时属于借用。

**性能**：

- 关键在于是否有合适的索引。如果去重列上有索引，两者都可以走索引有序性避免临时表。
- 无索引时两者都慢，差距通常不大，不要指望换写法带来数量级提升。
- `GROUP BY` 在 8.0 已不再隐式排序（5.7 曾对 `GROUP BY` 结果隐式排序），所以"`GROUP BY` 更慢"的老经验不再成立。

**需要聚合时**：用 `GROUP BY`，例如统计每个值出现几次。

```sql
-- 去重
SELECT DISTINCT city FROM users;

-- 去重并统计重复次数
SELECT city, COUNT(*) AS cnt FROM users GROUP BY city HAVING cnt > 1;
```

### UNION 与 UNION ALL 的区别

- `UNION`：合并两个结果集并**去重**，内部需要排序或哈希去重，开销更大。
- `UNION ALL`：直接拼接，**不去重**，效率更高。

要求：两侧的列数相同、对应列的类型兼容（否则会隐式转换，可能导致索引失效或结果异常）。

选择原则：确定不会重复（或业务能容忍重复）时一律用 `UNION ALL`；需要去重时优先考虑"在子查询里先过滤"而不是依赖 `UNION` 去重。

```sql
SELECT id, name FROM t1
UNION ALL
SELECT id, name FROM t2;
```

### MySQL 中 in 和 exists 的区别

- `IN`：判断某个值是否在列表中（列表可以是常量集合，也可以是子查询结果）。
- `EXISTS`：判断子查询是否返回至少一行，通常写成相关子查询。

```sql
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE status = 1);

SELECT * FROM orders o
 WHERE EXISTS (SELECT 1 FROM users u WHERE u.id = o.user_id AND u.status = 1);
```

**选择原则**（注意这是经验规律，最终以 `EXPLAIN` 为准）：

- 子查询结果集小、外表大：`IN` 通常更合适（先算出小集合，再在外表上过滤）。
- 外表小、子查询表大且有索引：`EXISTS` 通常更合适（对外表每行做一次索引查找，命中即停）。
- 现代优化器会把 `IN` 子查询做半连接（semi-join）改写，二者差异被大幅抹平。

特别注意 NULL：`NOT IN` 的子查询若返回 NULL，整个条件恒为 UNKNOWN，查不出任何数据；此时应改用 `NOT EXISTS` 或 `LEFT JOIN ... IS NULL`。

### Join 算法详解

| 算法 | 原理 | 适用场景 | 版本 |
|---|---|---|---|
| NLJ（嵌套循环） | 驱动表每行，去被驱动表逐行匹配 | 通用，被驱动表无索引时效率低 | 全版本 |
| INLJ（索引嵌套循环） | 被驱动表的连接列有索引，用索引查找 | 被驱动表连接列有索引 | 全版本 |
| BNL（块嵌套循环） | 驱动表分批放入 `join_buffer`，减少被驱动表扫描次数 | 被驱动表无索引 | 全版本 |
| Hash Join | 用小表建哈希表，再扫大表探测 | 等值连接、无可用索引、大表 | 8.0.18+ |
| Batched Key Access（BKA） | 批量取驱动表键值，排序后批量回表 | 配合 MRR，减少随机 IO | 需开启 `optimizer_switch` |
| Sort-Merge Join | 两表按连接键排序后归并 | 数据已有序或可低成本排序 | 非 MySQL 常规路径 |

`EXPLAIN` 中 `Extra` 出现 `Using join buffer (hash join)` 说明用了哈希连接，`Using join buffer (Block Nested Loop)` 说明用了 BNL。

优化方向：尽量让被驱动表的连接列有索引（走 INLJ）；无法建索引时，8.0.18+ 的 Hash Join 通常优于 BNL；控制 `join_buffer_size`，避免大连接把内存吃满。

### 为什么大厂不建议使用多表 join

1. **性能不可控**：多表 JOIN 的代价随表数量与数据量非线性增长，执行计划一变就可能从毫秒级变成分钟级。
2. **可扩展性差**：分库分表后，跨库 JOIN 需要在应用层或中间件里做数据搬运，代价极高。
3. **维护成本高**：复杂 SQL 难以阅读、难以定位问题，字段变更影响面大。
4. **架构约束**：微服务强调数据自治，跨服务 JOIN 直接违反了服务边界。
5. **缓存与复用困难**：单表查询结果更容易缓存与复用。

替代策略：适度反范式（冗余常用字段）、在应用层分步查询后组装、用宽表/物化视图预计算、把检索交给搜索引擎、用 CQRS 拆分读写模型。

但也要避免教条：**同库同实例内 2~3 张小表的 JOIN 完全没问题**，甚至比多次往返更快。是否拆分要看数据量与部署形态，而不是看"是不是 JOIN"。

### 7 种 SQL 进阶用法

**1. `ORDER BY FIELD()` 自定义排序**

```sql
SELECT * FROM orders
 ORDER BY FIELD(status, 'pending', 'paid', 'shipped');
```

按给定顺序排序，未列出的值排在最前（返回 0）。

**2. NULL 值排序**

```sql
SELECT * FROM users ORDER BY age IS NULL, age;   -- NULL 排最后
SELECT * FROM users ORDER BY age IS NULL DESC, age;  -- NULL 排最前
```

**3. `CASE WHEN` 条件分支**

```sql
SELECT name,
       CASE WHEN score >= 90 THEN 'A'
            WHEN score >= 80 THEN 'B'
            ELSE 'C' END AS grade
  FROM scores;
```

**4. `GROUP_CONCAT` 分组拼接**

```sql
SELECT dept, GROUP_CONCAT(name ORDER BY name SEPARATOR ',') AS members
  FROM employees
 GROUP BY dept;
```

注意 `group_concat_max_len` 默认 1024 字节，超长会被截断。

**5. `WITH ROLLUP` 汇总行**

```sql
SELECT dept, COUNT(*) FROM employees GROUP BY dept WITH ROLLUP;
```

在结果末尾追加汇总行，汇总行的分组列为 NULL。

**6. `WITH` 公用表表达式（CTE，MySQL 8.0+）**

```sql
WITH high_scores AS (
  SELECT * FROM scores WHERE score > 90
)
SELECT * FROM high_scores WHERE student_id > 100;
```

8.0 还支持递归 CTE（`WITH RECURSIVE`），可用来查树形结构。

**7. `INSERT IGNORE` / `REPLACE` / `ON DUPLICATE KEY UPDATE`**

```sql
INSERT IGNORE INTO t (id, name) VALUES (1, 'a');          -- 冲突则跳过
REPLACE INTO t (id, name) VALUES (1, 'b');                 -- 冲突则先删后插（会触发删除语义）
INSERT INTO t (id, name) VALUES (1, 'c')
  ON DUPLICATE KEY UPDATE name = VALUES(name);             -- 冲突则更新
```

`REPLACE` 会真正删除旧行再插入，自增 ID 与触发器行为可能与预期不同；`ON DUPLICATE KEY UPDATE` 更可控。8.0.20 起推荐用行别名写法 `AS new` 代替已废弃的 `VALUES()` 函数。

### MySQL 常用函数解析

按类别整理高频函数，示例结果写在箭头后。

#### 数学函数与聚合

| 函数 | 说明 | 示例 |
|---|---|---|
| `COUNT(field)` | 统计行数（忽略 NULL） | `SELECT COUNT(1) FROM orders;` |
| `SUM(field)` | 求和 | `SELECT SUM(price) FROM orders;` |
| `AVG(field)` | 平均值（忽略 NULL） | `SELECT AVG(price) FROM orders;` |
| `ROUND(n, x)` | 保留 x 位小数（四舍五入） | `ROUND(123.4567, 2)` → 123.46 |
| `ABS(n)` | 绝对值 | `ABS(-88)` → 88 |
| `RAND()` | 0~1 随机数 | `SELECT RAND();` |

#### 类型转换

```sql
SELECT CAST('123' AS SIGNED);        -- 字符串转整数
SELECT CAST(123 AS CHAR);            -- 整数转字符串
SELECT CONVERT('2023-01-01', DATE);  -- 转日期
```

隐式转换是索引失效的常见原因：字符串列与数字比较时，MySQL 会把列转成数字，索引失效。

#### 字符串函数

| 函数 | 说明 | 示例 |
|---|---|---|
| `CONCAT(d1, d2, ...)` | 拼接，任一参数为 NULL 则结果为 NULL | `CONCAT(1,2,3,4)` → 1234 |
| `CONCAT_WS(sep, d1, ...)` | 指定分隔符拼接，忽略 NULL | `CONCAT_WS('-',1,2,3)` → 1-2-3 |
| `GROUP_CONCAT()` | 分组内拼接 | `GROUP_CONCAT(name)` |
| `DATE_FORMAT(date, fmt)` | 格式化时间 | `DATE_FORMAT('2025-03-28','%Y-%m-%d')` → 2025-03-28 |
| `LENGTH(s)` | 字节长度 | `LENGTH('123')` → 3 |
| `CHAR_LENGTH(s)` | 字符个数 | `CHAR_LENGTH('中文')` → 2 |
| `REPLACE(s, old, new)` | 替换 | `REPLACE('1234abcd','1234','aaaaa-')` → aaaaa-abcd |
| `FIND_IN_SET(s, list)` | 在逗号分隔列表中查找位置 | `FIND_IN_SET('a','b,c,a')` → 3 |
| `LOCATE(s1, s)` | 子串首次出现位置 | `LOCATE('2','123')` → 2 |

`DATE_FORMAT` 常用格式符：`%Y` 四位年、`%m` 月、`%d` 日、`%H` 24 小时、`%i` 分、`%s` 秒。

#### 日期函数

| 函数 | 说明 |
|---|---|
| `CURDATE()` | 当前日期 |
| `CURTIME()` | 当前时间 |
| `NOW()` | 当前日期时间 |
| `DATE_ADD(d, INTERVAL n unit)` | 日期加减 |
| `DATEDIFF(d1, d2)` | 相差天数 |
| `UNIX_TIMESTAMP()` / `FROM_UNIXTIME()` | 与时间戳互转 |

注意：对索引列使用 `DATE(create_time)=...` 会让索引失效，应改写为半开区间。

#### 逻辑函数

| 函数 | 说明 | 示例 |
|---|---|---|
| `IF(expr, a, b)` | 条件判断 | `IF(1=1,'成立','不成立')` → 成立 |
| `CASE WHEN` | 多分支 | `CASE WHEN score>=60 THEN 'pass' ELSE 'fail' END` |
| `IFNULL(a, b)` | 为 NULL 时取 b | `IFNULL(NULL,'111')` → 111 |
| `COALESCE(a, b, ...)` | 返回第一个非 NULL 值 | `COALESCE(NULL, 0)` → 0 |
| `NULLIF(a, b)` | 相等返回 NULL | `NULLIF(1,1)` → NULL |

### MySQL 多表查询时有哪些连接方式

| 连接类型 | 说明 | 备注 |
|---|---|---|
| `INNER JOIN` | 只返回两表都匹配的行 | 最常用 |
| `LEFT JOIN` | 返回左表全部行，右表无匹配补 NULL | 注意右表条件写在 `ON` 还是 `WHERE` 会影响结果 |
| `RIGHT JOIN` | 返回右表全部行，左表无匹配补 NULL | 可用 `LEFT JOIN` 改写，更易读 |
| `FULL OUTER JOIN` | 返回两表所有行 | **MySQL 不支持**，用 `LEFT JOIN ... UNION ALL ... RIGHT JOIN`（去重）模拟 |
| `CROSS JOIN` | 笛卡尔积 | 慎用，行数为两表行数乘积 |
| 自连接（Self Join） | 同一张表用别名关联 | 常见于层级、比较场景 |

一条容易踩坑的写法：`LEFT JOIN` 后把右表条件写在 `WHERE` 里，会过滤掉右表为 NULL 的行，等价于 `INNER JOIN`；条件应写在 `ON` 中。

## 表设计、数据类型与对象

索引与 SQL 决定"查询多快"，表结构决定"上限在哪"。这一章覆盖字段类型选择、范式与反范式、NULL 陷阱、自增 ID 耗尽、DDL 与大表清理、备份等偏"工程规范"的内容。

### 表设计经验 15 条

1. **存储引擎选 InnoDB**：支持事务、行锁、崩溃恢复。
2. **字段尽量 `NOT NULL`**：给默认值，避免三值逻辑与索引统计问题。
3. **整数类型按范围选**：`TINYINT`（1 字节）< `SMALLINT`（2）< `MEDIUMINT`（3）< `INT`（4）< `BIGINT`（8）。
4. **定长用 `CHAR`，变长用 `VARCHAR`**：长度固定且短（如身份证、状态码）用 `CHAR`。
5. **时间类型按语义选**：`DATE` 只存日期，`TIME` 只存时间，`DATETIME` 存日期时间（范围 1000-9999 年，不受时区影响），`TIMESTAMP` 存时间戳（范围 1970~2038 年，受时区影响，可自动更新）。
6. **金额用 `DECIMAL`**：`FLOAT`/`DOUBLE` 是二进制浮点，`0.1+0.2 != 0.3`。
7. **主键用自增 `BIGINT`**：避免 UUID 做主键，随机值会导致页分裂与索引膨胀。
8. **单表字段不宜过多**：经验上不超过 50 个，宽表拆到扩展表。
9. **大字段单独拆表**：`TEXT`/`BLOB` 会触发行溢出，影响主表扫描效率。
10. **适度冗余**：把高频查询需要的少量字段冗余到主表，减少 JOIN。
11. **枚举值用 `TINYINT` 或短字符串**：避免用长字符串存状态，也别滥用 `ENUM`（改枚举要 DDL）。
12. **组合索引遵循最左前缀**：按查询设计，不按字段设计。
13. **不在索引列上做函数或运算**：否则索引失效。
14. **提前规划容量**：预估数据量与增长速度，必要时分区或分库分表。
15. **命名规范**：表名、字段名用小写加下划线，避免使用保留字（如 `order`、`desc`、`key`）。

### MySQL 记录货币用什么字段类型

推荐 `DECIMAL`，它是精确的定点数类型，适合金额、价格、积分等不允许舍入误差的场景。

```sql
CREATE TABLE account (
  id      BIGINT PRIMARY KEY AUTO_INCREMENT,
  balance DECIMAL(18, 2) NOT NULL DEFAULT 0.00   -- 共 18 位，其中 2 位小数
);
```

优点：精确计算、范围可控、`SUM`/`AVG` 结果可靠。
缺点：比整型占用更多空间，运算比 `BIGINT` 略慢。

两种常见替代方案：

- **以"分"为单位存 `BIGINT`**：性能最好，展示时除以 100；适合高频交易系统。
- **多币种场景**：单独存币种字段（`CHAR(3)`），并明确"金额精度按币种不同"的规则。

不要用 `FLOAT`/`DOUBLE` 存金额：二进制浮点无法精确表示 0.1，累计误差在财务场景不可接受。

### CHAR 和 VARCHAR 的区别

| 特性 | CHAR(n) | VARCHAR(n) |
|---|---|---|
| 存储方式 | 定长，不足部分用空格补齐 | 变长，额外 1~2 字节记录实际长度 |
| 占用空间 | 固定为 n 个字符的字节数 | 按实际长度 + 长度前缀 |
| 尾部空格 | 存储时补齐，**检索时默认去掉尾部空格** | 原样保留 |
| 最大长度 | 255 个字符 | 65535 字节（受行大小限制） |
| 访问效率 | 定长便于定位，略快 | 变长需读长度前缀，略慢 |

选择建议：长度固定且较短（如 `CHAR(2)` 存省份代码、`CHAR(1)` 存性别）用 `CHAR`；长度差异大或较长的用 `VARCHAR`。`VARCHAR(255)` 与 `VARCHAR(20)` 存储相同内容时占用空间几乎一样，按真实最大长度声明即可，不必一律写 255。

注意：`CHAR` 检索时去掉尾部空格是默认行为（`sql_mode` 不含 `PAD_CHAR_TO_FULL_LENGTH` 时），因此 `CHAR` 不适合存"尾部空格有意义"的数据。

### 数据库三大范式是什么

- **第一范式（1NF）**：每列都是原子值，不可再分。例如"地址"拆成省、市、详细地址，而不是塞在一个字段里用逗号分隔。
- **第二范式（2NF）**：在 1NF 基础上，非主键列必须完全依赖整个主键，不能只依赖联合主键的一部分。
- **第三范式（3NF）**：在 2NF 基础上，非主键列不能依赖其他非主键列（消除传递依赖）。例如订单表只存 `user_id`，不存 `user_name`（用户名从用户表查）。

目的：减少冗余、避免更新异常（同一数据多处存储，改一处漏一处）、提高一致性。

实践中的取舍：互联网业务常做**反范式**设计——为减少 JOIN 与提升查询性能，刻意冗余少量字段（如订单表冗余用户名、商品快照），代价是要接受"冗余字段可能短暂不一致"，并通过业务逻辑或定时任务校准。

### 为什么不推荐使用外键

1. **性能开销**：每次写入都要检查父表是否存在，批量导入时开销明显。
2. **锁范围扩大**：外键检查会对父表记录加共享锁，高并发下增加锁冲突与死锁概率。
3. **分库分表不适用**：跨库无法维护外键约束。
4. **灵活性差**：数据迁移、归档、批量修复都要考虑约束顺序，DDL 变更也更麻烦。
5. **微服务边界**：跨服务的数据一致性应由业务保证，而不是数据库约束。

替代做法：应用层保证引用完整性（写入前校验、删除时校验或软删除），配合定时对账任务发现脏数据。

适合使用外键的场景：内部管理系统、数据模型简单、团队规模小、对开发效率的要求高于极致性能。

### NULL 的 5 个陷阱

1. **`COUNT(column)` 不统计 NULL**：`COUNT(*)` 统计行数，`COUNT(col)` 只统计非 NULL 行。
2. **比较结果为 UNKNOWN**：`NULL = NULL` 结果是 NULL 而不是 TRUE，`WHERE col = NULL` 永远查不到数据，必须用 `IS NULL` / `IS NOT NULL`。
3. **参与运算结果为 NULL**：`NULL + 1`、`CONCAT('a', NULL)` 都是 NULL，容易在报表里出现空白。
4. **聚合函数忽略 NULL**：`AVG(col)` 的分母是非 NULL 行数，`SUM` 遇到全 NULL 返回 NULL，需要 `IFNULL(SUM(x),0)`。
5. **`GROUP BY` 把 NULL 归为一组**：所有 NULL 会被合并成一个分组，`DISTINCT` 也把 NULL 视为同一个值。

补充两个更隐蔽的坑：

- **`NOT IN` 遇 NULL 恒为空**：`WHERE id NOT IN (1, NULL)` 永远不返回数据。
- **唯一索引允许多个 NULL**：见下一节。

### 唯一索引 + NULL 导致重复数据

**问题**：SQL 标准规定 NULL 不等于任何值（包括 NULL），因此唯一索引对 NULL 不做唯一性检查，同一列可以插入任意多条 NULL。

示例：

```sql
CREATE TABLE t (id BIGINT PRIMARY KEY AUTO_INCREMENT, mobile VARCHAR(20), UNIQUE KEY uk_mobile (mobile));
INSERT INTO t (mobile) VALUES (NULL), (NULL), (NULL);  -- 全部成功
```

这对"逻辑删除 + 唯一索引"是致命组合：如果把删除行的唯一列置为 NULL，就会不断累积重复数据。

三种可行方案：

**方案一：用特殊值代替 NULL**

删除时把 `mobile` 改成 `CONCAT('deleted_', id)` 这类唯一值，而不是 NULL。

**方案二：联合唯一索引 + 删除标记**

```sql
ALTER TABLE t ADD COLUMN is_deleted TINYINT NOT NULL DEFAULT 0,
  ADD UNIQUE KEY uk_mobile_del (mobile, is_deleted);
```

删除时把 `is_deleted` 设为该行 id（保证唯一），未删除行保持 0。

**方案三：生成列 + 唯一索引（推荐）**

MySQL **没有** PostgreSQL 那样的"部分索引（partial index，`CREATE INDEX ... WHERE ...`）"，网上流传的 `CREATE UNIQUE INDEX ... WHERE is_deleted = 0` 在 MySQL 上会直接语法报错。正确做法是用生成列把"未删除才参与唯一"表达出来：

```sql
ALTER TABLE t
  ADD COLUMN uk_key BIGINT GENERATED ALWAYS AS (IF(is_deleted = 0, id, NULL)) VIRTUAL,
  ADD UNIQUE KEY uk_alive (mobile, uk_key);
```

未删除行的 `uk_key` 等于 id（唯一），已删除行为 NULL（不参与唯一性检查），从而既保留历史数据又保证"存活行唯一"。

### MySQL 自增 ID 用完怎么办

MySQL 里有四种容易混淆的"ID"。

| ID 类型 | 长度 | 归属 | 用完之后 |
|---|---|---|---|
| 表的 `AUTO_INCREMENT` | 取决于列类型 | Server/InnoDB | 插入报错（`Duplicate entry` 或 `Out of range`），需扩容类型或分表 |
| InnoDB 隐藏 `row_id` | 6 字节（最大 2^48） | InnoDB | 循环复用，可能与旧行冲突，导致数据覆盖 |
| `Xid`（binlog 中的事务 ID） | 8 字节 | Server 层 | 实际不会耗尽 |
| `trx_id`（InnoDB 事务 ID） | 6 字节 | InnoDB | 循环使用，配合 ReadView 判断可见性 |

容量参考：`INT UNSIGNED` 上限约 42.9 亿，`INT` 约 21.4 亿；`BIGINT UNSIGNED` 上限约 1.8×10^19，按每天 1 亿条计算可用约 5000 亿天，实际上不会耗尽。

处理办法：

1. **预防**：主键直接用 `BIGINT UNSIGNED`，不要等到出问题再改。
2. **已用满的应急**：把列改成 `BIGINT`（`ALTER TABLE ... MODIFY id BIGINT UNSIGNED NOT NULL AUTO_INCREMENT`），大表需要用 Online DDL 或 gh-ost/pt-osc 工具。
3. **分表**：按业务维度拆分，避免单表 ID 空间耗尽。
4. **无主键表的风险**：依赖隐藏 `row_id` 的表在达到 2^48 后会循环覆盖，务必给每张表定义主键。

### 为什么不建议使用存储过程

1. **可移植性差**：语法与数据库强绑定，换库要重写。
2. **调试困难**：缺少断点、单步、日志等成熟工具。
3. **版本管理难**：难以纳入 Git 与 CI，多人协作容易冲突。
4. **可读性与维护性差**：业务逻辑散落在数据库里，排查问题要同时看应用与 SQL。
5. **扩展性差**：数据库是稀缺资源，把计算放在数据库里难以水平扩展。
6. **执行计划不可控**：复杂逻辑难以用 `EXPLAIN` 分析，出问题不好定位。

适合的场景：极高频的短事务（减少网络往返）、需要原子性的多步批处理、多个应用共享同一套数据处理逻辑、数据迁移脚本。

实践建议：核心业务逻辑放在应用层，存储过程只用于"性能极敏感且逻辑稳定"的少量场景，并纳入版本管理。

### truncate、delete、drop 的区别

| 特性 | `TRUNCATE TABLE` | `DELETE` | `DROP TABLE` |
|---|---|---|---|
| 作用 | 清空所有数据，保留表结构 | 删除满足条件的行（可全表） | 删除表结构与数据 |
| 类型 | DDL（隐式提交） | DML | DDL（隐式提交） |
| 能否回滚 | 不能 | 能（在事务内） | 不能 |
| 执行方式 | 重建表空间，按页释放 | 逐行删除并写 undo/binlog | 直接删除文件 |
| 速度 | 快 | 慢（行数越多越慢） | 最快 |
| 自增 ID | 重置为初始值 | 不重置 | 随表删除 |
| 触发器 | 不触发 | 触发 `DELETE` 触发器 | 不触发 |
| 锁 | 元数据锁 | 行锁（走索引时） | 元数据锁 |

注意：`TRUNCATE` 虽然快，但在主从复制中会整表重放，大表执行后从库可能有延迟；`DELETE` 全表会产生大量 undo 与 binlog，务必分批。

### 7 种 MySQL 大表删除方案

1. **`TRUNCATE`**：清空全表最快，不可回滚，自增 ID 重置。仅适用于"整表不要了"。
2. **`DROP PARTITION`**：分区表按分区删除，秒级完成且不产生大量 undo。**大表清理的首选**，但要求表已按时间等维度分区。
3. **表重建**：新建同结构表 → 导入要保留的数据 → `RENAME TABLE` 原子切换 → 删除旧表。适合"保留少部分数据"的场景。
4. **批量 `DELETE`**：`DELETE FROM t WHERE ... LIMIT 1000` 循环执行，每批之间 sleep 几十毫秒，避免长事务与主从延迟。
5. **`pt-archiver`**：Percona Toolkit 工具，分批归档并删除，可控制每批行数与节奏，对线上影响小。
6. **`RENAME` + 异步清理**：先 `RENAME TABLE t TO t_old, t_new TO t`，业务立即写新表，旧表在低峰期慢慢删。
7. **软删除**：加 `is_deleted` 标记，业务查询过滤，后台任务定期物理清理。适合需要保留审计痕迹的场景。

选择依据：要不要保留数据、表是否分区、能否停写、对主从延迟的容忍度。

### Online DDL：加索引/改表会不会锁表

**结论：MySQL 5.6 起支持 Online DDL，多数 `ALTER TABLE` 可以在不阻塞读写的情况下完成；5.5 及更早加索引会锁表。**

Online DDL 的执行分三个阶段：

1. **准备（prepare）**：持有 MDL 写锁，检查存储引擎能力、确定执行方式，这个阶段极短。
2. **执行（execute）**：降级为 MDL 读锁，允许并发 DML；期间对表的变更记录在 online log 中（大小受 `innodb_online_alter_log_max_size` 限制）。
3. **提交（commit）**：再次升级为 MDL 写锁，应用 online log 中的增量，替换表定义，释放锁。

两个关键参数：

| 参数 | 取值 | 含义 |
|---|---|---|
| `ALGORITHM` | `INPLACE` | 在原表上完成，不复制整表（部分操作仍需重建） |
| | `COPY` | 建临时表 + 复制数据，阻塞写入，需要额外空间 |
| | `INSTANT` | 只改元数据（8.0.12+ 支持 `ADD COLUMN`，8.0.29+ 支持在任意位置增删列），秒级完成 |
| `LOCK` | `NONE` | 允许并发读写（最优） |
| | `SHARED` | 阻塞写、允许读 |
| | `EXCLUSIVE` | 阻塞读写 |

```sql
ALTER TABLE scores
  ADD INDEX idx_student_id (student_id),
  ALGORITHM=INPLACE, LOCK=NONE;
```

注意事项：

- **不是所有 DDL 都支持 `INPLACE`**：修改列类型、改变字符集通常仍需 `COPY`，会重建表。
- **MDL 才是真正的风险点**：如果表上有长事务未提交，DDL 会一直等 MDL 写锁，同时把后面所有查询堵住。执行前先查 `information_schema.innodb_trx`，并设置 `lock_wait_timeout`（默认 31536000 秒，建议临时调小到几十秒）。
- **大表加索引仍会消耗 IO**：`INPLACE` 不阻塞 DML，但会扫全表构建索引，建议低峰期执行，必要时用 gh-ost / pt-online-schema-change。
- **8.0 的原子 DDL**：DDL 操作整体原子，崩溃后不会留下"半张表"的中间状态。

### MySQL 备份 3 种方式

| 方式 | 类型 | 说明 | 优点 | 缺点 |
|---|---|---|---|---|
| 冷拷贝（停库 `cp`/`rsync` 数据目录） | 物理 | 停库后直接复制数据文件 | 简单、恢复快 | 需要停机；运行中直接拷 InnoDB 文件会得到损坏副本 |
| `mysqldump` | 逻辑 | 导出 SQL 语句 | 可在线（`--single-transaction` 对 InnoDB 做一致性快照）、跨版本/跨平台 | 慢、恢复需重放 SQL、大库耗时长 |
| Percona XtraBackup / MySQL Enterprise Backup | 物理 | 热备份，复制数据文件并应用 redo | 在线、速度快、恢复快、支持增量 | 需额外工具、版本兼容性要求高 |

```bash
# 逻辑备份（InnoDB 一致性快照，不锁表）
mysqldump --single-transaction --routines --triggers --events \
  -u root -p mydb > mydb_$(date +%F).sql

# 物理热备
xtrabackup --backup --target-dir=/backup/full --user=root --password=***
```

选型建议：数据量小于几十 GB 且需要跨版本迁移时用 `mysqldump`；数据量大、要求快速恢复时用物理热备；无论哪种，都要定期做**恢复演练**——没有验证过的备份等于没有备份。

## 架构与高可用

单机 MySQL 的能力有上限。这一章从"一条 SQL 在 MySQL 内部怎么走"讲起，再延伸到连接池、分库分表与主从复制，帮助建立整体架构视角。

### 一条 SQL 的执行过程是怎样的

以 `SELECT` 为例，一条 SQL 会经过这些组件：

1. **连接器（connection layer）**：建立 TCP 连接、校验用户名密码与权限、分配线程；连接空闲超时由 `wait_timeout` 控制。
2. **查询缓存**：MySQL 8.0 已移除；5.7 及以前若命中则直接返回（5.7.20 起废弃）。
3. **解析器（parser）**：词法分析（识别关键字、表名、列名）与语法分析，生成解析树；语法错误在这一步报 `You have an error in your SQL syntax`。
4. **预处理器/语义检查**：检查表、列是否存在，展开 `*`，检查权限。
5. **优化器（optimizer）**：基于成本选择索引、决定 JOIN 顺序、做子查询改写（半连接、物化）、条件下推，产出执行计划。
6. **执行器（executor）**：按执行计划调用存储引擎接口，逐行取数据并做 Server 层过滤（`Using where` 就发生在这里）。
7. **存储引擎（InnoDB）**：通过 Buffer Pool 读取页，必要时从磁盘加载；返回行给执行器。
8. **返回结果**：结果写入 `net_buffer`，边读边发给客户端。

写语句（`UPDATE`/`DELETE`/`INSERT`）还要额外经过：加锁 → 写 undo（用于回滚与 MVCC）→ 修改 Buffer Pool 中的数据页（标记为脏页）→ 写 redo（prepare）→ 写 binlog → redo commit，最终由后台线程把脏页刷盘。

### 为什么需要数据库连接池

1. **避免频繁建连开销**：建立连接要做 TCP 握手、身份认证、权限加载，单次成本远高于一条简单查询。
2. **控制连接总数**：数据库的连接数上限（`max_connections`）是硬约束，连接池把并发控制在安全范围内，避免"连接打满"。
3. **复用与预热**：连接复用减少资源消耗，池中连接可保持长连接减少握手。
4. **故障检测**：通过心跳/校验 SQL 剔除失效连接，避免业务拿到坏连接。
5. **统一治理**：可在池层做超时、熔断、慢 SQL 统计。

常见实现：HikariCP（Spring Boot 默认，性能好）、Druid（监控与防护能力强）、DBCP、C3P0。

配置要点：`maximumPoolSize` 不是越大越好，经验值为"CPU 核数 × 2 + 磁盘数"，并结合数据库 `max_connections` 与实例数计算；`connectionTimeout`、`maxLifetime` 要小于数据库侧的 `wait_timeout`，避免拿到已被服务端关闭的连接。

### 说下你对分库分表的理解

当单表数据量或单库并发超过单机能力时，需要把数据分散到多个库/表。

**垂直切分**

- 垂直分库：按业务拆库（用户库、订单库、商品库），降低单库压力，符合微服务边界。
- 垂直分表：把宽表按"常用列 / 大字段"拆开，减少单行大小，提高缓存命中率。

**水平切分（Sharding）**

- 同一张表的行按规则分散到多个结构相同的表或库：按用户 ID 取模、按时间范围、按哈希。
- 分片键（shard key）的选择决定后续绝大多数查询能否路由到单分片。

**带来的问题与应对**

| 问题 | 应对 |
|---|---|
| 跨分片事务 | 尽量避免；必要时用 2PC/XA、TCC、Saga 或本地消息表实现最终一致 |
| 跨分片查询/聚合 | 广播查询后内存归并；引入宽表、ES 或数据仓库承担复杂查询 |
| 全局唯一 ID | Snowflake、号段模式（Leaf）、Redis `INCR`、数据库号段表 |
| 分页与排序 | 各分片取前 N 再归并（见"分库分表下如何精准分页"） |
| 扩容 | 一致性哈希、双倍扩容、基因法（把分片信息编入 ID） |
| 运维复杂度 | 使用 ShardingSphere、MyCat 等中间件；优先考虑"先优化再拆分" |

经验建议：单表千万级、单库连接/IO 接近瓶颈时再考虑拆分；拆分前先做索引优化、归档、读写分离与缓存。

### 分表后非分片键的查询、排序怎么处理

分片键之外的查询无法定位到单个分片，通常有四种处理方式。

1. **广播查询 + 内存归并**：向所有分片发同一条 SQL，应用层合并结果。实现简单，但分片越多越慢，需限制分片数量与返回行数。
2. **建立映射表/索引表**：例如用"订单号 → 用户 ID"的映射表（或 Redis）把非分片键查询转换成按分片键查询。
3. **冗余分片键**：在业务允许时把常用的非分片键（如商家 ID）作为第二分片维度，建"多套分片"或"基因法"把两个维度编入同一个 ID。
4. **异构索引**：把数据同步到 Elasticsearch / ClickHouse，复杂查询与排序交给搜索引擎或分析库。

排序与分页的通用做法：各分片按同一排序键取前 `offset + limit` 条，应用层归并后再截取；深度分页改用游标（记录上一页最后一条的排序键）。

### 分库分表下如何实现精准分页

跨分片分页的难点是"全局第 N 页"没法由单个分片给出。

**跨分片（同库多表）**

- **游标分页**：每页记录最后一条记录的排序键（如 `create_time + id`），下一页各分片都从"大于该键"的位置继续取，归并后截取前 N 条。优点是稳定、无深翻页问题，缺点是不能跳页。
- **归并分页**：各分片取 `offset + limit` 条，归并排序后取第 `offset` 到 `offset+limit` 条。分片多、页深时内存与网络开销大，需限制最大页数。

**跨库**

- **查询路由 + 归并**：中间件把请求分发到各库，聚合结果；适合页数不深的场景。
- **统一查询库**：把分片数据近实时同步到一个不分片的查询库（或 ES），在查询库上做分页；适合需要复杂条件与跳页的场景。
- **二次查询法**：先在各分片取 `limit` 条并记录最小/最大排序值，再按边界值做第二轮精确查询，减少数据传输量。

工程建议：产品上优先支持"下一页"而非"跳到第 N 页"；对必须跳页的场景设置页数上限（如 1000 页），超限引导用户缩小筛选条件。

### 讲讲主从复制原理与延迟

**复制流程（异步复制）**

1. 主库（source）把变更写入 binlog。
2. 从库（replica）的 I/O 线程连接主库，拉取 binlog 并写入本地 relay log（中继日志）。
3. 从库的 SQL 线程（applier）读取 relay log 并在从库重放。
4. 从库把重放进度记录在 `relay_log_info` 中，主库的 binlog 位置记录在 `master_info` 中。

相关命令：`SHOW REPLICA STATUS`（8.0.22+，旧命令 `SHOW SLAVE STATUS`），配置用 `CHANGE REPLICATION SOURCE TO`（8.0.23+，旧语法 `CHANGE MASTER TO` 已被标记废弃）。

**延迟的常见原因**

1. **从库重放能力不足**：主库并发写入高，而从库重放线程数不够（8.0 可开启并行复制并调大 `replica_parallel_workers`，并行类型按版本选择）。
2. **大事务**：一次更新百万行，主库执行 10 秒，从库也要重放 10 秒。
3. **无主键/无索引的表**：ROW 格式下从库重放要对每行做全表扫描定位，极慢。
4. **从库负载高**：从库还承担大量读请求，CPU/IO 被挤占。
5. **网络带宽与大字段**：binlog 传输慢，尤其是有大 `BLOB` 写入时。
6. **从库数量多**：主库要为每个从库各推一份 binlog，主库网络与 CPU 压力上升。

**优化手段**

- 开启并行复制并调大 worker 数；把大事务拆小；
- 所有表必须有主键；避免无索引更新；
- 从库只承担读流量并做好隔离，或增加从库分担；
- 关键业务读走主库或使用半同步复制（`rpl_semi_sync_source_enabled`）降低"读到旧数据"的概率；
- 监控 `Seconds_Behind_Source`，并对延迟设置告警。

注意：`Seconds_Behind_Source` 只是粗略指标，主库长时间无写入时会显示 0 但实际可能已滞后，更可靠的是对比 GTID 集合或心跳表。

### MySQL 有哪些高可用方案

| 方案 | 原理 | 优点 | 局限 |
|---|---|---|---|
| 主从复制 + 手动/脚本切换 | 一主多从，故障时提升从库 | 简单、成本低 | 切换有数据丢失风险，需人工或脚本介入 |
| MHA（Master High Availability） | 管理节点监控主库，故障时选最接近的从库提升并补齐差异 | 切换快、能减少数据丢失 | 项目多年未活跃维护，新架构不建议作为首选 |
| Orchestrator | 拓扑管理与自动故障转移，支持复杂复制拓扑 | 拓扑可视化、支持多种切换策略 | 需要额外部署与运维 |
| MGR（MySQL Group Replication） | 基于 Paxos 变种的一致性组复制，多数派确认 | 自动选主、强一致、无中心 | 对网络延迟敏感，配置复杂，写入受多数派影响 |
| InnoDB Cluster | MGR + MySQL Shell + MySQL Router | 官方一体化方案，含读写路由 | 组件较多，运维门槛高 |
| NDB Cluster | 共享无关（share-nothing）的内存集群 | 高可用、高吞吐 | 限制多（不支持外键等），适合特定场景 |
| 云托管 RDS/高可用版 | 云厂商提供主备切换、备份、监控 | 免运维 | 成本较高，受厂商能力约束 |

选型建议：中小规模用"主从 + 半同步 + Orchestrator/脚本切换"；对一致性要求高的核心库用 MGR/InnoDB Cluster；架构复杂或人力有限时优先考虑云托管。

无论哪种方案，都要做到：定期演练切换、监控复制延迟与磁盘空间、准备只读降级预案、保证切换后应用能自动重连（连接池 + DNS/VIP）。

### 业务系统每天增加五万条数据，预计运维三年怎么优化

先算量：5 万条/天 × 365 × 3 ≈ 5475 万条，约 5500 万。这个量级单表 InnoDB 完全可以承载，重点是"别让它变成慢查询"，而不是急着分库分表。

按优先级：

1. **表结构**：主键用 `BIGINT`，字段类型够用即可，避免大字段进主表；按查询设计索引（不要给每个字段都加）。
2. **SQL 规范**：禁止 `SELECT *`、禁止无索引更新、分页用游标、批量写入代替逐条写入。
3. **归档策略**：按时间分区或定期归档历史数据（如只保留 12 个月热数据），控制单表规模。
4. **读写分离**：报表与列表查询走从库，主库只承担写入与强一致读。
5. **缓存**：热点数据（配置、字典、首页列表）放 Redis，降低数据库读压力。
6. **监控与治理**：慢查询日志 + 定期 `EXPLAIN` 巡检 + 索引使用率分析。
7. **预留扩展**：按用户或时间维度提前设计好分片键，等到单表超过 5000 万~1 亿行时再平滑拆分。
8. **备份与演练**：每日全量 + binlog 增量，定期做恢复演练。

结论：5500 万行的关键不是"扛不住"，而是"访问方式是否合理"。先把索引、SQL、归档、读写分离做扎实，分库分表留作后手。
