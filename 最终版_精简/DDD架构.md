# DDD架构知识汇总

## DDD中的贫血模型和充血模型有什么区别？

两者都是领域模型的表现形式，**核心区别在于领域对象是否包含业务逻辑**。

#### 贫血模型（Anemic Domain Model）

**面向过程**的编程形式。实体只含数据属性及getter/setter，业务逻辑交由服务层等外部组件负责，即数据与操作分离。

- 好处：模型简单、上手快，多人协作时设计不易变形，适合轻量级应用。
- 坏处：实体无法直接体现业务能力，复杂业务中逻辑梳理困难，不利于后期演进。

#### 充血模型（Rich Domain Model）

**面向对象**的编程形式。实体既含数据属性，也含引起属性变化的核心业务动作，数据与业务能力绑定。

- 好处：符合业务人员的思考方式，对业务友好，利于封装和保护领域规则，尤其适合复杂业务。
- 坏处：对业务熟悉度要求高，需在上手之初就设计好模型实体、暴露的操作与业务逻辑；贫血模型则可边实现边修改。

若从优缺点对比：

### 1. 贫血模型

- **数据与逻辑分离**：领域对象仅含数据及访问方法（getter/setter），业务逻辑集中于服务层。
- **对象职责单一**：领域对象仅作数据容器，不含业务行为。
- **优点**：符合单一职责，领域对象只存储数据；逻辑与数据分离，便于清晰分层。
- **缺点**：违背面向对象思想，领域对象缺乏行为；业务逻辑分散在服务层，难以维护和测试。

### 2. 充血模型

- **数据与逻辑结合**：领域对象既含数据，也封装相关业务逻辑。
- **对象自治**：领域对象自主管理状态与行为，逻辑与数据紧密结合。
- **优点**：更好遵循封装、单一职责等面向对象原则；业务逻辑集中，便于维护和测试；更适合复杂业务，能更好地表达业务规则。
- **缺点**：业务逻辑多时领域对象可能变复杂；设计不当可能违反单一职责。

### 选择建议

- **贫血模型**：适合简单业务或需要清晰分层的系统。
- **充血模型**：更适合复杂业务，能更好封装业务逻辑，保持灵活性与可维护性。

贫血模型重简单易上手，充血模型重复杂业务；具体选择取决于业务需求、系统复杂度和团队技术能力。

## 在DDD中，如何处理模型的聚合和聚合根？

聚合是一组紧密关联的实体和值对象，共同完成特定业务逻辑，由聚合根统一管理。聚合根是聚合的根节点，作为对外暴露的唯一访问入口，负责管理聚合内部对象状态并协调交互。

主要步骤：

1. **识别聚合**：找出紧密关联、高内聚低耦合、业务语义一致的实体和值对象，共同构成一个聚合。
2. **定义聚合根**：选择具有全局唯一性的对象作为聚合根。例如订单聚合含订单、商品、地址、用户等实体，订单即为合适的聚合根。
3. **保证聚合内部一致性**：聚合内对象要么一起成功创建/修改/删除，要么一起失败，由聚合根协调。
4. **限制聚合外部访问**：外部只能通过聚合根访问聚合内对象。例如访问订单聚合内的商品、用户，必须经由订单实体。
5. **合理规划业务行为**：DDD强调梳理实体状态变化，不引起状态变化的操作（如查询）不必严格按聚合划分。例如统计一天内卖出的商品，可直接统计而无需先经订单聚合根。
6. **暴露聚合的服务**：在聚合根暴露领域服务或应用服务，供其他应用访问聚合内数据与逻辑，遵循统一接口规范并保证安全性。

总之，处理聚合与聚合根需仔细设计聚合组成、聚合根选择、内部关系、行为及服务暴露，以提高系统的可维护性、可扩展性和可重用性。

## 什么是领域驱动设计中的CQRS模式？

CQRS（Command Query Responsibility Segregation）将系统操作分为两类：

- **命令（Command）**：引起数据变化的操作（新增、更新、删除等），通常不返回数据，仅触发状态变化。
- **查询（Query）**：不改变数据的操作（按条件查找等），用于获取系统状态快照或特定信息，通常返回数据。

CQRS要求命令与查询分开处理，通常在两个独立部署的应用中处理，特殊情况下也可部署在同一应用的不同接口上。通过职责分离、不同数据存储和事件驱动，更好地满足性能与可伸缩性需求。

使用CQRS需注意：事务方面，命令与查询分属不同系统，需解决时间差及更新失败导致的数据不一致；查询模型方面，需解决查询接口过多的问题，可将同一领域的查询集中管理，或独立为微服务。

总之，CQRS将领域模型与查询功能分离，使复杂查询摆脱领域模型限制、以更简单的DTO形式展现，并可分离不同存储结构。虽引入额外复杂性和技能要求，但在大型复杂业务系统中，能让命令与查询拆分、领域模型与数据模型边界更清晰。

## 在DDD中，如何处理领域对象的持久化？

DDD中领域对象的持久化通常通过**仓库（Repository）**和**工厂（Factory）**实现。仓库负责领域对象在内存与持久存储（如数据库）之间的保存与检索；工厂负责从持久存储组装领域对象。

需注意：

- **定义仓库接口**：为每个需持久化的领域对象创建对应仓库接口，包含存储与检索方法；实现时可用泛型扩大适用场景。
- **通过工厂组装实体**：实体带有面向业务的特性，数据库数据带有技术特性，通过工厂让实体设计摆脱具体数据库限制，真正面向业务构建。
- **合理进行业务隔离**：数据访问与修改应通过仓库和工厂完成，而非直接访问数据库，以统一接口保证数据的完整性与一致性。
- **事务管理**：保存或检索领域对象时确保事务正确提交或回滚，保持数据一致性。
- **隔离异常**：与数据库交互产生的异常应在仓库和工厂中封装，业务异常尽量不要蔓延到领域层。

总之，仓库和工厂是两个核心概念，其设计需考虑应用需求、领域模型结构和数据访问方式，以提高系统的可维护性、可扩展性和可重用性。

## DDD的四层领域模型是怎样的？包含哪些基础概念？

1. **展现层**：向用户显示信息、解释用户命令，完成前端界面逻辑，并将请求传递给应用层。
2. **应用层**：很薄的一层，负责协调领域层中的领域对象以组成应用场景。应尽量简单，不含业务规则，不保留业务对象状态，只保留应用任务进度，注重流程性，直接依赖领域层。
3. **领域层**：业务软件的核心，包含领域对象（实体、值对象）、领域服务及其关系，负责表达业务概念、状态与规则，即领域模型。DDD强调领域层不依赖任何外部。
4. **基础设施层**：向其他层提供通用技术能力，如为应用层传递消息（API网关）、为领域层提供持久化机制（数据库资源）。

其中展现层与应用层组成前端应用，领域层与基础设施层组成后端应用，前后端通过API通信。

此外还有两个基础概念：**聚合根**代表业务对象群在领域模型中的根节点，可包含多个实体和值对象，负责管理其状态以保证整体一致性；**限界上下文**用于构建子域，每个限界上下文代表独立的业务能力或主题，包含特定的业务逻辑和数据。

## 在DDD中，如何处理跨多个实体的复杂业务？

跨多个实体的复杂业务通常交由**领域服务**协调，设计应遵循：

1. **定义服务接口**：定义清晰的接口（方法与参数），使其他模块无需关心实现细节。
2. **实现业务逻辑**：实现具体的业务逻辑，可跨越多个聚合或领域。
3. **暴露业务数据**：可向其他模块暴露部分业务数据，但需注意封装与安全，敏感数据遵循最小权限原则。
4. **尽量减少依赖**：减少对其他模块的依赖，使服务更独立、可维护。
5. **考虑可测试性**：便于进行单元测试和集成测试。
6. **定义服务调用方式**：可为本地或远程服务，远程服务需考虑网络通信、调用性能与安全。

处理跨多个实体的复杂业务是DDD的关键挑战，需深入理解业务、合理划分聚合、制定适当的领域服务与规则，并持续建模迭代。

## 如何在微服务架构中使用领域驱动设计？

1. 定义微服务边界：每个微服务对应一个限界上下文，拥有自己的领域模型和语言。
2. 用领域模型建模各微服务的核心业务逻辑，包括实体、值对象、聚合、领域服务等，并定义其关系与交互。
3. 基于领域模型明确微服务间的接口与通信协议（如HTTP/REST、AMQP）。
4. 使用事件驱动架构保证微服务间的数据同步。
5. 每个微服务拥有自己的仓库与工厂，负责数据管理与持久化。
6. 团队结构反映微服务划分，每个团队专注自己的微服务。
7. 自动化部署与运维，用监控工具跟踪微服务性能。
8. 不断迭代改进，根据反馈优化系统。

在微服务架构中使用DDD，可通过定义领域模型、识别限界上下文、设计聚合与聚合根、实现领域服务与接口、使用通信协议交互、实现数据存储等步骤，构建高质量、可维护、可扩展的微服务架构。

## DDD中的实体和值对象有什么区别？

1. **唯一性**：实体有唯一标识符，属性变化后仍是同一实体；值对象无唯一标识符，属性完全相同的两个值对象也视为不同对象。
2. **状态变化**：实体可有状态且随时间/场景变化（如订单从待支付变为已支付）；值对象通常属性固定，无状态变化。
3. **生命周期**：实体有明确生命周期（创建、更新、删除）；值对象无独立生命周期，用时创建、不用时回收。
4. **相等性**：实体以标识符判定相等；值对象以属性比较判定相等。

实体通常表示有唯一标识和状态变化的领域概念，值对象通常表示无唯一标识、不可变的属性集合。值对象形式上是一个对象，本质与一个属性值等价。

## DDD中的限界上下文是什么？有什么用？

限界上下文（Bounded Context）指一个边界内的领域模型及与之相关的语义环境，用于定义和隔离领域模型。每个限界上下文代表一个明确定义、有边界的领域模型，描述业务领域的一部分，有助于在大型系统中管理和组织复杂领域模型，保证各部分之间的一致性与清晰性。

- 它是一种语义边界，将领域模型与外部环境隔离，保证其独立性与纯净性；边界内概念和操作含义明确。
- 团队成员可据此更清晰地了解业务领域，避免使用不准确或有歧义的术语，使交流更准确高效。
- 可作为微服务设计的重要参考：限界上下文的边界往往就是微服务的边界，有助于更好地拆分和设计微服务。

总之，限界上下文有助于更好地描述和理解业务领域、提高协作效率，并作为微服务设计的重要参考。

## 请解释下什么是DDD领域驱动设计？

领域驱动设计（Domain-Driven Design，DDD）是一种软件设计方法，聚焦软件开发中的领域概念，帮助团队在复杂系统中实现业务逻辑。

- 核心思想：将实现连接到持续进化的模型，通过领域模型驱动系统设计。
- 倡导统一语言，提出实体、值对象、聚合根等一系列概念，帮助团队理解和表达业务模型。
- 目标：通过清晰的领域模型、领域语言和领域边界理解和解决业务问题；鼓励跨职能团队合作，使软件与业务需求保持一致，并能应对变化和复杂性。
- 价值：打破需求分析与系统设计之间的隔阂，使软件更灵活快速地跟随需求变化，减少误解，提高质量与可维护性；是解决复杂大型软件问题的有效方法。
