# 网络安全知识汇总

## 一、网络安全到底在保护什么

这一章先回答最基础的问题：网络安全到底在保护什么。把三个目标记住之后，后面每一种攻击手法都可以归到"它破坏了哪个目标"上。

### 1.1 计算机网络安全是什么

计算机网络安全，是指保护计算机网络及其设备、数据和服务，使其免受未授权的访问、使用、披露、破坏、干扰或篡改的一系列措施和技术。

可以用小区安保来理解：门禁决定谁能进（访问控制），保险柜保证东西不被拿走（保密性），监控录像保证东西没被动过（完整性），备用电源保证不停电（可用性）。任何单独一项都不够，需要组合使用。

行业里通常用 **CIA 三元组**（Confidentiality、Integrity、Availability，即机密性、完整性、可用性）来描述安全目标：

| 目标 | 含义 | 被破坏的典型场景 |
| --- | --- | --- |
| 机密性（Confidentiality） | 数据只被授权者看到 | 数据库被拖库、密码明文传输 |
| 完整性（Integrity） | 数据不被偷偷修改 | 转账金额在传输中被改写 |
| 可用性（Availability） | 服务在需要时能用 | 网站被打到无法访问 |

网络安全的重要性主要体现在四个方面：

1. **保护机密信息**：防止商业机密、个人隐私、财务数据等敏感信息被未授权获取和利用。
2. **维护业务连续性**：防止网络攻击和漏洞导致服务中断、系统崩溃、数据丢失，保障组织正常运营。
3. **防止经济损失**：减少网络攻击和数据泄露带来的财务损失、声誉受损和法律诉讼等风险。
4. **防范个人隐私侵犯**：保护个人敏感信息、身份和隐私免受入侵和滥用。

### 1.2 为什么写业务代码的人也要懂安全

大部分真实事故发生在应用层，而应用层代码是业务开发者写的：把用户输入拼进 SQL、把内部字段整条返回给前端、把密钥写进配置文件、依赖库几年不升级。这些都不是"运维的问题"，而是编码习惯的问题。

这里涉及两个反复出现的原则：

- **最小权限原则**（least privilege）：只给程序、账号、人员完成本职工作所必需的最小权限。这样即使某一环被攻破，损失范围也被限制住。
- **纵深防御**（defense in depth）：不指望单一措施万无一失，而是在网络、主机、应用、数据各层都设一道关卡，任何一层被突破都还有下一层。

## 二、漏洞与攻击面

这一章讲漏洞从哪里来、攻击者怎么把漏洞变成入侵，以及企业内部评估安全状况的两种常见手段。

### 2.1 零日漏洞与漏洞利用

**零日漏洞**（zero-day vulnerability）指软件、操作系统或固件中存在的、厂商尚未知晓或尚未发布修复补丁的安全漏洞。NIST 的术语表把"零日攻击"定义为利用此前未知的硬件、固件或软件漏洞发起的攻击。"零日"这个名字通常被解释为：等漏洞被公开时，厂商可用来修复的时间已经是零天。

因为补丁还不存在，攻击者可以抢先利用，而受害者在漏洞公开前往往毫不知情。

**漏洞利用**（exploit）指利用已知或未知的漏洞，通过特定的攻击代码或技术入侵系统。攻击者常针对已知漏洞编写恶意代码或工具，以获取非授权访问、执行恶意操作、窃取敏感信息、传播恶意软件等。

漏洞利用通常包括以下步骤：

1. **发现漏洞**：通过自身研究或从地下市场购买漏洞信息。
2. **编写或获取攻击代码**：根据漏洞特性和目标情况，编写或获取合适的攻击代码或工具。
3. **执行攻击**：对目标应用攻击代码，实现远程代码执行、绕过安全措施、提权、篡改数据等。
4. **控制目标系统**：利用成功后控制目标系统，以它作为继续后续攻击的据点。

可以用一扇连房东都不知道的暗门来理解零日漏洞：小偷先发现了它，房东还没听说，自然也就谈不上装锁。这也解释了为什么"漏洞公开"和"补丁可用"之间总有一段时间差。

防护上，厂商应持续发布安全补丁和更新；使用者应让软件和系统保持在受支持的版本，并配合防火墙、安全软件、最小权限等措施降低风险。需要注意，从漏洞公开到补丁真正装上的这段时间被称为"暴露窗口"，所以"及时更新"和"减少对外暴露的入口"要一起做，不能只依赖其中一项。

### 2.2 网络扫描与渗透测试

两者都是评估安全状况的手段，区别在于：扫描偏"清点门窗"，渗透测试偏"模拟小偷真的翻一次墙"。

- **网络扫描**：使用专门的扫描工具对目标网络进行主机发现和端口扫描，找出开放的入口和正在运行的服务，再比对已知漏洞信息，评估安全性。
- **渗透测试**（penetration test）：一种经授权的攻击模拟，用真实攻击者的技术和方法去验证漏洞能否被真正利用，并给出改进和修复建议。

渗透测试通常包括**信息收集**、**脆弱性分析**、**渗透攻击**、**权限提升**和**结果报告**等步骤。

必须强调合法性：这两类活动都只能在**书面授权**范围内、对自有或受托系统进行，未经授权扫描或攻击他人系统可能构成违法。对个人用户而言，对应的防护动作是：安装安全软件、定期更新补丁、不点击来源不明的链接。

## 三、身份认证：单因素、双因素与多因素

系统要先确认"你是你"，才谈得上授权。这一章讲认证的三种基本要素，以及为什么单靠密码并不够。

### 3.1 认证的三种基本要素

**认证因素**（authentication factor）指用来证明身份的一类依据，通常分为三类：

| 因素类别 | 通俗说法 | 典型例子 |
| --- | --- | --- |
| 知识因素 | 你知道什么 | 密码、PIN 码、安全问题答案 |
| 持有因素 | 你拥有什么 | 手机、硬件令牌、U 盾、智能卡 |
| 生物特征 | 你是谁 | 指纹、人脸、虹膜 |

NIST SP 800-63B 强调：多因素认证要求来自**两个不同类别**的因素；同一类别里的两样东西（例如两个密码）不算多因素。

### 3.2 单因素认证

**单因素认证**只用一种要素验证身份，最常见的是"用户名 + 密码"：只要凭证正确，就获得访问权限。

风险在于：密码一旦被猜测、撞库（拿别处泄露的账号密码批量尝试登录）、钓鱼或社工获取，攻击者就能冒充合法用户；弱密码也很容易遭受字典攻击（用常见密码字典逐个尝试）。

单因素认证像只用一把普通挂锁看门：钥匙一旦被配走，门就等于没锁。

### 3.3 双因素认证与多因素认证

**双因素认证**（2FA）要求在"用户名 + 密码"（第一因素，属于知识因素）之外，再提供一个**不同类别**的第二因素，例如手机验证码、硬件令牌、指纹或人脸。这样即使攻击者拿到了密码，也过不了第二关。

**多因素认证**（MFA）是更宽的说法：两个及以上不同类别的因素都算。

几个实践中容易搞错的点：

- 手机短信验证码属于持有因素，但存在 SIM 卡被补办、号码被转移等风险。NIST SP 800-63B 把基于公共电话网的带外认证标注为**受限使用**，并要求校验号码与具体设备的绑定关系；语音电话和邮件不能用于带外认证。
- 指纹、人脸等生物特征本身只提供"你是谁"这一因素。按 NIST 的观点，生物特征要与一个物理认证器（例如手机）配合使用，单独使用不视为一个完整的认证器。
- 一次性验证码（OTP）必须一次性使用，并配合失败次数限流，否则可能被暴力枚举。

双因素认证已成为银行、邮箱、社交媒体、云服务等的常见安全措施，能显著降低身份盗用和未授权访问的风险。

### 3.4 在 Java 项目里怎么落地

1. 密码只存哈希，不存明文。OWASP 的建议是优先使用 Argon2id，其次 scrypt；bcrypt 主要用于遗留系统且工作因子不低于 10；需要 FIPS 合规时用 PBKDF2-HMAC-SHA256，迭代次数 60 万以上。MD5、SHA-1、SHA-256 这类"快"哈希不适合存密码。
2. 每个密码使用独立的随机盐（主流密码库内部已自动处理）。
3. 登录失败要限流；改密码、换绑手机等敏感操作要二次验证。
4. 第二因素优先选 TOTP（基于时间的一次性密码，通常每 30 秒生成一次、常见为 6 位数字）或硬件密钥，短信作为兜底方案。

```java
// 使用 Spring Security 的 BCrypt，仅示意"注册存哈希、登录比对"的写法
PasswordEncoder encoder = new BCryptPasswordEncoder(12);

String hash = encoder.encode(rawPassword);        // 注册：数据库里存 hash
boolean ok = encoder.matches(rawPassword, hash);  // 登录：比对明文与哈希
```

## 四、加密基础：对称与非对称

**加密**（encryption）是把明文变换成密文的过程，**密钥**（key）是参与变换的那串秘密数据。这一章讲两类加密算法的分工，以及 HTTPS 为什么两者都用。

### 4.1 对称加密

**对称加密**使用同一把密钥加密和解密：发送方用密钥把消息加密，接收方用同一把密钥还原明文。代表算法是 AES（Advanced Encryption Standard，高级加密标准），常见密钥长度为 128、192、256 位。

- 优点：速度快，适合加密大量数据。
- 难点：密钥怎么安全地送到对方手里；密钥一旦泄露，用它加密过的历史数据也可能被解开。

对称加密像一把既能锁门又能开门的钥匙，麻烦之处在于必须先把钥匙安全地交给对方。

### 4.2 非对称加密

**非对称加密**（也叫公钥加密）使用一对密钥：公钥可以公开分发，私钥由自己保管。发送方用接收方的公钥加密，接收方用自己的私钥解密。代表算法是 RSA 和 ECC（椭圆曲线密码）。

- 优点：不需要事先共享密钥，只要私钥不泄露，就解决了密钥分发问题。
- 缺点：计算量大、速度慢，通常只用于加密少量数据或做数字签名。

非对称加密像门口的信箱投递口：谁都能把信投进去（公钥），但只有拿着钥匙的主人才取得出来（私钥）。

### 4.3 混合加密：实际系统的做法

只用对称加密解决不了密钥分发，只用非对称加密又太慢，于是实践中把两者结合：**用非对称加密安全地协商出一把临时的对称密钥，再用对称加密算法保护真正的业务数据**。HTTPS 就是这样做的。

| 维度 | 对称加密 | 非对称加密 |
| --- | --- | --- |
| 密钥 | 加解密用同一把 | 公钥加密、私钥解密 |
| 速度 | 快 | 慢 |
| 典型用途 | 批量数据加密 | 密钥交换、数字签名 |
| 代表算法 | AES、ChaCha20 | RSA、ECC |

## 五、安全协议与 TLS

这一章讲协议层面的保障：网络上传的数据怎样做到"别人看不懂、改不了、冒充不了"。重点是网页和接口背后的 TLS。

### 5.1 安全协议要解决的四个问题

**网络安全协议**是为保障网络中数据传输安全性和可靠性而制定的规范，包含加密、认证、访问控制和数据完整性等机制，用于防止未授权访问、数据篡改和窃听。

主要目标：

- **保密性**：通过加密确保数据只被合法接收方读取。
- **完整性**：通过数据摘要、数字签名等确保数据未被篡改。
- **认证与鉴别**：通过身份验证和合法性检查，确认通信双方的身份和权限。
- **不可否认性**：可追踪并证明通信双方的行为，防止事后否认。

常见协议：

| 协议 | 工作层次 | 典型用途 |
| --- | --- | --- |
| TLS（及其前身 SSL） | 应用层与传输层之间 | 网页、接口、邮件等的加密传输 |
| IPsec | 网络层（IP 层） | 站点间 VPN、加密 IP 数据包 |
| SSH | 应用层 | 远程登录、安全文件传输 |

### 5.2 SSL 与 TLS 是什么关系，哪些版本还能用

SSL 和 TLS 是同一脉的加密协议：SSL 由 Netscape 在 20 世纪 90 年代提出，TLS 是 IETF 接手后的标准化版本。今天说"SSL 证书""SSL 加密"，实际使用的几乎都是 TLS。

版本现状需要注意，很多旧资料没有更新这一点：

- SSL 2.0、SSL 3.0 均已不安全。IETF 在 RFC 7568（2015 年）中明确要求 **SSL 3.0 不得使用**，也不允许从任何 TLS 版本回退到 SSL 3.0。
- TLS 1.0、TLS 1.1 已在 RFC 8996（2021 年）中被正式弃用，规定**不得协商使用**。
- 当前应至少使用 TLS 1.2，并优先 TLS 1.3（RFC 8446，2018 年）。

### 5.3 TLS 的作用

TLS 的作用是在客户端和服务器之间建立一条安全通道，提供三件事：

1. **机密性**：数据加密传输，中间人看不到内容（TLS 不隐藏报文长度，只能通过填充等方式缓解流量分析）。
2. **完整性**：数据被改动会被发现。
3. **身份认证**：客户端通过证书验证服务器身份；启用双向认证时，服务器也验证客户端。

### 5.4 握手与数据传输：分版本理解

**握手**（handshake）是正式传数据前的协商过程：双方确认协议版本、选定加密算法、验证证书、协商出会话密钥。可以理解为进门前先对暗号：暗号对上了才开门，之后用这次对出来的临时口令说话，说完即弃。

旧资料里常见的描述是下面这条路径，它对应 **TLS 1.2 及更早版本中的 RSA 密钥交换**：

1. **握手阶段**：客户端发送自己支持的加密算法列表；服务器选定一种双方都支持的算法并返回证书。客户端验证证书合法性，生成一个随机数（预主密钥）作为对称密钥的原料，用服务器证书里的公钥加密后发给服务器。
2. **密钥交换阶段**：服务器用自己的私钥解密，得到同样的密钥原料，双方各自推导出相同的会话密钥。
3. **数据传输阶段**：此后双方用这把对称密钥加密通信，并用消息认证码（MAC，message authentication code，用于校验数据是否被篡改）或带认证的加密算法验证数据完整性。

这里需要更正并补充两点，否则容易理解成一个"永恒的流程"：

- **这条 RSA 路径在 TLS 1.3 中已被删除。** RFC 8446 明确移除了静态 RSA 和静态 DH 密钥交换，只保留基于 (EC)DHE 或 PSK 的方式，所有公钥密钥交换都具备前向安全性（forward secrecy，指长期私钥日后泄露也解不开此前录下的流量）。因此在 TLS 1.3 里不存在"客户端用服务器公钥加密预主密钥"这一步：双方各自生成临时参数、交换后算出共享密钥。
- TLS 1.3 只允许 AEAD（Authenticated Encryption with Associated Data，带关联数据的认证加密，如 AES-GCM、ChaCha20-Poly1305）类算法，加密与完整性校验一次完成；ServerHello 之后的握手消息也全部加密。TLS 1.2 则既有"加密 + HMAC"的组合，也支持 AEAD。

### 5.5 怎么配：一个 Spring Boot 例子

服务端只启用 TLS 1.2 与 TLS 1.3，并挑选支持前向安全的套件：

```yaml
server:
  port: 8443
  ssl:
    enabled: true
    key-store: classpath:keystore.p12
    key-store-type: PKCS12
    key-store-password: ${SSL_KEYSTORE_PASSWORD}
    enabled-protocols: TLSv1.3,TLSv1.2
    ciphers:
      - TLS_AES_256_GCM_SHA384
      - TLS_CHACHA20_POLY1305_SHA256
      - TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384
```

部署后可以用 openssl 客户端确认实际协商到的版本与套件（示例域名为占位，换成自己的域名）：

```bash
openssl s_client -connect example.com:443 -tls1_3 -brief
```

### 5.6 进阶了解（可跳过）

初学可略过本节，不影响后续阅读。前向安全性意味着即使服务器私钥将来泄露，攻击者也无法解密此前录下的流量，这是 TLS 1.3 只保留 (EC)DHE 的原因。TLS 1.3 还提供 0-RTT（零往返）模式，可在恢复连接时立刻发送数据以省一个往返，代价是这部分早期数据可能被重放，因此只应用于幂等的请求。

## 六、经典攻击手法

这一章汇总最常见的几类攻击：它们各自破坏了哪个安全目标，以及开发时怎么防。

### 6.1 SQL 注入

**是什么**：SQL 注入（SQL injection）指应用程序把不可信的用户输入当成 SQL 语句的一部分拼接执行，让攻击者得以改写查询逻辑、执行未经授权的数据库操作。

**为什么危险**：一旦成功，攻击者可能读取、修改或删除数据；在数据库账号权限足够时，还可能执行管理操作、读写服务器文件，甚至执行系统命令。典型后果是数据泄露（俗称"拖库"）、数据篡改和拒绝服务。

先看一段错误写法（仅作反例）：

```java
// 错误：把用户输入直接拼进 SQL
String sql = "SELECT balance FROM account WHERE user_name = '" + name + "'";
Statement st = conn.createStatement();
ResultSet rs = st.executeQuery(sql);
// 若 name 传入 a' OR '1'='1 ，条件恒真，将返回所有账户
```

**怎么防**：

1. **参数化查询或预编译语句（首选）**：SQL 结构固定，用户输入只作为参数绑定，永远不会变成语法。

```java
String sql = "SELECT balance FROM account WHERE user_name = ?";
try (PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.setString(1, name);            // 输入只会被当作值，不会被当作代码
    try (ResultSet rs = ps.executeQuery()) {
        // 处理结果
    }
}
```

2. **白名单校验**：表名、列名、排序方向（ASC/DESC）这类"结构"无法用占位符参数化，应把它们映射到代码里固定的几个取值，其它一律拒绝。
3. **最小权限**：应用连数据库的账号只给必需权限，不要用 DBA 账号；只读业务就配只读账号。
4. **输入验证与输出编码**：类型、长度、格式校验作为纵深防御的一层。

这里需要更正一条流传很广的建议：OWASP 明确**不推荐手工转义**用户输入来拼 SQL。不同数据库方言的转义规则不同、容易漏字符，正确做法是参数绑定；手工转义只能作为无法参数化时的最后手段，而不能当作主要防线。

### 6.2 中间人攻击（常被称作"三明治"攻击）

**是什么**：中间人攻击（Man-in-the-Middle，MITM）指攻击者插入通信双方之间，拦截并转发流量，使双方都以为在和对方直接通信，同时监听、窃取或修改通信内容。

"三明治攻击"在安全语境中通常就是中间人攻击的通俗说法——攻击者像夹在两片面包中间的那层馅。需要注意，这个名称并非标准化术语，在不同领域（例如区块链交易）含义完全不同，看到时要结合上下文判断。

中间人攻击就像寄信途中被人拆开偷看、改几个字，再重新封好转交，收寄双方都不知情。

**常见场景**：咖啡店、机场等公共 Wi-Fi。攻击者搭建一个与正规热点同名的假热点诱导用户连接，此后流量都经过攻击者，从而窃取登录凭证、银行账户等敏感信息；此外，DNS 劫持、ARP 欺骗（伪造局域网内的地址映射）也常被用来把流量引向攻击者。

**怎么防**：

1. 使用 HTTPS 等加密协议，确保传输加密；客户端要真正校验证书，不要在代码里图省事关掉证书校验。
2. 避免在公共 Wi-Fi 上发送敏感信息，尤其是金融或个人账户数据。
3. 使用可信的 VPN 建立加密隧道。
4. 选择已知可信的网络和访问点，注意同名热点的拼写差异。
5. 定期更新操作系统和安全补丁。
6. 使用强密码并启用多因素认证。

### 6.3 DoS 攻击

**拒绝服务攻击**（Denial of Service，DoS）指通过向目标系统或网络发送大量请求、数据包或恶意指令，耗尽它的资源，使其无法正常提供服务或崩溃。

DoS 通常由单台或少数几台计算机发起。攻击者占用目标系统的带宽、连接数、处理能力等关键资源，导致合法用户无法访问，可能造成服务中断、响应延迟或系统崩溃。

常见方式包括：

- **流量洪泛**：例如 SYN Flood——只发送 TCP 连接请求的前半步、不完成三次握手，把服务器的连接表占满。
- **反射放大**：伪造源地址向第三方发起请求，让大量应答涌向目标（例如历史上利用 ICMP 广播的 Smurf 攻击）。
- **资源耗尽**：大量消耗 CPU、内存、磁盘或数据库连接。

近年来，利用未受保护的智能设备（IoT）发起的 DoS 也很常见，这些被感染的设备群俗称**僵尸网络**（botnet，指被攻击者远程操控的一批设备）。

**防御**：配置防火墙、入侵检测系统、负载均衡、流量清洗和限流；对接口做限流与熔断；及时修补漏洞；加强安全意识培训。

### 6.4 DDoS 攻击

**分布式拒绝服务攻击**（Distributed DoS，DDoS）是 DoS 的规模化版本：攻击者控制网络上的多台被感染设备组成僵尸网络，协调它们同时向目标发起攻击，使目标在容量上无法承受，导致资源耗尽、服务不可用或响应极慢。

CISA 的分析里有两个要点值得记住：一是僵尸网络常由弱口令、缺少维护的物联网设备组成，规模可达数十万台，设备主人往往毫不知情；二是 DDoS 除了直接打瘫服务，还常被当作"烟雾弹"——攻击者在别处实施真正的入侵，用 DDoS 转移防守方的注意力。

**应对措施**：

1. 使用专业的 DDoS 防护设备或云清洗服务，检测并过滤恶意流量。
2. 配置防火墙、入侵检测系统及流量限制和过滤规则。
3. 增加带宽并具备弹性扩容能力，以承受更大流量压力。
4. 监控网络流量和系统性能，及时发现并处理异常。

### 6.5 网络钓鱼与钓鱼网站

**网络钓鱼**（phishing）是一种欺诈手段：攻击者伪装成银行、支付机构、公司 IT 部门等可信实体，通过邮件、短信、社交软件等引诱用户提供账号密码、验证码，或直接转账。**钓鱼网站**则仿冒合法网站的页面，外观高度相似，用于骗取账号、密码、银行卡信息。

钓鱼攻击利用的是**社会工程学**（social engineering），即利用人的信任、恐惧、好奇、从众等心理弱点，而不是技术漏洞。攻击者诱导用户点击链接、填写表单或下载附件，进入钓鱼网站输入敏感信息；由于页面设计巧妙，不易察觉，成功率往往较高。

**怎么防**：

1. 对陌生发件人和可疑消息保持警惕，尤其警惕带"紧急""限时""账户将被冻结"字样的内容。
2. 验证发件人身份：核对邮箱域名拼写，必要时通过电话等其他渠道确认。
3. 不轻易点击链接，先把鼠标悬停看清真实地址；访问重要站点时直接手动输入域名。
4. 注意一点：页面带 HTTPS 和有效证书只说明"传输是加密的"，并不等于"站点可信"，如今不少钓鱼站点也部署了证书。判断可信度要看域名、主体资质和其他佐证。
5. 定期更新防火墙、反病毒和反钓鱼工具，开启浏览器与邮件网关的钓鱼拦截。
6. 提高安全意识，形成习惯，例如任何索要短信验证码的请求都先当作可疑处理。

## 七、恶意软件

这一章看"跑在机器里的敌人"：恶意软件有哪些家族、各自怎么传播，以及为什么蠕虫特别难缠。

### 7.1 什么是恶意软件

**恶意软件**（malware）指具有恶意意图的软件，目的是破坏系统、窃取信息或滥用系统资源，通常在用户不知情的情况下被安装或执行。

### 7.2 六种常见类型

| 类型 | 核心特征 | 主要危害 |
| --- | --- | --- |
| 病毒（virus） | 需要寄生在文件或程序中，靠用户运行被感染的文件传播 | 损坏或删除文件、破坏系统，或等待特定条件触发 |
| 蠕虫（worm） | 能自我复制并通过网络自动传播，不需要宿主程序 | 网络拥塞、资源耗尽、服务中断 |
| 木马（trojan） | 伪装成正常软件，诱导用户安装 | 后台盗取信息、开启远程控制后门 |
| 间谍软件（spyware） | 潜伏在设备上监视用户活动 | 记录键盘输入、窃取资料，甚至调用摄像头与麦克风 |
| 广告软件（adware） | 大量推送广告并收集用户画像 | 干扰正常使用、隐私泄露 |
| 勒索软件（ransomware） | 加密用户文件并索要赎金 | 数据不可用、业务停摆、被迫支付 |

**传播途径**包括虚假链接、被感染的文件、系统或应用漏洞、垃圾邮件附件，以及来路不明的破解软件。

**防护**：安装可信的安全软件并保持更新；定期更新系统和应用；谨慎打开陌生文件和链接；重要数据定期做离线备份——面对勒索软件，可用的备份往往是最有效的一道防线。

### 7.3 蠕虫为什么比病毒更难缠

**蠕虫**是一种能自我复制并独立传播的恶意软件。

与病毒不同——病毒需要依附宿主程序、靠人运行才传播——蠕虫利用网络漏洞直接感染其他计算机：一旦某台设备被感染，它会自动扫描并尝试感染下一个存在同样漏洞的目标，整个过程不需要用户点击任何东西。

病毒像必须搭便车才走得了的乘客，蠕虫则像自己长了脚、还会挨家敲门的访客。

因此蠕虫常导致大规模网络拥塞、资源耗尽和服务中断，扩散速度远快于依赖人工触发的恶意软件。它还会留下后门、开启远程访问权限，为后续的数据窃取、系统瘫痪或更大规模攻击铺路。

**防范**：及时更新操作系统和应用以修补漏洞（这是切断传播链最关键的一步）；使用防病毒软件和防火墙检测、阻断；定期备份重要数据；遵循基本安全实践，例如强密码、限制不必要的远程访问、关闭不用的端口。

## 八、检测与防御

前面几章讲的是"会被怎么打"，这一章讲"怎么发现"和"日常该做什么"。

### 8.1 IDS 是什么

**IDS**（Intrusion Detection System，入侵检测系统）是监测并识别网络中恶意活动和入侵行为的安全设备或软件，通过收集和分析网络流量、日志和事件数据来发现潜在入侵。

关键是分清职责：IDS 负责**发现和告警**，一般不主动阻断；负责阻断的是 IPS（Intrusion Prevention System，入侵防御系统），可以理解为 IDS 加上"能动手"的能力。

常见检测思路：

- **基于签名**：比对已知攻击的特征，准确但只能发现见过的攻击。
- **异常行为分析**：先建立正常行为基线，偏离基线就告警，能发现未知攻击，但误报相对多。
- **统计分析**：用阈值、频率等统计模型识别异常流量。

按部署位置主要分为两类：

| 类型 | 部署位置 | 能看到什么 | 局限 |
| --- | --- | --- | --- |
| 网络型 IDS（NIDS） | 网络关键节点，如交换机镜像口、边界出口 | 网络层与传输层的数据包，可发现扫描、攻击流量和异常连接 | 加密流量看不到内容 |
| 主机型 IDS（HIDS） | 单台主机或服务器上 | 系统调用、文件变更、应用日志 | 只覆盖本机，且占用主机资源 |

可以用摄像头来类比：NIDS 像小区门口的监控，看谁进出；HIDS 像每户门上的门磁和报警器，看屋里发生了什么。

### 8.2 Java 后端开发者的日常防护清单

1. **依赖安全**：定期用 OWASP Dependency-Check 或构建工具的安全插件检查第三方库，及时升级存在已知漏洞的版本。
2. **输入校验与输出编码**：所有外部输入（请求参数、请求头、上传文件名、第三方回调）都视为不可信；SQL 用参数绑定，页面输出做 HTML 编码。
3. **最小权限**：数据库账号、对象存储账号、服务间调用账号都按需授权；不要把管理员凭证写进代码或配置文件。
4. **密钥与配置管理**：密钥放环境变量或密钥管理服务，不要进代码仓库，并定期轮换。
5. **限流与熔断**：对公开接口按 IP、用户、接口维度限流，配合熔断和降级，降低被 DoS 打瘫的概率。
6. **日志与告警**：记录登录、权限变更、敏感数据访问等关键事件；日志中不要打印密码、身份证号、完整卡号等信息。
7. **安全响应**：发现异常时先隔离（下线接口、封禁来源），再定位原因，最后补上检测规则和回归用例。

## 九、网络隐私

这一章从个人视角收尾：网络上"关于我的信息"归谁管、怎样少泄露。

### 9.1 网络隐私包括什么

**网络隐私**指个人在使用互联网和网络服务时，对**个人身份**、**个人信息**和**在线活动**的保护权利。

内容包括：

- 个人身份和个人信息的保护；
- 数据安全的保障，即存储与传输过程中不被窃取；
- 公开信息的选择权：哪些信息可以被收集、被谁使用、用于什么目的；
- 对跟踪与监视的防范，例如浏览记录、位置信息、设备指纹。

### 9.2 怎么保护

- **账号侧**：使用强密码并配合密码管理器；开启多因素认证；不同站点不复用密码。
- **设备侧**：及时更新系统和应用；只从可信来源安装软件；关闭不必要的权限。
- **行为侧**：谨慎对待不可信链接和附件；少在公开平台填写真实敏感信息；定期检查应用的隐私设置。
- **传输侧**：优先使用加密连接；在公共网络上避免处理敏感业务。
- **制度侧**：个人信息保护相关的法律与监管要求在持续完善，组织应建立数据分级、最小收集、告知同意等流程。

保护网络隐私对个人和组织都至关重要：它关系到个人隐私权与个人信息安全，也关系到商业机密、数据安全，以及用户信任和组织声誉的维护。
