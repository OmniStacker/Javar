## 一、设计模式基础

这一章先建立共同语言：什么是模式、为什么值得学、23 种模式分别解决哪类问题。后面的具体模式都建立在这套分类之上。

### 1.1 什么是设计模式

设计模式（Design Pattern）是软件设计中常见问题的可复用解决方案模板。它描述的是一组相互协作的类和对象如何分工，而不是一段可以原样粘贴的代码。GoF（Gang of Four，四人组）在 1994 年的《设计模式》一书中把模式拆成四个要素：

- **名称**：团队沟通时使用的词汇，例如“这里用策略模式”。
- **问题**：在什么场景下会遇到，需要满足哪些约束。
- **解决方案**：类与对象的职责、协作关系和调用顺序。
- **效果**：采用之后得到什么、牺牲什么，例如灵活性提升但类数量增加。

需要强调的是，模式不是语法特性，也不是越用越高级。它是对“变化点”的封装经验；如果代码里没有对应变化，套用模式只会增加理解成本。

### 1.2 为什么使用设计模式

使用设计模式的主要原因可以归纳为五点：

1. **可重用性**：把经过验证的协作方式复用到不同项目，避免重复踩坑。
2. **可维护性**：把职责和关注点分开，减少类与类之间的硬编码依赖。
3. **可扩展性**：新增行为时尽量只加类、不改调用方，符合开闭原则（对扩展开放、对修改关闭）。
4. **共享经验**：模式名称本身就是对设计意图的压缩表达。
5. **提高沟通效率**：说“用观察者解耦”比临场解释一大段回调注册逻辑更快。

但模式也有成本：抽象层变多、调用链变长、调试更绕。合理的做法是先用简单代码跑通，确认变化方向后再重构出模式，而不是一开始就摆出完整模式骨架。

### 1.3 GoF 23 种模式与三大分类

GoF 按“模式解决哪类问题”把 23 种模式分成三组：创建型 5 种、结构型 7 种、行为型 11 种。这个数量划分是核对分类是否完整的基准。

| 分类 | 模式（英文） | 一句话意图 |
| --- | --- | --- |
| 创建型（5） | 单例 Singleton | 保证一个类只有一个实例，并提供全局访问点 |
| 创建型 | 工厂方法 Factory Method | 定义创建对象的接口，由子类决定实例化哪个类 |
| 创建型 | 抽象工厂 Abstract Factory | 创建一系列相关或相互依赖的对象族，而不指定具体类 |
| 创建型 | 建造者 Builder | 把复杂对象的构建过程与表示分离，同样的过程可造出不同表示 |
| 创建型 | 原型 Prototype | 通过复制已有实例来创建新对象 |
| 结构型（7） | 适配器 Adapter | 把一个类的接口转换成客户端期望的另一个接口 |
| 结构型 | 桥接 Bridge | 把抽象部分与实现部分分离，使二者可以独立变化 |
| 结构型 | 组合 Composite | 把对象组合成树形结构，让单个对象和组合对象被一致对待 |
| 结构型 | 装饰器 Decorator | 动态地给对象添加职责，而不改变其类结构 |
| 结构型 | 外观 Facade | 为子系统提供统一的高层接口，简化客户端使用 |
| 结构型 | 享元 Flyweight | 共享大量细粒度对象，减少内存占用 |
| 结构型 | 代理 Proxy | 为其他对象提供代理以控制对该对象的访问 |
| 行为型（11） | 责任链 Chain of Responsibility | 让多个处理器依次尝试处理请求，直到被处理或链结束 |
| 行为型 | 命令 Command | 把请求封装成对象，从而支持参数化、排队、记录和撤销 |
| 行为型 | 解释器 Interpreter | 给定语言，定义其文法表示及解释器 |
| 行为型 | 迭代器 Iterator | 顺序访问聚合元素，而不暴露其内部表示 |
| 行为型 | 中介者 Mediator | 用中介对象封装一组对象之间的交互，减少直接依赖 |
| 行为型 | 备忘录 Memento | 在不破坏封装的前提下保存并恢复对象状态 |
| 行为型 | 观察者 Observer | 定义一对多依赖，主题状态变化时通知所有观察者 |
| 行为型 | 状态 State | 对象内部状态改变时改变其行为，看起来像换了类 |
| 行为型 | 策略 Strategy | 把一系列算法封装成可互相替换的策略 |
| 行为型 | 模板方法 Template Method | 在父类定义算法骨架，把部分步骤延迟到子类实现 |
| 行为型 | 访问者 Visitor | 在不改变元素类的前提下，为元素增加新的操作 |

几个容易混淆或漏项的地方需要特别说明：

- **模板方法属于行为型**，不是结构型；它关注的是算法步骤在继承体系中的分配。
- **原型属于创建型**；`clone()`、拷贝构造器等都是它的实现手段。
- **结构型完整是 7 种**，除常见的适配器、装饰器、代理、外观外，还包括桥接、组合、享元。
- 口语里的“工厂模式”通常泛指“简单工厂 + 工厂方法”。其中**简单工厂**（用一个工厂类加 `switch`/`if` 创建不同产品）是常见编程习惯，但**不属于 GoF 23 种模式**；GoF 的工厂方法强调“子类决定创建哪个产品”。

### 1.4 学习与选用原则

学习模式时，建议按“问题 → 角色 → 代价”的顺序记，而不是背 UML（统一建模语言）图。选型时可以问自己四个问题：

1. 这里真正会变化的是什么：对象创建、对象组合，还是对象间的通信？
2. 变化发生时，希望改一处还是改多处？如果必须改多处，说明抽象位置不对。
3. 新增的抽象是否有人使用？只有一个实现的接口通常不值得抽。
4. 团队里其他人能否只看类名就猜出意图？命名比图更重要。

## 二、创建型模式

创建型模式处理“对象怎么来”的问题。它们把 `new` 的细节从调用方移走，让系统在“创建哪个类、创建多少、如何复用”上更灵活。本章覆盖 GoF 的全部 5 种创建型模式。

### 2.1 建造者模式（Builder）

#### 要解决什么问题

当一个对象有很多可选参数，或者构建过程必须按固定步骤执行时，构造函数会迅速膨胀：要么写出一长串重载，要么出现 `new User("a", 0, null, false, true, ...)` 这种“参数是什么全靠猜”的调用。建造者模式把“设置参数”和“最终创建”分开，让构建过程可读、可控，也更容易保证对象不可变。

#### 生活化比喻

像在快餐店点套餐：汉堡、饮料、小食可以逐项选择，店员按固定流程组装，最后交给你一个完整套餐。你不需要一次报出所有配料，也不需要知道后厨怎么打包。

#### 结构与角色

- **产品（Product）**：最终要构建的复杂对象。
- **抽象建造者（Builder）**：定义构建产品的各个步骤，通常是链式方法。
- **具体建造者（Concrete Builder）**：实现步骤，保存中间状态，并提供 `build()` 返回产品。
- **指导者（Director）**：可选，负责按某个固定顺序调用建造步骤，适合多种“套餐组合”。

#### 可运行 Java 示例

```java
public final class User {
    private final String name;
    private final int age;
    private final String email;
    private final boolean vip;

    private User(Builder builder) {
        this.name = builder.name;
        this.age = builder.age;
        this.email = builder.email;
        this.vip = builder.vip;
    }

    public static Builder builder(String name) {
        return new Builder(name);
    }

    public static final class Builder {
        private final String name;
        private int age;
        private String email = "";
        private boolean vip;

        private Builder(String name) {
            if (name == null || name.isBlank()) {
                throw new IllegalArgumentException("name 不能为空");
            }
            this.name = name;
        }

        public Builder age(int age) {
            this.age = age;
            return this;
        }

        public Builder email(String email) {
            this.email = email;
            return this;
        }

        public Builder vip(boolean vip) {
            this.vip = vip;
            return this;
        }

        public User build() {
            return new User(this);
        }
    }

    @Override
    public String toString() {
        return "User{name='" + name + "', age=" + age
                + ", email='" + email + "', vip=" + vip + '}';
    }
}

class BuilderDemo {
    public static void main(String[] args) {
        User user = User.builder("user_a")
                .age(20)
                .email("user_a@example.com")
                .vip(true)
                .build();
        System.out.println(user);
    }
}
```

如果一类对象有几种固定搭配，可以再加一个 `Director`，把“先设 A 再设 B”的顺序封装起来；只有一个调用点时直接用链式 Builder 更简单。

#### 何时用、何时别用

适合：参数较多且可选、需要构建不可变对象、构建步骤有先后约束、同一条构建流程要产出不同表示（例如不同风格的文档、游戏中不同种类的角色）。

不适合：只有两三个必填参数、对象本身简单、构建过程没有复用价值。此时普通构造函数或静态工厂方法更直观。

#### 常见误用

- 给两三个字段的类也套 Builder，代码量翻倍但可读性没有提升。
- Builder 被重复使用却没重置状态，第二次 `build()` 带上了上一次的字段。
- `build()` 只做 `new`，所有校验都放在 setter 里，导致半成品状态可以存在。校验应尽量前移，`build()` 里再做一次整体校验。
- 产品仍暴露 setter，Builder 的“不可变”优势就消失了。

### 2.2 工厂方法模式（Factory Method）

#### 要解决什么问题

调用方直接 `new EmailNotification()`、`new SmsNotification()` 时，每新增一种实现都要改调用方，而且调用方被迫知道具体类名。工厂方法把“创建”抽成一个方法，由子类决定实例化哪个产品，调用方只依赖产品接口。

#### 生活化比喻

像连锁咖啡店：总部规定“下单后给顾客一杯现做饮品”的流程，具体做美式还是拿铁由各门店决定。顾客只认“咖啡”这个接口，不需要知道门店用哪台机器。

#### 结构与角色

- **产品（Product）**：客户端使用的接口。
- **具体产品（Concrete Product）**：不同实现。
- **创建者（Creator）**：声明工厂方法 `createProduct()`，并可提供依赖该产品的通用业务方法。
- **具体创建者（Concrete Creator）**：重写工厂方法，返回具体产品。

#### 可运行 Java 示例

```java
interface Notification {
    void send(String message);
}

class EmailNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("邮件通知: " + message);
    }
}

class SmsNotification implements Notification {
    @Override
    public void send(String message) {
        System.out.println("短信通知: " + message);
    }
}

abstract class NotificationFactory {
    protected abstract Notification createNotification();

    public void notifyUser(String message) {
        Notification notification = createNotification();
        notification.send(message);
    }
}

class EmailNotificationFactory extends NotificationFactory {
    @Override
    protected Notification createNotification() {
        return new EmailNotification();
    }
}

class SmsNotificationFactory extends NotificationFactory {
    @Override
    protected Notification createNotification() {
        return new SmsNotification();
    }
}

public class FactoryMethodDemo {
    public static void main(String[] args) {
        NotificationFactory factory = new SmsNotificationFactory();
        factory.notifyUser("您的订单已发货");
    }
}
```

#### 何时用、何时别用

适合：产品类型会扩展、创建逻辑较复杂（需要读配置、做缓存、初始化资源）、框架需要把“创建哪个实现”交给使用方决定。

不适合：产品永远只有一种、创建逻辑只有一行 `new`。此时直接构造或使用静态工厂方法即可。

#### 常见误用

- 把 `switch(type)` 塞进一个工厂类的静态方法里，然后称之为“工厂方法”。这是简单工厂，新增产品仍要改工厂类，违反开闭原则。
- 工厂方法返回 `null` 表示“不支持”，调用方很容易漏判。应抛异常或返回空对象。
- 工厂方法被声明为 `public`，客户端绕过通用流程直接创建产品，模板流程就失去意义。

### 2.3 抽象工厂模式（Abstract Factory）

#### 要解决什么问题

当系统要创建的是**一族**相互配套的对象（例如同一主题下的按钮、复选框、输入框），如果分别创建，很容易出现“浅色按钮配深色面板”的混搭。抽象工厂把一整族产品的创建集中到一个工厂接口里，保证同一工厂产出的产品风格一致。

#### 生活化比喻

像买整套家具：北欧风格的桌子、椅子、柜子必须来自同一套设计。你只选“北欧”或“中式”这个套装，不需要逐件搭配。

#### 结构与角色

- **抽象工厂（Abstract Factory）**：声明创建一族产品的方法。
- **具体工厂（Concrete Factory）**：实现一族具体产品。
- **抽象产品（Abstract Product）**：每个产品维度的接口。
- **具体产品（Concrete Product）**：具体工厂返回的实现。
- **客户端（Client）**：只依赖抽象工厂和抽象产品。

#### 可运行 Java 示例

```java
interface Button {
    void render();
}

interface Checkbox {
    void render();
}

interface UiFactory {
    Button createButton();

    Checkbox createCheckbox();
}

class LightButton implements Button {
    @Override
    public void render() {
        System.out.println("渲染浅色按钮");
    }
}

class LightCheckbox implements Checkbox {
    @Override
    public void render() {
        System.out.println("渲染浅色复选框");
    }
}

class DarkButton implements Button {
    @Override
    public void render() {
        System.out.println("渲染深色按钮");
    }
}

class DarkCheckbox implements Checkbox {
    @Override
    public void render() {
        System.out.println("渲染深色复选框");
    }
}

class LightUiFactory implements UiFactory {
    @Override
    public Button createButton() {
        return new LightButton();
    }

    @Override
    public Checkbox createCheckbox() {
        return new LightCheckbox();
    }
}

class DarkUiFactory implements UiFactory {
    @Override
    public Button createButton() {
        return new DarkButton();
    }

    @Override
    public Checkbox createCheckbox() {
        return new DarkCheckbox();
    }
}

public class AbstractFactoryDemo {
    public static void main(String[] args) {
        UiFactory factory = new DarkUiFactory();
        factory.createButton().render();
        factory.createCheckbox().render();
    }
}
```

#### 何时用、何时别用

适合：产品成族出现、需要切换整套实现、客户端不应知道具体类。

不适合：产品族只有一个维度（那更像工厂方法）、族内产品经常增删（每加一个产品都要改所有工厂接口）。

#### 常见误用

- 把抽象工厂当成“万能工厂”，一个接口里塞十几种产品，新增产品导致所有具体工厂都要改。
- 只用一个具体工厂，却保留抽象工厂和接口，属于过度设计。
- 工厂负责创建，却又在内部做业务判断，职责混杂。

### 2.4 单例模式（Singleton）

#### 要解决什么问题

有些对象在进程内只应存在一份，例如全局配置、连接池管理器、注册表。如果每次 `new`，会重复加载资源，状态也不一致。单例模式保证一个类只有一个实例，并提供一个访问点。

#### 生活化比喻

像公司前台：整个办公区只有一个前台，所有人找前台都走同一个窗口，不需要每人配一个。

#### 结构与角色

- **单例类（Singleton）**：私有构造方法，持有静态实例，提供静态获取方法。
- 外部代码只能通过 `getInstance()` 拿到实例，不能自行 `new`。

#### 可运行 Java 示例

```java
import java.util.HashMap;
import java.util.Map;

public enum ConfigRegistry {
    INSTANCE;

    private final Map<String, String> config = new HashMap<>();

    ConfigRegistry() {
        config.put("timeout", "3000");
        config.put("retry", "2");
    }

    public String get(String key) {
        return config.get(key);
    }

    public void put(String key, String value) {
        config.put(key, value);
    }
}

class SingletonDemo {
    public static void main(String[] args) {
        ConfigRegistry.INSTANCE.put("region", "cn-north");
        System.out.println(ConfigRegistry.INSTANCE.get("region"));
    }
}
```

枚举实现由 JVM（Java 虚拟机）保证线程安全，也能抵御反射和序列化创建新实例，是《Effective Java》推荐的做法。如果必须延迟初始化，可以使用静态内部类 Holder：

```java
public final class LazyConfig {
    private LazyConfig() {
    }

    private static class Holder {
        private static final LazyConfig INSTANCE = new LazyConfig();
    }

    public static LazyConfig getInstance() {
        return Holder.INSTANCE;
    }
}
```

#### 何时用、何时别用

适合：确实需要进程内唯一、创建成本高且可共享、需要统一管理全局资源。

不适合：只是为了“方便取用”而把普通服务做成单例；单例会隐藏依赖关系，让单元测试难以替换实现。分布式系统中，单例只能保证**单个 JVM 内**唯一，不能跨节点保证唯一。

#### 常见误用

- 双重检查锁忘记给实例字段加 `volatile`，可能拿到未初始化完成的对象。
- 整个 `getInstance()` 加 `synchronized`，每次访问都加锁；应缩小锁范围或改用 Holder。
- 用单例保存请求级数据，多个线程互相覆盖。
- 通过反射调用私有构造方法破坏单例；枚举实现可以避免这个问题。

### 2.5 原型模式（Prototype）

#### 要解决什么问题

有些对象创建成本很高（需要查库、读文件、复杂计算），但新对象与已有对象只差少量字段。与其从头构造，不如复制一个现成实例再修改。原型模式用“克隆”代替“新建”。

#### 生活化比喻

像复印一份已经排好版的合同：不用重新逐字排版，复印后只改签名和日期。

#### 结构与角色

- **原型（Prototype）**：声明 `clone()` 方法。
- **具体原型（Concrete Prototype）**：实现复制逻辑。
- **客户端（Client）**：通过克隆原型得到新对象。

#### 可运行 Java 示例

```java
import java.util.ArrayList;
import java.util.List;

public class Document implements Cloneable {
    private String title;
    private List<String> tags;

    public Document(String title, List<String> tags) {
        this.title = title;
        this.tags = new ArrayList<>(tags);
    }

    @Override
    public Document clone() {
        try {
            Document copy = (Document) super.clone();
            // 深拷贝：可变引用类型必须重新创建
            copy.tags = new ArrayList<>(this.tags);
            return copy;
        } catch (CloneNotSupportedException e) {
            throw new AssertionError("Document 已实现 Cloneable", e);
        }
    }

    public void addTag(String tag) {
        tags.add(tag);
    }

    @Override
    public String toString() {
        return title + tags;
    }
}

class PrototypeDemo {
    public static void main(String[] args) {
        Document original = new Document("设计模式", List.of("技术"));
        Document copy = original.clone();
        copy.addTag("Java");
        System.out.println(original);
        System.out.println(copy);
    }
}
```

#### 何时用、何时别用

适合：对象初始化代价高、需要保留某个快照、需要大量相似对象。

不适合：对象层级深且引用关系复杂（深拷贝容易漏字段）、对象本身很轻量。此时用拷贝构造器或工厂重建往往更清晰。

#### 常见误用

- 只调用 `super.clone()` 做浅拷贝，结果两个对象共享同一个 `List`，改一个影响另一个。
- 以为实现了 `Cloneable` 就自动拥有 `clone()`；`Cloneable` 只是标记接口，`clone()` 来自 `Object`。
- 在克隆后忘记重新生成 ID、时间戳等“每个实例唯一”的字段。

## 三、结构型模式

结构型模式关注“类和对象如何组合成更大的结构”。它们不改变对象的行为算法，而是通过包装、转换接口、共享实例等方式，让系统在保持各部分独立的同时协同工作。本章讲代理、装饰器、适配器、外观、组合、桥接、享元这 7 种结构型模式。

### 3.1 代理模式（Proxy）

#### 要解决什么问题

有些对象不能或不应被调用方直接访问：远程对象跨网络、大对象加载慢、敏感操作需要权限校验、业务方法需要统一加日志或事务。如果把这些逻辑硬编码进目标类，目标类会承担过多职责；如果让每个调用方自己处理，又会重复且容易遗漏。代理模式在调用方与目标对象之间加一层“替身”，由替身控制访问，并在转发前后附加逻辑。

#### 生活化比喻

像艺人的经纪人：主办方不直接找艺人谈合同，而是先找经纪人。经纪人负责筛选请求、安排档期、谈价格，真正的演出仍由艺人完成。

#### 结构与角色

- **抽象主题（Subject）**：目标对象和代理共同实现的接口。
- **真实主题（Real Subject）**：真正执行业务的对象。
- **代理（Proxy）**：持有真实主题的引用，在调用前后插入控制逻辑。
- **客户端（Client）**：面向 `Subject` 编程，不知道背后是代理还是真实对象。

#### 可运行 Java 示例

先看一个不依赖框架的静态代理，理解“转发 + 增强”的本质：

```java
interface UserService {
    void save(String name);
}

class UserServiceImpl implements UserService {
    @Override
    public void save(String name) {
        System.out.println("保存用户: " + name);
    }
}

class UserServiceProxy implements UserService {
    private final UserService target;

    UserServiceProxy(UserService target) {
        this.target = target;
    }

    @Override
    public void save(String name) {
        System.out.println("[日志] 开始 save");
        try {
            target.save(name);
        } finally {
            System.out.println("[日志] 结束 save");
        }
    }
}

public class StaticProxyDemo {
    public static void main(String[] args) {
        UserService service = new UserServiceProxy(new UserServiceImpl());
        service.save("user_a");
    }
}
```

静态代理的缺点是每个接口都要手写一个代理类。框架里更常见的是动态代理：运行时生成代理类。JDK 自带的 `java.lang.reflect.Proxy` 只能代理**接口**，生成的代理类继承 `Proxy` 并实现指定接口；要代理没有接口的类，需要使用 CGLIB、Javassist 或 Byte Buddy 这类字节码工具。

下面的框架片段涉及 Spring、Dubbo、MyBatis 的内部实现，初学可以先跳过，只记住“代理在调用前后加逻辑”即可。

**Spring AOP（Aspect-Oriented Programming，面向切面编程）的 JDK 动态代理（简化示意）**

```java
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;
import java.util.List;

import org.aopalliance.intercept.MethodInvocation;
import org.springframework.aop.framework.AdvisedSupport;
import org.springframework.aop.framework.AopProxy;
import org.springframework.aop.framework.ReflectiveMethodInvocation;

public class JdkDynamicAopProxy implements AopProxy, InvocationHandler {
    private final Object target;
    private final AdvisedSupport advised;

    public JdkDynamicAopProxy(Object target, AdvisedSupport advised) {
        this.target = target;
        this.advised = advised;
    }

    @Override
    public Object getProxy(ClassLoader classLoader) {
        return Proxy.newProxyInstance(
                classLoader,
                target.getClass().getInterfaces(),
                this
        );
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // 取出匹配当前方法的拦截器链（可能包含多个通知）
        List<Object> chain = advised.getInterceptorsAndDynamicInterceptionAdvice(
                method, target.getClass()
        );
        MethodInvocation invocation = new ReflectiveMethodInvocation(
                proxy, target, method, args, target.getClass(), chain
        );
        return invocation.proceed();
    }
}
```

真实实现还会处理 `equals`、`hashCode`、`toString`、目标对象为 `null`、拦截器链为空等情况，这里省略以突出代理结构。

**Spring 声明式事务：代理的典型应用**

```java
import org.aopalliance.intercept.MethodInterceptor;
import org.aopalliance.intercept.MethodInvocation;
import org.springframework.transaction.PlatformTransactionManager;
import org.springframework.transaction.TransactionStatus;
import org.springframework.transaction.support.DefaultTransactionDefinition;

public class TransactionProxy implements MethodInterceptor {
    private final PlatformTransactionManager transactionManager;

    public TransactionProxy(PlatformTransactionManager transactionManager) {
        this.transactionManager = transactionManager;
    }

    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        TransactionStatus status = transactionManager.getTransaction(
                new DefaultTransactionDefinition()
        );
        try {
            Object result = invocation.proceed();
            transactionManager.commit(status);
            return result;
        } catch (Throwable e) {
            transactionManager.rollback(status);
            throw e;
        }
    }
}
```

`@Transactional` 能生效，前提是调用经过代理。同一个类里 `this.methodB()` 这种自调用不经过代理，事务、日志等增强都会失效，这是实践中最常见的“事务不生效”原因之一。

**Dubbo 远程调用代理**

Dubbo 为远程接口生成代理，调用方像调本地方法一样发起 RPC（Remote Procedure Call，远程过程调用）。下面的写法来自 `JavassistProxyFactory`：它用 Dubbo 自己的 Javassist 代理生成器创建代理实例，失败时回退到 JDK 代理。

```java
import org.apache.dubbo.common.bytecode.Proxy;
import org.apache.dubbo.rpc.Invoker;
import org.apache.dubbo.rpc.proxy.AbstractProxyFactory;
import org.apache.dubbo.rpc.proxy.InvokerInvocationHandler;
import org.apache.dubbo.rpc.proxy.jdk.JdkProxyFactory;

public class JavassistProxyFactory extends AbstractProxyFactory {
    private final JdkProxyFactory jdkProxyFactory = new JdkProxyFactory();

    @Override
    @SuppressWarnings("unchecked")
    public <T> T getProxy(Invoker<T> invoker, Class<?>[] interfaces) {
        try {
            return (T) Proxy.getProxy(interfaces)
                    .newInstance(new InvokerInvocationHandler(invoker));
        } catch (Throwable fromJavassist) {
            // Javassist 生成失败时回退到 JDK 动态代理
            return jdkProxyFactory.getProxy(invoker, interfaces);
        }
    }
}
```

`InvokerInvocationHandler` 会把方法名、参数类型、参数值封装成 `RpcInvocation`，再交给 `Invoker` 走集群容错、负载均衡和网络调用。调用方看到的返回值，是代理把远程结果反序列化后的对象。

**MyBatis Mapper 代理**

MyBatis 的 Mapper 接口没有实现类，却能直接调用，是因为启动时为每个 Mapper 接口生成了 JDK 动态代理。代理拦截方法调用后，把“接口 + 方法”解析成一条 SQL 并执行。

```java
import java.io.Serializable;
import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

import org.apache.ibatis.binding.MapperMethod;
import org.apache.ibatis.session.SqlSession;

public class MapperProxy<T> implements InvocationHandler, Serializable {
    private final SqlSession sqlSession;
    private final Class<T> mapperInterface;

    public MapperProxy(SqlSession sqlSession, Class<T> mapperInterface) {
        this.sqlSession = sqlSession;
        this.mapperInterface = mapperInterface;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        // toString、hashCode、equals 等 Object 方法直接在代理上执行
        if (Object.class.equals(method.getDeclaringClass())) {
            return method.invoke(this, args);
        }
        MapperMethod mapperMethod = new MapperMethod(
                mapperInterface, method, sqlSession.getConfiguration()
        );
        return mapperMethod.execute(sqlSession, args);
    }

    @SuppressWarnings("unchecked")
    public static <T> T newMapperProxy(SqlSession sqlSession, Class<T> mapperInterface) {
        return (T) Proxy.newProxyInstance(
                mapperInterface.getClassLoader(),
                new Class<?>[]{mapperInterface},
                new MapperProxy<>(sqlSession, mapperInterface)
        );
    }
}
```

真实实现会缓存 `MapperMethod`，并额外处理接口默认方法（default method）；上面的版本保留了核心分支，便于理解。

#### 代理模式的通用能力

1. **功能增强**：性能监控、安全控制、日志记录、事务管理。
2. **调用控制**：远程方法调用、延迟加载、缓存、熔断降级。
3. **设计优势**：解耦系统组件、不修改原有代码、动态扩展功能、提高代码可维护性。

#### 实现技术

1. **静态代理**：编译期手写代理类，直观但每个接口都要写一份，扩展性较差。
2. **动态代理**：JDK Proxy、CGLIB、Javassist，运行时生成代理类。JDK 代理要求目标实现接口；CGLIB 通过继承生成子类，不能代理 `final` 类或 `final` 方法。
3. **字节码增强**：AspectJ、Byte Buddy，可在编译期或加载期修改字节码，能力更强，理解成本也更高。

#### 性能与最佳实践

1. 根据目标是否有接口、是否为 `final` 选择合适的代理技术。
2. 避免过度使用代理，一层代理就够时不要套三层。
3. 关注反射和拦截器链带来的开销；高频调用路径可用缓存或编译期增强。
4. 合理设计代理层次，避免代理链难以排查。
5. 缓存代理类的创建结果，不要每次调用都生成新代理。

#### 何时用、何时别用

适合：远程调用、权限控制、日志记录、性能监控、事务管理、缓存、懒加载，以及任何“访问前后要统一做点事”的场景。

不适合：目标对象很简单、没有横切逻辑；对延迟极其敏感的紧循环；目标类没有接口却坚持用 JDK 代理；团队无法接受调用链变长带来的调试成本。

#### 常见误用

- 以为加了 `@Transactional` 就一定生效，忽略自调用、私有方法、非 `public` 方法不经过代理的问题。
- 把 JDK 代理对象强转成实现类，抛出 `ClassCastException`；应面向接口编程。
- 在代理的 `invoke` 里吞掉异常或改变返回类型，破坏接口契约。
- 代理里再调用目标对象的其他方法时，误以为会再次经过代理，实际不会。
- 只代理了部分方法，其余方法直接暴露真实对象，访问控制出现缺口。

代理模式是开源框架中最常见的设计模式之一：它不修改目标代码，就在调用链上增加了访问控制与横切能力。

### 3.2 装饰器模式（Decorator）

#### 要解决什么问题

需要给对象动态增加职责，但又不想为每种组合写子类。例如咖啡可以加奶、加糖、加奶泡，如果按“奶 + 糖 + 奶泡”逐一继承，类数量会爆炸。装饰器用组合代替继承：装饰器实现同一接口，内部持有被装饰对象，在调用前后追加行为，并且可以层层嵌套。

#### 生活化比喻

像奶茶加料：基础茶底不变，每加一种料就用一个小杯子/标签包一层，价格和描述累加。你可以只加珍珠，也可以珍珠加椰果，组合是运行时决定的。

#### 结构与角色

- **组件（Component）**：被装饰对象和装饰器共同的接口。
- **具体组件（Concrete Component）**：基础实现。
- **装饰器（Decorator）**：实现组件接口，持有另一个组件引用。
- **具体装饰器（Concrete Decorator）**：在转发前后增加职责。

#### 可运行 Java 示例

```java
interface Coffee {
    String description();

    double cost();
}

class SimpleCoffee implements Coffee {
    @Override
    public String description() {
        return "美式咖啡";
    }

    @Override
    public double cost() {
        return 18.0;
    }
}

abstract class CoffeeDecorator implements Coffee {
    protected final Coffee wrapped;

    protected CoffeeDecorator(Coffee wrapped) {
        this.wrapped = wrapped;
    }

    @Override
    public String description() {
        return wrapped.description();
    }

    @Override
    public double cost() {
        return wrapped.cost();
    }
}

class MilkDecorator extends CoffeeDecorator {
    MilkDecorator(Coffee wrapped) {
        super(wrapped);
    }

    @Override
    public String description() {
        return wrapped.description() + " + 牛奶";
    }

    @Override
    public double cost() {
        return wrapped.cost() + 3.0;
    }
}

class SugarDecorator extends CoffeeDecorator {
    SugarDecorator(Coffee wrapped) {
        super(wrapped);
    }

    @Override
    public String description() {
        return wrapped.description() + " + 糖";
    }

    @Override
    public double cost() {
        return wrapped.cost() + 1.0;
    }
}

public class DecoratorDemo {
    public static void main(String[] args) {
        Coffee coffee = new SugarDecorator(new MilkDecorator(new SimpleCoffee()));
        System.out.println(coffee.description() + "，价格: " + coffee.cost());
    }
}
```

#### 何时用、何时别用

适合：需要运行时叠加职责、组合方式多、又不想修改原类；典型场景是 Java I/O 的 `BufferedInputStream`、`InputStreamReader` 层层包装，GUI 组件加滚动条、边框、颜色也是同一思路。

不适合：职责组合固定、只有一两种；接口方法很多（装饰器要为每个方法写转发，成本高）；需要改变对象接口本身（那是适配器）。

#### 常见误用

- 装饰顺序影响结果却没人约定，例如“先打折后满减”和“先满减后打折”金额不同。
- 在装饰器里保存可变状态，多个调用方共享同一个装饰器时互相污染。
- 装饰器没有完整转发接口方法，漏掉的方法行为丢失。
- 用装饰器解决接口不兼容问题；接口不匹配应该用适配器。

### 3.3 适配器模式（Adapter）

#### 要解决什么问题

系统里已经有一个可用的类或第三方库，但它的接口与当前代码期望的接口不一致。直接改老代码风险大，改第三方库更不现实。适配器模式在中间加一个转换层：实现目标接口，内部调用被适配对象，把参数和返回值转换成对方能接受的形式。

#### 生活化比喻

像旅行转换插头：墙上的插座和电脑的插头形状不匹配，转换头本身不供电，只负责把两边的形状对上。

#### 结构与角色

- **目标接口（Target）**：客户端期望的接口。
- **适配器（Adapter）**：实现目标接口，持有被适配对象。
- **被适配对象（Adaptee）**：已有但与目标接口不兼容的类。
- **客户端（Client）**：只依赖目标接口。

Java 中常见两种写法：对象适配器（组合，推荐）和类适配器（同时继承 Adaptee 并实现 Target，受单继承限制）。

#### 可运行 Java 示例

```java
interface ModernLogger {
    void log(String message);
}

// 老系统留下的日志类，接口不兼容
class LegacyLogger {
    public void writeLog(String level, String message) {
        System.out.println("[" + level + "] " + message);
    }
}

class LegacyLoggerAdapter implements ModernLogger {
    private final LegacyLogger legacyLogger;

    LegacyLoggerAdapter(LegacyLogger legacyLogger) {
        this.legacyLogger = legacyLogger;
    }

    @Override
    public void log(String message) {
        legacyLogger.writeLog("INFO", message);
    }
}

public class AdapterDemo {
    public static void main(String[] args) {
        ModernLogger logger = new LegacyLoggerAdapter(new LegacyLogger());
        logger.log("订单创建成功");
    }
}
```

#### 何时用、何时别用

适合：集成旧系统、复用已有类但接口不匹配、对接第三方 SDK（软件开发工具包）、需要在不改原类的前提下统一多个实现。

不适合：自己可控的新代码接口设计不合理——此时应直接重构接口，而不是长期维护适配层；适配逻辑本身很复杂时，要考虑是否值得引入。

#### 常见误用

- 把适配器当成“万能胶”，每个不匹配都包一层，系统里全是转换类。
- 适配器里写业务逻辑，导致同一业务散落在适配器和目标实现两处。
- 双向适配器同时承担两个方向的转换，职责过重、容易递归。
- 只转换了方法名，没有处理异常语义、线程安全、资源释放等差异。

### 3.4 外观模式（Facade）

#### 要解决什么问题

一个子系统由很多类组成，客户端完成一次业务要按顺序调用多个接口，还要处理参数准备、异常和回滚。外观模式提供一个高层入口，把子系统内部的协作封装起来，客户端只调用一个方法。

#### 生活化比喻

像医院导诊台：患者不需要自己跑挂号、缴费、检验、取药各个窗口的路线，导诊台告诉你流程并统一协调；具体检查仍由各科室完成。

#### 结构与角色

- **外观（Facade）**：对外提供简化接口，内部协调多个子系统。
- **子系统（Subsystem）**：完成具体功能的类，彼此可以独立。
- **客户端（Client）**：只与外观交互。

#### 可运行 Java 示例

```java
class InventoryService {
    boolean reserve(String sku, int count) {
        System.out.println("锁定库存: " + sku + " x " + count);
        return true;
    }
}

class PaymentService {
    boolean pay(String orderId, double amount) {
        System.out.println("支付订单: " + orderId + "，金额: " + amount);
        return true;
    }
}

class ShippingService {
    void arrange(String orderId) {
        System.out.println("安排发货: " + orderId);
    }
}

class OrderFacade {
    private final InventoryService inventory = new InventoryService();
    private final PaymentService payment = new PaymentService();
    private final ShippingService shipping = new ShippingService();

    public boolean placeOrder(String orderId, String sku, int count, double amount) {
        if (!inventory.reserve(sku, count)) {
            return false;
        }
        if (!payment.pay(orderId, amount)) {
            return false;
        }
        shipping.arrange(orderId);
        return true;
    }
}

public class FacadeDemo {
    public static void main(String[] args) {
        OrderFacade facade = new OrderFacade();
        facade.placeOrder("ORDER-001", "SKU-001", 2, 199.0);
    }
}
```

#### 何时用、何时别用

适合：子系统接口多而客户端只用其中一部分、需要为复杂流程提供统一入口、要降低客户端与子系统的耦合；数据库连接、文件读写等复杂操作也可以封装成统一入口。

不适合：客户端需要精细控制子系统每一步；子系统本身很简单；外观逐渐演变成什么都管的“上帝类”。

#### 常见误用

- 外观类里堆积业务规则、校验、事务和远程调用，最后难以测试。
- 外观把子系统全部方法都转发一遍，等于多了一层无价值包装。
- 误以为外观会阻止客户端直接访问子系统；外观只是提供便捷入口，不是访问控制。

### 3.5 组合模式（Composite）

#### 要解决什么问题

当对象天然呈树形结构（文件系统、菜单、组织架构、UI 容器），客户端经常要区分“叶子节点”和“容器节点”，写两套处理逻辑。组合模式让叶子节点和容器节点实现同一接口，客户端可以统一地递归处理整棵树。

#### 生活化比喻

像文件和文件夹：文件不能再包含子项，文件夹可以；但复制、统计大小、重命名这些操作对两者是统一的，资源管理器不需要为“文件”和“文件夹”写两套入口。

#### 结构与角色

- **组件（Component）**：叶子与容器的共同接口。
- **叶子（Leaf）**：没有子节点，实现基本操作。
- **容器（Composite）**：持有子组件列表，把操作递归转发给子节点。
- **客户端（Client）**：面向组件接口操作整棵树。

#### 可运行 Java 示例

```java
import java.util.ArrayList;
import java.util.List;

interface FileNode {
    String name();

    int size();

    void print(String indent);
}

class FileLeaf implements FileNode {
    private final String name;
    private final int size;

    FileLeaf(String name, int size) {
        this.name = name;
        this.size = size;
    }

    @Override
    public String name() {
        return name;
    }

    @Override
    public int size() {
        return size;
    }

    @Override
    public void print(String indent) {
        System.out.println(indent + name + " (" + size + " KB)");
    }
}

class DirectoryNode implements FileNode {
    private final String name;
    private final List<FileNode> children = new ArrayList<>();

    DirectoryNode(String name) {
        this.name = name;
    }

    void add(FileNode child) {
        children.add(child);
    }

    @Override
    public String name() {
        return name;
    }

    @Override
    public int size() {
        int total = 0;
        for (FileNode child : children) {
            total += child.size();
        }
        return total;
    }

    @Override
    public void print(String indent) {
        System.out.println(indent + name + "/");
        for (FileNode child : children) {
            child.print(indent + "  ");
        }
    }
}

public class CompositeDemo {
    public static void main(String[] args) {
        DirectoryNode root = new DirectoryNode("root");
        DirectoryNode docs = new DirectoryNode("docs");
        docs.add(new FileLeaf("设计模式.md", 120));
        docs.add(new FileLeaf("Java.md", 300));
        root.add(docs);
        root.add(new FileLeaf("README.md", 5));

        root.print("");
        System.out.println("总大小: " + root.size() + " KB");
    }
}
```

#### 何时用、何时别用

适合：树形结构、希望客户端忽略“单个对象”和“组合对象”的差异、需要对整棵树做统一操作，例如 GUI 中的嵌套布局、菜单和文件目录。

不适合：结构不是树、层级很浅且固定、叶子与容器的行为差异很大（强行统一接口会导致大量空实现）。

#### 常见误用

- 在 `Leaf` 上实现 `add()`/`remove()` 却直接抛异常，客户端无法在编译期发现误用；可把管理子节点的方法只放在 `Composite` 上，或返回明确的“不支持”结果。
- 递归遍历没有环检测，树被误连成图后栈溢出。
- 容器的 `size()` 每次全量递归计算，树很大时性能差；可以缓存并标记失效。
- 把组合模式用于非树形结构，只是为了“统一接口”。

### 3.6 桥接模式（Bridge）

#### 要解决什么问题

当一个类有两个独立变化的维度时，用继承扩展会导致子类数量相乘。例如图形既有形状（圆形、方形）又有颜色（红色、蓝色），如果写成 `RedCircle`、`BlueCircle`、`RedSquare`、`BlueSquare`，每增加一种形状或颜色，都要新增一批类。桥接模式把其中一个维度抽成“实现”，让抽象部分持有实现部分的引用，两个维度各自独立扩展。

#### 生活化比喻

像遥控器和电视：遥控器负责“换台、调音量”的抽象操作，电视负责真正显示。你可以换一台电视而继续用同一个遥控器，也可以换一个高级遥控器而不用换电视，两者不必绑死。

#### 结构与角色

- **抽象（Abstraction）**：定义高层操作，持有实现者引用。
- **细化抽象（Refined Abstraction）**：扩展抽象部分。
- **实现者（Implementor）**：定义实现维度的接口。
- **具体实现者（Concrete Implementor）**：实现某一具体维度。

#### 可运行 Java 示例

```java
interface Color {
    String name();
}

class Red implements Color {
    @Override
    public String name() {
        return "红色";
    }
}

class Blue implements Color {
    @Override
    public String name() {
        return "蓝色";
    }
}

abstract class Shape {
    protected final Color color;

    protected Shape(Color color) {
        this.color = color;
    }

    abstract String name();

    abstract double area();

    String describe() {
        return color.name() + name() + "，面积 " + area();
    }
}

class Circle extends Shape {
    private final double radius;

    Circle(Color color, double radius) {
        super(color);
        this.radius = radius;
    }

    @Override
    String name() {
        return "圆形";
    }

    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}

class Rectangle extends Shape {
    private final double width;
    private final double height;

    Rectangle(Color color, double width, double height) {
        super(color);
        this.width = width;
        this.height = height;
    }

    @Override
    String name() {
        return "矩形";
    }

    @Override
    double area() {
        return width * height;
    }
}

public class BridgeDemo {
    public static void main(String[] args) {
        Shape circle = new Circle(new Red(), 2);
        Shape rectangle = new Rectangle(new Blue(), 3, 4);
        System.out.println(circle.describe());
        System.out.println(rectangle.describe());
    }
}
```

#### 何时用、何时别用

适合：一个类存在两个以上独立变化的维度、希望在运行时切换实现、不希望继承层次继续膨胀。JDBC 的 `DriverManager` 与各数据库 `Driver` 就是桥接思路：调用方面向统一 API，具体驱动独立实现。

不适合：只有一个变化维度（普通继承或策略就够）、两个维度强绑定且不会分别演化。

#### 常见误用

- 把桥接和策略混为一谈：策略替换的是一段算法，桥接拆分的是两个可独立演化的维度。
- 抽象部分直接依赖具体实现者，桥接退化成普通的组合。
- 为了“预留扩展”硬拆两个维度，结果两个维度都只有一个实现。
- 实现者接口设计得过宽，具体实现被迫写大量空方法。

### 3.7 享元模式（Flyweight）

#### 要解决什么问题

系统里对象数量巨大，但其中很多对象的“固有状态”完全相同。例如棋盘上有几百枚棋子，颜色和形状只有黑白两种；如果每枚棋子都保存一份颜色、形状、图片，内存浪费严重。享元模式把状态拆成可共享的内部状态和由调用方传入的外部状态，相同内部状态只保留一份实例。

#### 生活化比喻

像围棋棋子：棋子的“颜色、材质、大小”只有黑白两种规格，可以共用；每个棋子的“位置”是每枚棋子自己的，下棋时由棋盘传入。你不需要为每一手棋重新造一颗棋子。

#### 结构与角色

- **享元（Flyweight）**：包含可共享的内部状态。
- **具体享元（Concrete Flyweight）**：具体实现。
- **享元工厂（Flyweight Factory）**：按 key 缓存并复用享元。
- **客户端（Client）**：维护外部状态，使用时传给享元。

#### 可运行 Java 示例

```java
import java.util.HashMap;
import java.util.Map;

class TreeType {
    private final String name;
    private final String color;

    TreeType(String name, String color) {
        this.name = name;
        this.color = color;
    }

    void draw(int x, int y) {
        System.out.println("在 (" + x + ", " + y + ") 画一棵"
                + color + "的" + name);
    }
}

class TreeTypeFactory {
    private final Map<String, TreeType> cache = new HashMap<>();

    TreeType get(String name, String color) {
        String key = name + "#" + color;
        return cache.computeIfAbsent(key, k -> new TreeType(name, color));
    }

    int size() {
        return cache.size();
    }
}

class Tree {
    private final TreeType type;
    private final int x;
    private final int y;

    Tree(TreeType type, int x, int y) {
        this.type = type;
        this.x = x;
        this.y = y;
    }

    void draw() {
        type.draw(x, y);
    }
}

public class FlyweightDemo {
    public static void main(String[] args) {
        TreeTypeFactory factory = new TreeTypeFactory();
        TreeType ginkgo = factory.get("银杏", "绿色");
        TreeType maple = factory.get("枫树", "红色");

        Tree[] trees = {
                new Tree(ginkgo, 1, 1),
                new Tree(ginkgo, 2, 3),
                new Tree(maple, 5, 8),
                new Tree(ginkgo, 9, 9)
        };
        for (Tree tree : trees) {
            tree.draw();
        }
        System.out.println("共享的树类型数量: " + factory.size());
    }
}
```

#### 何时用、何时别用

适合：大量对象、内部状态可共享且不可变、外部状态可以由调用方传入、内存占用是主要瓶颈。

不适合：对象数量不大、内部状态经常变化（共享会串数据）、外部状态难以拆分。不要为了“省一点内存”提前引入缓存，先测量再优化。

#### 常见误用

- 把可变状态放进享元，多个使用方互相影响。
- 工厂缓存没有淘汰策略，长期运行后反而占用更多内存。
- 客户端把外部状态也存进享元，导致享元无法复用。
- 用享元包装本来就很轻的对象，缓存查找的成本超过收益。

## 四、行为型模式

行为型模式关注对象之间如何通信、职责如何分配。它们把“谁来做、按什么顺序做、状态变了怎么办”从硬编码的条件分支中抽出来，交给对象协作完成。本章先讲最常用的观察者、策略、模板方法，再讲责任链、命令、状态、迭代器，最后补齐中介者、备忘录、解释器、访问者。

### 4.1 观察者模式（Observer）

#### 要解决什么问题

一个对象状态变化后，需要通知多个其他对象，但又不希望它直接依赖这些对象的具体类型。例如用户注册成功后要发邮件、送积分、写审计日志；如果注册服务里逐个调用，每加一个后续动作都要改注册代码。观察者模式让主题只维护一个观察者列表，状态变化时遍历通知，新增动作只需注册新的观察者。

#### 生活化比喻

像关注一个公众号：你关注后，号主发布新文章，所有关注者都会收到推送；你取关后就不再收到。号主不需要知道每个读者是谁，只需要维护关注列表。

#### 结构与角色

- **主题（Subject）**：也称被观察者，维护观察者列表，提供注册、移除、通知方法。
- **观察者（Observer）**：定义接收通知的更新接口。
- **具体主题（Concrete Subject）**：状态变化时调用通知。
- **具体观察者（Concrete Observer）**：收到通知后执行自己的逻辑。

#### 可运行 Java 示例

```java
import java.util.ArrayList;
import java.util.List;

interface Observer {
    void update(String message);
}

class MessageSubject {
    private final List<Observer> observers = new ArrayList<>();

    public void register(Observer observer) {
        observers.add(observer);
    }

    public void unregister(Observer observer) {
        observers.remove(observer);
    }

    public void publish(String message) {
        // 复制一份，避免观察者在回调中增删导致并发修改异常
        for (Observer observer : new ArrayList<>(observers)) {
            observer.update(message);
        }
    }
}

class EmailObserver implements Observer {
    private final String email;

    EmailObserver(String email) {
        this.email = email;
    }

    @Override
    public void update(String message) {
        System.out.println("发送邮件到 " + email + ": " + message);
    }
}

class SmsObserver implements Observer {
    private final String phone;

    SmsObserver(String phone) {
        this.phone = phone;
    }

    @Override
    public void update(String message) {
        System.out.println("发送短信到 " + phone + ": " + message);
    }
}

public class ObserverDemo {
    public static void main(String[] args) {
        MessageSubject subject = new MessageSubject();
        Observer email = new EmailObserver("user_a@example.com");
        subject.register(email);
        subject.register(new SmsObserver("13800000000"));

        subject.publish("订单已发货");
        subject.unregister(email);
        subject.publish("订单已签收");
    }
}
```

#### 框架中的观察者

**Spring 事件机制**

Spring 的 `ApplicationEventPublisher` 负责发布事件，`ApplicationListener` 负责监听。默认是同步调用：发布线程会依次执行所有监听器，监听器抛异常会影响发布方，除非加上 `@Async` 或使用异步事件广播器。

```java
import org.springframework.context.ApplicationEvent;
import org.springframework.context.ApplicationEventPublisher;
import org.springframework.context.ApplicationListener;
import org.springframework.stereotype.Component;
import org.springframework.stereotype.Service;

class UserRegisteredEvent extends ApplicationEvent {
    private final User user;

    UserRegisteredEvent(Object source, User user) {
        super(source);
        this.user = user;
    }

    User getUser() {
        return user;
    }
}

record User(String username, String email) {
}

@Component
class EmailNotificationListener implements ApplicationListener<UserRegisteredEvent> {
    @Override
    public void onApplicationEvent(UserRegisteredEvent event) {
        User user = event.getUser();
        System.out.println("发送注册通知邮件给: " + user.email());
    }
}

@Component
class UserPointsListener implements ApplicationListener<UserRegisteredEvent> {
    @Override
    public void onApplicationEvent(UserRegisteredEvent event) {
        User user = event.getUser();
        System.out.println("为新用户初始化积分: " + user.username());
    }
}

@Service
class UserService {
    private final ApplicationEventPublisher eventPublisher;

    UserService(ApplicationEventPublisher eventPublisher) {
        this.eventPublisher = eventPublisher;
    }

    public void registerUser(User user) {
        // 用户注册逻辑
        eventPublisher.publishEvent(new UserRegisteredEvent(this, user));
    }
}
```

Spring 4.2 之后也可以用 `@EventListener` 注解普通方法，不必强制实现 `ApplicationListener`。

**Guava EventBus**

Guava 的 `EventBus` 是一个进程内事件总线：`register()` 注册订阅者，`post()` 发布事件，`@Subscribe` 标记处理方法。它同样是同步的，`AsyncEventBus` 可以配合线程池异步派发。

```java
import com.google.common.eventbus.EventBus;
import com.google.common.eventbus.Subscribe;

enum OrderStatus {
    CREATED, PAID, SHIPPED, DELIVERED
}

class OrderEvent {
    private final String orderId;
    private final OrderStatus status;

    OrderEvent(String orderId, OrderStatus status) {
        this.orderId = orderId;
        this.status = status;
    }

    String getOrderId() {
        return orderId;
    }

    OrderStatus getStatus() {
        return status;
    }
}

class OrderEventHandler {
    @Subscribe
    public void handleOrderCreated(OrderEvent event) {
        if (event.getStatus() == OrderStatus.CREATED) {
            System.out.println("订单已创建: " + event.getOrderId());
            checkInventory(event.getOrderId());
        }
    }

    @Subscribe
    public void handleOrderPaid(OrderEvent event) {
        if (event.getStatus() == OrderStatus.PAID) {
            System.out.println("订单已支付: " + event.getOrderId());
            confirmPayment(event.getOrderId());
        }
    }

    private void checkInventory(String orderId) {
        // 库存检查逻辑
    }

    private void confirmPayment(String orderId) {
        // 支付确认逻辑
    }
}

class OrderService {
    private final EventBus eventBus = new EventBus("OrderEventBus");

    void registerListener(Object listener) {
        eventBus.register(listener);
    }

    void createOrder(String orderId) {
        eventBus.post(new OrderEvent(orderId, OrderStatus.CREATED));
    }

    void payOrder(String orderId) {
        eventBus.post(new OrderEvent(orderId, OrderStatus.PAID));
    }
}

public class EventBusDemo {
    public static void main(String[] args) {
        OrderService orderService = new OrderService();
        orderService.registerListener(new OrderEventHandler());

        String orderId = "ORDER-001";
        orderService.createOrder(orderId);
        orderService.payOrder(orderId);
    }
}
```

**RxJava 响应式事件流**

RxJava 把事件流抽象成 `Observable`（可观察源），通过 `subscribe()` 注册观察者。与经典观察者相比，它多了线程调度、操作符组合等能力（背压由支持背压的 `Flowable` 提供），适合处理异步数据流。

```java
import io.reactivex.rxjava3.core.Observable;
import io.reactivex.rxjava3.schedulers.Schedulers;

record User(String username, String email) {
}

class UserService {
    Observable<User> registerUser(String username, String email) {
        return Observable.create(emitter -> {
            try {
                User user = new User(username, email);
                emitter.onNext(user);
                emitter.onComplete();
            } catch (Exception e) {
                emitter.onError(e);
            }
        });
    }
}

public class RxJavaDemo {
    public static void main(String[] args) throws InterruptedException {
        UserService userService = new UserService();

        userService.registerUser("user_a", "user_a@example.com")
                // 转换用户信息
                .map(user -> new User(user.username(), user.email()))
                // 在 IO 线程执行订阅逻辑
                .subscribeOn(Schedulers.io())
                // 在另一个线程观察结果；Android 上可换成 AndroidSchedulers.mainThread()
                .observeOn(Schedulers.single())
                .subscribe(
                        user -> System.out.println("用户注册成功: " + user.username()),
                        error -> System.err.println("用户注册失败: " + error.getMessage()),
                        () -> System.out.println("用户注册流程完成")
                );

        Thread.sleep(500);
    }
}
```

#### 设计要点

1. **解耦机制**：主题只依赖观察者接口，支持动态注册和移除，新增订阅方不必修改主题。
2. **事件驱动**：状态变化触发通知，多个观察者可以各自处理，传播关系比较松散。
3. **性能取舍**：同步通知会阻塞发布线程；观察者多时可用异步派发、批量合并、惰性计算或队列缓冲，但会引入延迟和顺序问题。

#### 实现建议

1. 在需要时使用弱引用或及时反注册，避免观察者被主题长期持有造成内存泄漏。
2. 提供线程安全的注册/通知实现，明确通知是同步还是异步。
3. 控制事件传播范围，避免一个事件触发整条链路。
4. 合理设计事件层次，事件类不要承担业务逻辑。
5. 高并发场景可用队列缓冲事件，但要考虑丢失、重复和顺序。

#### 适用场景

消息通知系统、实时数据同步、GUI（图形用户界面）事件处理、分布式系统解耦、状态变更通知，以及 Spring 事件、Guava EventBus 这类进程内事件机制。

#### 潜在挑战

复杂的事件依赖难以追踪；同步通知带来性能开销；多监听器执行顺序不确定；监听器异常可能中断后续通知；异步化之后又会出现重复消费和顺序问题。

#### 高级扩展

事件过滤、事件编排、优先级机制、事务性事件（事务提交后再发布）。Spring 的 `@TransactionalEventListener` 就是“事务提交后触发”的典型实现。

#### 何时用、何时别用

适合：一对多通知、发布方不应知道订阅方具体类型、需要动态增减订阅者。

不适合：只有固定一两个后续动作（直接调用更清楚）；强依赖执行顺序和返回值；跨进程、需要可靠投递（应使用消息队列的发布-订阅）。

#### 常见误用

- 在监听器里做耗时操作，拖慢整个发布线程。
- 监听器抛异常没有隔离，导致后续监听器不执行、发布方回滚。
- 注册了监听器却从不反注册，尤其在长生命周期容器里持有短生命周期对象。
- 用事件机制隐藏主流程，读代码时很难看出注册后到底发生了什么。
- 把进程内事件当成可靠消息，进程崩溃后事件就丢了。

观察者模式通过解耦发布方与订阅方，为系统提供了灵活的事件通知机制；选 Spring 事件、Guava EventBus 还是 RxJava，取决于是否需要异步、线程调度和流式组合。

### 4.2 发布-订阅模式（Pub-Sub）

#### 要解决什么问题

观察者模式里，主题直接持有观察者列表，二者仍有直接引用。当发布者和订阅者数量都很多、部署在不同进程，或者希望彼此完全不知道对方存在时，需要引入一个中间通道：发布者把消息投递到通道，订阅者从通道按主题订阅。这就是发布-订阅模式，常由消息队列或事件总线实现。

#### 生活化比喻

像报纸订阅：作者把稿件交给报社，报社印刷发行；读者向报社订阅。作者不需要知道有哪些读者，读者也不需要认识作者。

#### 结构与角色

- **消息通道（Message Channel）**：连接发布者与订阅者的中介，可以是进程内事件总线，也可以是 Kafka、RabbitMQ 这类消息中间件。
- **发布者（Publisher）**：把消息发布到通道，通常只指定主题。
- **订阅者（Subscriber）**：订阅感兴趣的主题，从通道接收消息。

#### 可运行 Java 示例

下面用进程内的简单消息总线演示发布-订阅的结构：发布者只认主题，订阅者按主题注册，双方不直接持有对方。

```java
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

interface Subscriber {
    void onMessage(String topic, String message);
}

class SimpleMessageBus {
    private final Map<String, List<Subscriber>> topics = new HashMap<>();

    void subscribe(String topic, Subscriber subscriber) {
        topics.computeIfAbsent(topic, key -> new ArrayList<>()).add(subscriber);
    }

    void publish(String topic, String message) {
        for (Subscriber subscriber : topics.getOrDefault(topic, List.of())) {
            subscriber.onMessage(topic, message);
        }
    }
}

class LogSubscriber implements Subscriber {
    private final String name;

    LogSubscriber(String name) {
        this.name = name;
    }

    @Override
    public void onMessage(String topic, String message) {
        System.out.println(name + " 收到 [" + topic + "] " + message);
    }
}

public class PubSubDemo {
    public static void main(String[] args) {
        SimpleMessageBus bus = new SimpleMessageBus();
        bus.subscribe("order", new LogSubscriber("audit"));
        bus.subscribe("order", new LogSubscriber("email"));
        bus.publish("order", "ORDER-001 已支付");
    }
}
```

#### 与观察者模式的异同

| 维度 | 观察者模式 | 发布-订阅模式 |
| --- | --- | --- |
| 耦合方式 | 主题直接持有观察者引用 | 发布者与订阅者通过通道间接通信 |
| 通信方式 | 主题主动调用观察者的更新方法 | 消息经通道路由，通常是异步的 |
| 关系规模 | 典型是一对多 | 可以多对多 |
| 生命周期 | 观察者通常与主题同进程 | 发布者、订阅者、通道可独立部署 |
| 典型实现 | Spring 事件、Guava EventBus、RxJava | Kafka、RabbitMQ、Redis Pub/Sub、事件总线 |
| 可靠性 | 依赖进程内调用，进程退出即丢失 | 取决于中间件，可持久化、重试、堆积 |

#### 使用情况

- **观察者模式**：一个对象状态变化需要通知多个依赖对象，且对象之间有一定关联，例如 GUI 事件、模型与视图同步、应用内领域事件。
- **发布-订阅模式**：存在复杂消息网络、多个发布者和多个订阅者、需要跨进程或异步解耦，例如分布式系统事件通知、日志采集、订单状态广播。

需要说明的是，发布-订阅是一种架构风格，不属于 GoF 23 种设计模式；观察者则是 GoF 的行为型模式。很多框架把两者混用，关键看是否存在独立的消息通道。

#### 何时用、何时别用

适合：发布者与订阅者需要跨进程或异步解耦、存在多个发布者和多个订阅者、需要削峰填谷或可靠投递、订阅方可以独立部署和扩缩容。

不适合：同一进程内简单的一对多通知（观察者模式更直接）、要求强一致或严格全局顺序、团队没有消息中间件的运维能力。

#### 常见误用

- 默认消息只投递一次，消费端不做幂等，重试后产生重复数据。
- 假设同一主题的消息全局有序；实际顺序通常只保证分区/队列内有序。
- 没有死信队列、重试上限和告警，消费失败的消息被静默丢弃。
- 把发布-订阅当成同步 RPC 使用，调用方等待回执，失去异步解耦的意义。
- 消息格式没有版本号，订阅方升级后无法兼容旧消息。

### 4.3 策略模式（Strategy）

#### 要解决什么问题

同一业务有多种算法，例如促销有打折、满减、满赠；如果写成 `if/else` 或 `switch`，每加一种规则都要改原方法，方法会越来越长，测试也越来越难。策略模式把每种算法封装成独立类，让它们实现同一接口，运行时由上下文选择。

#### 生活化比喻

像出行导航：去同一个目的地可以开车、骑车、走路，路线规划算法不同，但“从 A 到 B”这个目标一致。你根据时间、费用、天气切换方式，不需要改目的地。

#### 结构与角色

- **策略接口（Strategy）**：定义算法方法。
- **具体策略（Concrete Strategy）**：实现一种算法。
- **上下文（Context）**：持有策略引用，把调用委托给策略；客户端可运行时切换。

#### 可运行 Java 示例

```java
interface PromotionStrategy {
    double calculatePrice(double originalPrice);
}

class DiscountStrategy implements PromotionStrategy {
    private final double discountRate;

    DiscountStrategy(double discountRate) {
        this.discountRate = discountRate;
    }

    @Override
    public double calculatePrice(double originalPrice) {
        return originalPrice * discountRate;
    }
}

class FullReductionStrategy implements PromotionStrategy {
    private final double threshold;
    private final double reduction;

    FullReductionStrategy(double threshold, double reduction) {
        this.threshold = threshold;
        this.reduction = reduction;
    }

    @Override
    public double calculatePrice(double originalPrice) {
        return originalPrice >= threshold ? originalPrice - reduction : originalPrice;
    }
}

class PromotionContext {
    private PromotionStrategy promotionStrategy;

    void setPromotionStrategy(PromotionStrategy strategy) {
        if (strategy == null) {
            throw new IllegalArgumentException("策略不能为空");
        }
        this.promotionStrategy = strategy;
    }

    double calculateFinalPrice(double originalPrice) {
        if (promotionStrategy == null) {
            return originalPrice;
        }
        return promotionStrategy.calculatePrice(originalPrice);
    }
}

public class StrategyDemo {
    public static void main(String[] args) {
        PromotionContext context = new PromotionContext();

        // 双十一：8 折
        context.setPromotionStrategy(new DiscountStrategy(0.8));
        System.out.println("双十一价格: " + context.calculateFinalPrice(1000));

        // 圣诞节：满 1000 减 200
        context.setPromotionStrategy(new FullReductionStrategy(1000, 200));
        System.out.println("圣诞节价格: " + context.calculateFinalPrice(1200));
    }
}
```

#### 策略模式的优势

1. 符合开闭原则：新增策略只需新增类，不必修改上下文。
2. 算法独立：各策略互不依赖，便于单独测试。
3. 运行时动态切换。
4. 消除大量条件语句。
5. 提高代码可维护性。

#### 实践建议

- 策略数量不宜过多，避免类爆炸；可以把相近的小策略合并。
- 策略之间应该是平等的，不要在一个策略里调用另一个策略。
- 优先使用组合，而非继承。
- 结合工厂模式管理策略创建，用 `Map<String, PromotionStrategy>` 注册，避免上下文里再写 `switch`。
- 策略最好无状态；如果必须有状态，要保证线程安全。

#### 何时用、何时别用

适合：多种可互换算法、算法会频繁新增、需要在运行时选择、想把复杂的条件分支拆开。

不适合：算法只有一两种且几乎不变；算法之间需要共享大量中间状态；调用方需要知道算法内部细节。

#### 常见误用

- 上下文里仍用 `if/else` 选择策略，只是把代码从一个地方挪到另一个地方。
- 策略类持有请求级数据，多个线程共享同一个策略实例时互相污染。
- 策略接口设计得过宽，包含多个不相关方法，具体策略被迫写空实现。
- 把策略模式和状态模式混为一谈：策略由客户端主动选择，状态由对象内部流转。

策略模式让促销规则可以独立变化，新增活动时只需增加策略类，不必修改价格计算主流程。

### 4.4 模板方法模式（Template Method）

#### 要解决什么问题

多个流程大体相同，只有个别步骤不同。如果每个流程都复制一遍，公共逻辑重复，改一处要改多份；如果全部塞进一个方法用 `if/else` 区分，又会越来越臃肿。模板方法把固定流程写在父类的模板方法里，把可变步骤声明为抽象方法或钩子方法，由子类实现。父类控制“什么时候做什么”，子类只决定“某一步怎么做”。

#### 生活化比喻

像按图纸盖房子：打地基、主体施工、封顶、验收的顺序由图纸规定，不同项目只在地基深度、外立面材料等步骤上有差异，不能随意调整整体顺序。

#### 结构与角色

- **抽象类（Abstract Class）**：定义模板方法（算法骨架），声明抽象步骤和钩子方法。
- **具体类（Concrete Class）**：实现抽象步骤，按需重写钩子，但不能改变模板方法的流程。
- **模板方法**：通常声明为 `final`，防止子类改写流程。
- **钩子方法（Hook）**：有默认空实现，子类可选重写，用于在关键节点插入扩展。

#### 可运行 Java 示例

```java
abstract class DataImporter {
    // 模板方法：固定导入流程
    public final void importData(String path) {
        open(path);
        try {
            String raw = read();
            String parsed = parse(raw);
            save(parsed);
            afterImport();
        } finally {
            close();
        }
    }

    protected abstract void open(String path);

    protected abstract String read();

    protected abstract String parse(String raw);

    protected abstract void save(String parsed);

    protected abstract void close();

    // 钩子方法：默认什么也不做
    protected void afterImport() {
    }
}

class CsvImporter extends DataImporter {
    @Override
    protected void open(String path) {
        System.out.println("打开 CSV: " + path);
    }

    @Override
    protected String read() {
        return "name,age\nuser_a,20";
    }

    @Override
    protected String parse(String raw) {
        return raw.replace(",", " | ");
    }

    @Override
    protected void save(String parsed) {
        System.out.println("保存 CSV 数据: " + parsed);
    }

    @Override
    protected void close() {
        System.out.println("关闭 CSV 文件");
    }
}

public class TemplateMethodDemo {
    public static void main(String[] args) {
        DataImporter importer = new CsvImporter();
        importer.importData("users.csv");
    }
}
```

#### 框架中的应用

**Spring 的 `AbstractApplicationContext#refresh()`**

`refresh()` 是典型的模板方法：它规定了容器启动的固定步骤，其中 `onRefresh()` 是留给子类的钩子。不同子类（如 `ClassPathXmlApplicationContext`、`AnnotationConfigApplicationContext`）在钩子里做自己的初始化。

```java
public abstract class AbstractApplicationContext implements ConfigurableApplicationContext {
    private final Object startupShutdownMonitor = new Object();

    @Override
    public void refresh() throws BeansException, IllegalStateException {
        synchronized (this.startupShutdownMonitor) {
            prepareRefresh();

            ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();
            prepareBeanFactory(beanFactory);

            postProcessBeanFactory(beanFactory);
            invokeBeanFactoryPostProcessors(beanFactory);
            registerBeanPostProcessors(beanFactory);

            initMessageSource();
            initApplicationEventMulticaster();

            // 钩子：子类可以在这里完成自己的刷新逻辑
            onRefresh();

            registerListeners();
            finishBeanFactoryInitialization(beanFactory);
            finishRefresh();
        }
    }

    protected void onRefresh() throws BeansException {
        // 默认空实现
    }
}
```

上面的代码沿用 Spring 6.1 及更早版本的写法（`synchronized (this.startupShutdownMonitor)`），并省略了异常处理和销毁逻辑，只保留流程骨架。Spring 6.2 起改为 `ReentrantLock` 显式加锁，但模板方法的步骤划分没有变。

**MyBatis 的 `BaseExecutor`**

MyBatis 的 `BaseExecutor` 把“清缓存、判空、调子类”的流程固定下来，把真正的 SQL 执行交给 `doUpdate`、`doQuery` 等抽象方法。`SimpleExecutor`、`ReuseExecutor`、`BatchExecutor` 分别实现这些步骤。

```java
public abstract class BaseExecutor implements Executor {
    @Override
    public int update(MappedStatement ms, Object parameter) throws SQLException {
        if (closed) {
            throw new ExecutorException("Executor was closed.");
        }
        clearLocalCache();
        return doUpdate(ms, parameter);
    }

    @Override
    public <E> List<E> query(MappedStatement ms, Object parameter, RowBounds rowBounds,
                             ResultHandler resultHandler) throws SQLException {
        BoundSql boundSql = ms.getBoundSql(parameter);
        CacheKey key = createCacheKey(ms, parameter, rowBounds, boundSql);
        return query(ms, parameter, rowBounds, resultHandler, key, boundSql);
    }

    protected abstract int doUpdate(MappedStatement ms, Object parameter) throws SQLException;

    protected abstract <E> List<E> doQuery(MappedStatement ms, Object parameter, RowBounds rowBounds,
                                           ResultHandler resultHandler, BoundSql boundSql) throws SQLException;
}
```

注意：`SqlSessionTemplate` 本身是具体类，它通过动态代理把调用转给 `SqlSession`，并不是带 `beforeExecution()`/`afterExecution()` 钩子的抽象模板。MyBatis 中更典型的模板方法在 `BaseExecutor`。

**JUnit 的 `TestCase`**

JUnit 3 风格的 `TestCase` 用 `runBare()` 作为模板方法：先 `setUp()`，再执行测试，最后一定执行 `tearDown()`，即使测试抛异常也不跳过清理。

```java
public abstract class TestCase extends Assert implements Test {
    public void runBare() throws Throwable {
        Throwable exception = null;
        setUp();
        try {
            runTest();
        } catch (Throwable running) {
            exception = running;
        } finally {
            try {
                tearDown();
            } catch (Throwable tearingDown) {
                if (exception == null) {
                    exception = tearingDown;
                }
            }
        }
        if (exception != null) {
            throw exception;
        }
    }

    protected void setUp() throws Exception {
    }

    protected void tearDown() throws Exception {
    }

    protected void runTest() throws Throwable {
        // JUnit 4 的兼容实现会按测试方法名反射调用 testXxx()
    }
}
```

这里容易记反：**模板方法是 `runBare()`，`runTest()` 只是被它调用的一个步骤**。JUnit 3.8.1 和 JUnit 4 的 `junit.framework.TestCase` 中，`runTest()` 都已经提供默认实现（按测试方法名反射调用 `testXxx`），不需要子类强制实现；控制 `setUp → 测试 → tearDown` 顺序的始终是 `runBare()`。

#### 在开源框架中的应用特点

1. **统一执行流程**：定义标准算法骨架、控制整体执行步骤、提供可插拔的扩展点。
2. **灵活性设计**：使用抽象类和接口、提供钩子方法、支持部分方法重写。
3. **扩展机制**：抽象方法强制实现、钩子方法可选重写、提供默认实现。

#### 设计原则与最佳实践

1. **开闭原则**：流程对修改关闭，步骤对扩展开放。
2. **依赖倒置**：父类依赖抽象的步骤方法，不依赖具体实现。
3. **单一职责**：每个步骤只做一件事，模板方法只负责编排。
4. 模板方法尽量声明为 `final`，防止子类破坏流程。
5. 钩子方法命名要能看出调用时机，例如 `beforeExecute`、`afterCompletion`。

#### 使用建议

1. 谨慎设计抽象类层次，继承链不要太深。
2. 合理使用 `final` 方法，保护算法骨架。
3. 为抽象方法和钩子写清楚注释：必须实现什么、什么时候被调用。
4. 避免过度继承；步骤变化频繁时，组合（策略）可能更合适。
5. 关注模板方法的性能开销，避免在循环里频繁创建子类。

#### 应用场景

框架生命周期管理、标准化处理流程、事务管理、测试框架、ORM（对象关系映射）框架、依赖注入容器，以及各种“固定流程 + 可变步骤”的导出、导入、审批、支付流程。

#### 何时用、何时别用

适合：多个子类共享同一流程骨架、流程顺序必须固定、可变步骤有限且稳定。

不适合：步骤经常增删、需要运行时切换流程、子类组合爆炸。此时用策略、责任链或工作流引擎更合适。

#### 常见误用

- 模板方法没有加 `final`，子类重写后流程被破坏。
- 在父类构造方法里调用可重写方法，子类字段还没初始化，出现空指针。
- 抽象方法过多，子类被迫实现一堆用不到的方法；应提供合理默认实现或拆分抽象类。
- 把业务判断塞进模板方法，子类只能靠重写钩子“打补丁”。
- 为了复用一点点代码引入三层继承，最后比复制更难维护。

模板方法把稳定流程收进父类、把变化步骤留给子类，是框架最常用的扩展方式之一；使用时要注意流程保护与继承深度。

### 4.5 责任链模式（Chain of Responsibility）

#### 要解决什么问题

一个请求可能由多个对象中的某一个处理，但发送者不应事先知道到底是谁。例如报销审批：金额小于 1000 组长批，小于 5000 经理批，再大由总监批。如果发送者写死判断，新增审批级别就要改发送者。责任链把处理器串成一条链，请求沿链传递，直到被处理或链结束。

#### 生活化比喻

像客服工单升级：一线客服先处理，解决不了转二线，二线解决不了转专家。用户只提交一次工单，不需要知道最终由谁处理。

#### 结构与角色

- **处理者（Handler）**：声明处理请求的方法，并持有下一个处理者的引用。
- **具体处理者（Concrete Handler）**：能处理就处理，不能处理就转发给下一个。
- **客户端（Client）**：把请求交给链头。

#### 可运行 Java 示例

```java
abstract class Approver {
    private Approver next;

    Approver setNext(Approver next) {
        this.next = next;
        return next;
    }

    public final void handle(int amount) {
        if (canApprove(amount)) {
            approve(amount);
        } else if (next != null) {
            next.handle(amount);
        } else {
            System.out.println("金额 " + amount + " 无人可审批");
        }
    }

    protected abstract boolean canApprove(int amount);

    protected abstract void approve(int amount);
}

class TeamLeader extends Approver {
    @Override
    protected boolean canApprove(int amount) {
        return amount <= 1000;
    }

    @Override
    protected void approve(int amount) {
        System.out.println("组长审批: " + amount);
    }
}

class Manager extends Approver {
    @Override
    protected boolean canApprove(int amount) {
        return amount <= 5000;
    }

    @Override
    protected void approve(int amount) {
        System.out.println("经理审批: " + amount);
    }
}

class Director extends Approver {
    @Override
    protected boolean canApprove(int amount) {
        return amount <= 20000;
    }

    @Override
    protected void approve(int amount) {
        System.out.println("总监审批: " + amount);
    }
}

public class ChainDemo {
    public static void main(String[] args) {
        Approver chain = new TeamLeader();
        chain.setNext(new Manager()).setNext(new Director());

        chain.handle(800);
        chain.handle(3000);
        chain.handle(15000);
        chain.handle(50000);
    }
}
```

#### 何时用、何时别用

适合：多个对象可能处理同一请求、处理顺序可动态调整、发送者不应依赖具体处理者、需要在不改发送者的情况下增删处理器（如过滤器、拦截器、网关鉴权链）。

不适合：请求必须被某个处理器处理且不能丢（需要额外兜底）、链很长且大部分处理器都不处理、处理顺序必须严格固定且简单。

#### 常见误用

- 具体处理者忘记调用 `next.handle()`，请求静默丢失。
- 链形成环，请求无限循环。
- 每个处理器都依赖前一个处理器的副作用，链顺序一变就出错。
- 没有兜底处理者，链尾直接抛异常或返回 `null`。
- 把责任链当成流程引擎，节点里塞满业务分支。

### 4.6 命令模式（Command）

#### 要解决什么问题

有时需要把“一次请求”当成对象来传递：排队执行、记录日志、支持撤销、把调用者与执行者解耦。例如遥控器按钮不应直接依赖灯、电视、空调的具体类；按钮只持有一个命令对象，按下时执行，撤销时反向执行。

#### 生活化比喻

像餐厅点菜：服务员在点菜单上写下一道菜（命令对象），把单子交给后厨（接收者）。单子可以排队、可以加急、可以退菜；服务员不需要知道菜怎么做。

#### 结构与角色

- **命令（Command）**：声明 `execute()`，有时还有 `undo()`。
- **具体命令（Concrete Command）**：持有接收者，把请求转成接收者的一个或多个动作。
- **接收者（Receiver）**：真正执行操作的对象。
- **调用者（Invoker）**：持有命令并触发执行，不关心命令内部。
- **客户端（Client）**：创建命令并绑定接收者。

#### 可运行 Java 示例

```java
interface Command {
    void execute();

    void undo();
}

class Light {
    void on() {
        System.out.println("灯已打开");
    }

    void off() {
        System.out.println("灯已关闭");
    }
}

class LightOnCommand implements Command {
    private final Light light;

    LightOnCommand(Light light) {
        this.light = light;
    }

    @Override
    public void execute() {
        light.on();
    }

    @Override
    public void undo() {
        light.off();
    }
}

class LightOffCommand implements Command {
    private final Light light;

    LightOffCommand(Light light) {
        this.light = light;
    }

    @Override
    public void execute() {
        light.off();
    }

    @Override
    public void undo() {
        light.on();
    }
}

class RemoteControl {
    private Command lastCommand;

    void press(Command command) {
        command.execute();
        lastCommand = command;
    }

    void undo() {
        if (lastCommand != null) {
            lastCommand.undo();
        }
    }
}

public class CommandDemo {
    public static void main(String[] args) {
        Light light = new Light();
        RemoteControl remote = new RemoteControl();

        remote.press(new LightOnCommand(light));
        remote.press(new LightOffCommand(light));
        remote.undo();
    }
}
```

#### 何时用、何时别用

适合：需要撤销/重做、任务排队、延迟执行、把请求写入日志后重放、调用者与接收者解耦、需要组合多个命令（宏命令）。

不适合：只是简单的一次方法调用、没有撤销或排队需求、命令与接收者一一对应且永远不会变化。

#### 常见误用

- 撤销逻辑与执行逻辑不对称，`undo()` 无法真正恢复原状态。
- 命令对象里保存了不属于它的业务状态，导致重放时结果不一致。
- 宏命令执行到一半失败，没有回滚已执行的子命令。
- 为了“解耦”把简单的 service 调用包成命令，系统里全是只有一行的类。

### 4.7 状态模式（State）

#### 要解决什么问题

对象的行为随内部状态变化而变化，例如订单在“待支付、已支付、已发货、已完成”下，能执行的操作不同。如果用 `switch(state)` 在每个方法里判断，状态一多就会散落大量条件分支，新增状态容易漏改。状态模式把每个状态封装成独立类，由状态对象决定能做什么，并在合适的时机切换到下一个状态。

#### 生活化比喻

像红绿灯：同一盏灯，红灯时“行”与“停”的规则和绿灯时不同；灯还是那盏灯，行为由当前状态决定。

#### 结构与角色

- **上下文（Context）**：持有当前状态，把行为委托给状态对象。
- **状态（State）**：声明各状态下可执行的操作。
- **具体状态（Concrete State）**：实现本状态的行为，并负责触发状态转换。

#### 可运行 Java 示例

```java
interface OrderState {
    void pay(Order order);

    void ship(Order order);

    String name();
}

class CreatedState implements OrderState {
    @Override
    public void pay(Order order) {
        System.out.println("支付成功");
        order.setState(new PaidState());
    }

    @Override
    public void ship(Order order) {
        System.out.println("未支付，不能发货");
    }

    @Override
    public String name() {
        return "待支付";
    }
}

class PaidState implements OrderState {
    @Override
    public void pay(Order order) {
        System.out.println("已经支付，请勿重复支付");
    }

    @Override
    public void ship(Order order) {
        System.out.println("发货成功");
        order.setState(new ShippedState());
    }

    @Override
    public String name() {
        return "已支付";
    }
}

class ShippedState implements OrderState {
    @Override
    public void pay(Order order) {
        System.out.println("已发货，不能再支付");
    }

    @Override
    public void ship(Order order) {
        System.out.println("已经发货");
    }

    @Override
    public String name() {
        return "已发货";
    }
}

class Order {
    private OrderState state = new CreatedState();

    void setState(OrderState state) {
        this.state = state;
    }

    void pay() {
        state.pay(this);
    }

    void ship() {
        state.ship(this);
    }

    String stateName() {
        return state.name();
    }
}

public class StateDemo {
    public static void main(String[] args) {
        Order order = new Order();
        order.ship();
        order.pay();
        order.ship();
        System.out.println("当前状态: " + order.stateName());
    }
}
```

#### 何时用、何时别用

适合：对象行为随状态明显变化、状态数量较多、状态转换规则集中且需要可维护、需要避免大量重复条件分支。

不适合：状态只有两三个且转换简单、状态之间没有行为差异、状态转换需要跨多个对象协同（可能需要工作流引擎）。

#### 常见误用

- 把状态模式写成“状态 + 巨大 `switch`”，状态类只负责改字段，行为仍集中在上下文。
- 状态转换散落在各个业务方法里，没有统一入口，难以审计。
- 状态对象保存请求级数据，多个订单共享同一个状态实例时串数据。
- 与策略模式混淆：策略由外部选择算法，状态由内部流转驱动行为。

### 4.8 迭代器模式（Iterator）

#### 要解决什么问题

集合的内部结构可能千差万别（数组、链表、树、哈希表），如果让客户端自己按下标或节点遍历，就必须了解内部实现；换一种存储结构，所有遍历代码都要改。迭代器把“如何遍历”封装起来，客户端只使用 `hasNext()`、`next()` 这类统一方法。

#### 生活化比喻

像导游带团：游客不需要知道景区道路怎么修，只要跟着导游按顺序走，导游负责判断“还有没有下一个景点”。

#### 结构与角色

- **迭代器（Iterator）**：定义 `hasNext()`、`next()` 等遍历方法。
- **具体迭代器（Concrete Iterator）**：维护遍历游标。
- **聚合（Aggregate）**：定义创建迭代器的方法。
- **具体聚合（Concrete Aggregate）**：返回与自己结构匹配的迭代器。

#### 可运行 Java 示例

```java
import java.util.Iterator;
import java.util.NoSuchElementException;

class NameCollection implements Iterable<String> {
    private final String[] names;

    NameCollection(String[] names) {
        this.names = names.clone();
    }

    @Override
    public Iterator<String> iterator() {
        return new Iterator<>() {
            private int index = 0;

            @Override
            public boolean hasNext() {
                return index < names.length;
            }

            @Override
            public String next() {
                if (!hasNext()) {
                    throw new NoSuchElementException();
                }
                return names[index++];
            }
        };
    }
}

public class IteratorDemo {
    public static void main(String[] args) {
        NameCollection collection = new NameCollection(
                new String[]{"user_a", "user_b", "user_c"}
        );

        for (String name : collection) {
            System.out.println(name);
        }

        Iterator<String> iterator = collection.iterator();
        while (iterator.hasNext()) {
            System.out.println("手动遍历: " + iterator.next());
        }
    }
}
```

Java 的 `Iterable`/`Iterator` 就是该模式的官方抽象，`for-each` 语法底层会调用 `iterator()`；`ArrayList`、`HashMap` 等都提供了自己的迭代器实现。

#### 何时用、何时别用

适合：需要统一遍历不同结构、不希望暴露内部表示、需要支持多种遍历方式（正序、逆序、深度优先）。

不适合：集合本身就是简单数组且只在内部使用；遍历逻辑需要频繁随机访问；使用现成集合库已经足够。

#### 常见误用

- 边遍历边用集合自身的 `remove()` 修改结构，触发 `ConcurrentModificationException`；应使用迭代器的 `remove()` 或收集后再删。
- 迭代器没有保护游标，多个线程共享同一迭代器导致结果错乱。
- `next()` 越界时返回 `null` 而不是抛 `NoSuchElementException`，调用方无法区分“没有元素”和“元素为 null”。
- 在迭代器里做重量级业务处理，遍历与业务耦合。

### 4.9 中介者模式（Mediator）

#### 要解决什么问题

当多个对象需要相互通信时，最容易写成“每个人都持有其他人”的网状结构：新增一个对象，所有人都要改；删除一个对象，引用它的地方都要清理。中介者模式引入一个中心节点，同事对象只与中介者通信，由中介者负责转发和协调，把网状依赖变成星形依赖。

#### 生活化比喻

像机场塔台：飞机之间不直接对话，而是都向塔台报告，由塔台统一安排起降顺序。飞机不需要知道其他飞机的存在，只需要和塔台通信。

#### 结构与角色

- **中介者（Mediator）**：定义同事对象通信的接口。
- **具体中介者（Concrete Mediator）**：协调各个同事对象，知道它们的存在。
- **同事（Colleague）**：持有中介者引用，通过中介者与其他同事通信。

#### 可运行 Java 示例

```java
import java.util.ArrayList;
import java.util.List;

interface ChatMediator {
    void join(ChatUser user);

    void send(String message, ChatUser from);
}

class ChatRoom implements ChatMediator {
    private final List<ChatUser> users = new ArrayList<>();

    @Override
    public void join(ChatUser user) {
        users.add(user);
    }

    @Override
    public void send(String message, ChatUser from) {
        for (ChatUser user : users) {
            if (user != from) {
                user.receive(from.name() + ": " + message);
            }
        }
    }
}

class ChatUser {
    private final String name;
    private final ChatMediator mediator;

    ChatUser(String name, ChatMediator mediator) {
        this.name = name;
        this.mediator = mediator;
        mediator.join(this);
    }

    String name() {
        return name;
    }

    void send(String message) {
        mediator.send(message, this);
    }

    void receive(String message) {
        System.out.println(name + " 收到 " + message);
    }
}

public class MediatorDemo {
    public static void main(String[] args) {
        ChatRoom room = new ChatRoom();
        ChatUser a = new ChatUser("user_a", room);
        ChatUser b = new ChatUser("user_b", room);
        ChatUser c = new ChatUser("user_c", room);

        a.send("大家好");
        b.send("你好");
    }
}
```

#### 何时用、何时别用

适合：对象之间依赖关系复杂、通信方式经常变化、希望把协调逻辑集中管理（聊天室、UI 控件联动、网关聚合）。

不适合：对象很少、关系简单；中介者会逐渐变成什么都知道的“上帝类”，反而更难维护。

#### 常见误用

- 中介者里堆积业务规则，所有同事都依赖它，单点故障且难测试。
- 同事对象绕过中介者直接调用另一个同事，网状依赖又回来了。
- 中介者承担了本应由领域对象承担的职责，领域模型被掏空。
- 把中介者当成事件总线使用，却不定义清晰的消息契约。

### 4.10 备忘录模式（Memento）

#### 要解决什么问题

需要保存对象某一时刻的状态，以便之后恢复（撤销、回滚、存档），但又不想把对象的私有字段暴露给外部。备忘录模式把状态快照封装成一个不可变对象，由原发器负责创建和恢复，由管理者负责保存，外部只能持有快照而不能修改它。

#### 生活化比喻

像游戏存档：游戏进度被写进一个存档文件，玩家可以读档回到那个时间点；存档文件由游戏自己读写，玩家不需要知道内部数据结构。

#### 结构与角色

- **原发器（Originator）**：拥有内部状态，负责创建和恢复备忘录。
- **备忘录（Memento）**：保存原发器某一时刻的状态，对外只暴露必要信息。
- **管理者（Caretaker）**：保存备忘录，不修改其内容。

#### 可运行 Java 示例

```java
import java.util.ArrayDeque;
import java.util.Deque;

class EditorSnapshot {
    private final String text;

    EditorSnapshot(String text) {
        this.text = text;
    }

    String text() {
        return text;
    }
}

class Editor {
    private String text = "";

    void type(String content) {
        text += content;
    }

    EditorSnapshot save() {
        return new EditorSnapshot(text);
    }

    void restore(EditorSnapshot snapshot) {
        this.text = snapshot.text();
    }

    String text() {
        return text;
    }
}

class History {
    private final Deque<EditorSnapshot> stack = new ArrayDeque<>();

    void push(EditorSnapshot snapshot) {
        stack.push(snapshot);
    }

    EditorSnapshot pop() {
        return stack.poll();
    }
}

public class MementoDemo {
    public static void main(String[] args) {
        Editor editor = new Editor();
        History history = new History();

        editor.type("设计模式");
        history.push(editor.save());

        editor.type("：Java 实战");
        System.out.println("当前内容: " + editor.text());

        editor.restore(history.pop());
        System.out.println("撤销后: " + editor.text());
    }
}
```

#### 何时用、何时别用

适合：需要撤销/重做、事务回滚点、游戏存档、编辑器的历史记录。

不适合：状态体积很大且频繁保存（内存压力大）、状态包含大量外部资源句柄、只需要保留最近一次状态（一个字段就够）。

#### 常见误用

- 备忘录直接暴露原发器的可变引用，外部改了快照，恢复出来的状态也变了。
- 每次操作都无条件保存全量状态，内存迅速膨胀；应限制历史深度或做增量。
- 管理者参与状态修改，破坏了“原发器负责恢复”的边界。
- 把备忘录当成数据库快照，跨进程/跨版本恢复时没有考虑兼容性。

### 4.11 解释器模式（Interpreter）

#### 要解决什么问题

当系统需要反复解释一种简单的语言或表达式（例如自定义规则、查询条件、算术表达式），可以把文法中的每条规则表示成一个类，通过组合这些类递归求值。这样新增语法规则就是新增类，不需要在一个巨大的 `switch` 里堆分支。

#### 生活化比喻

像计算器读表达式：数字是终结符，“加号”连接两个子表达式；计算器按语法树逐层求值，而不是把整串字符硬编码成固定公式。

#### 结构与角色

- **抽象表达式（Abstract Expression）**：声明 `interpret(context)`。
- **终结符表达式（Terminal Expression）**：直接返回值，例如数字、变量。
- **非终结符表达式（Nonterminal Expression）**：组合子表达式，例如加法、乘法。
- **上下文（Context）**：保存变量值等全局信息。

#### 可运行 Java 示例

```java
import java.util.HashMap;
import java.util.Map;

interface Expression {
    int interpret(Map<String, Integer> context);
}

class NumberExpression implements Expression {
    private final int value;

    NumberExpression(int value) {
        this.value = value;
    }

    @Override
    public int interpret(Map<String, Integer> context) {
        return value;
    }
}

class VariableExpression implements Expression {
    private final String name;

    VariableExpression(String name) {
        this.name = name;
    }

    @Override
    public int interpret(Map<String, Integer> context) {
        Integer value = context.get(name);
        if (value == null) {
            throw new IllegalArgumentException("未定义变量: " + name);
        }
        return value;
    }
}

class AddExpression implements Expression {
    private final Expression left;
    private final Expression right;

    AddExpression(Expression left, Expression right) {
        this.left = left;
        this.right = right;
    }

    @Override
    public int interpret(Map<String, Integer> context) {
        return left.interpret(context) + right.interpret(context);
    }
}

public class InterpreterDemo {
    public static void main(String[] args) {
        Map<String, Integer> context = new HashMap<>();
        context.put("a", 1);
        context.put("b", 2);

        // 表达式：a + b + 3
        Expression expression = new AddExpression(
                new AddExpression(new VariableExpression("a"), new VariableExpression("b")),
                new NumberExpression(3)
        );
        System.out.println("结果: " + expression.interpret(context));
    }
}
```

#### 何时用、何时别用

适合：文法简单且稳定、规则需要频繁组合、希望把语法规则显式建模（规则引擎、简单查询 DSL（领域特定语言）、表达式求值）。

不适合：文法复杂（运算符优先级、类型系统、错误恢复），此时应使用解析器生成器或现成的表达式引擎。解释器模式通常只适合小规模语言。

#### 常见误用

- 用解释器实现完整编程语言，类数量爆炸且性能差。
- 每个终结符都创建一个新对象，表达式很大时内存开销高；可共享不可变终结符。
- 上下文用全局变量传递，导致并发问题。
- 没有处理非法输入和除零等边界，解释过程直接抛异常。

### 4.12 访问者模式（Visitor）

#### 要解决什么问题

当对象结构中的元素类型稳定，但需要不断新增操作（导出、统计、校验、格式化）时，如果每个操作都写进元素类，元素类会越来越臃肿，而且每次新增操作都要修改所有元素类。访问者模式把操作从元素中抽出来，元素只负责“接受访问者”，具体操作由访问者实现。

#### 生活化比喻

像博物馆的不同访客：展品（元素）本身不变，讲解员、摄影师、修复师（访问者）各自对展品做不同的事。展品只需要“接待”访客，不需要内置所有职业的操作。

#### 结构与角色

- **访问者（Visitor）**：为每种元素声明一个 `visit` 方法。
- **具体访问者（Concrete Visitor）**：实现具体操作。
- **元素（Element）**：声明 `accept(visitor)`。
- **具体元素（Concrete Element）**：调用访问者对应的 `visit` 方法。
- **对象结构（Object Structure）**：遍历元素，接受访问者。

#### 可运行 Java 示例

```java
import java.util.List;

interface Visitor {
    void visit(Book book);

    void visit(Fruit fruit);
}

interface Item {
    void accept(Visitor visitor);
}

class Book implements Item {
    private final String name;
    private final double price;

    Book(String name, double price) {
        this.name = name;
        this.price = price;
    }

    String name() {
        return name;
    }

    double price() {
        return price;
    }

    @Override
    public void accept(Visitor visitor) {
        visitor.visit(this);
    }
}

class Fruit implements Item {
    private final String name;
    private final double weight;
    private final double pricePerKg;

    Fruit(String name, double weight, double pricePerKg) {
        this.name = name;
        this.weight = weight;
        this.pricePerKg = pricePerKg;
    }

    String name() {
        return name;
    }

    double totalPrice() {
        return weight * pricePerKg;
    }

    @Override
    public void accept(Visitor visitor) {
        visitor.visit(this);
    }
}

class PriceVisitor implements Visitor {
    private double total;

    @Override
    public void visit(Book book) {
        total += book.price();
        System.out.println("书籍: " + book.name() + "，价格 " + book.price());
    }

    @Override
    public void visit(Fruit fruit) {
        total += fruit.totalPrice();
        System.out.println("水果: " + fruit.name() + "，价格 " + fruit.totalPrice());
    }

    double total() {
        return total;
    }
}

public class VisitorDemo {
    public static void main(String[] args) {
        List<Item> items = List.of(
                new Book("设计模式", 59.0),
                new Fruit("苹果", 2.5, 8.0)
        );

        PriceVisitor visitor = new PriceVisitor();
        for (Item item : items) {
            item.accept(visitor);
        }
        System.out.println("总价: " + visitor.total());
    }
}
```

#### 何时用、何时别用

适合：元素类型稳定、操作种类经常增加、希望把相关操作集中到一个访问者里（抽象语法树 AST 处理、报表导出、对象结构上的多种统计）。

不适合：元素类型经常增加（每加一种元素，所有访问者都要改）、元素内部状态需要严格封装、操作很少且稳定。

#### 常见误用

- 元素类型频繁变化，访问者接口跟着改，所有实现都要重编译。
- 访问者直接修改元素内部状态，破坏封装。
- 为了“支持未来操作”提前引入访问者，结果只有一种访问者。
- 双重分派理解不清，`accept` 里调错 `visit` 重载，导致运行时行为不符合预期。


## 五、易混模式对比

很多模式的结构看起来相似，区别往往在**意图**而不是类图。这一章用表格对比最常被问到的几组，选型时先问“我要解决的核心问题是什么”。

### 5.1 代理、装饰器、适配器

| 维度 | 代理 Proxy | 装饰器 Decorator | 适配器 Adapter |
| --- | --- | --- | --- |
| 核心目的 | 控制对目标对象的访问 | 动态增加职责 | 转换接口，使双方能协作 |
| 接口是否变化 | 不变，与目标实现同一接口 | 不变，与被装饰对象同一接口 | 变为客户端期望的目标接口 |
| 是否持有原对象 | 持有，通常自己创建或注入 | 持有，层层包装 | 持有被适配对象 |
| 典型增强 | 权限、懒加载、远程、事务、日志 | 叠加功能，可组合多个 | 参数/返回值/异常语义转换 |
| 客户端感知 | 通常不知道是代理 | 可自由组合装饰器 | 只知道目标接口 |
| 典型场景 | Spring AOP、MyBatis Mapper、Dubbo 引用 | Java I/O 流、咖啡加料 | 旧日志系统接入、第三方 SDK 包装 |

一句话区分：**代理控制访问，装饰器叠加功能，适配器转换接口。**

### 5.2 策略、状态、命令

| 维度 | 策略 Strategy | 状态 State | 命令 Command |
| --- | --- | --- | --- |
| 行为由谁决定 | 客户端选择算法 | 对象内部状态决定 | 调用者选择并触发命令 |
| 是否运行时切换 | 是，随时替换 | 是，随状态流转 | 是，但切换的是“请求对象” |
| 封装内容 | 可互换的算法 | 每个状态下的行为与转换 | 一次请求及其撤销逻辑 |
| 典型场景 | 促销计算、支付渠道、排序算法 | 订单流转、电梯、连接状态 | 遥控器、任务队列、撤销重做 |

### 5.3 模板方法与策略

| 维度 | 模板方法 Template Method | 策略 Strategy |
| --- | --- | --- |
| 复用方式 | 继承：父类定义骨架，子类实现步骤 | 组合：上下文持有策略对象 |
| 绑定时机 | 编译期确定子类 | 运行期替换策略 |
| 扩展单位 | 子类 | 策略类 |
| 流程控制 | 父类控制步骤顺序 | 上下文只负责委托，流程由调用方编排 |
| 适用 | 流程稳定、步骤可变 | 算法可互换、需要动态切换 |

### 5.4 组合与外观

| 维度 | 组合 Composite | 外观 Facade |
| --- | --- | --- |
| 核心目的 | 统一对待单个对象和组合对象 | 为复杂子系统提供简化入口 |
| 结构 | 树形，容器递归包含子节点 | 星形，外观协调多个子系统 |
| 客户端 | 面向统一组件接口递归操作 | 只调用外观的高层方法 |
| 典型场景 | 文件系统、菜单、组织架构 | 下单流程、启动流程、SDK 封装 |

## 六、实践建议与常见误区

知道模式“怎么用”还不够，更重要的是知道“什么时候不用”。这一章把前文的选型建议集中起来，并列出业务代码中最常见的误用。

### 6.1 什么时候不该用设计模式

1. **需求还没稳定**：变化方向不明确时，先写简单实现，等变化点出现再重构。
2. **只有一种实现**：为唯一实现抽接口、加工厂，通常只是增加跳转。
3. **团队不熟悉**：模式名称不能代替注释和文档；如果团队读不懂，维护成本会超过收益。
4. **性能敏感路径**：多层代理、反射、事件派发都会带来开销，需要实测而不是凭感觉。
5. **为了“看起来专业”**：模式是解决问题的手段，不是代码评审的评分项。

### 6.2 常见误区清单

- 把简单工厂当成 GoF 的工厂方法，新增产品仍要修改工厂类。
- 认为单例能保证分布式系统全局唯一；它只保证单个 JVM 内唯一。
- 使用双重检查锁却漏写 `volatile`。
- 用 `super.clone()` 做浅拷贝，导致可变字段被共享。
- 加了 `@Transactional` 就以为事务一定生效，忽略自调用和代理边界。
- 把 JDK 动态代理对象强转成实现类。
- 观察者监听器里做耗时操作或吞异常。
- 策略上下文里仍写 `if/else` 选择策略。
- 模板方法没有声明 `final`，流程被子类改写。
- 责任链没有兜底，请求静默丢失。
- 状态模式退化成“状态字段 + 巨大 switch”。
- 边遍历集合边直接删除元素，触发并发修改异常。
