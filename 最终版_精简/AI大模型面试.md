## 一、大模型基础概念

本章建立整体印象：大模型到底"大"在哪里、为什么规模上去之后会出现新能力、GPT 和 BERT 两类模型各自负责什么活。这些概念是后面微调、RAG、推理加速的共同语言。

### 1.1 大模型是什么：从"参数"说起

**参数（Parameter）** 是神经网络里可被训练调整的数值，可以理解成模型的"经验权重"。传统程序把业务规则写成 `if/else`，大模型则把规则变成了几十亿个浮点数——规则没有被写出来，而是从海量文本里"统计"出来的。

规模用参数量衡量：1B 表示 10 亿参数，7B 表示 70 亿参数。常见的量级是 7B、13B、70B 以及 MoE 结构下的数百 B（总参数大、每次只激活一部分，见 5.3）。

一个必须记住的换算是**权重显存**：

```text
权重显存 ≈ 参数量 × 每个参数的字节数
FP16/BF16：2 字节/参数  → 7B 模型约 14GB
INT8：1 字节/参数        → 7B 模型约 7GB
INT4：0.5 字节/参数      → 7B 模型约 3.5GB
```

这个式子后面反复用到：它解释了为什么 7B 模型在 24GB 显存的卡上只能勉强跑推理，而 70B 模型必须多卡。

大模型有三类基本能力：**理解**（分类、抽取、情感判断）、**生成**（写文案、写代码、生成摘要）、**推理**（多步计算、条件判断）。同一个模型可以同时具备三种能力，具体偏向哪边取决于它的结构（见 1.3）和训练方式。

### 1.2 涌现能力（Emergent Abilities）

**涌现能力**指模型在**没有被专门训练过的任务**上，随着规模（参数量、数据量、算力）增大到某个临界点后突然表现出的能力，例如突然会做多步算术、会按格式输出、会"举一反三"。

生活化比喻：这有点像给系统加内存——加到某个阈值之前，缓存命中率一直是 40%，看不出效果；越过阈值后命中率突然跳到 90%，用户体验"突然变好"。能力不是线性长出来的，而是跨过临界点后成规模地出现。

产生原因通常从四个角度解释：

| 原因 | 说明 |
| --- | --- |
| 数据量增加 | 互联网文本规模暴涨，模型见过更广泛的语言现象和语境，泛化面更宽 |
| 算力提升 | GPU/TPU 让训练更大模型成为可能，规模本身是能力的前提 |
| 架构改进 | Transformer 的自注意力能建模长距离依赖，表达能力强于 RNN 系结构 |
| 预训练 + 微调范式 | 先在海量无标注数据上预训练，再在具体任务上微调，知识可迁移 |

需要客观补充一点：也有研究认为部分"涌现"是**评测指标不连续**造成的错觉——比如用"完全答对才算对"的严格指标时曲线很陡，换成连续打分指标（如 token 级准确率）后曲线就变平滑了（Schaeffer 等，NeurIPS 2023）。所以看到"某能力在某规模突然出现"的说法，要留意它用的指标是什么。

工程上的用法：涌现能力意味着**换更大的模型可能直接解决某些难题**，但也意味着小模型上"多喂点数据"未必能补上，选型时要先做基线对比，而不是靠猜。

### 1.3 GPT 与 BERT：两条技术路线

两者都基于 Transformer，但一个只留解码器、一个只留编码器，这决定了它们擅长的事完全不同。

| 维度 | GPT（Decoder-only，仅解码器） | BERT（Encoder-only，仅编码器） |
| --- | --- | --- |
| 注意力方式 | 掩码自注意力，每个位置只能看到左边（历史） | 双向自注意力，每个位置能看到全句 |
| 训练目标 | 自回归（AR）：给定前文预测下一个词 | 掩码语言模型（MLM）：挖掉部分词再还原 |
| 擅长 | 生成：对话、写作、代码、摘要 | 理解：分类、实体识别、语义匹配、抽取 |
| 典型用法 | 提示词 + 生成接口，或继续微调 | 加一个分类头做微调 |
| 短板 | 看不到"未来"信息，长文生成易跑偏 | 不能直接生成文本，需另设生成头 |
| 位置信息 | 可学习位置嵌入（GPT 系列） | 可学习位置嵌入，最大长度受训练长度限制 |

> 常见误区：有说法称"BERT 用可学习位置编码、GPT 用正弦位置编码"。实际上 GPT 系列与 BERT 用的都是**可学习位置嵌入**；正弦（Sinusoidal）编码是原始 Transformer 论文的方案，后来被 RoPE 等相对位置方案取代（见 2.4）。

**案例 1（理解任务，选 BERT）**：把用户投诉邮件分成"物流问题/产品质量/服务态度"三类，用 BERT 微调后准确率约 95%，原因是双向注意力能同时看到"物流延迟"和"包装破损"这类前后呼应的线索。

```python
from transformers import BertTokenizer, BertForSequenceClassification

model = BertForSequenceClassification.from_pretrained(
    'bert-base-uncased', num_labels=3
)
# 之后接常规微调循环：前向 → 交叉熵 → 反向 → 更新
```

**案例 2（生成任务，选 GPT）**：给长新闻生成摘要，用生成式模型 + 提示词即可，摘要流畅、覆盖关键信息，但单向结构偶尔会漏掉后文细节。

**案例 3（混合架构最优）**：电商导购机器人里，用 BERT 做意图识别（"查订单""要退货"），用 GPT 生成回复话术，两者串联后响应速度与准确率都更好。

**选型建议**：需要生成、需要零样本/少样本迁移，选生成式（GPT 系）；需要高精度分类、抽取，数据量有限但要稳定，选编码器式（BERT 系）。近年趋势是两类结构融合（如 T5、UniLM 同时支持理解与生成），大模型时代生成式更通用，但 BERT 在"小而准"的分类场景仍不可替代。

### 1.4 PrefixLM 与 CausalLM：注意力能不能"回头看"

**CausalLM（因果语言模型）** 严格自回归：生成第 n 个词时只能看前 n-1 个词。**PrefixLM（前缀语言模型）** 允许对"前缀"部分做双向注意力，只对生成部分做单向注意力。

生活化比喻：CausalLM 像只能往后翻的书，读过的不许回头再看；PrefixLM 像先给你一张"背景资料卡"，这张卡可以反复看，只有正文要一句一句往后写。

| 任务 | PrefixLM 的表现 | CausalLM 的表现 |
| --- | --- | --- |
| 智能客服多轮回复 | 历史对话作为前缀，生成时可见上下文，回复更连贯 | 需外部状态管理（把历史拼进 prompt）才能利用上下文 |
| 新闻标题生成 | 前缀会引入冗余信息，不适用 | 输入正文，自回归生成标题，简单直接 |
| 文档翻译 | 可先编码原文前缀再生成译文 | 按原文顺序逐句生成 |

多轮对话中的前缀写法（示意）：

```python
# 历史对话作为前缀
prefix = "用户：我的订单编号是12345，什么时候发货？\n客服：您的订单预计明天发货。"
# 生成回复时模型可见整个前缀
response = model.generate(prefix)
```

标题生成则只需当前内容：

```python
text = "科学家发现新型量子材料，导电效率提升200%。"
title = causal_lm.generate(text)
```

**怎么选**：任务强依赖上下文（多轮对话、长文档理解）优先 PrefixLM 思路；只需"接龙"（创作、翻译、续写）用 CausalLM 更省事。复杂系统可以组合：前缀部分负责理解上下文，生成部分负责输出答案。

### 1.5 常见问法

- **问：大模型的"大"体现在哪？** 参数量（7B~数百 B）、训练数据量（TB 级文本）、算力投入三个维度同时放大；参数量直接决定权重显存，是工程上最关心的数字。
- **问：涌现能力是真 capability 还是指标错觉？** 两种解释都存在：规模跨过临界点后组合能力确实增强；同时部分"突变"源于评测指标不连续。回答时给出两个视角更稳妥。
- **问：GPT 和 BERT 一定要二选一吗？** 不必。生产系统常见"BERT 做意图分类 + GPT 做回复生成"的组合，各自用在其擅长的位置。
- **问：PrefixLM 和 CausalLM 的区别一句话说清？** 区别在注意力掩码：前缀能否被双向看到。能用上下文的是 PrefixLM，只能看历史的是 CausalLM。

## 二、模型结构与注意力机制

本章讲清一个核心问题：**一句话进模型，为什么能"理解"它？** 答案落在三个零件上——注意力机制决定"看哪里"，位置编码决定"知道先后"，归一化与激活函数决定"训练是否稳"。把这些零件弄明白，看论文和调参就不会盲人摸象。

### 2.1 编码器-解码器结构的工作流程

**编码器（Encoder）** 负责把输入句子压成一组带语义的向量；**解码器（Decoder）** 负责在这些向量的"提示"下，一个词一个词地写出结果。原始 Transformer 就是 6 层编码器 + 6 层解码器。

生活化比喻：编码器像把一份外文合同翻译成内部"要点清单"，解码器像拿着这份清单用中文重写一份新合同——清单不保留原文语序，只保留意思。

**编码器每一层做什么**：

1. 多头自注意力：让每个词和句子里所有词算相关度，得到"融合了上下文"的新表示。
2. 前馈网络（FFN）：对每个位置独立做两次线性变换 + 激活，负责"加工特征"。
3. 残差连接 + 层归一化：把输入直接加到输出上，再做归一化，保证深层也能训得动。

**解码器每一层多两个零件**：

1. 掩码多头自注意力：只能看已生成的词（防止"偷看答案"）。
2. 编码器-解码器注意力（Cross-Attention）：Q 来自解码器，K/V 来自编码器输出，实现"对着原文写译文"。

**案例：英译中机器翻译**

1. 数据准备：清洗英中平行语料，分词后转成词嵌入。
2. 模型配置：编码器 6 层、解码器 6 层、8 个注意力头、模型维度 512、FFN 维度 2048。
3. 训练：交叉熵损失 + Adam，学习率预热后衰减，标签平滑防过拟合。
4. 推理：束搜索（Beam Search，同时保留若干候选序列）生成译文，用束宽和长度惩罚调质量。
5. 长句与低资源语言：增加位置编码维度、调注意力头数；低资源方向用迁移学习 + 数据增强。

推理过程举例：输入 "The cat sat on the mat."，编码器输出上下文向量；解码器从起始符开始，逐词生成"猫 → 坐 → 在 → 垫子 → 上 → 结束符"。

```python
import torch

# 伪代码：编码器-解码器逐词生成
encoder_output = model.encoder(encoder_input)
decoder_input = torch.tensor([[0]])          # 起始标记
for _ in range(10):
    decoder_output = model.decoder(decoder_input, encoder_output)
    next_token = torch.argmax(decoder_output[:, -1, :], dim=-1)
    decoder_input = torch.cat([decoder_input, next_token.unsqueeze(0)], dim=-1)
    if next_token.item() == 7:               # 结束标记
        break
```

**案例：智能客服系统**（编码器 4 层理解用户语义、解码器 4 层生成回复）：用户问"我的订单状态是什么？"，编码器提取"订单""状态"等关键信息，解码器结合历史对话（订单号 12345）生成"您的订单正在配送中，预计明天送达"。工程要点：联合训练编码器与解码器、用对抗训练提升鲁棒性、用温度参数控制回复多样性；多轮一致性靠对话状态跟踪模块保证。

**优势与局限**

| 维度 | 说明 |
| --- | --- |
| 优势 | 可并行计算（不像 RNN 必须逐词算）；自注意力直接建模长距离依赖；层数/头数/维度可灵活调整 |
| 局限 | 参数量大、算力需求高；注意力计算量随序列长度平方增长；效果高度依赖数据质量 |
| 演进方向 | 稀疏/线性注意力降低复杂度；多模态融合；蒸馏与量化做轻量化 |

### 2.2 自注意力与多头注意力

**自注意力（Self-Attention）** 的本质是"让每个词去问全句每个词：你和我有多相关？"实现上把输入投影成三个矩阵：

- **Q（Query，查询）**：我想找什么。
- **K（Key，键）**：我能提供什么。
- **V（Value，值）**：我实际的内容。

相似度用点积算，再除以 $\sqrt{d_k}$ 缩放，softmax 归一化成权重，最后对 V 加权求和：

$$\text{Attention}(Q,K,V)=\text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}}\right)V$$

为什么要除以 $\sqrt{d_k}$：维度越高点积越大，softmax 会被推到极端（几乎 one-hot），梯度趋近于 0，训练就"卡住"了。缩放把数值拉回合理区间。

**多头注意力（Multi-Head Attention）** 把 $d_{model}$ 维切成 $h$ 份，每份独立算一次注意力，最后拼起来再线性变换。不同头会自然分工：有的头盯数字、有的头盯否定词、有的头建立术语关联。

Java 类比：单头注意力像一个人读完需求文档后给结论；多头注意力像 8 个各管一块的评审（性能、安全、兼容性……）分别给意见，最后汇总成一份评审报告——比一个人看得更细。

**项目案例：金融客服系统的多头改造**

- 把 512 维向量拆成 8 个 64 维子空间，头 1 专门捕捉序数（"第 2 年第 3 次调整"），头 3 建立"LPR"与"基点"的术语关联，头 6 检测否定词对业务语义的影响。
- 实现上用线性变换生成 Q/K/V 后分头计算，用缩放点积稳定梯度；用门控（GLU）融合各头输出替代简单拼接，提升特征交互效率；底层结合 FlashAttention 优化长文本。
- 效果：复合意图识别准确率 89%，处理耗时从 230ms 降到 150ms，且注意力权重可视化能辅助 badcase 分析。

**头数怎么定**：常用经验是让每个头的维度 $d_{head}=d_{model}/h$ 保持在 64 左右，即 $h \approx d_{model}/64$（例如 512 维配 8 头、4096 维配 32 头）。头数超过 8 时建议考虑参数共享或分组，长文本场景优先用稀疏注意力，工业部署必须考虑 KV Cache 显存（见 5.4）。

> 注意：头数常被写成"经验公式 $h=2^{\log_2(d_{model}/64)}$"，但该式化简后就是 $d_{model}/64$，写成指数形式没有额外含义，按 $h\approx d_{model}/64$ 理解即可。

### 2.3 位置编码的作用

**位置编码（Positional Encoding）** 是给每个 token 附加的"序号信息"。原因很直接：自注意力对输入顺序是**不敏感**的——把"猫吃鱼"和"鱼吃猫"的词向量打乱喂进去，注意力算出来的集合结果一样，模型分不清谁在前。

生活化比喻：自注意力像一次不带 `ORDER BY` 的多表 JOIN，结果集里谁先谁后它不关心；位置编码就是给每行加一列 `seq_no`，让后续处理能排序。

**绝对位置编码 vs 相对位置编码**

| 维度 | 绝对位置编码 | 相对位置编码 |
| --- | --- | --- |
| 信息载体 | 每个位置绑定一个固定向量（正弦函数，或可学习向量） | 只关注位置之间的距离（如 RoPE 的旋转、T5 的相对偏置） |
| 外推能力 | 受训练长度限制，超出后失效 | 依赖相对距离，天然更适合长序列 |
| 计算开销 | 低（查表或直接计算） | 略高（需额外矩阵运算或偏置表） |
| 适用场景 | 短文本分类、固定长度任务 | 长文本生成、翻译、摘要 |

**案例：跨境电商评论情感分析**（最长 512 词）：初期用 BERT 的绝对位置编码，超过 512 词后模型分不清后段语义，中文还因分词粒度不同出现跨词依赖断裂。改为 RoPE 相对位置编码后支持到 1024 词，同时用 SentencePiece 分词减少跨词冲突。

### 2.4 位置编码的演进

四个阶段，一条主线：从"记住绝对坐标"走向"记住相对距离"。

| 阶段 | 代表模型 | 做法 | 问题 |
| --- | --- | --- | --- |
| 正弦编码（2017） | 原始 Transformer | 固定三角函数：$PE(pos,2i)=\sin(pos/10000^{2i/d})$，$PE(pos,2i+1)=\cos(\cdot)$ | 无外推能力，超训练长度后位置信息失真 |
| 可学习位置嵌入（2018） | BERT、GPT | 把位置索引映射成可训练向量 | 长度硬性受限（如 512），长文直接截断 |
| 相对位置编码（2020） | T5、DeBERTa | 在注意力里加相对距离偏置：$A_{m,n}=Q_mK_n^{\top}+b_{m-n}$ | 需预设最大距离，偏置表占参数 |
| 旋转位置编码 RoPE（2021） | LLaMA、ChatGLM、Baichuan | 用旋转矩阵把位置"转"进 Q/K，使点积只依赖位置差 | 超长外推仍需配合缩放技巧 |

**RoPE 的核心恒等式**：把位置 $m$ 的 query 和位置 $n$ 的 key 分别旋转 $m\theta$、$n\theta$，点积结果只与 $(m-n)$ 有关：

$$\text{Attention}(q_m,k_n)=\text{Re}\left[\langle q_m e^{im\theta},\,k_n e^{in\theta}\rangle\right]=\langle q_m,k_n\rangle\,e^{i(m-n)\theta}$$

这带来两个好处：相对位置信息**内生于**注意力计算，不需要额外参数；只改注意力计算、不存位置矩阵，显存占用更低。

简化版实现（成对维度旋转，示意）：

```python
def apply_rope(q, k, pos_ids, dim):
    theta = 1.0 / (10000 ** (2 * torch.arange(dim // 2) / dim))
    angles = pos_ids[:, None] * theta[None, :]
    sin, cos = torch.sin(angles), torch.cos(angles)
    q_rot = q[..., :dim // 2] * cos + q[..., dim // 2:] * sin
    k_rot = k[..., :dim // 2] * cos + k[..., dim // 2:] * sin
    return q_rot, k_rot
```

**长度外推（NTK-aware 缩放）**：把 RoPE 的底数 `base` 从 10000 调大（例如调到 500000），相当于把不同维度的旋转频率整体"压平"，让模型在更长序列上仍然看到相近的相位差，从而不改权重也能扩上下文。调大 `base` 是主流做法；工程上常按目标长度倍数选取（2K 扩到 32K 是 16 倍，实践里 base 常取几十万量级，需实测）。

> 注意：NTK-aware 缩放常被写成"逐维缩放旋转角 $\theta'=\theta\cdot\text{scale}^{-2/d}$"，这只是对"频率被整体压低"的近似描述；真正落地可操作的是调大 `base`（或等价地调频率）。

**案例：ChatGLM-6B 的长文本优化**：初始版本超过 512 token 后性能明显下降。方案是改用 RoPE 编码 + NTK 缩放把窗口从 2K 扩到 32K，无需全量微调；结果长文档摘要类任务准确率提升约 37%，显存只增加约 8%（该数字为项目实测经验值）。

**趋势**：动态外推方案（如 YaRN）自适应调频率，避免人工设定倍数；多模态场景统一文本/图像/视频的位置表示。

### 2.5 归一化：LayerNorm 与 BatchNorm 怎么选

**归一化（Normalization）** 的作用是把每层输入拉回稳定分布，避免"越往深层数值越飘"，从而加速收敛。

- **LayerNorm**：对**单个样本**的所有特征维度做归一化（减均值、除标准差），再乘缩放、加偏置。
- **BatchNorm**：对**同一批次内同一特征维度**做归一化，依赖这一批数据的统计量。

生活化比喻：BatchNorm 像按"全班平均分"给每个人打分——班里人少或换班（批次小、分布变）时平均分就不靠谱；LayerNorm 像按"每个人自己的各科平均分"折算——只看自己，跟同班是谁无关。

| 维度 | LayerNorm | BatchNorm |
| --- | --- | --- |
| 统计范围 | 单样本、跨特征 | 跨样本、同特征 |
| 依赖批次 | 不依赖，batch=1 也能算 | 强依赖，批次小则统计噪声大 |
| 变长序列 | 天然适配 | 需 padding 对齐，处理麻烦 |
| 典型场景 | NLP（Transformer、RNN）、推荐序列建模 | CV（CNN）、固定尺寸输入、语音帧特征 |

**案例 1（LayerNorm，电商评论情感分析）**：长文本导致梯度波动大，不同长度样本分布差异明显；在 Transformer 层后加 LayerNorm 稳定特征分布，训练速度提升约 25%，F1 提升约 4.2%（项目经验值）。

**案例 2（BatchNorm，医学图像分割）**：眼底血管分割用 UNet、输入 512×512；batch_size=4 时 BatchNorm 统计量噪声大、分割边缘模糊，且不同患者图像亮度差异影响鲁棒性。做法是卷积后接 BatchNorm 加速收敛，同时做亮度归一化；结果 Dice 提升约 12%，训练时间缩短约 20%。

```python
class UNetBlock(nn.Module):
    def __init__(self, in_channels, out_channels):
        super().__init__()
        self.conv1 = DoubleConv(in_channels, out_channels)
        self.bn1 = nn.BatchNorm2d(out_channels)
        self.conv2 = DoubleConv(out_channels, out_channels)
        self.bn2 = nn.BatchNorm2d(out_channels)

    def forward(self, x):
        x = F.relu(self.bn1(self.conv1(x)))
        x = F.relu(self.bn2(self.conv2(x)))
        return x
```

**实践建议**：先看数据形态——序列任务选 LayerNorm，固定尺寸图像选 BatchNorm；小批量训练慎用 BatchNorm，可换 GroupNorm；最终用消融实验确认收益。

### 2.6 LLaMA 的两个改动：RMSNorm 与 SwiGLU

LLaMA 在 Transformer 上做了两处"减法/换件"，目的都是**在效果不掉的前提下省算力**。

#### 2.6.1 RMSNorm：去掉均值中心化

LayerNorm 的公式是：

$$\text{LayerNorm}(x)=\gamma\cdot\frac{x-\mu}{\sqrt{\sigma^{2}+\epsilon}}+\beta$$

要算均值 $\mu$ 和方差 $\sigma^2$，还要维护偏置 $\beta$。RMSNorm 的观察是：**"减均值"这一步对训练稳定性并非必需**，只要按均方根（RMS）做缩放就够：

$$\text{RMSNorm}(x)=\gamma\cdot\frac{x}{\sqrt{\frac{1}{d}\sum_{i=1}^{d}x_i^{2}+\epsilon}}$$

也就是说：不减均值（无 re-centering）、不加偏置 $\beta$（LLaMA 的实现里只有缩放参数 $\gamma$）。论文报告在多个模型上运行时间降低约 7%~64%，效果与 LayerNorm 相当（Zhang & Sennrich, NeurIPS 2019）。

> 注意：RMSNorm 常被误写成带偏置的形式 $\gamma\cdot x/\sqrt{\text{RMS}(x)+\epsilon}+\beta$。按论文与 LLaMA 的实现，RMSNorm **不含偏置 $\beta$**（只保留缩放参数 $\gamma$），$\epsilon$ 加在均方根内部。

```python
class RMSNorm(nn.Module):
    def __init__(self, hidden_size, eps=1e-6):
        super().__init__()
        self.eps = eps
        self.weight = nn.Parameter(torch.ones(hidden_size))

    def forward(self, x):
        variance = x.pow(2).mean(-1, keepdim=True)
        x = x * torch.rsqrt(variance + self.eps)
        return self.weight * x
```

#### 2.6.2 SwiGLU：给前馈层加一道"闸门"

**GLU（Gated Linear Unit，门控线性单元）** 的思想是：一路做"内容"，一路做"闸门"，两者逐元素相乘，让模型自己决定放多少信息过去。

标准 SwiGLU 形式（Shazeer, 2020）：

$$\text{SwiGLU}(x)=\text{Swish}(xW_1)\otimes(xW_3)$$

其中 Swish/SiLU 为 $x\cdot\sigma(x)$，$\otimes$ 表示逐元素乘，最后再接一个输出投影 $W_2$。

> 注意：常见的错误写法是 $x\cdot\sigma(W_2\cdot\delta(W_1x))$。SwiGLU 的标准形式是**两条并行的线性投影，其中一条过 Swish 激活后，与另一条逐元素相乘**，最后再接输出投影。

**参数量的真相**：SwiGLU 比 ReLU-FFN 多了一个投影矩阵，所以如果隐层维度不变，参数量反而**增加约 50%**。LLaMA 的做法是把 FFN 隐层维度从 $4d$ 降到约 $\tfrac{8}{3}d$，使总参数量与原来持平。因此"参数量减少 50%"的说法不成立，准确说法是"在同等参数量预算下效果更好"。

| 对比项 | 说明 |
| --- | --- |
| 计算复杂度 | 与 ReLU-FFN 同阶（都是 $O(d\cdot d_{ff})$），常数略高 |
| 效果 | 多个基准上优于 ReLU/GELU 前馈层（原论文结论） |
| 代价 | 多一个投影矩阵，需靠调小隐层维度平衡参数量 |
| 工程收益 | 门控让梯度传播更顺，长训练更稳（项目经验，非普适结论） |

**两个落地案例**

1. 跨境电商多语言客服：Embedding 层后加 RMSNorm、Cross-Attention 处保留 LayerNorm，FFN 换 SwiGLU 并做门控系数动态调整；阿拉伯语 BLEU 提升约 12.7%，训练崩溃次数减少约 63%，多语言混合任务响应速度提升约 41%（项目经验值）。
2. 金融风控文本分类：RMSNorm 与 GroupNorm 组合成双重归一化、引入自适应缩放因子；SwiGLU 用参数化变体并接残差；F1 提升约 9.2 个百分点，训练时间缩短约 37%（项目经验值）。

**综合应用要点**：分层用不同归一化（输入层 RMSNorm、注意力层 LayerNorm）；归一化参数不要一把梭，按层统计量动态调节；混合精度训练时归一化计算用 BF16、门控参数保留 FP32，兼顾速度与精度。

### 2.7 从 RNN/LSTM 到 Transformer：长距离依赖

**RNN/LSTM/GRU** 靠"循环"逐词传递状态；**Transformer** 靠"注意力"让任意两个位置直接相连。

生活化比喻：RNN 像传话游戏，一句话要经过 20 个人才能传到队尾，中途必然走样；Transformer 像开会时每个人都能直接对话，不需要经过中间人。

| 维度 | LSTM/GRU | Transformer |
| --- | --- | --- |
| 依赖处理方式 | 逐步传递，信息随步数衰减 | 直接计算任意两点关联，无路径衰减 |
| 最大有效距离 | 约 20~30 词（经验值） | 理论上不受限，实际受显存与训练长度限制 |
| 训练并行度 | 序列内无法并行，慢 | 矩阵运算高度并行，快 |
| 典型应用 | 短文本分类、传感器时序、资源受限设备 | 机器翻译、长文档生成、对话系统 |

**案例 1（机器翻译，英译中）**：需要跨 20 多个词捕捉从句嵌套（"The report that the committee submitted ... has finally been published"）。

| 模型 | BLEU-4 | 长句（>30 词）准确率 | 训练时间 |
| --- | --- | --- | --- |
| LSTM | 32.1 | 58% | 72 小时 |
| Transformer | 38.7 | 82% | 28 小时 |

（上表为项目实测对比，数值随语料与硬件变化，仅作量级参考。）LSTM 在嵌套从句上频繁漏译，因为信息传递超过 20 步后衰减严重；Transformer 通过自注意力直接把 `which` 与 `report` 关联起来。

**案例 2（金融文档摘要）**：输入 5000+ 词年报，关键信息分散在首尾。GRU + 滑动窗口（200 词一段）会切断"现金流风险"（开头）与"应对措施"（结尾）的联系；Transformer 直接读全文，ROUGE-L 提升约 21%，能关联"融资成本上升 → 发行低息债券置换"。

```text
文档开头: [融资环境恶化...利率上升] ------------------------ (注意力权重: 0.6)
文档结尾: [已发行10亿低息债券置换存量债务] ---------------- (注意力权重: 0.7)
输出摘要: "面对融资成本上升风险，公司通过低息债券置换降低利息支出。"
```

**选型建议**：序列短（<30 步）、硬件受限、时延敏感 → LSTM/GRU；长逻辑链、需要全局信息、训练速度优先 → Transformer。混合方案（如 Longformer 的局部 + 稀疏注意力）在超长文本上更划算。

### 2.8 FlashAttention：把中间矩阵"算掉"

**问题**：标准注意力要显式存下 $QK^{\top}$ 这个 $N\times N$ 的分数矩阵和 softmax 后的权重矩阵，显存 $O(N^2)$。8K 序列、FP32 时一个矩阵就是 $8192\times8192\times4\text{B}\approx256\text{MB}$，再乘层数（几十层）和 batch，显存迅速爆掉。

生活化比喻：像统计一张 8000×8000 的表格，但每次只用到其中一小块——标准做法是把整张表都打印出来贴在墙上，FlashAttention 则是拿一块小白板，算完一块擦掉再算下一块。

**三个手段**：

1. **分块计算（Tiling）**：把 Q、K、V 切成小块（如每块 128 个 token），逐个块算局部注意力，用"累加器"在线更新输出与归一化因子（online softmax），从而**不需要**存完整的分数矩阵。显存从 $O(N^2)$ 降到 $O(N)$。
2. **重计算（Recomputation）**：前向不存中间矩阵，反向时按块重算。以少量额外计算换数倍显存下降。
3. **硬件感知（IO-aware）**：让分块大小匹配 GPU 的 SRAM（片上高速缓存），数据在 SRAM 内算完再写回 HBM（显存），大幅减少显存读写次数。

**收益量级**（论文与工程实践给出的区间，非固定值）：显存从平方级降到线性级；长序列场景速度提升约 2~4 倍；反向重算带来的额外计算量约在 10%~20% 量级。

| 优化维度 | 传统 Attention | FlashAttention |
| --- | --- | --- |
| 显存占用 | $O(N^2)$ | $O(N)$ |
| 计算速度 | 慢（频繁读写显存） | 快（SRAM 内计算） |
| 长序列支持 | 受限（如 2K） | 显著更长（8K~100K 级） |
| 适用场景 | 短文本、低资源环境 | 长文本、科学计算、医疗影像 |

**三个案例**

1. 长文本摘要（8K）：标准注意力在 A100 上只能跑 2K 序列；改用分块后显存从 48GB 降到 16GB，训练速度从 3 samples/s 提升到 9 samples/s，摘要 ROUGE-L 提升约 27%（项目经验值）。
2. 基因序列分析（100K）：传统实现显存需求超 200GB 无法运行；分块 + 稀疏注意力（局部分块 + 全局关键点）后显存控制在 40GB 内，速度提升约 22 倍，变异检测准确率提升约 19%。
3. 医学影像分割（512³ 体素）：像素级注意力显存需求超 80GB；按 64×64 局部块分块后降到 18GB，训练时间从 7 天缩短到 1.5 天，Dice 提升约 11%。

**行业影响**：训练成本下降，让 65B 级模型在消费级显卡上做微调成为可能；被 vLLM、DeepSpeed 等框架集成，成为部署标配；其"分块 + 重算"思想已延伸到 MoE、RetNet 等新架构。

### 2.9 进阶了解（可跳过）

以下内容偏源码与极端调优，初学可略过，遇到具体性能问题再回来看。

- **融合算子**：把 LayerNorm、残差、激活合并成一个 kernel，减少显存往返（FlashAttention 的同类思路）。
- **KV Cache 布局**：分页式（PagedAttention）与连续式布局对显存碎片影响很大，见 5.4。
- **注意力变体**：滑动窗口（Mistral）、稀疏注意力（Longformer）、线性注意力，本质都是用"少算一些对"换长度。
- **数值精度**：BF16 比 FP16 动态范围大，长训练更稳；归一化统计量建议用 FP32 累加。

### 2.10 常见问法

- **问：为什么自注意力要除以 $\sqrt{d_k}$？** 防止高维点积数值过大把 softmax 推到饱和区，导致梯度消失。
- **问：多头注意力的"多头"到底带来了什么？** 提供多个互相独立的子空间，让模型并行捕捉不同类型的关系（位置、语法、术语、否定），比单头表达力更强且可并行计算。
- **问：位置编码为什么不能省？** 自注意力对顺序不敏感，没有位置编码时"猫吃鱼"和"鱼吃猫"对模型是同一个集合。
- **问：RoPE 相比正弦编码好在哪？** 相对位置内生于点积、无额外参数、支持长度外推；正弦编码没有外推能力。
- **问：LayerNorm 与 BatchNorm 一句话区别？** 归一化的维度不同：LayerNorm 看单个样本的全部特征，BatchNorm 看一批样本的同一特征。
- **问：FlashAttention 改变了模型结构吗？** 没有。它只改变注意力的计算与访存方式，输出在数学上等价，属于"实现层优化"。

## 三、训练与微调

本章回答工程上最常被问的两个问题：**微调要做哪些步骤**，以及**微调到底要多少显存**。前者决定流程设计（数据怎么准备、什么时候停），后者直接决定预算（买几张卡、能不能用 LoRA 代替）。本章还收进了混合精度、梯度累积、梯度消失这些"训练不稳时该调什么"的排查清单。

### 3.1 大模型微调的完整流程

**微调（Fine-tuning）** 是在预训练模型的基础上，用目标领域或任务的数据再训练一轮，让通用能力"偏"向具体业务。类比 Java 项目：预训练模型像一套成熟的通用框架，微调像写一个项目专属的配置和扩展点——框架内核不动，改的是适配层。

七个步骤：

1. **任务定义与数据准备**
   - 明确任务类型（分类、实体识别、生成）与评估指标（准确率、F1、BLEU）。
   - 收集并标注数据，保证质量与多样性；数据划分常用 80%/10%/10%（训练/验证/测试），验证集调参、测试集只用于最终评估。
2. **数据预处理与增强**
   - 转成模型输入格式（如 BERT 的 `[CLS] + 文本 + [SEP]`）。
   - 用与预训练模型匹配的分词器（如 BERT 的 WordPiece）切词。
   - 数据不足时用回译、随机遮盖、同义词替换扩充，提升泛化。
3. **模型选择与结构调整**
   - 理解类任务选编码器模型，生成类任务选解码器模型。
   - 全参数微调（更新所有参数）适合数据充足、任务差异大；参数高效微调（LoRA、Adapter）只训练少量参数，省算力。
   - 需要时加任务头（如分类任务加全连接层输出类别概率）。
4. **超参数与优化策略**
   - 学习率要小（全参数微调常用 $1\times10^{-5}$~$5\times10^{-5}$），避免破坏预训练特征；LoRA 这类只训练少量参数的方法可以用更大学习率（常见 $1\times10^{-4}$ 量级）。
   - 优化器常用 AdamW，配合权重衰减防过拟合。
   - 训练技巧：分层学习率（底层更新更慢）、梯度裁剪、早停、混合精度训练。
5. **训练与验证监控**
   - 同时盯训练损失与验证集指标；用 Dropout、数据增强、L2 正则抑制过拟合。
6. **模型评估与迭代**
   - 测试集算最终指标，确认没有"过拟合验证集"；做错误分析定位问题样本；用网格搜索或 Optuna 调学习率、批大小。
7. **部署与持续迭代**
   - 导出为生产格式（ONNX、TensorRT）提升推理效率。
   - 上线后监控表现，定期用新数据再微调；必要时量化、剪枝做轻量化，适配边缘设备。

**补充要点**：

- **领域自适应**：目标领域与预训练分布差异大时，先做领域预训练（Domain-Adaptive Pretraining）再微调，效果通常好于直接微调。
- **多任务学习**：多个相关任务共享底层参数一起微调，提升泛化性。
- **数据质量优先**：微调阶段数据量不需要很大（万级高质量样本往往就有效），但标注一致性要严格检查。

### 3.2 全参数微调需要多少显存

这是面试高频计算题，也是采购机器的依据。核心公式：

$$\text{显存} \approx \text{参数量}\times(2+2+4+8)\ \text{字节} + \text{激活值} = \text{参数量}\times16\ \text{字节} + \text{激活值}$$

四项的来历（混合精度 + Adam）：

| 项目 | 精度 | 字节/参数 | 说明 |
| --- | --- | --- | --- |
| 模型权重 | FP16/BF16 | 2 | 前向计算用 |
| 梯度 | FP16/BF16 | 2 | 反向传播产生 |
| FP32 主权重 | FP32 | 4 | 优化器更新时用的高精度副本 |
| Adam 状态 | FP32 | 8 | 一阶动量 4 + 二阶方差 4 |

再加框架与临时缓冲，工程上常按 **18~20 字节/参数** 估算，即常说的"全参数微调约需 20 倍参数量的显存"。

**案例：LLaMA-7B（6.7B 参数）医疗指令微调**

1. 权重（FP16）：$6.7\text{B}\times2=13.4\text{GB}$
2. 梯度（FP16）：$13.4\text{GB}$
3. Adam 状态（FP32 动量 + 方差）：$6.7\text{B}\times8=53.6\text{GB}$
4. FP32 主权重：$6.7\text{B}\times4=26.8\text{GB}$
5. 激活值：粗略估算 $\text{batch}\times\text{seq}\times\text{hidden}\times\text{layers}\times\text{系数}$，以 batch=32、seq=2048、hidden=4096、32 层、系数 12 计算约 98GB；开启梯度检查点后实际约 35GB。

合计：$13.4+13.4+53.6+26.8+35\approx142\text{GB}$。单卡装不下，需要多卡 + ZeRO-3（把优化器状态和参数切分到各卡），切分后单卡可降到 45GB 左右。

> 注意：只算"权重 2 + 梯度 2 + Adam 状态 8 = 12 字节/参数"会漏掉 FP32 主权重，把 6.7B 算成约 80GB，与实测的 142GB 对不上。按 16 字节/参数的完整口径，6.7B 的静态占用约 107GB，加上激活值才是 142GB。

**三种省钱手段**

| 手段 | 做法 | 收益 | 代价 |
| --- | --- | --- | --- |
| 梯度检查点 | 只存部分中间结果，反向时重算 | 激活值大幅下降（本例 98GB→35GB） | 训练速度下降（约 20%~30%） |
| 混合精度 | 权重/梯度用 FP16，优化器用 FP32 | 显存约减半 | 需 Loss Scaling，收敛略慢 |
| ZeRO-3 / FSDP | 参数、梯度、优化器状态分片到多卡 | 单卡显存随卡数近似线性下降 | 通信开销增加 |

**硬件选型经验**：7B 全参数微调至少 8×A100 80GB（配 ZeRO-3）；13B 需要 16 卡级别；LoRA 微调 7B 只需单卡 24GB 左右即可起步（秩取 8 时约 14~16GB，属经验值）。真实项目里，专业领域（医疗、法律）若追求知识完整性可选全参数微调，靠 ZeRO-3 解决显存瓶颈；多数业务场景 LoRA 已足够。

### 3.3 参数高效微调：LoRA 与它的同伴

**LoRA（Low-Rank Adaptation，低秩适配）** 冻结原模型权重，在旁边挂两个小矩阵 $A$、$B$（秩 $r$ 远小于原维度），只训练这两个矩阵，推理时把 $BA$ 加回原权重。

生活化比喻：像给现有系统加一层"插件配置"——主程序（原权重）一行不改，只维护一份很小的差异化配置，出问题把配置摘掉就回到原状态。

| 方法 | 做法 | 训练参数占比 | 特点 |
| --- | --- | --- | --- |
| 全参数微调 | 更新所有权重 | 100% | 效果上限高，显存与成本最高 |
| LoRA | 低秩旁路矩阵 | 通常 <1% | 显存省、可多任务并存（切换适配器） |
| Prefix-Tuning | 在输入前加可训练前缀向量 | 极少 | 不改结构，占用序列长度 |
| Adapter | 层间插入小适配层 | 少量 | 推理略增延迟 |

选型建议：显存紧、要多业务共用一份基座 → LoRA；任务与预训练差异极大、数据充足 → 全参数微调；追求极致轻量、序列不长 → Prefix-Tuning / Adapter。

### 3.4 混合精度训练与 Loss Scaling

**混合精度训练** 指前向/反向用 FP16（或 BF16）算，权重更新等关键步骤保留 FP32。目的：省显存、提速度，同时不把精度搞崩。

生活化比喻：像用"估算 + 精算"两套账——日常流水用粗算（快、省纸），月底结账用精算（准），只在关键处保留高精度。

**四个关键步骤**

1. **权重备份**：保留一份 FP32 权重，前向/反向用 FP16 副本。因为 FP16 数值范围窄，直接用它累积更新会丢精度。
2. **损失放大（Loss Scaling）**：FP16 能表示的最小正规数有限，小梯度会直接变成 0（下溢）。做法是把 loss 乘一个大常数（如 $2^{16}$）再反向，梯度同步放大，回传后再除回来。
3. **精度累加**：梯度累加、归一化统计等操作用 FP32 进行，避免"加着加着就没了"。
4. **动态缩放**：`GradScaler` 根据是否出现 inf/nan 自动调整放大倍数——溢出就调小，稳定就调大。

**Loss Scaling 到底解决什么**：只解决**梯度下溢**（小梯度被 FP16 抹成 0）。它不解决梯度爆炸，也不解决精度损失，这两件事分别靠梯度裁剪和 FP32 主权重。

```python
from torch.cuda.amp import autocast, GradScaler

scaler = GradScaler()

with autocast():
    outputs = model(input_ids, attention_mask=attention_mask, labels=labels)
    loss = loss_fn(outputs, labels)

scaler.scale(loss).backward()      # 放大后反向，防下溢
scaler.step(optimizer)             # 内部先反缩放梯度，再更新
scaler.update()                    # 根据是否溢出调整缩放倍数
```

工程提示：BF16 动态范围接近 FP32，很多场景可以不用 Loss Scaling，训练更省心（A100 及以上支持）。

### 3.5 梯度累积与 DDP 梯度同步

**梯度累积（Gradient Accumulation）** 解决"显存装不下大 batch"：把多个小 batch 的梯度先攒着，攒够等效 batch 后再更新一次参数。

生活化比喻：像批量插入数据库——不是每条记录都提交一次事务，而是攒够 1000 条再 commit，减少开销、等效吞吐更大。区别是梯度累积攒的是梯度而不是数据。

```python
accum_steps = 4
optimizer.zero_grad()
for i, batch in enumerate(loader):
    loss = model(batch) / accum_steps   # 缩放，保证等效学习率不变
    loss.backward()
    if (i + 1) % accum_steps == 0:
        torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
        optimizer.step()
        optimizer.zero_grad()
```

配梯度累积时通常还要做两件事：

- **数值稳定性**：混合精度下用 `GradScaler` 防下溢；用梯度裁剪防爆炸。

```python
scaler = torch.cuda.amp.GradScaler()
with torch.cuda.amp.autocast():
    loss = model(data)
scaler.scale(loss).backward()
```

```python
torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
```

- **分布式协同**：多卡训练时用 DDP（DistributedDataParallel），它在每次反向结束后自动做梯度 All-Reduce，保证各卡梯度一致；梯度累积要在同一个累积窗口内保持同步。

```python
# 使用 DDP 进行梯度同步
model = torch.nn.parallel.DistributedDataParallel(model)
```

**收益与边界**（经验值）：显存占用可下降 30%~60%（因为激活值按小 batch 算）；支持等效更大 batch；冷启动时建议逐步增加累积步数以观察稳定性。

```python
for epoch in range(5):
    accumulation_steps = min(epoch * 2, 8)   # 逐步加大
```

**最佳实践**：梯度累积 + ZeRO-Offload + FlashAttention 组合使用；重点监控显存占用率、梯度范数、loss 抖动；未来方向包括动态/稀疏梯度累积与框架原生支持（PyTorch/XLA 等）。

### 3.6 梯度消失与梯度爆炸

**本质**：反向传播按链式法则连乘，层数一多，连乘结果要么趋近 0（消失，底层几乎不更新），要么急剧变大（爆炸，出现 inf/nan）。类比：一层层转发消息，每层打个 0.9 折，20 层后只剩 12%；每层放大 1.5 倍，20 层后放大 3000 多倍。

**案例**：某银行用 BERT-base 做信贷风险分类，第 8 层之后梯度接近 0，底层学不动。方案是 DeepSpeed 混合精度（ZeRO stage 2）+ 梯度裁剪：

```json
{
  "fp16": {"enabled": true},
  "zero_optimization": {"stage": 2, "contiguous_gradients": true},
  "gradient_clipping": 1.0
}
```

效果：梯度峰值下降约 90%，训练稳定，最终困惑度（PPL）降到 16.8。

**三类解决手段**

1. **架构层（治本）**
   - 残差连接：$\text{输出}=\text{LayerNorm}(x+\text{Sublayer}(x))$，给梯度一条"高速公路"。
   - Pre-LayerNorm：把归一化放到子层之前（LLaMA 的做法），比 Post-LN 更稳。项目实测：改为 Pre-LN 后梯度方差从 0.35 降到 0.11，收敛快约 40%。
   - 门控机制：用门控制梯度流动路径。
2. **优化策略**
   - AdamW 比 SGD 更稳，$\beta_1/\beta_2$ 常用 0.9/0.999。
   - 梯度裁剪：`clip_grad_norm_(params, max_norm=1.0)`。
   - 学习率预热：前若干步从 0 线性升到目标值，避免早期爆炸（如 BERT 前 10% 步数升到 3e-5）。实测千亿参数级对话模型加 5000 步预热 + 裁剪后，NaN 出现次数从每轮 17 次降到 0。
3. **工程技巧**
   - 混合精度 + Loss Scaling（缩放因子常取 1024 量级）。
   - 梯度累积（见 3.5）。
   - 参数初始化：CNN 常用 Xavier，Transformer 常用带缩放的初始化（如 Kaiming/正态小方差）。

| 方案 | 适用场景 | 实现成本 | 效果 |
| --- | --- | --- | --- |
| Pre-LayerNorm | Transformer 架构 | 中 | 从结构上缓解梯度异常 |
| 梯度裁剪 | 几乎所有训练 | 低 | 快速止血，防爆炸 |
| 混合精度 + Loss Scaling | 显存受限 | 中 | 显存约减半、速度提升 |
| 自适应优化器 | 高维稀疏特征 | 低 | 收敛更稳 |

**排查顺序建议**：先打印梯度范数确认是消失还是爆炸 → 加裁剪/预热止血 → 检查归一化位置与残差 → 再考虑换优化器或调小学习率。

### 3.7 学习率与 Epoch 的关系

**Epoch** 是模型把训练集完整过一遍的次数；**学习率（Learning Rate）** 是每次参数更新的步长。

生活化比喻：Epoch 像复习的轮数，学习率像每轮翻书的"跨度"——跨度太大一眼扫过抓不住重点（震荡），跨度太小一页看半天（收敛慢甚至学不到东西）。

**典型现象**

- 学习率过大（如 >1e-4 做全参数微调）：验证准确率可能从 92% 骤降到 68%，参数剧烈震荡。
- 学习率过小：收敛极慢，生成任务容易退化成重复片段（"我认为……我认为……"）。
- **Epoch 边界效应**：训练到第 3 轮之后，生成内容开始出现编造（如虚构政策条文），往往是过拟合的信号。

**调参经验**

| 项目 | 建议 |
| --- | --- |
| 学习率范围 | 全参数微调 $1\times10^{-5}$~$5\times10^{-5}$；LoRA 可用 $1\times10^{-4}$ 量级 |
| 调度策略 | 预热 + 余弦衰减最常用；金融等高风险领域取更保守的学习率 |
| Epoch 数量 | 先用 3~5 轮快速验证，再根据验证集决定是否增加 |
| 早停 | 验证指标连续若干轮不升就停，避免过拟合 |
| 进阶 | 分层学习率（底层小、顶层大）、课程学习（由易到难喂数据） |

### 3.8 微调中的灾难性遗忘

**灾难性遗忘（Catastrophic Forgetting）** 指模型学新任务后，旧任务能力明显下降。类比：为了适配新客户把公共组件改得面目全非，老客户的功能全挂了。

**案例：医疗文本分类**，四层协同方案：

- **数据层**：混入约 10% 精选原始数据（用 TF-IDF 筛语义相关样本），保持知识连贯。
- **算法层**：加 EWC 正则（约束重要参数偏移，λ 经网格搜索取 0.3，偏移上限约 20%）。
- **训练层**：分层学习率——底层 1e-5 保住通用特征，顶层 5e-4 加速新任务适配，配合余弦退火。
- **监控层**：每 500 步做一次双任务验证，动态调整新旧数据的采样权重。

结果新旧任务准确率分别为 85% 与 89%，比基线提升约 17 与 8 个百分点。

**三个关键点**：留"知识锚点"（旧数据/参数约束）；渐进演化（控制更新幅度与方向）；动态平衡（实时监控、按需调整）。实践建议：以"20% 旧数据 + 正则化 + 分层学习率"为基础组合，再按需叠加 Adapter，通常可接受旧任务 5~10% 的合理衰减。

### 3.9 常见问法

- **问：全参数微调显存怎么估？** 参数量 × 16 字节（权重 2 + 梯度 2 + FP32 主权重 4 + Adam 8）+ 激活值；工程上按 18~20 倍参数量估更保险。
- **问：LoRA 为什么省显存？** 冻结原权重、只训练低秩旁路矩阵，优化器状态只覆盖这部分参数，激活值仍是主要开销，所以收益明显但不是"显存除以 10"。
- **问：Loss Scaling 解决的是上溢还是下溢？** 下溢。小梯度在 FP16 里被抹成 0，放大后才有有效数值。
- **问：梯度累积和加大 batch 有什么区别？** 数学上近似等价（需同步缩放学习率），但梯度累积的激活值按小 batch 算，显存占用低得多。
- **问：微调后旧能力掉了怎么办？** 混旧数据、加正则（EWC）、分层学习率、控制 epoch 数，必要时用 LoRA 只动旁路参数。

## 四、对齐技术：SFT、RLHF 与 DPO

微调让模型"会做事"，**对齐（Alignment）** 让模型"按人类希望的方式做事"——不该答的拒答、该谨慎的谨慎、语气符合业务要求。本章对比三种主流做法及其成本。

### 4.1 SFT：监督微调

**SFT（Supervised Fine-Tuning）** 用"输入-输出"成对数据做有监督训练，是最基础的一步。

- **原理**：给定提问，让模型输出标准答案，用交叉熵拉近两者分布。
- **优势**：训练稳定（就是普通梯度下降）；数据利用率高，万级样本即可见效。
- **劣势**：学不到"偏好"（比如两个答案都对，但一个更礼貌）；容易"机械复制"训练集里的表述。

### 4.2 RLHF：人类反馈强化学习

**RLHF（Reinforcement Learning from Human Feedback）** 三步走：先用偏好数据训练奖励模型（RM），再用强化学习（通常是 PPO）让模型朝着高奖励方向优化，同时用 KL 惩罚约束不要太偏离 SFT 模型。

$$R_{\text{total}}=R_{RM}(x,y)-\beta\,D_{KL}\big(\pi_\theta(y\mid x)\,\|\,\pi_{SFT}(y\mid x)\big)$$

- **优势**：能对齐复杂偏好（拒答、语气、谨慎程度）；医疗案例中有害建议率下降约 98%。
- **劣势**：成本极高（奖励模型 + 多轮 PPO，动辄百卡级）；流程复杂，RM 训练不稳、PPO 超参敏感。

### 4.3 DPO 与 PPO：为什么 DPO 能替代大部分 PPO

**DPO（Direct Preference Optimization）** 用数学推导把"奖励模型 + 强化学习"合并成一步：直接在偏好对（好回答 / 坏回答）上做分类式优化，不需要单独训奖励模型，也不需要在线采样。

| 维度 | PPO | DPO |
| --- | --- | --- |
| 训练流程 | 训 RM → 在线采样 → 策略优化，多阶段 | 单阶段端到端，直接在偏好对上优化 |
| 计算成本 | 高（多模型同时在显存里） | 低（只需策略模型 + 参考模型） |
| 稳定性 | 对 KL 系数、奖励缩放敏感 | 更鲁棒（KL 约束隐式内置） |
| 适用场景 | 需要细粒度多维奖励信号 | 有明确"好/坏"偏好对 |
| 数据需求 | 大量打分数据 + 在线交互 | 数千到数万组高质量偏好对 |

**案例：银行智能客服满意度优化**（基线 SFT 解决率 68%）

- PPO 方案：10 万条带 1~5 分满意度的对话训奖励模型，再跑 5 轮 PPO；8 卡 A100 × 36 小时。
- DPO 方案：从历史对话抽 3 万组偏好对，单阶段微调；4 卡 A100 × 12 小时。

| 指标 | SFT 基线 | PPO | DPO |
| --- | --- | --- | --- |
| 解决率 | 68% | 74% | 76% |
| 训练成本 | — | 约 9600 元 | 约 2800 元 |
| 人工评估一致率 | — | 82% | 89% |

结论：偏好数据规模不大但质量高时，DPO 效果更好、成本约降 70%；需要区分"1 分和 5 分"这类细粒度差异时，PPO 仍有优势。

**选型指南**

| 场景 | 推荐 | 原因 |
| --- | --- | --- |
| 数据少但质量高（医疗、金融垂直领域） | DPO | 单阶段、稳、成本低 |
| 需要多维奖励信号（复杂决策、游戏 AI） | PPO | 奖励模型可表达复杂偏好 |
| 资源紧张、要快速上线 | DPO | 训练速度通常快数倍 |

**实战技巧**：DPO 的偏好对可用"同一问题不同回复的胜率排序"构造；PPO 的 KL 系数常取 0.1~0.2，奖励缩放需归一化。趋势是混合路线——先用 DPO 快速对齐，再用 PPO 精细优化；或用 AI 反馈（RLAIF）替代部分人工标注。

### 4.4 三者对比一览

| 阶段 | 数据形态 | 目标 | 主要风险 |
| --- | --- | --- | --- |
| SFT | 输入-输出对 | 学会任务格式与知识 | 机械复制、学不到偏好 |
| RLHF/PPO | 偏好打分 + 在线采样 | 对齐人类偏好 | 成本高、训练不稳、易过优化 |
| DPO | 偏好对 | 对齐偏好，成本更低 | 依赖强 SFT 基座，多轮能力弱于 RLHF |

### 4.5 常见问法

- **问：SFT 和 RLHF 一定要都做吗？** 通常要。SFT 打底（教会格式），DPO/RLHF 再调偏好；跳过 SFT 直接做偏好优化，模型往往连格式都不对。
- **问：DPO 完全替代 PPO 了吗？** 没有。DPO 胜在简单稳定，PPO 在需要在线探索、细粒度奖励时仍不可替代。
- **问：为什么 RLHF 里要加 KL 惩罚？** 防止模型为了拿高奖励而偏离语言模型本质（胡说、谄媚），KL 项把它"拴"在 SFT 模型附近。医疗案例中该惩罚把知识遗忘率从 15% 降到 3%。
- **问：怎么构造 DPO 数据？** 同一 prompt 下人工挑选更好/更差的回答，或按业务规则（是否合规、是否解决用户问题）排序，成对保存。

## 五、压缩与推理加速

训练是一次性的，推理是天天要还的账。本章讲清"怎么用更少的卡跑同样的活"：量化压精度、蒸馏压模型、MoE 压计算量、vLLM 压显存浪费、分块压长文本，最后给出一套可复用的显存估算方法。

### 5.1 模型量化：用精度换成本

**量化（Quantization）** 把权重和/或激活从高精度浮点（如 FP32、FP16）转成低精度（INT8、INT4），从而减少显存占用、提升计算吞吐。

生活化比喻：像把高清照片转成压缩图——体积小了一半以上，肉眼看还行，但放大到细节就会丢；关键看业务能接受多大的画质损失。

**主流方法对比**

| 方法 | 精度 | 做法 | 适用 |
| --- | --- | --- | --- |
| 训练后动态量化 | INT8 | 权重离线量化，激活在推理时按批次动态算缩放 | 计算密集型层（线性层、注意力矩阵），BERT 类模型 |
| 静态量化 | INT8 | 用校准数据预先确定激活范围 | 输入分布稳定的场景，速度更快 |
| GPTQ / AWQ | INT4 | 分组量化 + 误差补偿，逐层校准 | 生成式大模型（LLaMA 系），显存吃紧 |
| 量化感知训练（QAT） | INT8/INT4 | 训练时就模拟量化误差 | 精度要求高、可接受再训练成本 |

**案例 1：金融客服 BERT 量化部署**：FP32 模型延迟 200ms，无法满足实时响应。用动态量化处理线性层与注意力矩阵，Embedding 层保留 FP16 保语义精度；再用 TensorRT 编译（层融合 + INT8 Tensor Core）。结果延迟 200ms→45ms，显存 1.2GB→0.3GB，F1 仅从 94.2% 降到 93.4%。

**案例 2：医疗报告 LLaMA-7B 边缘部署**：iPad Pro 上原 FP16 需 14GB，跑不起来。用 GPTQ INT4 分组量化（校准集 1k 条医疗文本，激活保留 FP16），转 CoreML 走神经引擎。结果体积 14GB→3.5GB，生成速度 12→28 token/s，CPU 占用 70%→25%（项目经验值）。

**权衡原则**：先看瓶颈是显存还是算力——显存不够优先 INT4 权重；算力不够优先 INT8 + 推理框架优化；精度敏感（医疗、金融合规）先做小范围 A/B，确认指标跌幅在可接受范围（常见 0.5~2 个百分点）再全量。

### 5.2 知识蒸馏：让小模型学会大模型的"手感"

**知识蒸馏（Knowledge Distillation）** 用大模型（教师）的输出分布去指导小模型（学生）训练。学生不仅学"正确答案"（硬标签），还学教师对各类别的概率分布（软标签），后者包含"哪些错答案也说得过去"这类隐含知识。

生活化比喻：像资深师傅带徒弟——不只是给结论（硬标签），还会说"这个件这样装也行，但那样装更容易出问题"，徒弟学到的是判断的"手感"，而不只是答案。

**关键要素**

| 要素 | 作用 |
| --- | --- |
| 软标签 | 教师输出的概率分布，携带类别间相似性信息 |
| 温度 T | 软化分布（T 越大越平滑），让学生看到更多"暗知识"，常用 3~10 |
| 损失组合 | 硬标签交叉熵 + 软标签 KL 散度（加权） |
| 蒸馏对象 | 可蒸输出（logits）、可蒸中间层特征、可蒸注意力图 |

**案例：变电站异物检测（边缘部署）**：教师模型是视觉大模型，准确率很高但参数量巨大（数十 B 级），无法装在摄像头侧；学生模型是蒸馏后的轻量模型，单点位内存占用仅 MB 级。蒸馏过程：教师生成正常/异物图像的概率分布 → 学生同时学硬标签与软标签 → 温度取 5 让学生学到"风筝与塑料袋视觉相似"这类隐性知识。该案例公开资料中未给出最终效果数据，此处不补数字。

**适用场景**：模型轻量化、边缘设备部署、跨任务迁移、数据效率提升。实践关键在温度系数与硬/软损失权重的调优。

### 5.3 MoE：稀疏激活降低计算成本

**MoE（Mixture of Experts，混合专家）** 把 FFN 拆成 N 个"专家"子网络，每个 token 只被路由到其中 k 个（通常 k=1 或 2）。

生活化比喻：像微服务网关按请求类型路由——请求只打到少数几个服务，不必让所有服务都算一遍，总服务数（总参数）可以很大，但单次请求的成本只与命中的服务数有关。

**计算成本怎么降**

- 稀疏激活：门控网络（Gating Network）为每个 token 选 Top-k 专家。前向计算量近似与"激活参数量"成正比，而不是与总参数量成正比。粗略估算单 token 前向浮点运算量 $ \approx 2\times P_{\text{activated}}$（乘加各算一次），整段序列再乘 token 数 $L$；训练还要算反向，通常按前向的约 3 倍估。
- 负载均衡：加辅助损失（如 Switch Transformer 的 load balancing loss）防止某些专家过载、某些闲置，否则并行设备利用率会掉。

**工程优化手段**

| 手段 | 说明 |
| --- | --- |
| 专家并行 | 把专家分散到不同 GPU，降低单卡显存压力 |
| 通信优化 | 用 All-to-All 取代 Broadcast，减少跨卡传输；重叠计算与通信 |
| 混合精度 | FP8 训练/推理进一步压缩显存与带宽 |
| 量化 + 蒸馏 | 边缘场景把专家权重压到 INT4，或蒸成更小的学生模型 |

**三个案例**

1. **DeepSeek-V2**：总参数约 2360 亿，每 token 只激活约 210 亿（约 8.9%）。关键设计：无辅助损失的负载均衡（动态路由）、DualPipe 通信优化（跨卡精细分配资源）、FP8 混合精度。推理成本显著低于同量级稠密模型。
2. **Switch Transformer**：MoE 的 All-to-All 通信是瓶颈；用分组专家并行 + 流水线调度重叠计算与通信，在 1024 专家规模下训练速度提升约 3 倍。
3. **医疗影像边缘部署**：16 个轻量 CNN 专家 + Top-1 门控，INT4 量化把体积压到 1/4，再用 MoE 大模型蒸馏出 MobileNetV3 级学生模型；推理延迟 120ms→15ms，显存 6GB→1.2GB，可在 Jetson 类设备运行。

**代价与边界**：MoE 省的是**计算**，不省**显存**——总参数仍要全部装下；路由不均衡会浪费算力；小 batch 场景收益有限。行业现状是千亿级以上模型普遍采用 MoE（DeepSeek 系、Mixtral 等）。

### 5.4 vLLM：把显存浪费压到最低

**vLLM** 是主流的高吞吐推理引擎，核心创新是 **PagedAttention**——借鉴操作系统虚拟内存分页的思想管理 KV Cache。

**先理解 KV Cache**：自回归生成时，每个已生成的 token 都要保留它在各层的 Key/Value 向量，避免重复计算。这部分显存随序列长度线性增长，长对话时非常可观（官方博客举例：LLaMA-13B 单条序列的 KV Cache 可达 1.7GB）。

**问题**：传统实现按"最大长度"预分配连续显存块，实际用不满就浪费。官方数据：现有系统因碎片与超额预留，浪费 **60%~80%** 的显存。

**方案**：把 KV Cache 切成固定大小的"块"（block），逻辑上连续、物理上可以不连续，用块表映射，按需分配。这样浪费只发生在每条序列的最后一块，实测浪费降到 **4% 以下**。

```python
# 传统静态分配：按最大长度预留，短请求也占满
max_length = 4096
kv_cache = torch.zeros(batch_size, max_length, hidden_size)

# PagedAttention 思路：按块分配，用多少给多少
block_size = 16                      # 每块容纳的 token 数（可配置）
blocks_needed = math.ceil(current_seq_len / block_size)
allocate_blocks(blocks_needed)       # 通过块表映射到物理块
```

> 注意：常见说法是"显存占用减少 4 倍，Llama-13B 从 48GB 降到 12GB"，这个数字不成立——13B 模型 FP16 权重本身就有约 26GB。准确表述是：**KV Cache 的浪费从 60%~80% 降到 4% 以下**，因此同样显存能并发更多请求；官方对比 HuggingFace Transformers 的吞吐提升最高约 24 倍（对 TGI 约 3.5 倍）。

**连续批处理（Continuous Batching）**：静态批处理要等一批里最慢的请求结束才能进下一批，GPU 大量空转。连续批处理按"迭代（每生成一个 token）"粒度调度：谁结束谁出队，新请求随时插入。效果是 GPU 利用率大幅提升（项目经验：35%→90% 量级），吞吐提升数倍。

**内存池（Memory Pooling）**：预申请大块显存循环复用，避免频繁 `malloc/free` 产生碎片。

```python
class MemoryPool:
    def __init__(self, block_size, num_blocks=100):
        self.free_blocks = [Block(block_size) for _ in range(num_blocks)]

    def alloc_block(self):
        if not self.free_blocks:
            self.free_blocks.extend([Block(self.block_size) for _ in range(10)])
        return self.free_blocks.pop()

    def free_block(self, block):
        self.free_blocks.append(block)   # 回收复用，不还给驱动
```

Java 类比：这就是 Netty 的 `ByteBuf` 池化 / 数据库连接池的思路——对象反复复用，避免反复申请释放带来的开销与碎片。

**案例：电商客服部署千问 7B，要求 500+ 并发**

- 问题 1：长文本（>2048 token）时块切换频繁，延迟抖动。解决：调大 `block_size`（32→64），长文本处理速度提升约 50%。
- 问题 2：高峰期请求突增导致 OOM。解决：开启 `swap_space`，把部分 KV Cache 换出到 CPU 内存（相当于用"磁盘换内存"的思路保命）。

**收益与适用**：高并发在线服务（客服、翻译）、长文本生成（摘要、代码）收益最大；可叠加量化（AWQ/GPTQ）进一步压缩；支持 LoRA 多适配器并存。

### 5.5 降低 API 服务的推理延迟与成本

八个方向，按"从模型到业务"的顺序排：

| 方向 | 具体手段 |
| --- | --- |
| 模型优化 | 量化（FP32→FP16/INT8）、剪枝（去掉冗余权重）、蒸馏（大模型教小模型）、换更高效的结构（如更小的同族模型） |
| 推理过程 | 动态批处理（多请求合并，需平衡吞吐与延迟）、请求优先级调度、异步推理（非实时任务排队处理） |
| 硬件与资源 | 专用加速卡 + TensorRT/ONNX Runtime、FP16/BF16、按流量自动扩缩容（如 K8s HPA） |
| 缓存与预处理 | 结果缓存（FAQ 类高频问题）、请求去重（相似输入合并）、客户端预处理（压缩、清洗） |
| 架构设计 | 模型并行/流水线并行、边缘节点部署降网络延迟、微服务化拆分预处理/推理/后处理 |
| 成本策略 | Spot/预留实例、及时替换低效模型版本、用监控定位瓶颈（Prometheus、profiler） |
| 网络传输 | 高效序列化（Protobuf）、压缩（gzip）、CDN/边缘缓存 |
| 业务策略 | 分级服务（付费用户优先）、限流与降级（高峰期简化模型） |

**关键判断**：先分清优化目标是**延迟**（单请求快）还是**成本**（单位请求便宜）。降延迟优先缓存、边缘部署、小模型、流式输出；降成本优先批处理、量化、弹性伸缩、分级服务。

### 5.6 推理显存怎么估

推理比训练简单：不需要梯度与优化器状态，主要是**权重 + KV Cache + 激活 + 框架开销**。

$$\text{推理显存}\approx\underbrace{P\times b}_{\text{权重}}+\underbrace{2\times L\times n_{kv}\times d_{head}\times b\times B}_{\text{KV Cache}}+\text{激活}+\text{框架开销}$$

其中 $P$ 为参数量、$b$ 为每参数字节数、$L$ 为层数、$n_{kv}$ 为 KV 头数、$d_{head}$ 为每头维度、$B$ 为并发序列数。

**广义拆解（适用于任意模型）**：显存占用 = 模型参数 + 输入数据 + 中间结果 + 框架开销。

**案例：3D U-Net 肺部结节检测**（V100 32GB，输入 512×512×32，batch=4，部署时占用 95% 导致失败）

1. **参数量**：某层参数 $=3\times3\times3\times16\times32$；全模型约 1.2 亿参数，FP32 占约 480MB。
2. **输入张量**：$512\times512\times32\times4\text{B}\times4\approx1\text{GB}$。
3. **中间特征图**：按 4 层、每层 256×256×16 估算，约 16MB。
4. **框架开销**：约 100MB。
5. **合计**：约 1.7GB。

理论值只有 1.7GB，但实际跑不起来——因为真实的前向中间激活、cuDNN workspace、内存碎片都会额外占用，理论估算只能当下限用。

**优化手段**

```python
import torch

# 限制本进程可用显存比例
torch.cuda.set_per_process_memory_fraction(0.8)

# 减小 batch：4 → 2，激活值近似减半
inputs = torch.randn(2, 1, 512, 512, 32).cuda()

# 混合精度推理
from torch.cuda.amp import autocast
with autocast():
    outputs = model(inputs)
```

另外还有剪枝（32 通道降到 16，参数减半）与 INT8 量化（体积约缩 4 倍）。

**验证工具**

```python
print(torch.cuda.memory_allocated())      # 当前分配
print(torch.cuda.max_memory_allocated())  # 峰值
```

```bash
watch -n 1 nvidia-smi
```

用 `torch.profiler` 可以按算子看显存占用，定位"到底是谁吃掉了显存"。

**结论**：估算公式给出下限，实际部署要留 20%~30% 余量；调优优先级为"硬件限制 → 精度需求 → 推理速度"；医疗影像案例中通过混合精度 + 调小 batch，把占用从 1.7GB 压到 800MB 后才稳定跑在 V100 上。

### 5.7 长文本处理的优化方案

长文本的难点有三：注意力计算随长度平方增长、位置编码外推能力有限、关键信息分散导致召回不全。优化从三个维度展开。

**案例 1：金融研报分析（平均 15K token）**

- 分块策略：标题块 512 token（保留章节标题 + 前 3 句）、核心段落块 1024 token（按论点切）、表格用 OCR 单独解析转 Markdown。
- 注意力优化：块内全连接 + 块间 top-k 相似度筛选（Blockwise Attention），相邻块加局部注意力偏置。
- 显存压缩：梯度检查点 + INT8 量化加载。

```python
model = AutoModel.from_pretrained(
    "chatglm3-6b",
    load_in_8bit=True,
    use_reentrant_checkpointing=True,
)
```

效果：处理速度提升约 4.2 倍，关键信息召回率 68%→92%，显存下降约 37%（项目经验值）。

**案例 2：法律合同审查（平均 20K token）**

- 滑动窗口重叠：窗口 2048 token、重叠 15%，重叠区按余弦相似度衰减加权。
- 动态分块：按句切分，超长时保留上一段尾部 20% 内容，保证条款上下文不丢。

```python
def dynamic_chunking(text, max_len=2048, keep_ratio=0.2):
    sentences = nltk.sent_tokenize(text)
    chunks, current = [], []
    for sent in sentences:
        if sum(len(tokenizer.encode(s)) for s in current + [sent]) > max_len:
            chunks.append(" ".join(current))
            keep = current[-max(1, int(len(current) * keep_ratio)):]
            current = list(keep)
        current.append(sent)
    return chunks
```

- 位置编码外推：把 RoPE 的 `base` 从 10000 调大（如 500000），配合位置插值把窗口从 2K 扩到更长。

**三层优化总结**

| 层面 | 手段 |
| --- | --- |
| 算法 | 稀疏/分块注意力、ALiBi 或 RoPE 外推、语义分块 |
| 工程 | 梯度检查点、激活量化、KV Cache 量化 + LRU 淘汰、FlashAttention |
| 训练 | 渐进式长度扩展（512→2048→8192）、增量预训练、batch 随长度递减 |

**核心经验**：20% 的文本往往包含 80% 的关键信息，分块要按语义而不是按字数；滑动窗口重叠率建议 10%~15%；ALiBi 与 NTK 类外推组合在 16K 以上场景表现较好；实际效果以业务指标（召回率、P99 延迟）为准，没有通用最优解。

### 5.8 常见问法

- **问：量化会掉多少点？** 没有固定答案。BERT 类 INT8 常见跌幅在 1 个百分点内；7B 级 INT4 在通用任务上通常可控，但专业术语密集的任务要单独验证。
- **问：MoE 省显存吗？** 不省。总参数全部要驻留显存，MoE 省的是每个 token 的计算量。
- **问：vLLM 为什么快？** 三点：KV Cache 按块分配把浪费压到 4% 以下、连续批处理避免等最慢请求、内存池减少碎片。
- **问：推理显存怎么快速估？** 权重 = 参数量 × 字节数；KV Cache 按"层数 × 头维度 × 2 × 序列长度 × 并发数 × 字节数"估；再留 20%~30% 余量。
- **问：长文本只能靠扩上下文吗？** 不必。分块 + 检索（RAG）常常比硬扩上下文更便宜、更准，且不受位置编码外推能力限制。

## 六、RAG 与向量检索

模型的知识止于训练截止时间，也不知道你公司的内部文档。**RAG（Retrieval-Augmented Generation，检索增强生成）** 就是给模型"配一个可查的资料库"：先检索，再把检索结果塞进提示词里让它照着答。本章讲清 RAG 的完整链路、每个环节的技术选型，以及"为什么不能只用 MySQL"这个高频问题。

### 6.1 RAG 的完整流程

**为什么需要 RAG**：大模型的知识只来自训练数据（公开语料），对私有数据、截止日期之后的信息一无所知；而重新训练成本极高。RAG 通过"检索相关信息 → 插入提示 → 生成回答"绕开这个问题。

生活化比喻：RAG 像客服坐席旁边的知识库窗口——坐席（模型）不必背下所有条款，遇到问题先查库，再照着查到的内容回答；查不到就明说查不到。

典型 RAG 应用分两段：

- **索引（Indexing）**：离线把文档处理成可检索的形态。
- **检索与生成（Retrieval & Generation）**：在线接收问题，检索片段，交给模型生成。

完整链路五步：

**① 索引：加载 → 分割 → 存储**

1. **加载（Load）**：用文档加载器读 PDF、网页、数据库。
2. **分割（Split）**：把长文档切成块（chunk）。块太大检索不准、也塞不进上下文窗口；块太小语义不完整。
3. **存储（Store）**：用嵌入模型把块转成向量，存进向量库并建索引。

**② 用户输入处理**

- 查询解析：关键词提取、实体识别（NER）、语义解析。
- 查询扩展：同义词替换、上下文联想（问"Transformer 结构"时补充"注意力机制"相关词）。
- 向量化：把查询转成向量（BERT、Sentence-BERT 等），供向量检索。

**③ 文档检索**

- 索引构建：倒排索引（关键词）、向量索引（FAISS、HNSW）。
- 检索算法：稀疏检索（BM25，擅长关键词精确命中）、稠密检索（DPR、ANCE 等语义向量匹配）。
- 多路召回：BM25 与向量检索同时跑，再融合排序，显著提升召回率。

**④ 文档后处理**

- 去重与排序：按相关性或多样性筛选。
- 截断与分块：用滑动窗口适配模型输入长度。
- 上下文增强：补上来源、时间戳等元信息。

**⑤ 生成与验证**

提示词拼接示例：

```text
[查询]：量子计算的优势是什么？
[相关文档1]：量子计算利用量子比特实现并行计算...
[相关文档2]：量子算法在加密破解领域有潜在应用...
[生成任务]：请综合上述信息，回答用户的问题。
```

- 生成模型：用预训练生成模型做条件生成；用 Temperature、Top-k 控制多样性与准确性。
- 后处理：文本润色（去重、纠错）、事实核验（用 NLI 模型判断回答是否被检索内容支持）、引用标注。

**主要挑战**

| 挑战 | 应对 |
| --- | --- |
| 检索质量（召回 vs 精度） | 多路召回 + 重排序；长尾查询单独补数据 |
| 检索与生成不协同 | 联合训练检索器与生成器（如原始 RAG 模型的做法） |
| 效率 | 近似最近邻（ANN）检索、压缩生成模型、缓存热点 |

**示例**：用户问"如何解决深度学习模型过拟合？"→ 检索到"Dropout 的作用""数据增强方法"等片段 → 模型综合生成包含正则化、早停的回答并标注来源。

### 6.2 RAG 系统的核心组件

| 组件 | 职责 | 常见选型 |
| --- | --- | --- |
| 检索器（Retriever） | 从知识库找回相关片段 | 向量库（Milvus、Chroma）+ 嵌入模型（BGE、Sentence-BERT）；BM25 兜底 |
| 索引构建器（Indexer） | 把文档切成块并转成向量 | 递归字符切分、按标题/表格切分、领域微调的嵌入模型 |
| 生成器（Generator） | 结合检索结果生成回答 | 通用大模型 + RAG 提示模板 + 后处理（答案校验、来源引用） |
| 后处理模块 | 提升可信度与可解释性 | 按相似度/置信度排序、标注引用来源 |

**工作逻辑（电商客服案例，日均 5 万+ 咨询）**：用户问"蓝牙耳机是否支持 IPX7 防水？"

1. 查询进入，转向量。
2. 检索：商品手册、FAQ 已按段落分块入向量库，按余弦相似度找到"防水等级""IPX7"相关片段。
3. 生成：把片段（"IPX7：可在 1 米深水下浸泡 30 分钟"）作为上下文输入模型，生成"根据产品说明书，该耳机支持 IPX7 防水，可在 1 米深水下正常使用 30 分钟"。
4. 后处理：标注来源；交叉验证历史对话，避免引用过时政策。

**常见挑战与解法**

| 挑战 | 解法 | 案例表现 |
| --- | --- | --- |
| 检索不相关 | 多模态检索（文本 + 表格）、查询重写 | 问"退货流程"，召回"售后政策"表格 + "退货步骤"文本 |
| 幻觉 | 强制基于检索内容作答、检索不到就明说 | 检索不到 IPX7 信息时回答"现有资料未提及" |
| 实时性 | 分布式索引、热点缓存 | 热门商品文档进内存缓存，多数查询延迟在百毫秒级 |

### 6.3 为什么用向量数据库而不是传统数据库

**核心差异**：传统数据库擅长**结构化数据 + 精确匹配**（`WHERE id = 123`）；向量数据库擅长**非结构化数据 + 语义相似**（"找意思相近的内容"）。

生活化比喻：MySQL 是按身份证号找人——必须号码完全一致；向量数据库是按长相找人——不需要记住号码，只要"看起来像"就能找到。

**（1）数据类型适配**

传统库（MySQL、Oracle）处理表格字段很在行，但文本、图像、音频、视频这类非结构化数据没法直接存和查。向量库通过 Embedding 把内容转成高维向量存起来：一段文本变成 768 维向量后，传统库既存不好也查不快，向量库则是原生支持。

**（2）相似性搜索的效率**

传统库靠精确匹配，向量库靠近似最近邻（ANN，Approximate Nearest Neighbor）算法（HNSW、IVF-PQ）快速算余弦相似度或欧氏距离，实现毫秒级响应。用户问"如何优化代码性能"，向量库能召回"代码优化技巧""性能调优案例"这类语义相近但字面不同的内容。

**特征与向量的关系**：区分事物靠特征（按体型、毛发、鼻长区分犬种）。特征足够多就构成高维坐标空间，每个事物在其中对应一个点。**相似性度量**常用三种：

| 度量 | 含义 | 适用 |
| --- | --- | --- |
| 欧氏距离（L2） | 两点间直线距离，反映绝对差异 | 关注"量级"的场景，如图像特征 |
| 余弦相似度 | 两向量夹角余弦，取值 [-1,1] | 文本语义匹配（只关心方向，不关心长度） |
| 点积相似度 | 向量内积，兼顾方向与长度 | 已归一化时可等价于余弦 |

**（3）高维与工程优势**

- 高维能力：BERT 输出 768 维、大模型常见上千维，传统 B 树的索引在高维空间效率急剧下降（"维度灾难"）；向量库专为高维设计，用量化、降维优化存储与计算，可支撑十亿级向量。
- 实时性：传统库处理非结构化数据要额外 ETL（文本→向量→存储），链路长；向量库端到端对接模型推理层。

**（4）在大模型应用中的三个作用**

1. **扩展"长期记忆"**：模型上下文窗口有限（GPT-4 早期为 8K/32K，GPT-4 Turbo、GPT-4o 等可达 128K），且知识静态；向量库存实时更新的行业报告、用户日志，通过 RAG 动态注入，缓解幻觉。
2. **多模态支持**：图文、语音的向量可统一存储，实现"以图搜文""语音问答"这类跨模态检索。
3. **成本优化**：传统方案要关联用户表、商品表、行为表做复杂 JOIN；向量库一次相似性搜索就能返回结果。

**（5）行业现状与边界**

向量库已成 AI 基础设施的一部分（Faiss 开源、Milvus 分布式、云厂商托管服务），但**不是替代关系**：结构化数据（订单、账户）仍在关系库，非结构化数据交给向量库，两者用唯一 ID 关联，形成混合架构。

也要客观说明局限：事务能力弱、与业务库的数据同步复杂、索引重建成本高。回答"为什么选它"时把这些一起讲，比只讲优点更可信。

### 6.4 RAG 中的语义鸿沟怎么解

**语义鸿沟（Semantic Gap）** 指"用户问的"与"库里存的"在语义层面接不上：用户说"嗓子疼吃什么药"，文档写的是"咽痛的对症处理"，字面不重合、向量也可能不够近。

以医疗 RAG 为例，四种手段组合使用：

**（1）知识图谱：构建全局语义网络**

用图算法（如 PageRank）识别关键节点，优先推荐高置信度关联路径。效果：跨源召回率提升约 37%，诊断准确率提升约 22%。例如图谱关联"发热 + 咳嗽 + 白细胞升高"路径，推荐"抗生素 + 抗病毒药物"组合。

**（2）上下文感知检索：动态重排序**

1. 初始检索：BM25 召回 Top 50。
2. 语义重排序：用语义相似度（如 BERTScore）结合时间权重（旧文献降权，衰减系数 λ=0.8）。
3. 多模态融合：从影像报告中提取关键句（如"肺部磨玻璃影"），与文本片段拼成复合上下文。

效果：上下文完整度提升约 45%，避免片段孤立导致的误判。

**（3）动态提示工程：结构化 Prompt**

先定角色，再拆步骤，最后加自洽校验：

```text
你是一名呼吸科主治医师，需结合最新临床指南和患者数据，给出诊断建议。

请按以下流程回答：
1. 确认患者主诉（发热、咳嗽）
2. 检索相关疾病（传染病、慢性病）
3. 对比症状匹配度（使用 ROC 曲线阈值 > 0.8）
4. 生成用药方案（优先推荐已获批药物）
```

再加一条约束："若推荐药物含阿莫西林，需检查患者过敏史。"效果：误推荐率下降约 19%，方案符合指南率约 92%。

**（4）跨模态对齐：多模态检索增强**

1. 用 CLIP 类模型把 CT 影像转成文本描述（如"双侧肺叶渗出灶"）。
2. 影像特征与文本查询拼成复合 Embedding：

```python
combined_embedding = 0.7 * text_embedding + 0.3 * image_embedding
```

3. 结果融合：优先返回同时匹配文本与影像的片段。

效果：影像相关病例诊断准确率提升约 31%。

**整体价值**（项目口径）：医疗 RAG 系统诊断准确率从 78% 提升到 91%，日均处理病例数增加约 40%。进一步方向包括 Self-RAG（让模型自己判断要不要检索、检索得够不够）与强化学习优化检索策略。

### 6.5 常见问法

- **问：RAG 能解决幻觉吗？** 能缓解不能根除。它把"凭记忆答"变成"照着资料答"，但如果检索错了、或模型不忠于检索内容，仍会出错，所以要配合引用与事实核验。
- **问：什么时候不该用 RAG？** 知识量很小（直接放进提示词即可）、对实时性要求极高且可缓存、或者需要多步推理而非查表时，RAG 收益有限。
- **问：BM25 还有用吗？** 有。关键词精确命中（型号、编号、专有名词）是向量检索的弱项，混合检索（BM25 + 向量）是主流做法。
- **问：向量数据库能替代 MySQL 吗？** 不能。它是补充：结构化数据留在关系库，语义检索交给向量库，用 ID 关联。
- **问：chunk 切多大合适？** 没有统一值。通常按语义单元切（段落、条款、FAQ 条目），大小几百 token；关键看检索命中率与答案完整性，需要实测调。

## 七、Agent 与知识图谱

RAG 解决"查得到"，**Agent（智能体）** 解决"会动手"：让模型自己决定调用哪个工具、调几次、结果怎么用。本章讲 LangChain 这套"胶水框架"、ReAct 的思考-行动循环、多 Agent 协作的系统设计，以及领域知识图谱的搭建流程。

### 7.1 LangChain：把大模型能力拼装成应用

LangChain 是构建大模型应用的开发框架，核心价值是**用统一抽象把"模型、数据、工具、流程"串起来**，避免每个项目重写一遍胶水代码。

Java 类比：它像 Spring 之于 Java Web——不是帮你写业务，而是提供一套标准件（模板、链、代理、记忆），让你专注业务逻辑。

**组件构成**

| 包/模块 | 作用 |
| --- | --- |
| langchain-core | 基础抽象与表达式语言（LCEL） |
| langchain-community | 第三方集成（各种模型、向量库、加载器） |
| 合作伙伴包（如 langchain-openai） | 只依赖 core 的轻量集成包 |
| langchain | 链、代理、检索策略等应用层编排 |
| langgraph | 用图（节点 + 边）建模有状态的多参与者流程 |
| langserve | 把链部署成 REST API |
| LangSmith | 调试、测试、评估、监控平台 |

**六大核心功能**

1. **模型集成**：统一接口对接多种模型（OpenAI、Anthropic、HuggingFace 等），换模型只改一行配置，避免厂商锁定。
2. **模块化组件**
   - 提示模板（Prompts）：变量注入、Few-shot 示例管理。
   - 文档加载器（Loaders）：PDF、网页、数据库。
   - 文本分割器（Splitters）：长文切片。
   - 向量存储（Vector Stores）：集成 FAISS、Chroma 等。
3. **链式调用（Chains）**：把多步组合成可复用流程，如"检索 + 生成"（RetrievalQA）、顺序执行多步（SequentialChain）。
4. **记忆机制（Memory）**：维护多轮对话历史（缓冲记忆、摘要记忆）。
5. **代理与工具（Agents & Tools）**：让模型动态选择工具（搜索、计算器、内部 API），工具可自定义扩展。
6. **数据增强（RAG）**：加载 → 向量化 → 检索 → 注入提示 → 生成。

**典型场景**：领域知识问答、多轮客服机器人、长文档分析、自动化流程（调接口、发邮件）、代码生成与校验。

**优势与边界**：模块化、灵活、易扩展、开发效率高；但抽象层较厚，出问题时要会往下钻；复杂流程建议用 langgraph 显式建模状态，而不是把逻辑堆在一个 chain 里。

### 7.2 ReAct：思考—行动—观察的循环

**ReAct（Reasoning + Acting）** 让模型交替进行"推理"和"调用工具"，每轮根据工具返回结果修正下一步，直到能给出答案。

生活化比喻：像一个排障的运维工程师——先看监控（观察），判断可能是数据库慢（推理），去查慢查询日志（行动），看到锁等待（观察），再决定加索引（行动）。不是一次性想完所有步骤，而是边走边看。

**对照其他范式**：CoT（思维链）只让模型"想"，不调用外部工具；ToT（思维树）会展开多条推理路径做搜索，但仍在"脑内"；ReAct 的关键是**把外部世界的反馈接进推理循环**。

**案例：生鲜电商动态定价（LangChain + ReAct + 天气 API + 库存系统）**

业务目标：根据供需动态调价，最大化利润。痛点：天气突变影响损耗、库存数据滞后；定价要考虑成本、市场均价、竞品、节日等 20 多个维度，规则引擎写不动；需要调多个异构数据源并交叉验证。

**① 推理阶段（Reasoning）**：把任务拆成可执行的思考步骤。


### 7.3 多 Agent 协作系统架构

单个 Agent 能力有限，复杂业务需要多个"专职 Agent"分工。设计要点：角色划分、通信机制、任务调度、容错、性能。

**案例：智能物流仓储系统**

痛点：人工分拣调度效率低（高峰期尤甚）、错误率高、资源分配不均（有的区闲、有的区爆）、难以应对突发订单与设备故障。

**角色定义**

| Agent | 职责 |
| --- | --- |
| 订单管理 Agent | 接收订单，拆成可执行任务 |
| 资源调度 Agent | 分配设备与人力，保持负载均衡 |
| 路径规划 Agent | 为机器人/分拣设备规划最短路径 |
| 错误检测 Agent | 实时监控流程，发现并纠正错误 |
| 监控 Agent | 监控系统状态，发现异常并触发恢复 |

**通信机制**：消息队列异步通信（保证可靠投递，削峰填谷）+ 事件驱动（状态变化触发行为）。这与 Java 后端的 MQ + 事件总线思路完全一致。

**任务分配与调度**：订单管理 Agent 按优先级与资源状态动态分配；资源调度 Agent 实时监控各区负载并调整。

**容错与恢复**：心跳检测（监控 Agent 定期探测，异常时启动恢复）；任务重试与重新分配（错误检测 Agent 触发）。

**性能优化**：路径规划用 A* 或 Dijkstra；资源预测基于历史数据提前调整。

**设计步骤（可复用）**

1. 需求分析：明确吞吐、错误率、资源利用率等指标。
2. Agent 划分：按职责边界切分，避免职责重叠。
3. 通信设计：同步还是异步、消息格式、幂等性。
4. 任务调度：分配算法、优先级、超时处理。
5. 容错机制：重试、降级、人工兜底。
6. 性能优化：负载均衡、缓存、并发控制。

**价值总结**：任务分解 + 专门化提升效率与可靠性；通信与调度是协作的关键；容错与性能优化保障稳定性。风险在于"多 Agent 互相等待"和"责任不清"，因此状态机与超时机制必不可少。

### 7.4 构建领域专属知识图谱

**知识图谱（Knowledge Graph）** 用"实体-关系-实体"的三元组描述领域知识，适合做关联推理（股权穿透、疾病-症状-药物）。

生活化比喻：关系库像一张张独立的表格，知识图谱像把这些表格用"关系"这张网连起来——问"这家公司最终被谁控制"时，沿着边一路走下去就有答案。

**五步解题框架**

1. 场景选择：明确领域需求（金融风控、医疗诊断、智能制造）。
2. 痛点分析：数据孤岛、语义异构、知识更新滞后。
3. 技术选型：NLP 工具（BERT/ERNIE 类）+ 图数据库（Neo4j、JanusGraph）。
4. 构建流程：数据采集 → 实体识别 → 关系抽取 → 图谱构建 → 知识融合 → 应用部署。
5. 优化迭代：持续注入新数据、用反馈修正。

**案例：商业银行企业风险知识图谱**

场景：整合工商信息、司法诉讼、舆情，识别集团客户的隐性关联风险。痛点：数据散在 10 多个系统、格式不统一；关系库做股权穿透类查询效率极低；人工分析一户要 3~5 天；监管要求穿透式排查。

### 7.5 常见问法

- **问：LangChain 和直接调 API 有什么区别？** 直接调 API 适合单步任务；一旦涉及检索、多步编排、工具调用、记忆，用框架能省掉大量胶水代码，也便于换模型。
- **问：ReAct 和 CoT 的区别？** CoT 只在模型内部推理；ReAct 会把行动结果（工具返回值）接回推理循环，能查实时数据、能操作外部系统。
- **问：多 Agent 是不是越多越好？** 不是。Agent 越多通信成本与失败面越大，通常 3~5 个职责清晰的 Agent 比十几个细碎 Agent 更稳。
- **问：知识图谱和向量库冲突吗？** 互补。向量库擅长"模糊语义召回"，图谱擅长"多跳关联推理"，很多系统两者并用。

## 八、多模态

**多模态（Multimodal）** 指同时处理文本、图像、音频、视频等多种输入。难点不在"多"，而在"对齐"——让模型知道图片里的这块区域对应文字里的哪个词。本章讲清多模态任务的技术路径、跨模态对齐的工程做法，以及常被混淆的 AE/VAE/GAN。

### 8.1 如何用大模型做多模态任务

核心是两件事：**跨模态对齐**（把不同模态映射到同一个语义空间）与**联合表征学习**（用统一表示做下游任务）。要解决两个关键问题：

- **模态异构**：文本是离散符号，图像是像素矩阵，分布差异极大，必须统一到同一语义空间。
- **时空关系**：视频带时序信息，需要建模长期依赖。

生活化比喻：跨模态对齐像给公司做统一工号——销售、研发、财务各有各的记录方式，但只要都映射到同一个工号体系，就能跨部门查人。

**技术路径**

1. **统一编码器**：用 Transformer 系结构（ViT、CLIP、Flamingo）编码多模态输入，通过共享参数或跨模态注意力（Cross-Attention）交互。例：图文问答里 CLIP 用对比学习把图像与文本对齐；视频摘要用 ViViT 处理时空特征。
2. **模态适配器**：给已训练好的单模态模型（BERT、ResNet）加轻量适配层，低成本接入新模态（如 BLIP-2 的 Q-Former）。
3. **训练策略**
   - 预训练：大规模多模态数据上做对比学习（图文匹配）、掩码重建、生成式预训练。
   - 微调：为下游任务加任务头（Task Head），用领域数据微调。
   - 提示学习：设计多模态提示（"问题：{Q} 图片：{IMG} 答案："）引导输出。
4. **任务定制**
   - 图文问答（VQA）：图像编码（ViT）+ 问题编码（BERT）→ 跨模态融合 → 生成式解码（T5）或候选排序；关键技术是视觉定位与常识推理。
   - 视频摘要：分段采样 → 时空编码（3D CNN 或 TimeSformer）→ 关键帧检测 → 生成摘要（BART/T5）；关键技术是时序注意力与多粒度建模（帧/片段/视频级）。

**挑战与解法**

| 挑战 | 解法 |
| --- | --- |
| 模态对齐不足 | 对比学习损失（InfoNCE）、跨模态检索增强 |
| 长视频建模困难 | 分层处理（片段编码 + 全局聚合）、记忆压缩 |
| 数据稀缺 | 合成数据（生成图像 + 文本描述）、跨任务迁移 |

**代表工作**：BLIP-2（冻结图像编码器 + 轻量 Q-Former + 大语言模型）实现零样本 VQA；ViT-E 类模型结合时空注意力做视频摘要。

**趋势**：端到端统一模型（GPT-4V、Gemini 类）、具身多模态（机器人感知 + 推理）、低资源优化（Adapter、LoRA）。

### 8.2 跨模态对齐的工程做法

**案例：三甲医院 AI 辅助诊断**（CT/MRI 影像 + 病历报告，用于肺癌筛查）

**痛点**

1. 数据异构：影像为高维空间信息，报告为自然语言，难以直接关联（影像的"毛玻璃影"要对应文本的"磨玻璃结节"）。
2. 标注成本高：需要医师同时标注影像与文本。
3. 噪声干扰：报告口语化（"肺结节可能"）与实际病灶位置有偏差。

**方法选择**：对比学习 + 知识图谱引导。对比学习把语义一致的影像-文本对拉近、不一致的推远；医学知识图谱（疾病-症状-影像特征）作为先验约束，降低噪声影响。

**实现过程**

1. 数据预处理：影像用 ResNet 提 2048 维特征；文本用 BERT 提 768 维并过滤低频词；2 名医师交叉标注 1000 对样本并给 0~1 的语义一致性评分。
2. 模型结构：

```python
class MultiModalAligner(nn.Module):
    def __init__(self):
        super().__init__()

        self.text_encoder = BertModel.from_pretrained("bert-base-chinese")
        self.align_layer = nn.Linear(2048 + 768, 512)
        self.knowledge_graph = MedicalKG()      # 医学知识图谱嵌入

    def forward(self, image, text):
        img_feat = self.image_encoder(image).pooler_output
        txt_feat = self.text_encoder(text).pooler_output
        fused = torch.cat([img_feat, txt_feat], dim=1)
        aligned = self.align_layer(fused)
        return self.knowledge_graph(aligned)     # 图谱约束
```


**效果**：影像-文本对齐准确率 89.2%（基线 78.5%）；肺结节检出召回率 92.7%（F1 约 0.89）。定性上能正确把"左肺上叶结节"与"偶发胸痛"关联；错误案例是右肺下叶钙化灶被误关联为"炎症"，原因是图谱里二者关联权重过高。

**部署优化**：知识蒸馏把 ResNet50 压成 MobileNetV3（推理约快 3 倍），在 Jetson 类边缘设备本地部署，满足数据不出院的要求。

**经验总结**：跨模态对齐要同时兼顾数据特性、任务需求与部署约束；"对比学习 + 知识约束"在医疗这类高噪声、强先验的场景效果好；未来方向包括动态对齐（强化学习调特征）、少样本学习、多知识图谱融合。

### 8.3 AE、VAE 与 GAN：三种生成机制

三者都用于"学数据分布并生成新样本"，但思路完全不同。

| 模型 | 基本原理 | 训练目标 |
| --- | --- | --- |
| AE（自编码器） | 编码器压缩成低维表示，解码器还原 | 最小化重构误差 |
| VAE（变分自编码器） | 编码器输出均值与方差，从分布采样后再解码 | 重构误差 + KL 散度 |
| GAN（生成对抗网络） | 生成器造假、判别器辨真，对抗训练 | 判别器分不出真假（极小极大博弈） |

生活化比喻：AE 像把文件压缩再解压，追求"还原得像"；VAE 像压缩时保留一点随机性，解压出来是"同风格的新文件"；GAN 像造假币的和验钞的互相较劲，直到验钞的也分不出来。

**生成机制**

- AE：编码 → 低维表示 → 解码 → 最小化重构误差，学到的表示可用于降维与特征提取，但本身不擅长"造新样本"。
- VAE：编码出均值与方差 → 从分布采样潜在向量 → 解码生成 → 优化重构 + KL。因为引入了概率分布，采样出来的点都在"合理区域"，所以能生成新样本。
- GAN：生成器出假样本 → 判别器判真假 → 双方对抗升级，直到判别器无法区分。

**优缺点**

| 模型 | 优点 | 缺点 |
| --- | --- | --- |
| AE | 简单、易实现；适合降维与特征提取；重构质量尚可 | 生成质量差（模糊、失真）；缺乏生成新样本的能力 |
| VAE | 生成质量较高且多样；能采样；有一定抗噪能力 | 训练较复杂、需调超参；清晰度常不如 GAN |
| GAN | 生成质量高、逼真；多样性好 | 训练不稳定（模式崩溃）；算力开销大；质量依赖判别器 |

**应用场景**：AE 用于降维、去噪、异常检测；VAE 用于图像生成与重建、数据插补；GAN 用于图像/视频生成与编辑、数据增强。

**一句话选型**：要"降维与特征"选 AE，要"可控采样生成"选 VAE，要"极致逼真"选 GAN（并接受训练难度）。

### 8.4 常见问法

- **问：多模态模型的核心难点是什么？** 对齐。不同模态的语义空间不一致，必须先映射到同一空间，否则融合只是"把两种数据拼在一起"。
- **问：CLIP 是怎么对齐的？** 用大规模图文对做对比学习：配对的图文向量拉近，不配对的推远，从而得到可比较的联合空间。
- **问：VAE 里 KL 散度起什么作用？** 约束编码出的分布接近标准正态，保证潜在空间连续、可采样，避免退化成普通 AE。
- **问：GAN 模式崩溃是什么？** 生成器只产出少数几种样本（总能骗过判别器），多样性崩塌；常用小批量判别、Wasserstein 损失等缓解。

## 九、应用落地：意图识别、幻觉与合规

前面几章讲"模型怎么工作"，本章讲"系统怎么不出事"。意图识别决定请求路由是否正确，幻觉治理决定回答能不能信，合规决定产品能不能上线——三者共同构成生产环境的护栏。

### 9.1 意图识别：把用户的话映射到业务动作

**意图识别（Intent Recognition）** 是从用户输入中判断其真实目标，例如把"帮我订一张明天去北京的机票"解析为"订机票"。本质是一个**文本分类**问题。

生活化比喻：像网关的路由规则——先判断这是哪类请求，才能转发到对应的服务；分错了，后面的处理全错。

**两个难点**

- 语义多样性：同一意图有无数种说法（"我要退钱""怎么申请退款"）。
- 短文本信息稀疏："订单错了"到底是改单还是取消，必须结合上下文。

**技术流程**

1. 数据准备：定义意图标签体系，人工标注或用聚类 + 弱监督冷启动；对样本少的意图做回译、同义词替换等增强。
2. 模型选型与训练
   - 短文本高精度场景（客服对话）用 BERT 类编码器 + 分类头（全连接 + Softmax）。
   - 长文本或需要生成式判断（邮件分类）可用生成式模型。
   - 对话场景需要上下文：用长文本模型或缓存历史状态。
3. 部署与迭代
   - 轻量化：蒸馏（如 DistilBERT）、量化（FP32→INT8）降延迟。
   - 持续迭代：监控 badcase，用主动学习挑高价值样本回流标注。

**案例：银行电话客服意图分类**：把录音转写文本分成 10 类（开户、转账、挂失等），准确率要求 95% 以上且响应时间严格。落地要点是先用 BERT 微调打底，再用量化把延迟压到业务可接受范围，最后靠 badcase 回流持续迭代。

### 9.2 幻觉：定义与三类典型表现

**幻觉（Hallucination）** 指模型生成**看似合理但与事实或逻辑不符**的内容。

生活化比喻：像一个特别会编的学生——考试时不知道答案，就编一个"看起来很像真的"历史事件，语气还很自信。

**三类典型幻觉**（案例：某银行智能投顾系统，生成金融建议时虚构数据）

| 类型 | 表现 | 解法 |
| --- | --- | --- |
| 事实性幻觉 | 声称某基金年化收益 35%（实际最高 12%） | 接入实时数据库，RAG 增强 |
| 逻辑性幻觉 | 推荐"低风险高收益"产品（违反金融常识） | 规则引擎校验，过滤矛盾表述 |
| 指令跟随偏差 | 用户问 A 股却推荐港股 ETF | 强化 SFT 的指令对齐数据 |

**为什么会幻觉**：训练数据有偏差或过时、模型倾向"补全"而不是"承认不知道"、上下文理解错误、解码时采样随机性过大。

### 9.3 幻觉的检测与抑制

治理思路是"检测 + 抑制"双轨：检测负责发现，抑制负责减少发生。

**检测手段**

| 手段 | 做法 |
| --- | --- |
| 事实核查 | 集成知识库（ES、知识图谱），把输出与可信源比对，未匹配即标记"疑似幻觉" |
| 一致性验证 | 用多轮对话日志检查前后矛盾（矛盾率超阈值即告警） |
| 置信度评分 | 输出时附带置信分数，低置信触发人工复核 |
| 专业校验器 | 医疗等场景用术语库/知识图谱扫描实体，标记"剂量超范围"这类异常 |

**抑制手段**

| 手段 | 做法 |
| --- | --- |
| RAG | 先检索再回答，提示词写"基于以下资料回答，不要推测" |
| 领域微调 | 用行业 QA 数据微调，强化术语与业务规则 |
| 提示工程 | 加约束指令："若不确定，回复'需人工协助'" |
| 解码约束 | 用 logits 偏置惩罚虚构内容的 token |
| 规则引擎 | 正则 + 业务关键词过滤高风险表述 |
| 人类反馈 | RLHF 让模型学会拒答与谨慎表达 |

**案例 1：保险 AI 客服（条款解读、理赔咨询）**

- 痛点：虚构条款、错误理赔建议（如误报"特定疾病可全额理赔"），引发纠纷，人工复核成本上升约 30%。
- 方案：事实核查模块对接条款库；多轮日志做一致性检查；RAG 注入条款与案例，提示词约束"基于检索结果回答"；10 万条行业 QA 微调；加"不确定则转人工"指令。
- 效果：幻觉率从约 15% 降到约 3%，问答准确率约 95%，投诉率下降约 40%。

**案例 2：医疗语音转写生成病历**

- 痛点：音频噪声与术语歧义导致虚构（如把"父亲再婚后去世"转成"她 65 岁去世"），大量病历需人工复核，医生复核时间增加约 50%。
- 方案：术语校验器（疾病库、药品库扫描实体）+ 上下文一致性分析（对比历史病历）；低信噪比片段转人工；医疗语料微调并注入"仅转录确认内容，模糊处标记[待核实]"；医生标注错误样本做 RLHF。
- 效果：幻觉率降到约 10%，转录效率提升约 60%。

**工程实现（金融场景混合方案）**

```python
def generate_finance_advice(query):
    # 1. 检索增强：先拿实时数据
    knowledge = rag_retriever(query, db=real_time_finance_db)

    # 2. 受约束生成：把资料塞进提示，并加 logits 惩罚
    prompt = f"基于以下真实数据回答：{knowledge}\n问题：{query}"
    response = llm.generate(prompt, logits_processor=[FactPenaltyLogits()])

    # 3. 后处理校验：命中高风险词就走人工
    if rule_engine.check_risk_keywords(response):
        return "根据监管要求，此问题需人工服务"
    return response
```

项目口径：幻觉率从 15.2% 降到 3.1%（人工评估 3000 条样本），投诉下降约 82%，推理速度只损失约 8%（靠异步检索 + 缓存补回来）。

**要点**：单一手段都不够。RAG 管"有没有依据"，规则引擎管"合不合规"，微调管"会不会说"，人工兜底管"剩下的"。上线必须留人工通道。

### 9.4 保证生成内容的合规性

从技术、流程、制度三层建防线，再加前沿手段。

**技术层**

- 数据清洗与预过滤：训练前用关键词、敏感词库、分类模型筛掉暴力、歧视、违法内容。
- RLHF：用人工标注的合规样本做偏好训练，让模型学会拒绝高风险请求。
- 合规微调：按当地法规与业务场景定制数据集做二次微调。
- 实时内容过滤：部署轻量审核模型（FastText、规则引擎），做敏感词匹配（词库动态更新）、相似度比对黑名单、图像 NSFW 识别。
- 输出阈值控制：对高风险类别（政治、医疗建议）设概率阈值，触发即返回拒绝响应。

**流程层**

- 多级审核：实时接口拦截（毫秒级）→ 异步人工复审（金融、医疗等高敏感场景）→ 用户举报反馈通道。
- 可解释性工具：用 LRP 等技术追溯生成逻辑，定位违规内容的产生路径。
- 灰度发布：新模型先 A/B 对比违规率与误拦截率，再全量。

**制度层**

- 法规映射：建立不同地区的合规矩阵（如欧盟 GDPR、国内算法推荐与生成式 AI 相关规定），动态更新拦截策略。
- 权限分级：按用户身份（未成年人、高风险地区）调整可生成范围。
- 日志溯源：记录 prompt、模型版本、过滤结果，满足审计要求。
- 第三方审计：红队测试模拟对抗攻击，验证系统健壮性。

**前沿手段**：宪法式 AI（用显式规则约束行为，而非只靠数据）、数字水印（给生成内容加隐形标识便于追溯）。

**要平衡的事**：过度拦截会伤体验（医疗咨询被误判为违规），需用对抗测试调阈值；多语言多文化场景要本地化词库（宗教禁忌、地区法规差异）。

### 9.5 常见问法

- **问：幻觉能彻底消除吗？** 不能。它是生成式模型的固有特性，只能把发生率和危害降到可接受水平，并配人工兜底。
- **问：RAG 和微调哪个更能治幻觉？** RAG 治"不知道却硬答"，微调治"表达与格式不合规"，两者互补；只做 RAG 而不约束提示词，模型仍可能忽略检索内容。
- **问：合规只靠过滤词表够吗？** 不够。词表只能拦显式违规，语义级违规要靠分类模型 + 人工复审 + 日志审计。
- **问：意图识别准确率上不去怎么办？** 先看标签体系是否互斥、再看数据是否覆盖长尾表达，最后才考虑换模型；多数问题是标注与样本分布问题。

## 十、评估与监控

"感觉效果不错"不能上线。本章给出三层评估：**自动指标**（BLEU/ROUGE/Perplexity）、**任务与业务指标**（准确率、F1、转化率、A/B）、**线上监控**（延迟、异常、漂移）。

### 10.1 BLEU、ROUGE 与 Perplexity

三个指标测的东西完全不同，混用是最常见的错误。

| 指标 | 本质 | 衡量什么 | 典型场景 |
| --- | --- | --- | --- |
| BLEU | 基于**精确率**（n-gram 命中率）+ 简短惩罚 | 生成文本与参考文本的**字面重合度** | 机器翻译、术语翻译 |
| ROUGE | 基于**召回率**（参考中的 n-gram 被覆盖多少） | 关键信息**覆盖是否完整** | 摘要、报告生成 |
| Perplexity | 语言模型的内在指标，$\text{PPL}=\exp(\text{交叉熵})$ | 模型对文本的**预测能力**（越低越好） | 预训练质量监控、领域适配 |

**BLEU 的两个要点**：它统计 1~4 元组的匹配精确率并取几何平均（BLEU-4 最常用）；同时乘上简短惩罚（brevity penalty），防止"只译对几个词就得高分"。

**Perplexity 的直觉**：模型看到每个词时"有多惊讶"。惊讶程度越低（概率越高），PPL 越小。它衡量的是语言建模能力，**不能反映事实准确性**——一本胡说八道但语法通顺的书，PPL 也可以很低。

**案例 1：BLEU 用于跨境电商翻译**（中/英/西/俄互译）

- 问题：超过 30 字符的句子，BLEU-4 与人工评分相关性只有 0.35；文化特定词（"旗袍"译成西语）导致分数虚低。
- 解法：按标题/参数/描述分块独立计算 BLEU；再与核心名词匹配度加权组合。

```python
def hybrid_evaluation(translation, reference):
    bleu_score = calculate_bleu(translation, reference)
    key_term_match = count_keyword_overlap(translation, reference)
    return 0.6 * bleu_score + 0.4 * key_term_match
```

- 效果：与人工评分相关性提升到 0.62。

**案例 2：ROUGE 用于医疗报告生成**

- 发现：ROUGE-L 的 F1 达到 0.68 时，仍有约 23% 的关键临床指标被漏掉（如"血钾 5.9mmol/L→危急值"）；ROUGE-2 对医学术语组合的召回率明显高于 ROUGE-1（项目口径高约 41%）。
- 解法：ROUGE 与专业术语召回率加权；生命体征参数用 ROUGE-1、诊断结论用 ROUGE-L 分层评估。

```python
medical_terms = ["心肌酶谱", "血氧饱和度", "QT间期延长"]     # 领域术语库
rouge_score = calculate_rouge(output, reference)
term_recall = len([t for t in medical_terms if t in output]) / len(medical_terms)
final_score = 0.7 * rouge_score + 0.3 * term_recall
```

- 效果：关键信息漏报率从 23% 降到 6%，审核时间缩短约 40%。

**案例 3：Perplexity 用于金融风控预训练**

- 痛点：通用模型在金融文本上 PPL 从 32 飙到 89；PPL 每降 10 点，风险分类准确率约提升 3.2%。
- 做法：50GB 金融语料（财报 60%/合同 25%/研报 15%）做领域自适应预训练，课程学习由易到难；验证集 PPL 超阈值触发数据复查。

```python
for epoch in range(epochs):
    train_loss = model.train(data)
    val_ppl = math.exp(train_loss)     # 交叉熵取指数
    if val_ppl > threshold:            # 例如 80
        trigger_data_review()
```

- 效果：金融领域 PPL 降到 41，欺诈检测 F1 提升约 12.7%。

**结论**

| 指标 | 最佳场景 | 重大局限 | 工业技巧 |
| --- | --- | --- | --- |
| BLEU | 短文本/术语翻译 | 文化适配、意译场景失真 | 分块 + 关键词匹配加权 |
| ROUGE | 摘要、报告的信息覆盖 | 忽略专业领域关键指标 | 术语召回监控 + 分层评估 |
| Perplexity | 预训练质量监控 | 无法反映事实性 | 领域自适应 + 阈值告警 |

三条经验：**别迷信单一指标**（有项目 BLEU 提升但投诉增加，因为过度直译丢了文化内涵）；**组合评估**（ROUGE-L + 术语召回 + 人工审核三层）；**领域适配**（通用语料的 PPL 不能代表领域内的建模质量）。

### 10.2 微调效果怎么评估

五层评估框架，从"模型有没有学会"到"业务有没有变好"。

**① 技术指标**

| 任务 | 指标 |
| --- | --- |
| 通用 | 训练损失（是否收敛）、验证损失（与训练损失的差距是否拉大） |
| 分类 | 准确率、精确率、召回率、F1、AUC-ROC |
| 生成 | BLEU、ROUGE、METEOR + 人工评估流畅性与逻辑性 |
| 回归 | MSE、MAE、R² |
| 语言建模 | 困惑度（PPL，越低越适应） |

同时做**对比实验**：与未微调基线比、与不同微调方式（LoRA vs 全参数）比；用学习曲线与交叉验证判断是否过拟合。

**② 业务适配性**

- 领域指标：自建领域测试集，验证术语、逻辑、行业规范是否掌握（医疗要答对诊断建议，金融要合规）。
- 业务 KPI：A/B 测试对比点击率、转化率、问题解决率。
- 人工评估：相关性、流畅性、事实准确性、多样性四个维度打分；把模型放进真实业务流做端到端验证（客服看解决率，代码生成看编译通过率）。

**③ 效率与稳定性**

- 推理速度是否满足时延要求。
- 显存、模型体积是否适配部署环境（移动端、边缘设备）。
- 输出稳定性：相同/相似问题的回答是否一致。

**④ 长期监控**

- 在线指标：用户反馈、错误率、异常输入处理。
- 数据漂移：输入分布变化 → 判断是否需要重新微调。

**⑤ 工具链**：W&B、TensorBoard 跟踪训练；Prometheus + Grafana 监控线上；日志与 Trace 做根因分析。

### 10.3 线上监控指标设计（推荐系统为例）

推荐系统的监控要覆盖"用户体验、模型效果、系统健康、安全合规"四类。

| 类别 | 指标示例 |
| --- | --- |
| 用户体验 | 多样性（推荐类目分布的熵，越高越分散）、新颖性、覆盖率 |
| 转化漏斗 | 曝光→点击→加购→下单各环节转化率，用于定位瓶颈（点击高但转化低，常是价格或详情页问题） |
| 冷启动 | 新用户/新商品的首次有效推荐率 |
| 模型效果 | CTR、CVR、GMV 归因 |
| 系统健康 | 延迟 P99、GPU 利用率、超时率、错误率 |
| 安全合规 | 异常请求检测（同 IP 高频请求防刷）、参数异常分布（商品 ID 越界）、违禁词命中率 |

**设计原则**

1. **对齐业务目标**：指标要能连到 GMV、转化率这类 KPI，否则只是"好看的数字"。
2. **可观测性优先**：覆盖输入（数据质量）、输出（预测结果）、系统（资源消耗）全链路。
3. **动态阈值**：促销期与日常期的阈值不同，需要按阶段调整。
4. **分层下钻**：模型层 → 系统层 → 业务层，逐层定位。
5. **自动告警与根因**：Prometheus + Grafana + Alertmanager 做多指标联动；结合日志与链路追踪定位瓶颈。

**排查示例**：CTR 下降 → 先查数据新鲜度（用户行为日志是否延迟）、再查特征漂移（特征重要性是否变化）、最后查模型版本；GPU 利用率低 → 查推理代码是否可优化（TensorRT）、批处理是否过小。

### 10.4 常见问法

- **问：BLEU 高就说明翻译好吗？** 不一定。BLEU 只看字面重合，意译、文化适配、语序调整都会让它偏低，反过来"逐词直译"又可能得高分却不可读。
- **问：ROUGE 和 BLEU 的区别一句话？** BLEU 看"生成的内容有多少是对的"（精确率），ROUGE 看"该说的有没有说到"（召回率）。
- **问：PPL 低是否代表模型更好？** 只代表它对这批文本更"不惊讶"。PPL 依赖分词与语料，跨模型、跨语料不可直接比；它也不反映事实正确性。
- **问：微调后怎么证明有效？** 三层证据：技术指标提升（同测试集对比基线）、业务指标提升（A/B 测试）、人工评估通过（抽样盲评）。
- **问：线上效果掉了先查什么？** 先查数据（分布漂移、上游字段变更），再查系统（延迟、超时、限流），最后才怀疑模型。

## 十一、速查表

工程估算与常用数值集中在这里，便于对照检查。

### 11.1 显存与算力

| 项目 | 公式/经验值 |
| --- | --- |
| 权重显存 | 参数量 × 字节数（FP16 2B、INT8 1B、INT4 0.5B） |
| 推理显存 | 权重 + KV Cache + 激活 + 框架开销，实测留 20%~30% 余量 |
| 训练显存（全参数） | 参数量 × 16B（权重 2 + 梯度 2 + FP32 主权重 4 + Adam 8）+ 激活值；工程按 18~20B 估 |
| 激活值（粗估） | batch × seq_len × hidden × layers × 系数，开梯度检查点后可降 2~3 倍 |
| 单 token 前向算力 | 约 2 × 激活参数量（FLOPs）；训练约再乘 3 |
| 小模型参考 | 7B：FP16 约 14GB；13B：约 26GB；70B：约 140GB |

### 11.2 常用超参

| 项目 | 常见取值 |
| --- | --- |
| 全参数微调学习率 | 1e-5 ~ 5e-5，预热 + 余弦衰减 |
| LoRA 学习率 | 1e-4 量级，秩 r 常取 8~64 |
| Batch size（等效） | 通过梯度累积放大，常见 32~512 |
| 序列长度 | 训练 2K~8K，长文本靠外推或分块 |
| 蒸馏温度 T | 3~10 |
| PPO 的 KL 系数 | 0.1~0.2 |
| 滑动窗口重叠率 | 10%~15% |
| 数据划分 | 训练/验证/测试 = 80/10/10 |

### 11.3 概念对照

| 容易混淆 | 正确理解 |
| --- | --- |
| BLEU vs ROUGE | 精确率 vs 召回率 |
| Perplexity | exp(交叉熵)，衡量预测能力，不衡量事实性 |
| LayerNorm vs BatchNorm | 归一化维度不同：单样本跨特征 vs 跨样本同特征 |
| RMSNorm | 不减均值、无偏置，只按均方根缩放 |
| SwiGLU | 两条线性投影，一条过 Swish 后与另一条逐元素相乘 |
| 量化 vs 蒸馏 | 压精度 vs 压模型（参数与结构） |
| MoE | 省计算不省显存（总参数仍需全部加载） |
| PagedAttention | 分页管理 KV Cache，把显存浪费从 60%~80% 压到 4% 以下 |
| PrefixLM vs CausalLM | 前缀能否双向可见 |
| 幻觉 vs 错误 | 幻觉是"自信地编"，错误可能是"知道但算错" |
