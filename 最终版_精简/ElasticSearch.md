## 1. Elasticsearch 是什么，解决什么问题

本章回答三个入门问题：它是什么、能干什么、和 MySQL 是什么关系。先把定位讲清楚，后面讨论分片和调优时才知道每一步在优化什么。

### 1.1 一句话定义

Elasticsearch（常简称 ES）是一个基于 **Apache Lucene** 构建的、**分布式**的、**RESTful** 风格的搜索与数据分析引擎。

三个关键词先解释清楚：

- **Apache Lucene**：Apache 的 Java 全文检索库，真正负责"倒排索引 + 相关性打分"这些底层能力。它是一个库，本身不是可独立部署的服务。
- **分布式**：一个索引的数据可以拆成多份，分散在多台机器上，并由集群自动调度。
- **RESTful**：用普通的网络请求（资源地址加 JSON 报文）就能读写数据，不依赖特定编程语言的客户端。

### 1.2 三个核心特征

1. **从核心技术看**：它是 Lucene 的分布式封装。Lucene 用起来相当繁琐，ES 用一套 JSON 接口把"建索引、写入、检索、聚合"都开箱化，并补上了 Lucene 本身不提供的分布式能力。
2. **从数据结构看**：它基于**倒排索引**（Inverted Index，见第 2 章）。这决定了它与 MySQL（B+ 树索引）的本质区别：MySQL 擅长精准的事务处理，ES 擅长模糊匹配与海量文本检索。
3. **从架构特性看**：它是**近实时**（NRT，near real-time）的——写入的数据默认约 1 秒后才可被搜到；同时支持水平扩展（scale out），可以通过加节点分担数据和请求。

### 1.3 主要用途

业界常见的三类场景：

| 场景 | 典型形态 | 关键能力 |
| --- | --- | --- |
| 全文检索 | 电商商品搜索、站内搜索、代码搜索 | 分词匹配、拼写纠错、高亮、相关性排序 |
| 日志分析与可观测性 | 日志平台、链路追踪检索 | 高写入吞吐、按时间范围快速过滤、聚合统计 |
| 数据分析与聚合 | 实时看板、运营报表 | Aggregations（聚合）做分组、统计、Top N |

日志场景常说的 **ELK** 指 Elasticsearch + Logstash + Kibana，采集端也常用 Beats；这套组合现在多统称为 Elastic Stack。

### 1.4 与 MySQL 的分工

理解两者差异，先看索引结构：

- **MySQL 的 B+ 树索引像一本书的目录**：按主键有序排列，知道 ID 时翻查极快；但要找"内容里包含某个词的文章"，目录帮不上忙，只能逐页翻，也就是全表扫描，`LIKE '%keyword%'` 就是这种代价。
- **ES 的倒排索引像书末的关键词索引页**：先建好"词 → 出现位置"的对照表，搜某个词时直接定位，不需要扫描全表。

| 维度 | MySQL | Elasticsearch |
| --- | --- | --- |
| 强项 | 事务（ACID）、精准查询、强一致 | 全文检索、模糊匹配、海量聚合分析 |
| 典型查询 | 主键、范围、连接 | 分词匹配、多条件过滤、聚合 |
| 一致性 | 强一致 | 近实时、最终一致 |
| 更新代价 | 行级更新 | 文档整体重建（底层是新增 + 标记删除） |

实践中常见的组合是：**MySQL 作为数据的源头（source of truth），ES 作为查询加速层**，通过双写或变更订阅（CDC）把数据同步过去，允许短暂不一致。ES 不能替代关系型数据库做事务，也不擅长多表关联。

### 1.5 三个常见误解

- 把 ES 当主库用：它没有跨文档事务，写入成功也不等于落盘到最终形态（见第 5 章）。
- 以为 ES 能高效 join：父子文档、nested 只能解决特定形态，本质仍是反范式设计。
- 以为"加字段没成本"：每个被映射的字段都要占磁盘和堆内存，字段爆炸会拖垮集群（见 7.5 节）。

## 2. 倒排索引与分词：ES 为什么搜得快

本章讲 ES 的地基：文本如何被切成词、词又如何变成可秒级定位的索引。理解了这一层，才能解释"为什么 `LIKE '%x%'` 慢、而 ES 快"，也才能理解后文各种查询优化为什么有效。

### 2.1 正排索引与倒排索引

- **正排索引**（forward index）：以文档为中心，记录"文档 ID → 它包含哪些词"。翻文档很方便，按词找文档很慢。
- **倒排索引**（inverted index）：以词为中心，记录"词（term）→ 包含它的文档列表"。这个列表叫**倒排列表**（posting list），通常不只存文档 ID，还会存词频、位置等信息，用于打分和高亮。

生活化的比喻：正排索引像按页码排列的正文，倒排索引像书末的"关键词 → 页码"索引页。想找书里所有提到"缓存"的地方，翻索引页远比逐页读快。

### 2.2 倒排索引怎么建立、怎么查询

建立过程分两步：

1. 对文档集合逐篇**分词**，把一句话拆成一个个词；
2. 为每个词维护一条倒排列表，记录它出现在哪些文档中，列表通常按文档 ID 有序存放，便于后续归并。

查询时：

1. 把查询语句用**同一套分析器**处理，得到查询词；
2. 取出每个词对应的倒排列表；
3. 多个词时对列表做归并（求交集、按文档顺序推进），再按相关性打分排序，返回结果。

这里的关键点是：**索引时和查询时必须使用同一个分析器**。如果索引时把 "Running" 处理成 "run"，查询时却按原样查找 "Running"，就匹配不上，这类问题在排障时非常常见。

### 2.3 分词与 Analyzer

**分词**是把连续文本切成一个个词元（token）的过程。中文没有天然的空格分隔，所以中文分词比英文更依赖算法和词典。

**Analyzer**（分析器）就是 ES 里负责这件事的组件：索引时把字段文本切成词元写入倒排索引，查询时把用户输入切成同样的词元去匹配。

一个分析器由三个部件按固定顺序组成：

| 部件 | 作用 | 数量 |
| --- | --- | --- |
| 字符过滤器（character filter） | 在分词前整理原始字符，如去掉 HTML 标签、替换特殊符号 | 0 个或多个 |
| 分词器（tokenizer） | 把字符流切成词元，并记录位置与偏移 | 恰好 1 个 |
| 词元过滤器（token filter） | 处理切好的词元，如转小写、去停用词、加同义词、提取词干 | 0 个或多个 |

比喻：做一道菜要"洗菜 → 切菜 → 调味"，字符过滤器是洗菜（去掉杂质），分词器是切菜（切成可下锅的块），词元过滤器是调味（统一大小写、合并同义词）。

### 2.4 自定义一个分析器

内置分析器可以直接用，也可以把三个部件组合成自定义分析器：

```json
PUT /my_index
{
  "settings": {
    "analysis": {
      "analyzer": {
        "my_analyzer": {
          "type": "custom",
          "char_filter": ["html_strip"],
          "tokenizer": "standard",
          "filter": ["lowercase", "stop"]
        }
      }
    }
  }
}
```

中文场景需要注意：内置 `standard` 分词器对中文通常按单字切分，检索效果往往不理想，实践中会改用中文分词插件或 `ngram` 方案；具体切分效果取决于插件版本与词典配置，需要用自己的语料实测。

### 2.5 进阶了解（可跳过）

初学可略过，面试被追问"为什么左模糊慢"时可以拿这几点回答：

- 词项在词典中是有序存放的，所以**前缀类**查询（prefix、edge ngram）可以借助有序性快速定位。
- **左模糊**（`*fox`）没有前缀，无法利用有序性，通常退化为遍历词典中的词项再逐个比对，代价随词项规模上升。
- Lucene 会对词典前缀做压缩（FST 等结构）以减小词典索引体积，这也是"前缀查询比通配符查询便宜"的底层原因之一。

## 3. 分片与副本：分布式存储的最小工作单元

本章讲 ES 如何把一份大数据切成多份、放在多台机器上，以及为什么"主分片数"是个一旦定下就不好改的决定。分片规划是 ES 使用中最容易踩坑的地方，值得多花点时间。

### 3.1 分片是什么

**分片（shard）是 ES 实现分布式存储和水平扩展的最小工作单元。** 可以从两个视角理解：

- **逻辑视角**：一个索引（index，类似关系库里的"表"）的数据量可能非常大，单机硬盘放不下，单机 CPU 和内存也扛不住高并发。分片把大索引切成多份，分散到多个节点，既解决存储瓶颈，又能并行计算。
- **物理视角**：**每个分片本质上是一个独立、功能完整的 Lucene 索引**，拥有自己的倒排索引和段文件。ES 里的一个 index，是由多个 Lucene index（也就是分片）组合而成的逻辑概念。

比喻：一部几十斤重的字典没法一个人搬，就拆成若干分册，每册自带目录和索引页，需要时多人同时查不同分册。

### 3.2 为什么需要分片

- 突破单机存储上限：数据总量超过单块磁盘容量。
- 提升并行度：一次查询可以同时打到多个分片，由多核并行处理。
- 便于扩容与迁移：加节点后可以把部分分片迁过去，实现水平扩展。
- 故障隔离：单个分片损坏，不至于让整个索引不可用（配合副本）。

### 3.3 主分片与副本分片

| 维度 | 主分片（primary shard） | 副本分片（replica shard） |
| --- | --- | --- |
| 定位 | 数据的"源头"，写入先落到主分片 | 主分片的完整拷贝 |
| 数量 | 建索引时指定，之后不能直接改 | 可随时调整，默认 1（`index.number_of_replicas`） |
| 作用 | 承载数据、承担写入 | 高可用 + 分担搜索请求 |
| 放置 | 由集群分配 | 不会与对应主分片放在同一节点 |

主分片故障时，某个副本会被提升为新的主分片，数据不丢；副本还能承接搜索请求，所以并发查询压力大时，增加副本数是常见的扩容手段——代价是写放大和更多磁盘占用。

### 3.4 路由：文档到底落在哪个分片

写入或按 ID 读取一条文档时，ES 用下面的公式决定目标分片：

```text
shard = hash(routing) % number_of_primary_shards
```

- `routing`：默认是文档 ID，也可以显式指定；
- `number_of_primary_shards`：主分片数量。

这就解释了**为什么主分片数建好之后不能改**：如果把 5 改成 10，取模结果整体变化，原来的文档按新公式会被算到别的分片去，等于全部"找不到"。所以主分片数属于静态设置。

补充两点实践中容易忽略的事实：

- 单个索引的主分片数有默认上限 1024，这是防止误操作拖垮集群的安全限制，可通过系统属性调整，但不建议随意放大。
- 数量虽不能直接改，但可以用 `_split`（拆成更多分片）或 `_shrink`（合并成更少分片）生成新索引再切换，本质上仍是"新建索引 + 迁移数据"。

`_split` 有硬性前提：源索引必须置为只读、集群健康状态为 green、目标分片数是源分片数的整数倍，并且能整除源索引的 `index.number_of_routing_shards`。

### 3.5 分片数量怎么规划

分片不是越多越好，也不是越大越好：

- 分片过多（oversharding）：每个分片都有固定开销，元数据要占用主节点堆内存，搜索线程池也更容易被打满。
- 分片过大：单分片故障后恢复时间长，搜索也变慢。

官方给出的经验区间是**单分片 10GB～50GB、单分片文档数低于 2 亿**（Lucene 的硬上限约为 21 亿篇）。此外，每个节点默认最多承载 1000 个非冻结分片。

| 指标 | 经验值 | 说明 |
| --- | --- | --- |
| 单分片大小 | 10GB～50GB | 官方通用建议；早期资料常写 30GB～50GB，属经验区间 |
| 单分片文档数 | 小于 2 亿 | 超过后搜索性能明显下降，ILM 也会隐式触发滚动 |
| 每节点分片数 | 小于 1000（默认上限） | 超出会拒绝分配 |
| 主节点索引数 | 每 GB 堆约 3000 个索引 | 官方经验值，用来估算 master 规格 |

这些数字都应以自己的数据量和硬件实测为准，不存在通用最优解。

### 3.6 需要改分片数时怎么办

| 手段 | 方向 | 前提与代价 |
| --- | --- | --- |
| `_split` | 主分片变多 | 源索引只读、集群 green、目标数为源的整数倍；需要额外磁盘 |
| `_shrink` | 主分片变少 | 源索引只读、目标数能整除源分片数 |
| `_reindex` | 重建到新索引 | 最通用，可同时改 mapping，但耗时长 |
| ILM rollover | 只影响新索引 | 最省事，适合时间序列数据 |

## 4. 集群架构与容量规划

本章把分片放回真实集群：谁负责决策、谁负责存数据、谁负责转发请求，以及"该给 JVM 多少内存"这个高频问题。看懂角色划分，才能理解后面各类调优手段为什么有效。

### 4.1 节点角色

| 角色 | 职责 | 配置方式 |
| --- | --- | --- |
| 主节点（master-eligible） | 管理集群状态、分配分片、选举主节点，不存业务数据 | `node.roles: [master]` |
| 数据节点（data） | 存储分片、执行写入与查询 | `node.roles: [data]` |
| 协调节点（coordinating） | 只做请求分发与结果汇聚，不存数据、不参与选举 | `node.roles: []` |

比喻：一家公司里，主节点是决策层（管组织和分工），数据节点是仓库（真正存货、取货），协调节点是前台（接单、跑腿、汇总答复）。

生产环境通常做**角色分离**：3 台小规格专用 master（且分布在不同可用区/机架，避免单机房故障同时带走多数投票节点）、若干台高配 data、可选若干台 coordinating。角色混布在中小集群也能跑，但故障影响面更大。

### 4.2 一个日志平台的规划样例

下面是一个"日增 1TB 日志、保留 7 天、1 副本"的容量估算示例。它是示例，不是标准答案，重点是演示**怎么算**：

- **总量**：1TB/天 × 7 天 × (1 主 + 1 副本) = 约 14TB。
- **节点数**：10 台 data 节点、每台 4TB 磁盘，共 40TB，实际占用约 35%。
- **余量**：剩余空间不是随便拍的百分比，而要对照磁盘水位线——默认低水位 85%、高水位 90%、洪泛水位 95%，超过 90% 集群就会开始搬分片，到 95% 会直接给相关索引加只读块。因此要保证常态使用率明显低于 85%，并给段合并、突发流量留出空间。
- **分片数**：按单分片 10GB～50GB 的经验区间，1024GB ÷ 24 ≈ 43GB/分片，于是每日索引设 24 个主分片。
- **节点规模**：3 台 master（小规格，如 4 核 8G，分布在不同的可用区）+ 10 台 data（如 16 核 64G、NVMe SSD）+ 2 台 coordinating，共 15 个节点（也就是常说的"13+2"：13 个承担存储与决策的节点，另加 2 个纯协调节点）。

### 4.3 堆内存与 Page Cache：为什么总说"别超过 32GB"

**是什么**：JVM 的**指针压缩**（compressed oops，compressed ordinary object pointers）。在 64 位 JVM 中，对象引用默认是 8 字节；当堆大小低于某个阈值时，JVM 可以用 32 位偏移量（按 8 字节对齐缩放）表示对象地址，从而把指针开销减半。

**为什么需要**：一旦堆超过这个阈值，指针退回 8 字节，同样大小的堆能容纳的对象变少，缓存效率下降——这就是"堆开到 33GB 反而不如 31GB"这类说法的来源。

**怎么配**：

- `-Xms` 与 `-Xmx` 设为相同值，避免运行期扩缩堆；
- 不超过节点物理内存的 50%，剩下的留给操作系统做 **Page Cache**（文件系统缓存，用来缓存段文件，对检索速度影响很大）；
- 不超过指针压缩阈值。官方文档的表述是"确切阈值因系统而异，多数系统上 26GB 是安全的，部分系统可到 30GB"；
- 用日志里的 `heap size [...], compressed ordinary object pointers [true]` 或节点信息中的 `jvm.using_compressed_ordinary_object_pointers` 确认是否生效。

比喻：指针压缩就像给仓库货位编号——用短编号（32 位）能覆盖的范围有限，一旦货架超过这个范围，就只能改用长编号，每张标签都变长，同样面积的仓库能贴的标签反而变少。

举例来说，一台 16 核 64G 的 data 节点，堆通常设在 26GB～30GB 区间，其余内存留给 Page Cache；而不是照着物理内存的一半机械地设成 32GB。

需要注意：官方当前的推荐是"优先使用自动推导的默认堆大小"，手动调整只在确有需要时进行，且不要超过上述两条上限。

### 4.4 协调节点与"存储与计算分离"

**是什么**：协调节点不持有分片，只负责接收请求、把查询广播给相关分片（scatter）、再把各分片结果合并排序（gather）。

**为什么需要**：聚合查询（aggregation）需要大量内存做分组和排序。如果查询直接落在 data 节点上，一次大聚合就可能把 data 节点堆打满，节点 OOM 后连写入都会中断。

**怎么用**：单独部署 `node.roles: []` 的节点，客户端只连协调节点。代价是多一跳网络开销，收益是把"计算风险"隔离在无状态的协调层，保住数据层的稳定。

这也是一条常见的架构演进路径：初期客户端直连 data 节点省钱；随着聚合查询变复杂、OOM 频发，才引入独立协调节点。架构是演进出来的，不是一开始就照搬大厂配置。

### 4.5 两个容易被忽略的部署细节

在 `elasticsearch.yml` 中开启内存锁定：

```yaml
bootstrap.memory_lock: true
```

- **锁定内存**：开启后 JVM 会锁定堆内存，防止被操作系统换出到 swap（换页会让查询延迟出现毛刺）。开启时还需同步调整系统的内存锁定上限，否则节点会启动失败。
- **关闭 swap**：即使不锁内存，也建议在系统层面关闭 swap，避免 GC 之外的停顿。

## 5. 写入链路：refresh、translog 与段合并

本章看一条文档写进 ES 后发生了什么。理解了"什么时候可被搜到""什么时候算真正落盘"，写入侧的参数（refresh、translog）就不再是需要死记的配置。

### 5.1 一条文档的写入过程

1. 请求到达某个节点，按路由公式定位主分片，转发过去；
2. 主分片把文档写入**内存缓冲区**，同时把这次操作追加到 **translog**（事务日志）；
3. 主分片把操作同步给副本分片，副本同样写内存缓冲和 translog，成功后向客户端返回；
4. **refresh** 发生时，内存缓冲里的数据被写成一个新的**段**（segment，Lucene 的最小存储单元，一旦写出就不再修改），此时文档才可被搜索到；
5. 后台**段合并**（merge）把许多小段合并成大段，清理被标记删除的文档；
6. **flush** 触发 Lucene 提交，把段真正持久化，并开始新的 translog 世代。

比喻：收银台先把每笔交易记在小票存根（translog）上，再把商品摆上货架（refresh 后可被顾客看到），打烊后统一记账归档（flush）。

### 5.2 关键参数与默认值

| 参数 | 默认值 | 作用 |
| --- | --- | --- |
| `index.refresh_interval` | `1s`（Serverless 为 `5s`） | 多久做一次 refresh，决定"写入到可搜"的延迟 |
| `index.translog.durability` | `request` | 每个写请求后都 fsync 事务日志，保证已确认的写入不丢 |
| `index.translog.sync_interval` | `5s` | `async` 模式下多久 fsync 一次 |
| `index.translog.flush_threshold_size` | `10GB` | translog 达到该体积时触发 flush |

补充：`refresh_interval` 设为 `-1` 只是关闭周期性刷新，并不代表文档永远不会可见——有其他机制也会触发 refresh。

### 5.3 日志类场景的写入优化

日志是"写多读少、允许秒级延迟"的典型场景，可以牺牲一点可见性换吞吐：

```json
PUT /logs-2026.11.18/_settings
{
  "index": {
    "refresh_interval": "30s",
    "translog.durability": "async",
    "translog.sync_interval": "5s"
  }
}
```

- `refresh_interval` 从 1s 调到 30s 甚至 `-1`，减少小段数量和随之而来的合并压力；
- `translog.durability` 改为 `async`，最多可能丢失最近一个 `sync_interval`（默认 5s）内已确认的写入；
- 批量写入用 Bulk 接口，单批大小经验上控制在 5MB～15MB，并控制并发，避免把写入队列打满。

批量写入的 Java 示例（Elasticsearch Java API Client 8.x）：

```java
BulkRequest.Builder builder = new BulkRequest.Builder();
for (Product product : products) {
    builder.operations(op -> op
        .index(idx -> idx
            .index("products")
            .id(product.id())
            .document(product)
        )
    );
}
BulkResponse response = client.bulk(builder.build());
if (response.errors()) {
    for (BulkResponseItem item : response.items()) {
        if (item.error() != null) {
            logger.error("写入失败：{}", item.error().reason());
        }
    }
}
```

注意"吞吐提升多少"高度依赖数据形态、磁盘和分片分布，无法给出通用倍数，应压测后按实际情况记录。

### 5.4 不能丢数据的场景

商品、订单这类数据不允许丢失，应保持 `translog.durability` 为 `request`（默认值），配合至少 1 个副本；集群级备份则依赖快照（snapshot）——官方明确说明，直接复制数据目录不是受支持的备份方式，只有快照能可靠恢复。

## 6. 查询链路：一次搜索是怎么走完的

本章解释搜索请求在集群内的两阶段执行过程，并说明"深分页"为什么会拖垮集群。这两点是查询优化和线上排障的基础。

### 6.1 两阶段：查询阶段与取回阶段

1. **接收请求**：任意节点收到搜索请求后，本次请求就由它担任协调节点；
2. **广播查询**：协调节点把请求转发给索引中每个分片的一个副本（主或副本均可），各分片在本地执行查询，构建一个大小为 `from + size` 的优先队列（按排序值排列），只返回文档 ID 和排序值；
3. **归并排序**：协调节点把所有分片的优先队列合并成全局有序列表，截取需要的区间；
4. **取回内容**：协调节点再向持有这些文档的分片批量请求 `_source`（原始文档），这一步叫 fetch；
5. **返回结果**：合并后返回给客户端。

比喻：先在各个书架登记"符合条件的书名清单"（查询阶段，只传名字，数据量小），确定最终名单后再去把对应的书取出来（取回阶段，才真正搬运内容）。

### 6.2 深分页：为什么 from + size 会出事

分页时每个分片都要准备 `from + size` 条候选，协调节点还要全部收上来再排序。翻到很深的页码时（例如每页 20 条、翻到第 1 万页，`from` 达到 20 万），内存与 CPU 开销随 `from + size` 线性上升，很容易触发堆压力甚至 OOM。为此 ES 默认用 `index.max_result_window = 10000` 限制 `from + size`。

| 方案 | 适用场景 | 关键限制 |
| --- | --- | --- |
| `from` + `size` | 前 1 万条以内的常规分页 | 超过 `max_result_window` 会被拒绝 |
| `scroll` | 批量导出、重建索引等离线任务 | 快照语义（看不到后续变更）；官方已不推荐用于深分页；默认最多 500 个并发 scroll 上下文 |
| `search_after` + PIT | 面向用户的实时深分页 | 必须提供稳定的排序（含唯一 tiebreaker）；`from` 只能为 0 或 -1 |

`search_after` 的思路是"从上一页最后一条之后接着取"，不做跳页：

```json
POST /products/_search
{
  "size": 20,
  "sort": [
    { "price": "asc" },
    { "id": "asc" }
  ],
  "search_after": [199.00, "p_10086"]
}
```

`sort` 里必须带一个能唯一区分文档的字段（如 `id`），否则相同排序值的文档可能在翻页时重复或漏掉。需要保证翻页期间索引状态稳定时，用 **PIT**（point in time，时间点快照）配合 `search_after`。

### 6.3 查询层的常见坑

- **过滤与打分混用**：只做筛选、不需要相关性得分的条件应放进 `bool.filter`。过滤上下文不计算得分，结果还能被缓存，通常比 `must` 更省资源。
- **前导通配符**：`*fox`、`?fox` 这类查询无法利用词典有序性，代价高（见 2.5 节），可改为写入时生成 `ngram` 或倒序字段，把左模糊转成前缀查询。
- **返回字段过多**：用 `_source` 过滤或 `fields` 只取需要的字段，避免把大文档整篇搬回客户端。
- **聚合与脚本**：大基数聚合、`script` 计算都吃内存和 CPU，注意用 `keyword` 字段做聚合，`text` 字段需配 `field.keyword` 子字段。
- **正则与超长查询**：`regexp`、过长的 `terms` 列表都会放大开销，注意相关默认上限。

## 7. 调优方法论与四层调优清单

本章把前面各章的知识收拢成可执行的调优路径。核心观点是：调优不是背参数，而是在"成本、性能、可靠性"之间做有依据的取舍。

### 7.1 四层调优模型

| 层次 | 关注点 | 常见动作 |
| --- | --- | --- |
| 硬件与部署 | 机器规格、角色划分、可用区 | 角色分离、堆内存设置、内存锁定、跨可用区部署 |
| 索引设计 | 分片与副本、mapping、生命周期 | 合理分片数、`keyword` 精确字段、ILM 滚动与删除 |
| 写入层 | refresh、translog、批量 | 调整刷新间隔、异步 translog、控制 Bulk 批次 |
| 查询层 | 查询写法、分页方式、聚合 | filter 上下文、避免左模糊、`search_after` 替代深分页 |

### 7.2 ILM 与索引滚动

**是什么**：ILM（Index Lifecycle Management，索引生命周期管理）用策略自动完成"热 → 温 → 冷 → 删除"的迁移与滚动。

**为什么需要**：时间序列数据（日志、指标）如果一直写进同一个索引，索引会无限膨胀，分片无法再切分，只能靠重建；用滚动（rollover）按大小或时间自动切新索引，才能持续保持单分片大小合理。

**怎么配**：

```json
PUT _ilm/policy/logs_policy
{
  "policy": {
    "phases": {
      "hot": {
        "actions": {
          "rollover": {
            "max_primary_shard_size": "50gb",
            "max_age": "30d",
            "min_primary_shard_size": "10gb"
          }
        }
      },
      "delete": {
        "min_age": "7d",
        "actions": { "delete": {} }
      }
    }
  }
}
```

要点：`max_size` 已标记弃用（较新版本推荐 `max_primary_shard_size`）；空索引默认不会滚动；任意一个 `max_*` 条件满足即滚动，`min_*` 条件用于避免产生大量过小的索引。

### 7.3 冷热分离与成本权衡

热数据放在 SSD 高配节点（`data_hot`），较旧的数据迁到 `data_warm`/`data_cold`，更久的数据可用可搜索快照放到廉价存储。业界常说"80% 的查询集中在 20% 的热数据"，这是经验观察而非定律，但足以支撑分层存储的设计：用架构复杂度换硬件成本。

### 7.4 为什么"加机器"不是第一步

加机器是线性成本，但性能瓶颈往往不在"机器不够"：可能是主节点被海量索引拖慢、分片分布倾斜导致个别节点过热、单分片过大导致恢复慢、或者查询写法本身有问题。这些情况下加机器收益递减。更合理的顺序是：先看监控定位瓶颈 → 优化查询与索引设计 → 再评估扩容。

### 7.5 大规模数据下的查询优化清单

1. **索引设计**：分片数与副本数匹配数据量和并发；字段类型选准（精确匹配用 `keyword`，全文检索用 `text`），避免无用字段膨胀 mapping。
2. **查询写法**：避免前导通配符与复杂正则；能用 `filter` 就不用打分查询；只返回必要字段。
3. **内存管理**：关注堆使用与熔断器（circuit breaker）指标，避免大聚合、大排序把堆打满。
4. **段合并**：对只读的历史索引在低峰期做 force merge，减少段数量和碎片；正在写入的索引不要频繁 force merge。
5. **数据结构与聚合**：优先用内置聚合能力（terms、date_histogram 等），少用 script；合理使用 `doc_values`。
6. **网络与超时**：保证节点间网络带宽与延迟；为长查询设置合理超时，避免请求堆积。
7. **监控指标**：持续跟踪查询延迟、拒绝数（rejected）、堆使用率、段数量、分片大小等指标，据此调整配置。

### 7.6 高并发下的稳定性与数据安全清单

1. **备份与恢复**：用快照定期备份，并验证恢复流程。
2. **分散负载**：合理设置分片数与路由，避免请求集中到少数节点。
3. **副本分片**：至少 1 个副本，兼顾可用性与读吞吐。
4. **监控告警**：对集群健康、磁盘水位、拒绝率、延迟设置阈值告警。
5. **安全认证**：开启身份认证与权限控制（如基于角色的访问控制），避免裸奔。
6. **限流**：对单用户的查询并发或耗时做限制，防止个别调用打垮集群。
7. **负载均衡**：客户端侧或前置代理做请求分发，避免只连一个协调节点。
8. **硬件与网络**：磁盘 IO 往往是瓶颈，SSD 优先；保证网络带宽。
9. **持久化存储**：使用可靠磁盘，并依赖副本与快照兜底。
10. **版本更新**：及时升级补丁版本，修复已知缺陷与安全问题。

### 7.7 集群与写入层优化清单

1. **防止脑裂**：6.x 及更早版本通过 `discovery.zen.minimum_master_nodes` 控制选举法定人数；7.0 起改为基于投票配置（voting configuration）的集群引导，配置项变为 `discovery.seed_hosts` 与 `cluster.initial_master_nodes`，旧参数已不在新版配置文档中。部署 3 台专用 master 是通用做法。
2. **锁定内存**：`bootstrap.memory_lock: true`，并关闭 swap。
3. **设置分片数**：按 3.5 节的经验区间规划，避免过小（分片爆炸）或过大（恢复慢）。
4. **优化 translog**：按数据重要性在 `index.translog.durability`（`request`/`async`）与 `index.translog.sync_interval` 之间取舍。
5. **角色分离**：master、data、coordinating 分开部署，避免相互影响。
6. **优化 mapping**：显式 mapping 代替动态 mapping，控制字段数量与类型。
7. **善用数据结构**：精确匹配与聚合用 `keyword`，全文检索用 `text`；用 `doc_values` 支持排序聚合。
8. **网络与连接**：复用连接、控制并发、合理设置超时与重试。
9. **定期合并段**：只读索引在低峰 force merge，减少段数量。
10. **持续监控**：以指标驱动调整，而不是凭感觉改参数。
