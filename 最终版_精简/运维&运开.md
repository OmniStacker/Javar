# 运维与运维开发知识汇总

运维（Operations，常简称 Ops）负责让服务器、系统和软件稳定、高效地跑着：装系统、配环境、盯监控、查故障、做备份、扛安全。对 Java 开发者来说，代码写完只是开始，真正上线后还要面对"进程为什么起不来""磁盘为什么满了""半夜为什么报警"这些问题，所以运维常识是后端工程师的必备技能。

这份文档按"是什么 → 为什么需要 → 怎么用"的顺序，把运维与运维开发方向的基础知识串起来，覆盖七个部分：运维的角色与基础指标、Linux 系统运维、网络运维、安全运维、自动化运维工具、监控与日志管理、云计算与虚拟化。

文中命令都给了可直接执行的示例；涉及版本差异、默认值的地方会注明"取决于实现/版本"，凡属经验判断的数字都会明确标为经验值，不作为硬指标。

## 一、运维的角色与基础指标

这一章先建立整体认知：运维到底在做什么、和运维开发有什么区别，以及日常盯的四个资源指标分别意味着什么。不理解指标含义，后面所有命令和报表都只是数字。

### 1.1 运维与运维开发分别做什么

**运维是什么。** 运维是保障系统、软件稳定运行和高效管理的一类工作，具体包括：系统安装与部署、配置管理、性能监控、故障排查、安全维护、备份恢复、容量规划。

可以把运维理解成小区的物业公司：保证水电（服务器与网络）不断、电梯（应用）能跑、监控（摄像头）看得见、出了事故（故障）有人第一时间到场。物业不生产住户要用的东西，但少了物业，整栋楼很快就会乱。

**为什么需要运维。** 一个应用从"能在我电脑上跑"到"能稳定支撑几千人同时用"，中间隔着一堆非业务问题：机器规格够不够、端口开没开、日志往哪写、磁盘满了怎么办、被攻击了怎么挡。这些问题不解决，代码写得再好也上不了线。

**运维开发是什么。** 运维开发（有时和 DevOps 混用）是用写代码的方式做运维：把重复的部署、巡检、扩缩容流程做成平台或工具，让运维工作可复用、可审计。区别可以这样记：运维是"物业公司"，运维开发是"给物业公司造工具和流水线的工程队"。

**职业特点（市场观察，非硬性结论）。** 从招聘信息看，运维/运维开发岗位对学历的要求通常低于后端研发，薪资水平与后端大体接近；掌握云原生相关技能时议价空间通常更大。这类专职岗位多见于中大型企业，小公司常由后端兼任。相对地，纯运维岗位的职业天花板一般低于后端研发，即便能做到定制云原生平台、甚至做二次开发。

这里出现的**云原生**（Cloud Native）指的是以容器、容器编排、声明式配置为基础来构建和运行应用的一套方式，典型代表是 Docker 与 Kubernetes（K8S）。

### 1.2 四个常见运维指标

**是什么。** 运维看系统健康，最常盯四类资源：CPU、内存、磁盘 I/O、网络带宽。

**为什么需要。** 应用变慢时，"慢"只是一个结果。要定位原因，必须落到具体资源：是 CPU 算不过来，还是内存不够开始换页，还是磁盘读写排队，还是带宽被打满。这四个指标就是排查的起点。

**怎么用。** 先记住它们各自衡量什么，再看经验参考值。下表数值均为经验参考，实际阈值应结合业务类型和压测结果确定。

| 指标 | 衡量什么 | 经验参考 | 生活化类比 |
| --- | --- | --- | --- |
| CPU 使用率 | CPU 时间被占用的比例 | 日常平均低于 70%~80% 较从容，持续更高可能变慢、任务积压 | 后厨的忙闲程度 |
| 内存使用率 | 物理内存被占用的程度 | 多数服务 50%~80% 属常见区间，接近上限并开始用 swap 需警惕 | 操作台的可用面积 |
| 磁盘 I/O | 磁盘每秒能完成的读写次数（IOPS）与吞吐 | 机械盘与 SSD 差一到两个数量级，须按设备型号评估 | 仓库取货的速度 |
| 网络带宽 | 单位时间能传输的数据量，常用 bps（比特每秒） | 取决于带宽规格与业务，如办公网常见 100Mbps~1Gbps | 门口通道的宽度 |

补充说明：

- **CPU 使用率**持续偏高会带来响应变慢、请求排队；但短时尖峰（如定时任务）不一定有问题，要看趋势和持续时间。
- **内存使用率**不能只看"空闲"数字。操作系统会把空闲内存拿去做缓存（cache），需要时再回收，所以"空闲很少"往往并不等于"内存不够"。多数发行版的 `free` 输出带有 `available` 列，它比 `free` 列更能反映真实可用内存。
- **磁盘 I/O** 方面，机械硬盘顺序读写通常在百 MB/s 量级、IOPS 几百到上千；SSD 顺序读可达 GB/s 量级、IOPS 上万（均为经验值，具体取决于型号与接口）。长时间 I/O 等待过长，会直接表现为应用响应迟缓。
- **网络带宽**要区分 bps（比特/秒）与 B/s（字节/秒），两者相差 8 倍：100Mbps 约等于 12.5MB/s。带宽被打满时会出现拥塞、延迟升高、丢包。

### 1.3 常见服务器操作系统

**是什么。** 服务器上跑的操作系统主要分三支：Windows Server、Linux、Unix。

**为什么需要区分。** 不同系统的命令行、软件包管理、服务管理方式完全不同，运维操作的第一句话往往是"这是哪套系统"。

- **Windows Server**：图形界面友好，集成 Active Directory（域账户管理）、DNS、DHCP 等服务，常见于企业内部办公环境和对图形化、兼容性要求高的场景。
- **Linux（CentOS、Ubuntu、Debian 等）**：开源、稳定、资源占用低，命令行与软件生态丰富，是 Web 服务器、数据库服务器、云平台的主流选择。
- **Unix（AIX、Solaris 等）**：历史悠久、稳定性出色，多用于金融核心等对可靠性要求极高的场景，但成本高、份额小于 Linux。

**怎么用。** 学运维建议以 Linux 为主：云服务器绝大多数是 Linux，容器与 K8S 生态也以 Linux 为底座。Windows Server 的差异点集中在服务管理（见 2.5 节）。

## 二、系统运维：Linux 日常操作

这一章是运维的"手上功夫"：看资源、管账号、管权限、装软件、管服务。这些命令覆盖了日常运维的大部分现场操作，建议在测试机上逐条敲一遍。

### 2.1 查看系统资源使用情况

**是什么。** Linux 把系统状态暴露成一组命令，最常用的六个如下表。

| 命令 | 主要用途 | 典型用法 |
| --- | --- | --- |
| top | 实时看整体状态：任务、CPU、内存、swap | `top`，按 `q` 退出 |
| free | 看内存与 swap 的总量、已用、缓存 | `free -h` |
| df | 看各挂载点的磁盘空间 | `df -h`、`df -i` |
| du | 看目录/文件占了多少空间 | `du -sh *` |
| iostat | 看 CPU 与磁盘 I/O 统计 | `iostat -x 1 5` |
| netstat | 看连接、监听端口、路由表、接口统计 | `netstat -tunlp` |

**怎么用。** 按"先看整体、再看局部"的顺序排查：

1. 系统卡 → 先 `top` 看是 CPU 高、内存高，还是 I/O 等待（`wa`）高。
2. 内存告警 → 用 `free -h` 看 `available` 列和 swap 使用量。
3. 磁盘告警 → 先 `df -h` 找满的挂载点，再 `du -sh *` 逐层找大文件/大目录。
4. 磁盘慢 → 用 `iostat -x 1 5` 看 `%util`、`await`（平均响应时间，含排队时间）。
5. 端口不通 → 用 `netstat` 或 `ss` 看端口是否在监听、是谁占用的。

```bash
  # 整体状态：CPU、内存、负载
top

  # 只看 CPU 汇总一次，适合脚本采集
top -bn1 | head -5

  # 内存，人类可读单位
free -h

  # 磁盘空间；-i 看 inode 是否耗尽（小文件极多时会遇到）
df -h
df -i

  # 找出当前目录下占用最大的几项
du -sh * | sort -rh | head -10

  # 每 1 秒采样一次，共 5 次；关注 %util、await、aqu-sz
iostat -x 1 5

  # 查看监听端口与占用进程（通常需要 root 才能看到进程名）
sudo ss -tunlp
```

几个需要留意的点：

- 在 `top` 界面里按 `1` 可以展开每个 CPU 核的使用率，按 `P`、`M` 可分别按 CPU、内存排序（不同版本的按键可能略有差异）。`load average` 三个数字分别是 1、5、15 分钟的平均负载，要结合核数看：8 核机器负载 8 大致相当于"满载"。
- `df` 显示"有空间"但写不进去，常见原因是 inode 用尽，用 `df -i` 确认。
- `iostat` 一般由 sysstat 软件包提供，若提示找不到命令，先装 sysstat。它的 `%util` 表示设备有 I/O 请求的时间占比，对机械盘接近 100% 通常意味着饱和；但对 SSD、RAID 这类可并行处理请求的设备，`%util` 接近 100% 并不能说明已到性能上限。
- `netstat` 属于老牌 net-tools 工具，很多新发行版默认不再安装；功能相近、信息更全的替代品是 iproute2 提供的 `ss`（看连接）和 `ip`（看地址、路由、接口）。两者输出含义相近，新环境优先用 `ss`。

### 2.2 用户与用户组管理

**是什么。** Linux 是多用户系统，每个账号属于一个主组，还可以加入若干附加组；权限按"用户 + 组"分配，所以建账号、分组的操作是权限管理的前置动作。

**为什么需要。** 生产环境不该所有人共用 root。正确做法是按角色建账号：数据库管理员在自己的组里，Web 服务用独立的低权限账号跑，出问题时能追溯到人。

**怎么用。** 常用命令与要点：

```bash
  # 添加用户（-m 表示同时创建家目录；是否需要该参数取决于发行版默认配置）
sudo useradd -m testuser

  # 设置/修改密码，按提示输入两遍
sudo passwd testuser

  # 删除用户；-r 连同家目录和邮箱文件一起删除
sudo userdel testuser
sudo userdel -r testuser

  # 添加用户组
sudo groupadd testgroup

  # 把用户追加到附加组：-a 追加，-G 指定组
sudo usermod -aG testgroup testuser

  # 查看某个用户所属的组
id testuser
```

一个高频坑：`usermod -G` 不带 `-a` 时，它的语义是"把用户的附加组设置为这一组"，用户原来所在的其它附加组会被移除。所以"追加组"必须写成 `-aG`，`-a` 也只能和 `-G` 一起用。

### 2.3 文件权限：rwx、属主与属组

**是什么。** 每个文件/目录都记录了属主（owner）、属组（group）和一组权限位。权限分三档：属主、属组、其他人；每档三位：`r`（读）、`w`（写）、`x`（执行）。

**为什么需要。** 权限是 Linux 上最基础的隔离手段：配置文件不能让所有人改，私钥不能让同组人读，脚本必须带执行位才能直接运行。

生活化的理解：文件像一个有三把锁的抽屉，属主、同组、其他人各有一把钥匙，`r/w/x` 决定这把钥匙能开哪一格。

**怎么用。** 关键是要知道 `r/w/x` 对文件和目录的含义不同：

| 权限 | 对文件 | 对目录 |
| --- | --- | --- |
| r | 可以读取内容 | 可以列出目录里的文件名 |
| w | 可以修改内容 | 可以在目录内创建、删除、重命名文件 |
| x | 可以作为程序执行 | 可以进入该目录（访问其中的文件） |

数字表示法把三位二进制折算成一个八进制数：`r=4`、`w=2`、`x=1`，相加即得该档的权限值。

```bash
  # 754：属主 rwx(7=4+2+1)、属组 r-x(5=4+0+1)、其他人 r--(4)
chmod 754 file1.txt

  # 等价的符号写法：属主加执行位，其他人去掉写权限
chmod u+x,o-w file1.txt

  # 改属主、改属组
sudo chown newuser file1.txt
sudo chgrp newgroup file1.txt

  # 一次改属主和属组
sudo chown newuser:newgroup file1.txt
```

补充两点：`chmod -R` 递归修改时要格外小心，容易把不该放开的目录一起放开；目录的 `x` 位经常被忽略——只有 `r` 没有 `x` 的目录，能看见文件名却进不去。

### 2.4 软件包管理（以 yum 为例）

**是什么。** 软件包管理工具负责从软件源下载、安装、升级、卸载软件，并自动处理依赖关系。RHEL/CentOS 系用 `yum`（RHEL 8 及之后通常由 `dnf` 提供兼容的 `yum` 入口），Debian/Ubuntu 系用 `apt`。

**为什么需要。** 手工编译安装要自己解决依赖和升级，一旦漏装依赖就会出现"少一个 .so 文件"的经典问题。包管理器把依赖解析、版本记录、卸载清理都接管了。

**怎么用。**

```bash
  # 安装（以 Apache 为例：Debian 系包名为 apache2，RHEL 系为 httpd）
sudo yum install httpd

  # 卸载
sudo yum remove httpd

  # 升级指定包 / 升级全部已安装的包
sudo yum update httpd
sudo yum update

  # 按关键字搜索
sudo yum search mysql

  # 查看包信息：版本、依赖、简介
sudo yum info httpd
```

RHEL 系的包名与 Debian 系常常不同（同一个软件两个名字），所以"装不上"时第一步应该是 `yum search` 确认真实包名，而不是怀疑源坏了。

### 2.5 Windows Server 的服务管理

**是什么。** Windows 上的"服务"（Service）是随系统启动、在后台常驻运行的程序，例如数据库、Web 服务器、监控代理都注册成服务。

**为什么需要。** 服务由服务控制管理器（SCM）托管，可以设置"开机自启/手动/禁用"，并在崩溃后按策略重启。相比手工双击运行，服务方式才能保证机器重启后业务自动恢复。

**怎么用。** 图形界面走"服务器管理器 → 工具 → 服务"，可以查看状态、启停、改启动类型（自动、手动、已禁用）。命令行用 `sc`：

```bat
sc query ServiceName
sc start ServiceName
sc stop ServiceName

rem 配置为自动启动（注意等号后面必须有一个空格）
sc config ServiceName start= auto

rem 手动启动（按需启动）
sc config ServiceName start= demand

rem 禁用
sc config ServiceName start= disabled

rem 延迟自动启动：开机后稍晚于其它自动服务启动
sc config ServiceName start= delayed-auto
```

两个容易踩的点：一是 `sc config` 的每个选项都必须带等号，且**等号与取值之间必须有空格**（写成 `start=auto` 会直接失败）；二是未指定 `start=` 时默认值是 `demand`（手动），不是自动。

### 2.6 进阶了解（可跳过）

初学阶段可以先略过这一节，等排障时再回来看。

- `userdel` 在用户还有正在运行的进程时会拒绝删除（返回码 8），`-f` 可以强制删除但风险较高，可能留下不一致的系统状态。
- `iostat` 的 `await` 包含请求在队列中排队的时间，所以它升高可能是"设备慢"，也可能是"排队太长"；此时结合 `aqu-sz`（平均队列长度）一起判断更准确。
- `top` 的 `%steal` 表示虚拟 CPU 被宿主机其它虚拟机抢占的时间占比，云主机上该值偏高往往说明宿主机资源争抢，需要联系云厂商而不是优化自己的代码。

## 三、网络运维

这一章解决"为什么连不上"的问题。排查网络故障有固定套路：先看协议分层定位问题在哪一层，再看地址与掩码判断"该不该通"，最后用工具逐段验证。掌握顺序比记住命令更重要。

### 3.1 TCP/IP 协议与四层模型

**是什么。** TCP/IP 是互联网的基础协议族。它的分层模型通常划分为四层，自下而上为：链路层、网络层、传输层、应用层。

**为什么需要分层。** 分层的本质是"各管一段、互不越界"：底层换了技术（比如从以太网换到 Wi-Fi），上层协议不用改。

可以用寄快递来类比：应用层是信的内容和格式；传输层负责编号、签收、丢件重发；网络层负责分拣和选择路由（从哪个城市转到哪个城市）；链路层负责最后一公里，把包裹从站点送到门口。

| 层次 | 主要职责 | 代表协议 |
| --- | --- | --- |
| 应用层 | 面向具体业务的通信规则 | HTTP、FTP、SMTP、DNS |
| 传输层 | 端到端通信，负责可靠性与流量控制 | TCP、UDP |
| 网络层 | 寻址与路由，把数据包送到目标主机 | IP、ICMP |
| 链路层 | 相邻节点间的数据帧传输、MAC 地址识别 | 以太网、ARP |

**怎么用。** 记住两条关键差异：

- **TCP** 面向连接、可靠：通过三次握手建立连接，用序列号、确认应答、超时重传保证数据不丢不乱序。适合网页、接口调用、数据库连接等"不能丢数据"的场景。
- **UDP** 无连接、不可靠但延迟低：不保证送达，也不保证顺序。适合直播、在线游戏、DNS 查询等"宁可丢一帧也不要卡住"的场景。

排查时按层对照：ping 不通是网络层及以下的问题；ping 通但端口连不上是传输层或防火墙的问题；端口通但接口报 404/500 才是应用层的问题。

### 3.2 子网掩码、网络地址与广播地址

**是什么。** 子网掩码（subnet mask）是一串和 IP 等长的二进制数字，用来把 IP 地址切成"网络号"和"主机号"两段。

**为什么需要。** 主机发数据前必须先判断"目标和我是不是同一个网络"：同网段就直接发，不同网段就交给网关转发。掩码就是做这个判断的依据。

生活化理解：IP 像"城市 + 街道 + 门牌号"，掩码规定了哪几位是城市、哪几位是门牌号。城市相同就本地投递，不同就送去分拣中心（网关）。

**怎么用。** 两个计算公式：

- 网络地址 = IP 地址 **按位与** 子网掩码（主机位全部清 0）。
- 广播地址 = 网络地址的**主机位全部置 1**。

例：IP `192.168.1.100`，掩码 `255.255.255.0`（即 /24）。

```text
IP   192.168.1.100 → 11000000.10101000.00000001.01100100
掩码 255.255.255.0 → 11111111.11111111.11111111.00000000
按位与            → 11000000.10101000.00000001.00000000 = 192.168.1.0（网络地址）
主机位全置 1      → 11000000.10101000.00000001.11111111 = 192.168.1.255（广播地址）
```

因此该网段可用主机地址范围是 `192.168.1.1` ~ `192.168.1.254`，共 254 个（首尾两个地址分别留给网络地址和广播地址）。

### 3.3 VLAN（虚拟局域网）

**是什么。** VLAN 把一台物理交换机在逻辑上划分成多个互相隔离的广播域：同一 VLAN 内的设备像接在同一台交换机上，不同 VLAN 之间默认无法直接通信。

**为什么需要。** 不划分时，广播报文会扩散到整个二层网络，机器越多广播风暴越严重；同时财务、研发、测试混在一个广播域里也不安全。VLAN 用配置而不是拉线来解决这两个问题。

生活化理解：同一栋办公楼，用不同的门禁卡把人分成几个区，物理上是一栋楼，逻辑上互相串不了门。

**怎么用。** 以 Cisco 交换机为例，典型三步：

```text
! 1. 创建 VLAN
Switch(config)# vlan 10
Switch(config-vlan)# name dev

! 2. 把端口划入 VLAN（access 口用于接终端）
Switch(config)# interface range gigabitEthernet 0/1 - 5
Switch(config-if-range)# switchport mode access
Switch(config-if-range)# switchport access vlan 10

! 3. 跨交换机传递多个 VLAN 时，互联口配成 trunk
Switch(config)# interface gigabitEthernet 0/24
Switch(config-if)# switchport mode trunk
```

不同 VLAN 之间要通信，必须经过路由器或三层交换机做 VLAN 间路由（单臂路由或 SVI 接口），因为二层隔离默认不跨越。

### 3.4 网络连通性排查命令

**是什么。** 四个最常用的诊断工具：`ping`、`traceroute`、`nslookup`、`netstat`（或 `ss`）。

**为什么需要。** 网络问题可能出在链路、路由、DNS、端口任意一环。用工具按"能不能通 → 通到哪断 → 域名解析对不对 → 端口有没有监听"的顺序逐段排除，比凭感觉猜快得多。

**怎么用。**

```bash
  # 1. 通不通：发 ICMP 回显请求，看是否有应答与往返延迟（-c 指定次数）
ping -c 4 203.0.113.10

  # 2. 断在哪：逐跳显示经过的路由器与耗时（Windows 上命令为 tracert）
traceroute 203.0.113.10

  # 3. 域名解析对不对
nslookup www.example.com
dig www.example.com +short

  # 4. 端口有没有在监听、谁在监听
ss -tunlp
```

对应关系与注意事项：

- `ping` 依赖 ICMP 回显请求/应答。很多云服务器和防护设备会主动丢弃 ICMP，所以 **ping 不通不等于服务不可用**，要继续验证端口。
- `traceroute` 利用 TTL 逐跳递减的原理，让路径上每个路由器回送"超时"消息，从而画出路径；中间显示 `*` 通常是该跳设备不回送此类消息，不代表链路断了。
- `nslookup` 查的是 DNS 解析结果，能区分"域名解析错"和"解析对了但服务不通"。
- `netstat`/`ss` 看的是本机视角：端口在 `LISTEN` 状态说明服务起来了；如果只监听在 `127.0.0.1`，外部访问必然失败，这时要改服务配置里的绑定地址，而不是去查防火墙。

### 3.5 防火墙与常见策略

**是什么。** 防火墙位于内网与外网之间（或主机上），按预设规则对进出的流量做允许、拒绝、限制。

**为什么需要。** 默认"全通"意味着数据库端口、管理端口都暴露在公网，扫描器几分钟就能发现。防火墙的作用是把暴露面收敛到"业务确实需要的那几个口"。

生活化理解：小区大门的保安，手里有一份名单和规则——哪些人可以进、走哪个门、什么时间能进，其余一律拦下。

**怎么用。** 常见策略维度：

| 维度 | 说明 | 例子 |
| --- | --- | --- |
| 源/目的 IP | 只允许特定网段访问 | 只允许办公网段访问管理后台 |
| 端口 | 只开放必要端口 | 开放 80、443，关闭其余入站 |
| 协议 | 按 TCP/UDP/ICMP 分别控制 | 允许必要 ICMP 用于诊断，限制其它类型 |
| 时间段 | 按时间窗口放行 | 工作时间允许访问业务系统，夜间仅保留运维通道 |

落地时通常分两层：云上的安全组（实例级）和主机上的 firewalld/iptables/ufw（系统级）。两层都要放行才通，这也是"安全组开了还是连不上"的常见原因——忘了本机防火墙。

## 四、安全运维

这一章讲"怎么不被攻破、被攻破后怎么减少损失"。核心思路只有一句：假设一定会出事，于是提前做隔离、做监控、做备份。

### 4.1 三类常见网络攻击与防范

**是什么。** 面向 Web 系统最常见的三类攻击：DDoS、SQL 注入、XSS。

**为什么需要了解原理。** 防御手段都是从攻击原理反推出来的：知道 DDoS 靠"量"，就会想到清洗与分摊；知道注入靠"拼接"，就会想到参数化；知道 XSS 靠"浏览器执行脚本"，就会想到转义与 CSP。

**DDoS（分布式拒绝服务）。** 原理是控制大量"肉鸡"向目标发送海量看似合法的请求，耗尽带宽或连接资源，让正常用户进不来。防范手段：接入流量清洗与高防服务，在边界做限速与黑名单；用 CDN、多节点分摊流量；为关键业务预留弹性带宽。

**SQL 注入。** 原理是把恶意 SQL 片段塞进输入框，让程序把"数据"当成"代码"执行，从而绕过验证、读写甚至删除数据。防范手段：用预编译语句（参数化查询）代替字符串拼接，Java 中即 `PreparedStatement`；对输入做类型与长度校验；数据库账号遵循最小权限；必要时前置 WAF。

**XSS（跨站脚本）。** 原理是把恶意脚本存进页面（或反射到页面），其他用户浏览时脚本在其浏览器中执行，窃取 Cookie、会话令牌，或篡改页面内容。防范手段：输出时做 HTML 转义，把 `<`、`&`、`"`、`'` 等转换为实体；给 Cookie 加 `HttpOnly`、`Secure` 属性；用内容安全策略（CSP）限制可执行的脚本来源。

一句话区分注入类问题：SQL 注入打的是"服务端把输入当代码"，XSS 打的是"客户端把输入当代码"。

### 4.2 账户与密码安全

**是什么。** 围绕账号的一整套控制：密码强度、认证方式、失败处理、审计。

**为什么需要。** 弱密码和撞库是入侵成本最低的路径。与其指望攻击者不来，不如让"猜中密码"这件事变得不划算。

**怎么用。** 实践中通常这样组合：

- **密码长度优先于复杂度。** 传统企业规范常要求"8 位以上，且包含大小写字母、数字、特殊字符"。需要说明的是，NIST SP 800-63B（2025 版，即 800-63-4）已不再建议强制字符组合规则，转而要求校验密码是否落在常见/已泄露口令的黑名单中，并建议单因素密码长度至少 15 个字符、多因素场景下的密码至少 8 个字符。落地时以所在组织的合规要求为准，但"长口令 + 黑名单校验"是更被推荐的方向。
- **不要强制周期性更换。** 过去常见的"30~90 天必须改密码"已被上述指南明确不再推荐（其结论是：强制轮换往往导致密码规律化，反而更弱），改为"发现或怀疑泄露时立即强制更换"。
- **启用多因素认证（MFA）**：在密码之外再叠加手机验证码、TOTP、硬件令牌或指纹，密码泄露后仍难以登录。
- **限制失败次数**：连续多次输错后锁定一段时间或指数退避，阻断暴力破解。
- **审计与告警**：定期检查登录日志、密码修改记录、异常时间与异常来源地的登录。

### 4.3 备份与恢复策略

**是什么。** 备份是把数据复制到另一份可独立使用的副本；恢复是把副本还原回可用状态。两者是一件事的两半。

**为什么需要。** 硬件会坏、人会误删、勒索软件会加密文件。备份是唯一能把"数据没了"降级为"数据退回几小时前"的手段。

生活化理解：备份像给重要文件配一把备用钥匙，并且要定期试一试这把钥匙还能不能开门。

**怎么用。** 先定策略，再落地执行，最后验证。

| 备份类型 | 备份内容 | 恢复时需要 |
| --- | --- | --- |
| 完全备份 | 全部数据 | 只需这一份 |
| 增量备份 | 自上次**任意**备份以来的变化 | 最近一次完全备份 + 之后所有增量 |
| 差异备份 | 自上次**完全**备份以来的所有变化 | 最近一次完全备份 + 最近一次差异备份 |

策略制定要点：

- **确定范围**：操作系统配置、应用数据、数据库文件、配置文件、证书与密钥都要覆盖。
- **组合类型与频率**：例如每周一次完全备份 + 每天一次增量备份，用备份窗口换恢复速度；关键数据可提高到每小时。
- **存储位置**：本地磁盘、磁带库、对象存储都要考虑，并做到"本地 + 异地"，避免同一场灾难把生产数据和备份一起带走。业界常用的 3-2-1 原则可作参考：至少 3 份副本、2 种介质、1 份异地。
- **明确 RTO 与 RPO**：RTO（Recovery Time Objective，恢复时间目标）指业务从中断到必须恢复的最长时间；RPO（Recovery Point Objective，恢复点目标）指能容忍的最大数据丢失量，等价于"多久备份一次"。例如在线交易系统可能要求 RTO 1 小时内、RPO 15 分钟。

执行与验证：

```bash
  # 全量打包压缩（示例：备份应用目录到备份盘）
tar -czf /backup/app-$(date +%F).tar.gz /opt/app

  # 增量同步到备份机（-a 保留属性，--delete 让目标与源保持一致）
rsync -avz --delete /opt/app/ backup@10.0.0.20:/backup/app/

  # 定期做恢复演练：把备份解到临时目录验证可读、可启动
tar -tzf /backup/app-2026-01-01.tar.gz | head
```

要点：备份任务要自动化（cron / 定时任务），否则迟早会忘；**没有验证过的备份约等于没有备份**，必须定期做恢复演练并记录耗时，确认能否满足 RTO。

### 4.4 病毒与恶意软件的检测与清除

**是什么。** 恶意软件包括病毒、木马、挖矿程序、勒索软件等；检测靠"特征匹配 + 行为异常"，清除靠"隔离 + 删除 + 修补入口"。

**为什么需要。** 服务器上出现挖矿程序时，最先暴露的往往是 CPU 长期 100%、对外异常连接；不处理会持续消耗资源，还可能横向感染同网段机器。

**怎么用。**

- **检测**：安装并更新杀毒/EDR 类工具做实时扫描；同时人工看行为异常——CPU 或磁盘突然异常、出现陌生进程与服务、大量对外连接、计划任务里多出未知条目。用任务管理器、`top`、`ps`、`ss` 交叉核对进程的路径、启动时间、父进程与网络连接。
- **清除**：优先用安全工具隔离或删除受感染文件；确认恶意进程已停止、持久化入口（计划任务、服务、启动项、注册表 Run 项）已清理；随后修补被利用的漏洞（弱口令、未打补丁的服务、暴露的数据库端口），否则很快会被再次植入。
- **手动清除属于高风险操作**，只建议在能确认文件归属时进行：误删系统文件可能导致系统无法启动，操作前应先做快照或备份。

## 五、自动化运维与工具

这一章讲"把重复劳动交给机器"。判断一件事该不该自动化，标准很简单：如果它每周都要做、步骤固定、且手工做错过至少一次，就值得自动化。

### 5.1 什么是自动化运维

**是什么。** 自动化运维是用脚本、工具和平台，把安装、配置、发布、巡检、扩缩容等重复性任务固化成可重复执行的流程，减少人工敲命令。

**为什么需要。** 手工操作有三个绕不开的问题：慢（10 台机器要敲 10 遍）、不一致（漏了一步、参数写错）、不可追溯（谁在什么时候改了什么，没有记录）。机器规模一大，这三条会直接变成故障来源。

**怎么用。** 自动化的收益主要体现在四点：

- **提效**：批量在多台服务器上装软件、改配置、发版本。
- **降错**：把"正确步骤"写进代码，避免手抖与漏步。
- **标准化**：流程固定后可评审、可复用、可交接给同事。
- **可扩展**：面对几十上百台机器、多云环境，仍能统一管理。

自动化工具普遍强调**幂等**（idempotent）：同一份配置执行一次和执行十次，结果一致。这让"重跑一遍"变成安全的操作，是自动化能放心使用的前提。

### 5.2 四类常见自动化运维工具

**是什么。** 主流工具分两类用途：配置管理（Ansible、Puppet、Chef）与持续集成/持续交付（Jenkins）。

**为什么需要区分。** 配置管理解决"机器该长什么样"，CI/CD 解决"代码怎么变成线上版本"。两者常常配合使用，但职责不同。

| 工具 | 定位 | 工作方式 | 典型场景 |
| --- | --- | --- | --- |
| Ansible | 配置管理与任务编排 | 无 Agent，通过 SSH 推送，YAML 描述 | 批量初始化、发版、临时运维任务 |
| Puppet | 配置管理 | 主从架构，Agent 定期拉取并收敛 | 大型基础设施的持续一致性 |
| Chef | 配置管理 | 客户端-服务器，Ruby 编写 Recipe | 互联网企业的基础设施自动化 |
| Jenkins | CI/CD 平台 | 监听代码变更，触发构建与部署流水线 | 代码提交后的自动构建、测试、发布 |

细节说明：

- **Ansible**：基于 Python 开发，用 YAML 写 Playbook，被管理节点只需能 SSH 登录、有 Python 环境，不需要常驻 Agent。适合"临时接手一批机器"和"不想在几百台机器上装客户端"的场景。生活化类比：上门维修的师傅自带工具箱，不用在你家装一套常驻设备。
- **Puppet**：声明式，管理员在 Master 上描述"期望状态"（装什么包、配置文件长什么样），Agent 定期通信并自行收敛到该状态。适合对一致性要求极高、机器数量大的环境。
- **Chef**：同样是声明式配置管理，用 Ruby 写 Recipe，以"资源"（包、文件、服务）为单位描述配置，再分发到各节点执行。与容器技术集成较好，适合快速迭代的场景。
- **Jenkins**：开源自动化服务器，负责把"提交代码 → 编译 → 单测 → 打包 → 部署"串成流水线，并提供构建结果与历史记录。它与 Git、Maven、测试框架、制品库都能对接。

### 5.3 用 Ansible Playbook 批量部署 Web 服务器

**是什么。** Playbook 是 Ansible 的任务描述文件（YAML 格式），一份 Playbook 可以描述"在哪些机器上、按什么顺序、做什么"。

**为什么需要。** 手工装 Apache 要登录每台机器敲 `apt install`、改配置、起服务；Playbook 把这些写成文件，一条命令就能在主机组的所有机器上执行，而且可以放进 Git 走评审。

**怎么用。** 一个最小可用的例子：

```yaml
---
- name: Deploy Apache web server
  hosts: webservers          # 目标主机组，需在 inventory 中预先定义
  become: true               # 提权执行（相当于 sudo）
  tasks:
    - name: Install Apache package
      apt:
        name: apache2
        state: present       # present=已安装即可；latest=升级到最新版

    - name: Start Apache service
      service:
        name: apache2
        state: started
        enabled: true        # 开机自启
```

RHEL/CentOS 系把安装任务换成 `yum` 模块，包名也要换成该发行版中的名字（Apache 在 RHEL 系叫 `httpd`，在 Debian 系叫 `apache2`）：

```yaml
    - name: Install Apache package (RHEL 系)
      yum:
        name: httpd                 # RHEL/CentOS 系 Apache 的包名
        state: present
```

执行与检查：

```bash
  # 先做语法检查
ansible-playbook deploy_apache.yml --syntax-check

  # 试运行：只报告会改什么，不真正执行
ansible-playbook deploy_apache.yml --check

  # 正式执行，并限制在某一台机器上先验证
ansible-playbook deploy_apache.yml --limit 10.0.0.11
```

各部分含义：

- **name**：给人看的任务描述，出错时日志里显示的就是它，建议写清楚"做什么"。
- **hosts**：目标主机或主机组，取值来自 inventory（主机清单）文件。写 `webservers` 表示清单里名为 `webservers` 的组。
- **become**：是否提权执行。装软件包、管服务通常需要 root，所以要开；只读检查类任务则不必。
- **tasks**：任务列表，按顺序执行。每个任务调用一个模块（`apt`、`yum`、`service`、`copy` 等），模块参数描述"期望状态"。
- **state**：`present` 表示"确保已安装"，`latest` 表示"确保是最新版本"，`absent` 表示"确保已卸载"。

两个新手常踩的坑：一是 `apt` 模块的 `state` 默认就是 `present`（可以不写），但 `update_cache` 默认**不会**执行，安装失败提示"找不到包"时往往需要加 `update_cache: true` 或先手工更新一次软件源；二是 `apt` 模块要求目标机装有 python3-apt，纯最小化系统可能缺失。

### 5.4 用 Jenkins 做一次构建与部署

**是什么。** Jenkins 把"人工执行的一串命令"变成"由事件触发的流水线"，并把每一步的输出留档。

**为什么需要。** 手工发版容易漏步骤、版本对不上、失败后无人知晓。流水线把构建、测试、部署固定下来，每次结果可回溯，也便于多人协作。

**怎么用。** 以 Java Web 项目为例，一次完整配置可以拆成六步：

1. **安装与初始化**：按操作系统选择安装方式（Linux 用包管理器，Windows 用安装包），设置管理员账号，安装必要插件（Git、构建工具、部署插件等）。
2. **新建任务**：在界面选择"新建任务"，输入名称（如 `myapp-build-deploy`），选择"自由风格项目"（Freestyle project）。
3. **配置源码管理**：选择 Git，填仓库地址与凭证，指定分支，让 Jenkins 能拉取代码。
4. **配置触发器**：可选定时构建（Cron 表达式）、轮询 SCM（定期检查变更，如每 15 分钟一次）、或由代码平台的 Webhook 推送触发。实践中 Webhook 比轮询更及时、更省资源。
5. **配置构建步骤**：准备 JDK、Maven 等环境，然后执行构建命令。
6. **配置部署与通知**：构建成功后执行部署（用插件把 WAR 部署到 Tomcat，或用 SSH 脚本分发并重启服务），并把结果通过邮件、企业微信/钉钉、Slack 等通知到人。

构建步骤的典型命令：

```bash
  # 清理、编译、跑单测、打包，产物在 target/ 下
mvn clean package

  # 部署示例：把产物拷到目标机并重启服务（需提前配置 SSH 免密或凭证）
scp target/myapp.jar deploy@10.0.0.21:/opt/app/
ssh deploy@10.0.0.21 "systemctl restart myapp"
```

部署前要确认目标机的环境已就绪（应用服务器、目录、端口、防火墙规则），否则流水线会在最后一步失败；同时建议保留上一版本产物，出问题时能快速回滚。

## 六、监控与日志管理

这一章解决"怎么知道系统出事了"。监控回答"现在好不好"，日志回答"刚才发生了什么"。两者缺一不可：只有监控，故障时无从下手；只有日志，故障时才发现已经晚了。

### 6.1 系统监控：指标与手段

**是什么。** 系统监控是持续采集、存储、展示系统和应用运行指标，并在超过阈值时告警的一整套机制。

**为什么需要。** 没有监控，故障只能靠用户投诉发现，恢复时间被投诉延迟放大。监控的价值不只是"看见"，更是"提前看见"——容量趋势、磁盘增长、慢查询上升，都是可以在故障前处理的信号。

生活化理解：监控就是汽车的仪表盘——速度、油量、水温实时可见，异常时亮灯，而不是等发动机冒烟才知道。

**怎么用。** 指标分三层，手段分三类。

| 指标层次 | 典型指标 | 说明 |
| --- | --- | --- |
| 系统资源 | CPU、内存、磁盘 I/O、网络带宽、负载 | 判断机器是否吃得消 |
| 应用性能 | 响应时间、错误率、QPS、数据库事务成功率、GC 次数 | 判断服务是否健康 |
| 业务连续性 | 实例在线状态、端口监听状态、核心接口可用性 | 判断用户是否真的能用 |

监控手段：

- **监控工具**：Zabbix（传统企业常用，功能全）、Prometheus（云原生生态主流，配合 Grafana 展示）、云厂商自带的云监控。它们负责采集、存储、可视化与告警。
- **日志分析**：从日志里发现错误突增、慢请求、异常登录。常用 ELK/Elastic Stack 做集中存储与检索。
- **流量监控**：用 Wireshark 抓包分析、用 ntopng 做流量统计，排查带宽占用、异常外联、协议分布。

告警设计的两条经验：一是必须分级（致命/严重/警告），否则所有人都会屏蔽告警；二是必须有"可执行性"——收到告警的人知道下一步该做什么，否则只是噪音。

### 6.2 Zabbix 的架构与工作原理

**是什么。** Zabbix 是一套开源的企业级监控系统，采用"服务器 + 采集端"的架构。

**为什么需要。** 它把采集、存储、阈值判断、告警、展示做成一体，适合"机器数量多、又不想自己拼装组件"的场景；相比 Prometheus，它更偏向传统主机与网络设备的监控。

**怎么用。** 先把它的组件和角色分清：

| 组件 | 作用 |
| --- | --- |
| Zabbix Server | 接收数据、计算触发器、发送告警、提供 Web 界面 |
| Zabbix Agent | 装在被监控主机上，采集本地指标并上报 |
| Zabbix Proxy | 可选，代服务器采集一片区域的数据，适合跨机房/大规模 |
| 后端数据库 | 存配置与历史数据（MySQL、PostgreSQL 等） |

四个核心概念：**主机**（被监控对象）、**监控项**（item，采什么，如 CPU 使用率）、**触发器**（trigger，什么条件下算异常，如连续 5 分钟 CPU > 90%）、**模板**（template，一组监控项与触发器的集合，批量套用到主机）。

数据流可以概括为五步：采集（Agent 主动上报，或服务器通过 SNMP、IPMI 等协议轮询无代理设备）→ 传输 → 存储（写入数据库）→ 判断与告警（触发器命中则生成事件，按媒介通知，可配置升级策略）→ 展示（Web 界面看图表、报表、拓扑）。

### 6.3 日志管理：任务与工具

**是什么。** 日志管理是对系统、应用、网络设备产生的日志做收集、存储、分析、审计的全过程。

**为什么需要。** 日志是排障与追责的唯一原始证据。出事后第一句话往往是"看日志"；如果日志只留在本机、被覆盖、格式混乱，那这条线索就断了。

生活化理解：日志就是飞机的黑匣子——平时没人看，出事时是唯一能还原现场的东西。

**怎么用。** 四项主要任务：

- **收集**：在各设备/应用上配置输出路径与格式，用 rsyslog、Filebeat、Flume 等汇总到统一位置，保证完整、及时。
- **存储**：按容量与保留期选择介质（文件、数据库、对象存储），设置轮转（logrotate）避免把磁盘写满，重要日志异地留存。
- **分析**：解析、过滤、聚合、关联。例如统计错误码分布、找出最慢的接口、发现异常登录来源。
- **审计与合规**：记录关键操作（谁在什么时候改了配置、删了数据），满足内部审查与法规要求。

常用工具：

- **Elastic Stack（ELK）**：Elasticsearch 负责存储与检索，Logstash 负责收集、解析、转发，Kibana 负责可视化。
- **Splunk**：商用产品，检索语言强大、告警与报表完善，成本较高。
- **rsyslog**：Linux 自带的日志系统，支持本地文件、远程日志服务器、多种传输协议，是最基础的收集端。
- **Loki + Grafana**：近年在云原生场景较常见的轻量组合，按标签索引日志（可作了解）。

### 6.4 用 ELK 做日志的收集、解析与可视化

**是什么。** ELK 是一条日志流水线：Logstash 采集并结构化，Elasticsearch 存储并建立倒排索引，Kibana 提供检索与图表。

**为什么需要。** 单机 `grep` 只能查一台机器、一种格式。集中之后，可以按时间、服务、级别、关键字跨机器检索，也能做趋势图与告警。

生活化理解：Elasticsearch 是书库，Logstash 是采购与编目，Kibana 是检索台；书进库前必须先编目，否则检索台查不到。

**怎么用。** 三步搭建：

1. **Elasticsearch**：按操作系统选安装包（DEB/RPM/Docker），改 `elasticsearch.yml` 设置集群名、节点名、监听地址，启动后确认服务可用。默认监听 9200 端口（Kibana 的默认连接目标就是本机 9200）。
2. **Logstash**：编写管道配置，定义 input（来源）、filter（解析）、output（去向），启动时指定该配置。
3. **Kibana**：改 `kibana.yml` 指向 Elasticsearch 地址，启动后浏览器访问，默认端口 5601。

一条最简的 Logstash 管道：

```ruby
input {
  file {
    path => "/var/log/myapp/*.log"
    start_position => "beginning"
  }
}

filter {
  # grok 用正则把非结构化日志拆成字段
  grok {
    match => { "message" => "%{TIMESTAMP_ISO8601:ts} %{LOGLEVEL:level} %{GREEDYDATA:msg}" }
  }
  date {
    match => [ "ts", "ISO8601" ]
  }
}

output {
  elasticsearch {
    hosts => ["127.0.0.1:9200"]
    index => "myapp-%{+YYYY.MM.dd}"
  }
}
```

之后在 Kibana 里创建**索引模式**（index pattern，告诉 Kibana 要查哪批索引），再用折线图、柱状图、饼图、地图等做仪表板。实践中有两个常见问题：一是日志格式不统一导致 grok 匹配失败，需要先规范应用日志输出（推荐 JSON 格式，可省掉大部分解析工作）；二是没设置索引生命周期，日志无限增长把磁盘吃满。

## 七、云计算与虚拟化运维

这一章讲"机器从哪来"。传统方式是采购硬件、上架、装系统；云时代更多是"点几下就有一台机器"，理解背后的服务模型与虚拟化方式，才能判断哪些事该自己做、哪些事云平台已经做了。

### 7.1 云计算与服务模型

**是什么。** 云计算是通过网络按需获取计算资源（服务器、存储、网络、平台、软件）的模式，特点是用量自服务、弹性伸缩、按使用付费。

**为什么需要。** 自建机房要提前估算峰值容量，闲时浪费、忙时不够；云上可以按需扩缩，把"资本支出"变成"运营支出"。

生活化理解：IaaS 像租毛坯房（水电到位，装修自理），PaaS 像住酒店（家具家电齐全，拎包入住），SaaS 像下馆子（只管吃，后厨与你无关）。

| 模型 | 提供什么 | 用户负责什么 | 例子 |
| --- | --- | --- | --- |
| IaaS（基础设施即服务） | 虚拟机、虚拟网络、存储卷 | 操作系统、中间件、应用、数据 | Amazon EC2、阿里云 ECS |
| PaaS（平台即服务） | 运行时、中间件、数据库、构建部署工具 | 应用代码与数据 | Heroku、Google App Engine |
| SaaS（软件即服务） | 可直接使用的软件 | 只负责使用与账号管理 | Salesforce、Microsoft 365 |

选择原则：能买到现成能力就别自己造，但要评估锁定成本与数据合规要求；对核心系统，IaaS 的可控性通常更重要。

### 7.2 虚拟化技术类型

**是什么。** 虚拟化是把一份物理资源抽象成多份逻辑资源的技术，中间那层叫 Hypervisor（虚拟机监视器）。

**为什么需要。** 一台物理服务器的资源往往用不满，虚拟化让多个业务共享同一硬件又互相隔离；同时也让"复制一台环境"从几小时缩短到几分钟。

生活化理解：把一栋楼隔成多个独立公寓，共用承重墙与水电主干，但每户有独立门锁。

| 类型 | 做什么 | 代表技术 | 典型场景 |
| --- | --- | --- | --- |
| 服务器虚拟化 | 一台物理机切成多台互相隔离的虚拟机 | VMware ESXi、Hyper-V、KVM | 提高资源利用率、服务器整合 |
| 桌面虚拟化 | 桌面在数据中心集中运行，用户远程接入 | Citrix Virtual Desktops、VMware Horizon | 统一运维、数据不落地 |
| 网络虚拟化 | 在物理网络上抽象出多个隔离的虚拟网络 | VLAN、SDN | 多租户隔离、灵活编排 |
| 存储虚拟化 | 多台物理存储整合成统一存储池 | SAN/NAS 虚拟化 | 存储整合、容灾 |

补充：Hypervisor 分两类——裸金属型（直接跑在硬件上，如 ESXi、KVM）和宿主型（跑在操作系统之上，如 VirtualBox）。生产环境以前者为主，性能与隔离性更好。

### 7.3 在 OpenStack 中创建与管理虚拟机

**是什么。** OpenStack 是一套开源的云计算平台，把计算、存储、网络资源池化后按需分配。常用组件包括：Nova（计算）、Neutron（网络）、Glance（镜像）、Cinder（块存储）、Swift（对象存储）、Keystone（认证）、Horizon（Web 控制台）。

**为什么需要。** 它提供了 IaaS 层的自建方案：私有云、混合云场景下，可以像公有云一样按需创建虚拟机，同时数据留在自己机房。

**怎么用。** 最常见路径是控制台（Horizon）操作，六步：

1. **登录控制台**：浏览器访问 Horizon，用具备权限的账号登录。
2. **选择镜像**：进入"项目 → 计算 → 实例"，点"启动实例"，选择镜像（Ubuntu、CentOS 等）。镜像由 Glance 管理，可上传自制镜像。
3. **选择实例类型（Flavor）**：Flavor 定义 vCPU、内存、磁盘容量。社区早期默认提供的规格中，`m1.tiny` 为 1 vCPU、512MB 内存，`m1.xlarge` 为 8 vCPU、16GB 内存；实际部署中 Flavor 常被自定义，以控制台里列出的规格为准。
4. **配置网络**：选择接入的网络（内部私有网络、外部公共网络），分配 IP。网络拓扑由 Neutron 预先创建，包含子网、路由、安全组。
5. **设置其它选项**：命名、元数据、密钥对（用于 SSH 登录，比密码更安全）。
6. **启动**：点击"启动实例"，Nova 在计算节点上调度并创建虚拟机。

创建之后的管理动作：

- **查看状态**：实例列表里看运行状态（运行中/已停止/已暂停）、IP、资源占用。
- **启停与删除**：按需操作。停止可释放 CPU/内存，但通常仍占用磁盘与 IP；删除前确认数据已备份。
- **调整规格**：多数平台要求先关机再改 Flavor（本质是重新调度到满足规格的节点），改完再启动；部分场景支持在线扩容。
- **快照**：为实例创建快照保存某一时刻的磁盘状态，可用于回滚或批量复制环境。快照不是备份的替代品——同一存储上的快照会随存储故障一起丢失。
