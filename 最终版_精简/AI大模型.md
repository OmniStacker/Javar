## 一、先建立正确的心智模型

这一章不涉及任何代码，只解决一个问题：**知道大模型能干什么、不能干什么**。后面所有配置和提示词技巧，本质上都是在绕开它的三个限制——记不住新知识、看不到你的私有数据、一次能读的字数有限。

### 1.1 大模型到底是什么

**大语言模型（Large Language Model，LLM）** 是一类在海量文本上训练出来的神经网络，它的核心工作只有一件事：给定前面的文字，预测下一个最可能出现的「词块」，然后把预测结果接到后面，继续预测下一个。

这个过程听起来很笨，但当模型足够大、读过的文本足够多时，「接龙」就表现出了翻译、写代码、总结、推理等能力。

一个合适的生活化比喻：**它像一位知识面极广、但只在「面试」时看过资料的外部顾问**。你问他什么他都能聊，但他不知道你公司昨天的会议内容，也不会主动去查数据库——除非你把资料摆在桌上（这就叫「上下文」）。

### 1.2 四个高频术语：token、上下文窗口、参数量、量化

| 术语 | 一句话解释 | 对 Java 开发者的类比 |
| --- | --- | --- |
| token（词元） | 模型处理文本的最小单位，一个汉字通常 1~2 个 token，一个英文单词常按词根切开 | 相当于 Java 里的「词法单元」，计费时按 token 数算钱，像按调用次数算接口费 |
| 上下文窗口（context window） | 一次请求里模型最多能「同时看到」的 token 总数，输入 + 输出都算 | 相当于一个有容量上限的 `ArrayBlockingQueue`，塞满之后最早的元素会被挤掉 |
| 参数量（parameters） | 模型内部可学习数字的个数，通常写 7B、32B、671B（B = 十亿） | 相当于配置项的总条数：条数越多越「懂」，但加载越慢、越占内存 |
| 量化（quantization） | 把模型权重从高精度浮点压成低精度整数，用少量精度换显存 | 相当于把金额从 `BigDecimal` 元改成 `int` 分存储：省空间，极端值会丢精度 |

**关于量化的常见格式**（以 Ollama 的模型标签为例）：

| 格式 | 每个参数约占 | 说明 |
| --- | --- | --- |
| `fp16` | 2 字节 | 半精度原样，质量最好，体积最大 |
| `q8_0` | 约 1 字节 | 8 位量化，质量接近 fp16 |
| `q4_K_M` | 约 0.6 字节 | 4 位量化的常用默认档，体积约为 fp16 的 1/3，日常对话够用 |

举个具体例子：DeepSeek-R1 在 Ollama 上提供了 `1.5b / 7b / 8b / 14b / 32b / 70b / 671b` 等尺寸，以及 `q4_K_M / q8_0 / fp16` 等量化标签；同一份「32b」模型，`q4_K_M` 版本下载量约 20 GB，而 `fp16` 版本要大三倍以上。

粗略估算显存需求的公式是「参数量 × 每参数字节数」，再额外加上**KV 缓存**（推理时保存中间状态的内存，随上下文长度线性增长）：

| 参数量 | fp16 仅权重 | q8_0 仅权重 | q4_K_M 仅权重 |
| --- | --- | --- | --- |
| 7B | 约 14 GB | 约 7 GB | 约 4~5 GB |
| 14B | 约 28 GB | 约 14 GB | 约 9 GB |
| 32B | 约 64 GB | 约 32 GB | 约 20 GB |
| 70B | 约 140 GB | 约 70 GB | 约 40 GB |
| 671B | 约 1300 GB | 约 670 GB | 约 400 GB |

> 表中数值是「仅权重」的估算，实际还要叠加 KV 缓存与运行时开销。所以「671B 满血版要几张 A100/H100」和「32B 用一张 24 GB 消费级卡就能跑」并不矛盾——差的是参数量和一个数量级的显存。

### 1.3 三个必须接受的限制：幻觉、知识截止、上下文上限

1. **幻觉（hallucination）**：模型在不知道答案时，倾向于「编一个通顺的」而不是说「不知道」。所以凡是让它回答私有数据、精确数字、最新政策，都必须给它参考资料（RAG）或要求它标注出处。
2. **知识截止**：训练数据有截止时间，模型不知道之后发生的事，也不知道你库里的表结构。需要实时信息就得开联网搜索，或把数据放进上下文。
3. **上下文上限**：一次能读的字数有限。原文写于 2025 年初，当时「输入上下文一般为 4K 或 16K，部分支持 32K/128K」；到 2026 年 11 月核对时，主流商用 API 已经普遍到 128K 以上，DeepSeek 官方 API 文档给出的上下文长度为 1M token、最大输出 384K。**具体的数字一定要看你所用模型当时的官方文档**，不要照抄旧文章。

> 面试常见问法：为什么大模型会「一本正经地胡说」？答题要点：它是按概率生成下一个 token，优化目标是「像人写的」，不是「事实正确」；缓解手段是 RAG、工具调用、要求引用来源、降低温度参数。

### 1.4 微调、蒸馏、RAG、Agent 到底有什么区别

这四个词经常被混着用，其实解决的是不同问题：

| 手段 | 一句话说明 | 生活化比喻 | 什么时候用 |
| --- | --- | --- | --- |
| 提示词（Prompt） | 把要求写清楚，直接问 | 当面把需求讲清楚 | 首选，成本最低 |
| RAG（检索增强） | 先从你的知识库里查出相关片段，再连同问题一起给模型 | 开卷考试：先翻书再答题 | 私有知识、需要引用出处、数据经常变 |
| 微调（Fine-tuning） | 用你的数据继续训练模型的一部分参数，改变它的「习惯」 | 让新员工按你们公司的规范写文档 | 有大量高质量样本、要固定输出风格或格式 |
| 蒸馏（Distillation） | 用大模型的输出当训练数据，训练一个小模型 | 师傅带徒弟：把师傅的解题过程抄成教材 | 想用小模型复刻大模型的能力、降低推理成本 |
| Agent（智能体） | 让模型自己决定调用哪个工具、循环执行直到完成 | 给它一套工具和一个 while 循环 | 任务需要多步操作、要访问外部系统 |

**微调和蒸馏最容易混淆**，区别在于「知识从哪来」：

- **微调**：来源是**人工标注的答案**（或业务数据），目的是让模型学会你的任务；
- **蒸馏**：来源是**另一个更大的模型的输出**，目的是把大模型的能力迁移到小模型上。

DeepSeek 官方开源的 `DeepSeek-R1-Distill-Qwen-1.5B`、`-7B` 等就是典型的蒸馏产物：用 R1 生成的大量推理数据去训练 Qwen 底座，所以你在 Ollama 上看到的 `deepseek-r1:1.5b` 其实是「R1 蒸馏版」，不是 671B 那个满血模型。

**Agent 的工作循环**（业界常称 ReAct：Reason + Act）可以写成一个伪代码：

```text
上下文 = [用户问题]
while 没完成:
    决策 = 大模型(上下文)          // 思考：下一步做什么
    if 决策 是 调用工具:
        结果 = 执行工具(决策.参数)  // 行动：查库、调接口、跑命令
        上下文 += 结果             // 观察：把结果喂回去
    else:
        返回 决策                  // 输出最终答案
```

这跟写一个带重试的 `while` 循环没有本质区别，只是「判断分支」交给了模型。

### 1.5 本地跑模型的两条路线：Ollama 与 vLLM

想让模型跑在自己的机器或自己的服务器上，最常用的两个工具定位完全不同：

| 对比项 | Ollama | vLLM |
| --- | --- | --- |
| 定位 | 个人桌面级「一键跑模型」，类似 `docker run` 的体验 | 面向 GPU 服务器的推理引擎，主打高吞吐 |
| 默认端口 | 11434（本地 HTTP 服务） | 8000（以启动日志为准） |
| 启动方式 | `ollama run <模型>` 自动下载并交互 | `vllm serve <模型>` 起一个 OpenAI 兼容服务 |
| 上下文默认值 | 4096 token，可用 `OLLAMA_CONTEXT_LENGTH` 或请求参数 `num_ctx` 调大 | 由模型配置与启动参数决定 |
| 关键优化 | 量化模型分发、自动选择 GPU/CPU | PagedAttention、连续批处理（continuous batching） |
| 适合场景 | 本地开发、隐私敏感的小规模试用 | 团队共享的推理服务、需要扛并发 |

**一句话选型**：自己电脑上试用选 Ollama；要给整个团队提供 API 就上 vLLM。

> 注意一个容易踩的坑：Ollama 默认上下文只有 4096 token（见官方 FAQ）。把整份文档丢进去做 RAG，如果不调大这个值，超出部分会被静默截断，表现就是「答得不全」，而不是报错。

2. 从插件页 URL 与 Version History 里取出两个字段：`itemName`（URL 查询参数里的 itemName，如 `ms-python.vscode-pylance`，按 `.` 拆成 fieldA、fieldB）和 `version`（如 `2025.1.102`）。

![1739855538404-421ea4f3-ffb8-4b50-a1ee-808aadb869bc.png](images/1739855538404-421ea4f3-ffb8-4b50-a1ee-808aadb869bc-850957.png)

3. 用取到的值替换模板 URL 中的同名字段：

```plain
https://marketplace.visualstudio.com/_apis/public/gallery/publishers/${itemName.fieldA}/vsextensions/${itemName.fieldB}/${version}/vspackage
```

4. 浏览器打开改好的 URL 下载插件；回到 Trae 打开插件市场，把下载的 `.vsix` 拖进 **插件市场** 面板，Trae 会自动安装并显示在 **已安装** 列表。

**禁用插件**：插件市场 → **已安装** 列表找到插件 → 悬浮点 **设置 > 禁用**，或进详情窗口点 **禁用**。

![1739855536109-99cf5d76-04c9-4547-8444-bbeb1dca53f5.png](images/1739855536109-99cf5d76-04c9-4547-8444-bbeb1dca53f5-719187.png)

**卸载插件**：插件市场 → **已安装** 列表找到插件 → 悬浮点 **卸载**，或进详情窗口点 **卸载**。

![1739855536478-c6b9911c-af5d-40bd-80b5-ea90172c70dd.png](images/1739855536478-c6b9911c-af5d-40bd-80b5-ea90172c70dd-244366.png)

**常见问题：提示「暂不支持安装 VS Code 插件市场中某版本的插件」**——这通常是因为该版本插件依赖了新版 VS Code 的接口，与当前 Trae 不兼容。查看它的 Version History，下载一个更早的版本即可。

![1739855537353-a311c31c-959e-4960-98e6-853e5dc9530b.png](images/1739855537353-a311c31c-959e-4960-98e6-853e5dc9530b-782760.png)

### 2.4 Builder 模式

Builder 是「从 0 到 1 做完整项目」的模式：AI 会按需求调用不同工具（分析代码、编辑代码、运行命令），并把结果纳入项目构建流程。可以理解为**给模型配了一个终端的 Agent 循环**——它自己读文件、改文件、跑命令、看输出。

- **系统要求**：Windows 上需要 PowerShell 6 或更高版本。
- **工作流程**：AI 主动读取项目文件 → 拆解任务 → 逐步执行（提取上下文、创建/修改文件、生成并运行终端命令、分析命令结果）。
- **启用**：用快捷键（macOS：`Command + U`；Windows：`Ctrl + U`）打开侧边对话框，点左上角 **Builder**。

![1739855688213-531b32ff-a7e8-4cc0-b2b5-2ae3b4d1c649.png](images/1739855688213-531b32ff-a7e8-4cc0-b2b5-2ae3b4d1c649-162526.png)

Builder 的主要能力：

- **添加上下文**：理解当前项目里的代码、文件和文件夹。
- **输入多模态内容**：会话里可以加图片（报错截图、设计稿、参考样式）。
- **生成并处理代码变更**：AI 自动创建或编辑文件，你可以接受或拒绝：
  - 多文件：点输入框上方文件列表的 **全部接受** / **全部拒绝**。

  ![1739855689186-4813af34-49f4-45fd-944b-9fdb4472a311.png](images/1739855689186-4813af34-49f4-45fd-944b-9fdb4472a311-051667.png)

  - 单文件：打开文件，点提示条 **接受**（macOS：`Command + Enter`；Windows：`Ctrl + Enter`）或 **拒绝**（macOS：`Command + Backspace`；Windows：`Ctrl + Backspace`）。

  ![1739855688350-3a054edb-809c-4d08-9961-b7d6672d389f.png](images/1739855688350-3a054edb-809c-4d08-9961-b7d6672d389f-252272.png)

  - 单处变更：点变更右上角 **^Y**（macOS：`Control + Y`；Windows：`Alt + Y`）或 **^N**（macOS：`Control + N`；Windows：`Alt + N`）。

  ![1739855688456-aad01c80-3589-44d4-822d-b94cb8ae39fb.png](images/1739855688456-aad01c80-3589-44d4-822d-b94cb8ae39fb-163872.png)
- **生成并运行命令**：AI 推荐需要的 Shell 命令，点 **运行** 后终端执行并自动分析结果，异常时给出解决方案；成功后点命令卡片右上角 **终端** 看日志。

![1739855688844-80de1914-8c74-4c30-bbdc-92f0be4f04f5.png](images/1739855688844-80de1914-8c74-4c30-bbdc-92f0be4f04f5-224968.png)

![1739855689846-a0383083-5a70-4cbc-8e3d-d00dffa6f9c8.png](images/1739855689846-a0383083-5a70-4cbc-8e3d-d00dffa6f9c8-182005.png)

![1739855690126-d09cc625-2486-4246-95db-1085124ffd3a.png](images/1739855690126-d09cc625-2486-4246-95db-1085124ffd3a-591370.png)

- **预览成果**：完成后提供 **预览** 按钮，用 **Webview** 窗口展示，也可以点 **在浏览器中打开**；继续对话时成果会实时更新。

![1739855690206-0ef18a2a-dae3-4aad-9368-fa4589abb2f4.png](images/1739855690206-0ef18a2a-dae3-4aad-9368-fa4589abb2f4-759379.png)

![1739855690596-7ee59685-b32e-47d7-bb22-01fddc370311.png](images/1739855690596-7ee59685-b32e-47d7-bb22-01fddc370311-662954.png)

- **回退版本**：把项目退回到某一轮会话发起前的状态（**不可撤销**；只支持最近活跃的 Builder 窗口、最近 10 轮会话）。点目标对话气泡左侧 **回退**，点文件名查看将要发生的变更，确认影响范围后点 **确定**。

![1739855690920-23442466-feac-4a97-ae44-227f9c10c258.png](images/1739855690920-23442466-feac-4a97-ae44-227f9c10c258-932690.png)

![1739855691042-891ec796-a447-4fd4-b701-708a5ae74881.png](images/1739855691042-891ec796-a447-4fd4-b701-708a5ae74881-061966.png)

- **管理历史对话**：点 **Builder** 窗口右上角 **历史会话**，左侧显示 **历史记录**（含 Chat 与 Builder 的全部对话）；点条目跳转，悬浮点 **删除** 图标删除。

![1739855691706-8a2bfa2f-4719-491e-9646-efa4e7f0b9c7.png](images/1739855691706-8a2bfa2f-4719-491e-9646-efa4e7f0b9c7-754181.png)

- **添加上下文**：理解当前项目的代码、文件、文件夹和整个工作空间。

- **生成并处理代码变更**：以 Diff 形式展示，可以接受或拒绝：

  - 单文件：打开文件，点提示条 **接受**（macOS：`Command + Enter`；Windows：`Ctrl + Enter`）/ **拒绝**（macOS：`Command + Backspace`；Windows：`Ctrl + Backspace`）。

- **生成并运行命令**：AI 给出可一键运行的 Shell 命令，可 **复制**、**添加到终端** 或 **运行**。

- **回退版本**：与 Builder 相同，回退到指定轮次发起前的版本（不可撤销；仅限最近活跃的 Builder 窗口、最近 10 轮会话）。

### 2.6 上下文：让 AI 看到「你正在看的东西」

AI 默认能看到当前正在编辑的文件。要让它看别的内容，有三种方式。可以把它理解成**给方法的入参**：不传参，它只能靠猜；传得准，答案才准。

**方式一：把编辑器里的内容作为上下文**

1. 选中代码。
2. 点悬浮菜单的 **添加到对话**，加进侧边对话框。

输入框里会显示所选内容的文件名和行号。

![1739856311726-79a79481-586f-4c30-b34f-72a63961ccdb.webp](images/1739856311726-79a79481-586f-4c30-b34f-72a63961ccdb-966826.webp)

3. （可选）继续追加其他片段或其他来源的上下文。

![1739856311448-846ae1e7-63e8-4e5d-90a6-8b7dc18af241.webp](images/1739856311448-846ae1e7-63e8-4e5d-90a6-8b7dc18af241-249570.webp)

4. 在上下文旁输入问题并发送。

![1739856311480-7df231d8-4cc7-4f2e-8633-f0e6a4e737f6.webp](images/1739856311480-7df231d8-4cc7-4f2e-8633-f0e6a4e737f6-594286.webp)

**方式二：把终端里的内容作为上下文**

1. 在终端里点选输出片段。
2. 点片段区域右上角 **添加到对话**。

输入框里会显示来源和行号。

![1739856311579-29f3f94b-0cb5-4cc2-8692-2f95f5f7b516.webp](images/1739856311579-29f3f94b-0cb5-4cc2-8692-2f95f5f7b516-000823.webp)

3. （可选）继续添加终端里其他片段或其他来源。

![1739856311546-b7317e4d-efb9-472a-a78b-632e6533bc4f.webp](images/1739856311546-b7317e4d-efb9-472a-a78b-632e6533bc4f-624907.webp)

4. 输入问题并发送。

![1739856311684-766c50c4-1945-4ceb-bccc-7e52b80940fb.webp](images/1739856311684-766c50c4-1945-4ceb-bccc-7e52b80940fb-226751.webp)

**方式三：用 `#` 键添加上下文**

在输入框里通过 `#` 添加代码、文件、文件夹、工作区等上下文；列表默认展示与当前文件相关的内容作为推荐，也可以自己搜索、组合多种来源。

> 若 Trae 里没有对应语言的 LSP（语言服务），请先安装，否则可能识别不到代码符号。

1. 输入 **#** 或点 **# 引用**，选 **Folder** 回车，列表展示相关文件夹，悬浮可预览目录。

### 2.7 多模态输入

Builder 和 Chat 两种模式都支持多种图片上传方式：

- 把图片从外部拖进对话输入框。
- 把项目文件树里的图片拖进去。

## 三、DeepSeek 入门与提问方法

DeepSeek 是国内使用门槛最低的大模型之一：网页端、App、API 三条入口都能用，而且 API 兼容 OpenAI 格式，Java 项目几乎不用改代码就能接。这一章先讲怎么用，再讲**怎么问**——同样的模型，问法不同，结果质量差一个档次。

### 3.1 DeepSeek 是什么

DeepSeek 是深度求索公司开发的大语言模型系列，具备自然语言理解与生成、代码、数学推理、多模态等能力。它在 2025 年初因为开源策略和低成本推理引起广泛关注：应用一度在美国苹果应用商店免费榜登顶，开源权重也让企业可以自行部署。

对开发者来说，最需要记住的是它的**两个产品形态**：

| 形态 | 入口 | 适合谁 |
| --- | --- | --- |
| 网页 / App | 官网与各大应用商店 | 日常问答、写文档、做原型 |
| API | 编程调用（OpenAI 兼容） | 接进业务系统、IDE 插件、脚本 |

> **版本说明（2026 年 11 月核对）**：DeepSeek 的模型迭代很快。原文写作时（2025 年初）主流是 `deepseek-chat`（V3）与 `deepseek-reasoner`（R1）；核对时官方 API 文档列出的模型是 `deepseek-flash` 与 `deepseek-v4-pro`，上下文长度 1M token、最大输出 384K，并支持「思考模式」开关。旧的模型名可能仍被接受但已指向新模型，**调用前请以官方「模型与价格」页为准**。

### 3.4 API 版本：用 OpenAI 兼容格式调用

DeepSeek 的 API **兼容 OpenAI 格式**：换掉 `base_url` 和 `model`，原来的 OpenAI SDK 就能直接用。这对 Java 项目的意义是——你不需要为 DeepSeek 单独写一套客户端。

| 参数 | 值（2026 年 11 月核对） |
| --- | --- |
| base_url（OpenAI 格式） | `api.deepseek.com`（走 HTTPS，完整地址见下方代码块） |
| 接口路径 | `POST /chat/completions` |
| 鉴权 | `Authorization: Bearer <API_KEY>` |
| 模型名 | `deepseek-flash`、`deepseek-v4-pro`（旧名可能仍兼容） |

先用 curl 验证连通性（**代码块里的地址是示例，不是正文引用**）：

```bash
curl https://api.deepseek.com/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer ${DEEPSEEK_API_KEY}" \
  -d '{
        "model": "deepseek-flash",
        "messages": [
          {"role": "system", "content": "You are a helpful assistant."},
          {"role": "user", "content": "用一句话解释什么是 token"}
        ],
        "stream": false
      }'
```

Java 里用 JDK 自带的 `HttpClient` 直接发这个请求，可以看清报文结构（生产环境建议用 SDK 或 Spring AI，见第七章）：

```java
import java.net.URI;
import java.net.http.*;
import java.nio.charset.StandardCharsets;

public class ChatDemo {
    private static final String API_KEY = System.getenv("DEEPSEEK_API_KEY");

    public static void main(String[] args) throws Exception {
        String body = """
            {
              "model": "deepseek-flash",
              "messages": [{"role": "user", "content": "用一句话解释什么是 token"}],
              "stream": false
            }
            """;

        HttpRequest request = HttpRequest.newBuilder()
                .uri(URI.create("https://api.deepseek.com/chat/completions"))
                .header("Content-Type", "application/json")
                .header("Authorization", "Bearer " + API_KEY)
                .POST(HttpRequest.BodyPublishers.ofString(body, StandardCharsets.UTF_8))
                .build();

        HttpResponse<String> response = HttpClient.newHttpClient()
                .send(request, HttpResponse.BodyHandlers.ofString());

    }
}
```

### 3.5 有效提问的五个黄金法则

这一节是全篇最实用的部分。**提示词（prompt）就是你给模型的入参**，入参写得含糊，返回值自然不能用。

1. **明确需求**：❌「帮我写点东西」 → ✅「我需要一封求职邮件，应聘新媒体运营岗位，强调 3 年公众号运营经验」。
2. **提供背景**：❌「分析这个数据」 → ✅「这是奶茶店过去三个月的销售数据，请分析周末与工作日的销量差异（附 CSV）」。
3. **指定格式**：❌「给几个营销方案」 → ✅「请用表格列出三种情人节咖啡店促销方案，含成本预估和预期效果」。
4. **控制长度**：❌「详细说明」 → ✅「请用 200 字以内解释区块链，让完全不懂技术的老人能听懂」。
5. **及时纠正**：不满意就追加约束，如「这个方案成本太高，请给出预算 500 元以内的版本」「请用更正式的语气重写第二段」。

用 Java 的话说：**把模型当成一个只能看到你消息的新同事**，接口文档、表结构、错误堆栈、期望输出格式，该给的都要给。

### 3.6 新手必学的 5 个基础指令

| 指令 | 作用 | 对应 Java 场景 |
| --- | --- | --- |
| `/续写` | 回答被截断时继续生成 | 长篇文档、代码文件被截断 |
| `/简化` | 把复杂内容换成大白话 | 看不懂的报错、论文、源码注释 |
| `/示例` | 要求给出实际案例 | 让它给出可运行的示例代码 |
| `/步骤` | 让 AI 分步骤指导 | 操作类任务（装环境、建库） |
| `/检查` | 帮你找文档里的错误 | 代码 review、文档校对 |

> 这类「斜杠指令」是否支持、叫什么名字，取决于你用的客户端版本；本质仍然是提示词，不生效时直接把要求写成自然语言即可。

**场景演练**：输入「/步骤 如何用手机拍摄美食照片」观察分步指导；输入「请解释量子计算，然后 /简化」，对比前后差异。

### 3.7 文件处理与代码生成

**文档分析**：点回形针图标上传文件（常见支持 PDF / Word / TXT），然后给出具体指令。

两个坑：超过 50 页的文档先拆开处理；扫描版 PDF 要确认文字可复制（否则模型看到的是图片）。

**让 AI 写代码的万能模板**：

```text
【语言】Python
【功能】自动下载网页图片
【要求】处理 SSL 证书错误；显示下载进度条；保存到指定文件夹
```

**执行策略**：先让它生成代码 → 要求加注释 → 请它逐行解释关键逻辑 → 遇到报错直接把完整堆栈贴进去。这相当于把「编译 → 报错 → 改」的循环交给它，你只做验收。

### 3.8 场景实战：论文、自媒体、学习规划

**学术论文全流程**

- **阶段 1 开题**：输入「我是机械工程专业本科生，请推荐 5 个适合毕设的智能机器人课题，要求具有创新性但不过于前沿、需仿真实验而非实物制作、附参考文献查找关键词」；也可以上传 10 篇 PDF，让它用表格按「创新点 / 局限 / 可借鉴处」三列对比。
- **阶段 2 正文写作**：方法描述用「请将这段实验步骤改写成学术被动语态」；数据可视化提供 Excel 后让它推荐图表类型；降重用「`/学术化改写` 保持原意但调整句式结构」。
- **阶段 3 格式调整**：如「请检查论文格式：三级标题用 1.1.1 格式、参考文献 [1] 补 DOI、图片居中加『图 1-』编号、行距 1.5 倍」。
- **阶段 4 文本辅助**：查重预检——「分析以下段落：[粘贴文本]，预测查重率及高危片段、识别潜在引用缺失、给出改写建议」；期刊匹配——按研究领域 / 创新点 / 数据量推荐冲刺、保底、新兴开源期刊并附影响因子与审稿周期；进度跟踪——「追踪[研究关键词]的最新预印本，每周生成简报」。
- **避坑**：警惕「该领域最新研究显示」这类模糊表述（很可能是编的）；敏感数据用「假设我们有某型号机床的振动频率数据」替代真实数据；答辩 PPT 生成后务必人工检查动画逻辑。

**自媒体运营从 0 到 1**

- **标题生成**：基础版「请生成 10 个关于『时间管理』的小红书标题，要求使用 emoji、含数字量化、突出痛点解决」；进阶版「把『Python 入门教程』改写成吸引大学生的短视频标题，要求悬念结构、不超过 15 字、带热门话题标签」。
- **内容创作模板**：`【类型】科普类短视频脚本 / 【主题】量子计算机原理 / 【要求】用「冰箱整理食物」类比解释量子比特；每 30 秒设置一个悬念转折；结尾引导点赞`。
- **排版优化**：「将这段文字改造成适合公众号的排版：每段不超过 3 行、关键句加 emoji、添加间隔符号、重要数据标注颜色」。
- **数据分析**：上传后台数据截图后输入「分析粉丝活跃时间段，建议下周最佳发稿时刻表，用 24 小时制展示高峰时段」。

**智能学习规划**

- **步骤演示**：①输入背景「我需要三个月内雅思达到 7 分，当前 5.5，每天可学习 3 小时」；②生成计划「请按周制定备考方案，包含每日各科时间分配、必备资料清单、阶段自测时间点」；③动态调整「本周听力正确率仅 60%，请重新调整下周听力训练计划」。
- **知识点攻克**：概念理解——「用三句话解释蒙特卡洛模拟，第一句类比生活场景、第二句技术定义、第三句应用案例」；错题分析——上传错题照片后「请解析错误根源，并推荐 3 道同类强化练习题」；记忆强化——「把这些医学名词生成记忆口诀，每句 7 个字押韵」。
- **学习监督**：每周日晚 8 点提醒提交学习总结；刷手机超 30 分钟发警示；完成阶段目标后生成奖励方案。
- **避坑**：论文场景慎用「帮我写文献综述」这类宽泛指令，改成「请对比 A 学者和 B 学者在 XX 理论上的分歧」；自媒体不要直接发布 AI 生成的时事评论，必须人工核实；学习场景当 AI 建议「每天背 200 个单词」时，追问一句「如何科学分配复习周期」。

### 3.9 进阶：私人知识库、自动化工作流、跨语言

**构建私人知识库（以「平台提供文档问答能力」为前提）**

> 说明：各平台（含 DeepSeek 网页端、百炼、Dify 等）的知识库入口与接口各不相同。原文给出的 Python 片段使用的是示意接口，**不是官方 SDK 的真实用法**，这里保留是因为它把「建库 → 传文档 → 设触发词 → 调用」的流程讲清楚了。

- **Step 1 数据准备**：适合法律判例库、疾病诊疗手册、产品知识等场景。先做结构化模板，例如糖尿病饮食管理（核心要点：每日碳水摄入 ≤ 130g、推荐荞麦 / 西蓝花 / 鳕鱼；禁忌：高 GI 水果荔枝 / 龙眼 / 香蕉，加工食品蜜饯 / 罐头 / 火腿肠；常见问题：无糖饮料建议每周不超过 2 罐）。格式转换：纸质资料用手机扫描成可编辑 PDF，聊天记录导出为 TXT。清洗指令：「请删除文档中的重复段落，并按『概念定义-操作步骤-注意事项』结构重组内容」。
- **Step 2 建立索引**：进「知识库」面板 → 新建 → 拖拽上传（PDF / Word / Markdown）→ 设置调用关键词（如「当问题包含『治疗方案』或『用药指南』时优先调用该库」）。流程示意代码：

```python
# 示意代码：展示建库调用的参数结构，非官方 SDK 用法
import os

def create_knowledge_base():
    config = {
        "name": "心血管疾病诊疗知识库",
        "documents": [os.path.abspath("data/heart_disease.pdf"),
                      os.path.abspath("data/treatment_guide.docx")],
        "description": "内科诊疗标准（2024 版）",
        "access_level": "private",   # private / internal / public
        "trigger_keywords": ["治疗方案", "用药指南"],
    }
    # create_knowledge_base(config) 的具体方法名取决于所用平台
    return config

if __name__ == "__main__":
    print(create_knowledge_base())
```

- **Step 3 调用与维护**：对话中激活，如 `@我的知识库[心血管疾病] 患者男性 58 岁，血压 160/95，有吸烟史，请推荐干预方案`；每月做一次「知识体检」——「找出知识库中过时的药品名称，对比最新版国家药典」；并加一条纠错机制「当用户指出知识库错误时自动生成修订工单」。

**自动化工作流**

- **场景 1 日报自动生成**：数据源接钉钉 / 企业微信日志、销售系统 CRM。处理链：`/创建自动化流程`，名称「销售日报生成」，触发条件每天 18:00，动作是读 CRM 今日订单 → 对比昨日算增长率 → 生成三段式日报（关键指标 / 异常预警 / 明日建议）→ 发邮件；异常处理：日报出现「下降」「异常」关键词时自动抄送技术负责人。
- **场景 2 智能客服中台**：官网表单收到咨询 → 触发模型 API → 按「售后 / 报价 / 技术」分类 → 简单问题直接回复、复杂问题生成工单派发。自动回复模板示例：`当问题包含["怎么退货","运费谁付"]时回复：7 天内无理由退货（标签未撕）、质量问题免运费（附照片证明），需人工帮助回复「转接客服」`。

**跨语言自由切换**

- **模式 1 精准翻译**：设定源语言中文、目标语商务英语，要求保留敬语格式、金额保留两位小数、使用 ICC 国际商会术语。例：「关于 FOB 上海条款，我方建议分批装运以降低风险」→ 商务英语邮件（Incoterms 2020、partial shipments、ICC guidelines）。
- **模式 2 学术润色**：模仿参考论文的用词风格翻译摘要；做术语一致性检查（确保「纳米材料」统一译为 nanomaterials）；保留格式（图表标题维持 `Figure 1-` 格式）。
- **模式 3 文化适配**：例如向印度客户解释「质量第一」的企业文化——用当地知名企业（如塔塔集团）的质量标准做类比代替国内案例、把「追求完美」改为「持续改进的承诺」、避开宗教敏感比喻。

**避坑**：不要直接上传机密合同，用「某品牌采购协议」替代真实名称；涉及财务审批的流程必须保留人工确认环节。

## 四、把 DeepSeek 用在 Java 日常工作里

这一章是给 Java 后端准备的「提示词清单」：需求评审、写代码、SQL 与 JVM 调优、线上排查、读源码，每个场景给出可直接复用的提问模板。模板的价值不在文字漂亮，而在于**把上下文和验收标准一次讲清**——这正是后面第六章要讲的提示词工程。

### 4.1 需求分析与设计阶段

**需求转技术方案**——提示词示例：

```text
我需要设计一个电商订单系统，要求：支持订单创建、支付、发货、确认收货；
考虑高并发；订单状态流转可追踪。
请给出系统架构建议、数据库表设计、关键类图、可能的性能瓶颈和解决方案。
```

它给出的**分层架构建议**通常包含：

- **接入层**：负载均衡（Nginx / HAProxy）分发请求，支持横向扩展。
- **业务服务层**：订单服务（创建与状态流转的原子操作）、支付服务（对接第三方支付、处理回调）、库存服务（预扣避免超卖 + 最终扣减）、物流服务（对接物流接口触发发货）、事件总线（Kafka / RabbitMQ 解耦，保证最终一致性）。
- **数据层**：MySQL（分库分表 + 读写分离）存订单核心数据；Redis 缓存热点订单、Elasticsearch 优化查询；时序数据库（InfluxDB）记录状态变更流水。
- **监控与治理**：分布式追踪（SkyWalking / Zipkin）记录状态流转链路；限流熔断（Sentinel / Hystrix）应对突发流量。

**数据库表设计**：订单主表 `order`（`order_id` 作分表键、`user_id`、`total_amount`、`status`、时间戳）；状态变更流水表 `order_status_log`（`from_status` / `to_status` / `operator`，用于追踪）；支付流水表 `payment`；物流表 `shipping`。

**关键类图**：`OrderService`（createOrder / payOrder / shipOrder / confirmReceipt）、`PaymentService`（executePayment / handlePaymentCallback）、`LogisticsService`（createShipping / updateShippingStatus）、`Order`（changeStatus）与枚举 `OrderStatus`（PENDING_PAYMENT / PAID / SHIPPED / RECEIVED）；状态变迁适合用**状态模式**管理——和 `switch(status)` 相比，状态模式把「每个状态下允许的动作」收敛到各自的类里，加状态不用改散落的 if。

**性能瓶颈与对策**：

| 瓶颈 | 常见对策 |
| --- | --- |
| 订单创建高并发写入 | 异步削峰（先写 Redis 队列，后台批量落库）、分库分表（按 `user_id` / `order_id` 哈希） |
| 状态查询频繁 | 多级缓存（Redis + 本地 Caffeine，设置合理 TTL）、读写分离 |
| 分布式锁竞争（支付回调、状态变更幂等） | 乐观锁（`version` 字段）、Redis 分布式锁 |
| 消息队列堆积 | 动态扩容消费者、批量消费 |

一句话总结：微服务拆分 + 异步化 + 分库分表 + 多级缓存扛并发，状态流转用流水表记录，再配合分布式追踪做全链路监控。

**设计模式应用**——提示词示例：

```text
以下场景应使用什么设计模式并给出示例代码：
① 支付功能支持多种支付方式（支付宝/微信/银行卡）；
② 支付过程需经风控、库存锁定、订单生成等步骤；
③ 支付完成后需通知多个子系统。
```

参考答案：策略模式、模板方法 / 责任链模式、观察者模式。

### 4.2 编码阶段

- **Entity 层**：提示词「生成订单实体类，包含基础字段（id / orderNo / userId / totalAmount / status / 时间）、JPA 注解、校验注解、builder 模式、业务方法」，产出带 `@Entity @Table @Data @Builder` 的 `Order` 类，含 `canPay()`、`pay()` 等业务方法。
- **Repository 层**：提示词「为 Order 实体生成 Repository 接口，含基础 CRUD、自定义查询、分页、必要注解」，产出 `@Repository` 接口，含 `findByOrderNo`、用 `@Lock` 加悲观锁的 `findByIdForUpdate`、按用户与状态查询、`Page` 分页查询。
- **缓存**：提示词「为订单查询接口添加多级缓存方案：用 Spring Cache 注解、集成 Redis、考虑缓存击穿 / 穿透 / 雪崩、添加缓存预热」，产出 `@Cacheable` / `@CacheEvict` 用法与 `RedisCacheManager` 配置（TTL、序列化、按 cache 名单独配置 TTL）。
- **异步处理**：提示词「实现订单创建成功后的异步处理（发短信、更新积分、生成对账），用 Spring 异步特性、异常处理、重试机制、幂等性」，产出 `@Async` + `@Retryable`（maxAttempts / backoff）+ `CompletableFuture` + Redis 分布式锁做幂等 + `@Recover` 失败入重试队列。
- **单元测试**：提示词「为以下 Service 方法生成完整单元测试：多个测试场景、JUnit 5、必要 Mock、边界条件、异常情况」，产出 `@ExtendWith(MockitoExtension.class)` 测试类，含正常场景、库存不足失败场景、参数校验边界测试（`@Mock` / `@InjectMocks` / `when` / `assertThrows` / `verify`）。

> 这四类提示词有个共同点：**把「要什么技术栈、要覆盖哪些边界」写进需求**。不写技术栈，它会用 Reactor 或 JPA 之外的东西给你惊喜；不写边界，它只测正常路径。

### 4.3 性能优化与维护

**SQL 优化**——提示词：「对一个含多表 `LEFT JOIN`、时间过滤与排序的查询，请提供索引建议、SQL 重写建议、可能的性能瓶颈、分页优化方案」。

**JVM 调优**——提示词：「现象是频繁 Full GC、老年代持续增长、响应时间不稳定、疑似内存泄漏，请提供诊断方法、JVM 参数调优建议、代码层面优化建议、监控方案」。

**日志分析**——提示词：「对如下错误日志（如 `Redis command timed out` 的 `TimeoutException` 堆栈）请给出可能原因、排查步骤、解决方案、预防措施」。

**代码重构**——提示词：「按 SOLID 原则、提取合适的设计模式、优化结构、补充注释，重构 `OrderProcessor.process()`」。

> 注意：模型给出的 JVM 参数、索引建议只是**候选方案**，必须结合压测与 `EXPLAIN` 验证。原文没有给出任何「调完快几倍」的数字，这里也不编——性能结论只能来自你自己的压测。

### 4.4 技术学习与提升

- **源码分析**：「解析 Spring `@Transactional` 注解的实现原理：代理机制、事务传播机制、回滚机制、隔离级别实现，并给出示例代码」。
- **框架特性**：「解释 Spring Boot 自动配置原理：`@EnableAutoConfiguration` 的作用、`spring.factories`（Boot 3 之后对应 `AutoConfiguration.imports`）的作用、条件注解的使用、自定义 starter 的开发步骤，并提供示例代码」。

读源码时最有效的一句追问是「**请指出这段逻辑在哪个类、哪个方法，并解释为什么这样设计**」——它会把「背结论」变成「讲链路」。

### 4.5 最佳实践建议

- **提示词编写技巧**：①结构化描述（明确输入输出格式、分点列举需求、提供上下文）；②渐进式优化（先拿到基础实现，再逐步加约束）；③场景细化（给具体业务场景、说明技术栈、指出性能要求）。
- **代码质量控制**：审查业务逻辑正确性、代码规范、性能影响三项，AI 生成 ≠ 可以直接合并。

## 五、用 AI 提升学习与复盘

这一章把提示词从「写代码」挪到「学习方法」上：读论文、刷错题、开会、建个人知识库、写脚本、准备面试，甚至写小说。**核心套路只有一个：把模糊的目标拆成可检查的步骤，让模型逐步产出。**

### 5.1 学习加速器

**论文精读（三阶速读法）**

1. **预判提问**（5 分钟）：「请用 200 字概括《[论文标题]》的核心创新点，用『已知…但…因此…』结构表述，并列出 3 个值得深挖的疑问」。
2. **图表解析**：「解释 Figure 3 的实验设计逻辑，用箭头图表示变量关系，并标注作者可能省略的控制变量」。
3. **批判思考**：「找出该研究方法的 3 个潜在局限，并提供 2 篇 2023 年后发表的反向证据论文」。

> 贴士：遇到公式用 `Alt + 鼠标拖动` 选中，直接问「请用小学数学知识解释这个公式的含义」。

**错题攻克（四步闭环）**

1. **错误诊断**：拍照或输入题目后问「分析我在这道几何题中的思维误区，用认知心理学中的『确认偏差』概念解释」。
2. **变式训练**：「基于该题知识点生成 3 道难度递增的变式题，附加解题路线图提示（不直接给答案）」。
3. **记忆强化**：「把解题关键步骤转化为顺口溜，要求押韵且包含『辅助线』『相似比』等术语」。
4. **监控报告**：「统计我过去一周在三角函数板块的错题类型分布，用饼状图呈现并标注突破优先级」。

> 避坑：别直接要答案，用「给我提示而不是答案」触发引导模式。

**会议纪要（30 秒整理）**

- **录音转重点**（需上传录音）：「提取关键决策，用【决议事项】【责任人】【时间节点】三栏表格呈现，标注有争议的内容」。
- **行动清单**：「把会议内容转化为 SMART 原则任务清单，标注需要跨部门协作的事项」。
- **可视化**：「将项目时间线转化为甘特图代码（Mermaid 语法），用 `!` 标注关键依赖节点」。

> 贴士：输入「开启时间戳模式」可让它标注每个议题的讨论时长。

**个人知识库（三步构建）**

1. **信息抓取**：「实时监控对话，自动提取以下内容到知识库：我重复使用 3 次以上的指令、被标记『重要』的解决方案、修改超过 2 次的输出内容」。
2. **智能标签**：「为知识库添加多维度标签：#常用指令 #合同模板 #技术难题 #已验证方案」。
3. **主动推送**：「当我讨论『用户增长』时，自动显示知识库中相关案例和过往成功方案」。

> 这类「自动抓取 / 主动推送」依赖具体工具的能力，多数通用对话产品并不原生支持；把它当成**设计目标**，用笔记软件 + 定期整理也能落地。

### 5.2 自我校正与复盘

**输出校准三板斧**：当答案太官方、不接地气时——①输入「开启小白模式」禁用专业术语；②追加「举个菜市场大妈能懂的例子」；③用「检查是否有超过 20 字的句子」精简。

例：`采用深度学习算法优化特征提取` → `就像用智能筛子快速挑出黄豆里的黑豆`。

**敏感内容自检**（发布前必做）：

| 风险类型 | 自检指令 | 修正方案 |
| --- | --- | --- |
| 医疗建议 | 「检查当前内容是否符合《互联网诊疗管理办法》」 | 添加「以上建议不能替代专业医生诊断」 |
| 投资理财 | 「标注涉及收益承诺的表述」 | 替换为历史数据展示 |
| 政治相关 | 「开启中立模式重写以下内容」 | 补充多方观点、保持平衡 |

### 5.3 零基础代码入门

**代码调试（5 分钟精准排错）**

- **步骤 1 错误信息翻译**：【错误诊断模式】「我遇到[语言]报错：『粘贴错误信息』，请用小白能懂的话解释问题本质、标注可能引发该错误的 3 个常见场景、给出最可能的修复方案（标★）和其他备选方案」。例：Python `IndexError: list index out of range` → 人话解释是「就像拿着只有 5 个座位的电影院票根，去找第 6 排的座位」；高频场景是循环条件错误、边遍历边删除元素、索引算错；修复是访问前加 `if len(your_list) > index:`。
- **步骤 2 上下文分析**：「结合上下文代码片段[粘贴代码]，用箭头图画出变量值变化轨迹、在可疑行号旁标注 🛑 并说明原因、输出修改后的代码差异（用 `+` / `-` 标注）」。
- **步骤 3 防御性编程**：「针对这个错误类型：设计 3 个单元测试用例（含边界条件）、生成自动检测同类错误的防护代码、推荐 2 个相关调试工具」。

> 贴士：复杂错误追加一句「用厨房做饭的比喻解释这个问题」，往往比看十页文档更快懂。

**自动化脚本（从需求到代码的四阶法）**

需求示例：「自动备份指定文件夹到网盘，每周一凌晨执行，保留最近 3 个版本」。

- **阶段 1 需求结构化**：「把需求拆解为技术要素：文件操作（增量备份 / 版本控制）、网盘 API 对接、定时任务、异常处理（网络中断 / 存储不足），输出技术选型建议表（含优缺点对比）」。
- **阶段 2 代码生成**：「用 Python 实现：遍历指定文件夹生成 MD5 校验文件、调用网盘 API 上传（需处理 OAuth2.0 认证）、加日志记录、用 APScheduler 设置每周定时任务；要求每段代码加中文注释、分离配置与核心逻辑、输出 `.env` 模板」。
- **阶段 3 测试优化**：「为上述代码设计测试方案：模拟断网下的重试机制、测试不同版本保留策略、内存泄漏检测方法，生成测试用例伪代码」。
- **阶段 4 交付文档**：「生成用户手册：安装依赖的 pip 命令清单、配置文件修改图示（标注必填项）、常见问题排障流程图、服务监控方案」。
- **避坑**：接口调用出问题时，直接要「生成带错误处理的 API 调用代码模板」；需要跨平台时追加「确保代码在 Windows / macOS / Linux 均可运行」。

**技术面试（精准打击考点）**

- **考点预测**：「根据[目标公司]近 3 年面经和我的技术栈[Java / Python / Go…]，输出高频考点 TOP10、对应算法题编号（标注原题 / 变式题）、系统设计重点领域（附学习路线图）」。示例：某大厂 Java 岗高频考点——并发编程（占比高，重点线程池参数与实战）、JVM 调优（GC 日志分析）。
- **白板编程模拟**：①出题「给我一道中等难度的二叉树题目，包含递归和非递归两种解法、设置 2 个易错测试用例、附时间复杂度分析要点」；②模拟面试「我先用伪代码描述思路（限时 10 分钟），你指出 3 个潜在 bug，我现场修复，最后给优化建议」；③智能反馈「根据我的代码[粘贴]，按大厂评分标准给出等级、标注亮点、指出可能扣分的坏味道」。
- **加分题**：「生成 10 个高频追问问题」，例如「如果数据量扩大 1000 倍如何优化」「这个算法在分布式环境怎么适配」。

> 注意：上面「考点占比 80% / 65%」这类数字来自原文，属于**某一时刻的抽样印象，无法核实**，因此这里只保留定性描述——真正的占比应该自己统计目标公司的面经。

### 5.4 小说创作与视频脚本

**人物关系管理（三维角色建模）**

- **角色档案生成**：「生成小说角色模板：姓名、核心欲望、关键秘密、关系网络（表面 / 真实盟友，直接 / 潜在对手，爱 / 恨 / 亏欠的情感羁绊）」。示例：药店老板 A——核心欲望是掩盖儿子肇事逃逸的真相，关键秘密是私藏了受害者的日记本，表面盟友是办案警员（定期提供假线索），真实对手是暗中调查的记者女儿。
- **关系可视化**：「基于以下人物列表[粘贴]，用 Mermaid 语法生成关系图（区分实线 / 虚线 / 不同颜色箭头）、标注 3 个潜在冲突爆发点、生成时间轴（关键事件对关系的影响）」。导出方式：把代码复制到支持 Mermaid 的 Markdown 编辑器实时渲染，或用 Draw.io 导入生成图表。
- **剧情冲突检测**：「分析当前章节[粘贴文本]：找出人物行为的矛盾点（与其档案不符）、建议 3 个增强戏剧性的改写方向、生成 2 个让读者惊呼的伏笔方案」。
- **避坑**：避免角色脸谱化——追加「给反派添加 3 个合理化动机」；防止剧情漏洞——用「时间线冲突检测」指令。

**视频脚本（情绪曲线）**

黄金结构模板（60 秒）：[0-15s] 反常识开头「你知道吗？90% 的人刷牙方式都是错的！」；[16-30s] 权威背书「口腔医学博士验证的 3 个标准动作」；[31-45s] 视觉演示（错误 / 正确对比，快剪 + 音效）；[46-60s] 行动召唤「点击下方领取刷牙自查表」。

情绪曲线优化：①原始脚本分析——「分析以下文案的情绪波动[粘贴]：输出情绪值曲线（紧张 / 有趣 / 感动）、高潮点间隔统计、建议优化的 3 个节奏卡点」；②峰值设计——「00:18 加入『震惊』事件（数据反差）、00:42 添加『共情』故事（用户证言）、01:05 设置『悬念』提问」；③分镜强化——把「产品优势」段落转成分镜表（时长 / 画面 / 台词 / 音效），如 3 秒手机摔落慢镜头配「每天承受 100 次…」+ 玻璃碎裂声。

## 六、业务系统接入大模型的三种方式

把大模型接进业务系统，业界总结出三种由浅入深的方式：**直接问（PROMPT）→ 先查资料再问（RAG）→ 改模型本身（Fine-tuning）**。这一章讲清三者的原理、成本与适用场景，并给出「先 Prompt、再 RAG、最后微调」的渐进式落地路径。

### 6.1 三种接入方式一览

OpenAI 在其首届开发者大会的技术分享中提出，业务系统接入大模型有三种方式：

| 方式 | 做法 | 成本 | 典型场景 |
| --- | --- | --- | --- |
| PROMPT（提示语） | 直接把要求写进提示词发给模型 | 最低 | 文本总结、改写、分类、写代码 |
| RAG（检索增强） | 先从向量库检索相关文档，再连同问题一起给模型 | 中 | 私域知识问答、客服、制度查询 |
| Fine-tuning（微调） | 用业务数据继续训练模型的部分或全部参数 | 高 | 固定风格 / 格式输出、领域术语密集 |

三句话概括区别：

- **PROMPT**：最简单直接，拿到模型（可以是开源的自己部署）后直接推理，用提示语解决问题，比如生成文章总结。
- **RAG**：先用向量数据库检索出与提问最相关的文档 / 知识，再融入模型的输入，让它在生成时参考这些信息，从而「懂业务」。
- **Fine-tuning**：在已经预训练好的模型基础上，用业务特定数据集对部分或全部参数做微调，让它更贴合特定任务或领域。

### 6.2 PROMPT 方式：提示词工程

PROMPT 方式就是给模型设计合适的提示语以产生对应输出。复杂业务场景下提示语往往非常复杂，于是有了「**提示词工程（Prompt Engineering）**」——利用模型自身能力，通过设计提示语完成任务，目标是找到「效果最好、成本最低」的那一版。（这一领域的公开资料可参考 Prompt Engineering Guide、OpenAI Cookbook 等公开文档。）

> 原文此处写着「目前大模型输入上下文长度一般为 4K 或 16K，部分已支持 32K/128K」。这个判断写于 2025 年初，已经过时：到 2026 年 11 月核对时，主流商用 API 普遍在 128K 以上，DeepSeek 官方文档给出的上下文为 1M token。**做容量设计时请查当前模型的官方规格**。

#### Zero-Shot / One-Shot / Few-Shot

OpenAI 关于 GPT-3 的论文《Language Models are Few-Shot Learners》（2020）的亮点之一就是 Few-Shot Learning：

| 方式 | 给几个例子 | 特点 |
| --- | --- | --- |
| Zero-Shot | 0 个 | 只用自然语言指令（如「把这段英文翻译成中文」），最方便但也最有挑战 |
| One-Shot | 1 个 | 指令 + 一个示例，比 Zero-Shot 更容易让模型理解任务与格式 |
| Few-Shot | 几个 | 指令 + 多个示例，通常能进一步提高准确性和稳定性 |

Prompt 就是承载「指令 + 少量例子」的那段话。类比 Java：Zero-Shot 像只写接口注释就让人实现，Few-Shot 像**附带单元测试**——测试用例本身就是最好的规格说明。

#### 链式思维（Chain of Thought）

把复杂问题拆成环环相扣的步骤逐步解决，能显著提升多步推理的正确率。《Large Language Models are Zero-Shot Reasoners》（Kojima 等，2022）报告：在 MultiArith 数学数据集上，只在答案前加一句「Let's think step by step」，准确率就从约 18% 提升到约 79%。

一个经典例子：杂耍者抛 16 个球，一半是高尔夫球、其中一半是蓝色，问多少个蓝色高尔夫球——不加提示它答「8 个」（错），加了提示后逐步推理「16 → 8 个高尔夫球 → 4 个蓝色」（正确）。

> 对 Java 开发者的类比：这就是「打日志分步调试」——让模型把中间结果写出来，错在哪一步一目了然。

#### 任务分解

把复杂任务拆成更小、更易处理的子任务，比如把「A、B 两城市间搬运货物」拆成装货、运输、卸货三步。浙大与微软研究院的 HuggingGPT 是典型应用：把一个多模态任务拆成多个子任务逐一执行，拆分本身也是通过提示词让模型完成，并在提示词后附上返回示例（即 Few-Shot）让格式更稳定。

#### 在 PROMPT 中嵌入业务知识

一个完整的 Prompt 通常由四个可选部分组成：

| 组成 | 作用 | 例子 |
| --- | --- | --- |
| 用户指令 | 明确要模型做什么（扮演角色、生成内容） | 「你是电商客服，请回答退货问题」 |
| 对话上下文 | 提供之前的对话，帮助理解背景 | 前几轮的用户问题与回复 |
| 附加内容 | 补充业务知识、基础库细节 | 退货政策原文、表结构说明 |
| 输出要求 | 指定格式与限制 | 「输出 JSON，字段为 …」 |

四部分并非必须全有，按需取舍。业务知识放「附加内容」，多轮场景放「对话上下文」。例如「AI 画原型」类项目，就是按这四要素把产品描述与设计规范一起塞进提示词，让模型生成标准前端页面。

### 6.3 RAG 方式：检索增强生成

直接 PROMPT 会遇到两个硬问题：①模型不了解你的业务知识，还可能产生幻觉；②嵌进提示词的业务知识需要随业务变化不断更新。RAG 正是为此设计的，核心是「**先检索相关知识，再融进模型输入**」。

它的价值在于：缓解知识不足与幻觉、避免把私域数据交给第三方训练、可以接入实时数据，从而提高时效性和专业度。

#### RAG 的流程

1. 用户按需求输入问题（如「公司 IT 的电话是多少？」）。
2. 检索器从业务知识池（**向量数据库**）中检索出相关片段。
3. 把用户问题和检索到的知识组合成提示词（如「基于如下内容回答：公司 IT 的电话是多少？内容：公司的 IT 电话是 XXXX」）。
4. 把提示词发给模型，得到回答。

#### 向量检索是怎么实现的

包括「录入」和「检索」两个环节：

- **知识录入**：①把业务文档切分成若干片段（chunk）；②用 **Embedding 模型** 为每个片段计算向量；③把片段原文和向量一起存入向量数据库。
- **知识检索**：①用户输入问题，用同一个 Embedding 模型把问题也算成向量；②在向量库里找与它最相似的片段向量；③返回这些片段。

**「向量相似」到底在算什么**：Embedding 把一段文字映射成一串浮点数（比如 1024 维），语义相近的句子在这个高维空间里距离更近。检索时通常用余弦相似度比较方向，用近似最近邻（ANN）索引加速。

> 生活化比喻：**给每段话在地图上标一个坐标，语义相近的挨在一起**；提问时先算出问题的坐标，再找最近的几个邻居。这和 Elasticsearch 的 kNN 检索是一回事，只是「倒排索引」换成了「向量索引」。

#### 一个业务例子

以「数仓指标智能分析」为例（用自然语言描述需求，直接生成可视化数据展示）：

1. Agent 接到用户问题后先访问向量数据库，找出需要用到的数仓指标定义；
2. Agent 把用户问题和指标定义一起交给大模型，由模型生成查询指令（如 SQL）；
3. Agent 执行查询拿到数据，再返回并呈现给用户。

注意这里的顺序：**先检索、再生成、后执行**——和我们写业务代码时「先查字典表、再拼 SQL」是同一个思路。

### 6.4 Fine-tuning 方式：微调训练

#### 一次完整训练的四个阶段

| 阶段 | 做什么 | 类比 |
| --- | --- | --- |
| 预训练（Pre-training） | 在大规模无标注文本上用自监督学习训练通用语言模型，学到语言的统计规律与语义知识 | 上大学通识课 |
| 指令调优（Instruction Tuning） | 用有标注的（指令，输出）对微调，让模型按人类指令生成期望输出 | 岗前培训：学会听指令 |
| RLHF | 以人类反馈为奖励信号做强化学习，让输出更符合人类偏好 | 试用期按主管反馈调整做法 |
| 业务微调 | 用你的业务数据继续训练 | 上手具体项目 |

#### 微调怎么落地

在平台化的工具上，微调通常只有四步：①选择基础模型；②上传训练数据；③配置训练参数（多数情况用默认配置即可，例如 **LoRA**）；④点按钮启动训练，平台自动处理训练任务。

**LoRA（Low-Rank Adaptation）** 值得单独解释一句：它不改动原模型的全部参数，只在部分层旁边挂一对小矩阵（Adapter），训练完只保存这一小份「外挂参数」（几 MB 到几百 MB），推理时再挂回原模型。好处是省显存、可多套并存——**像给同一个 Service 挂不同的策略实现，而不是 fork 整个仓库**。

#### 一个智能客服的微调例子

- **数据准备**：收集业务领域知识（文档、历史客服记录）；清洗数据（分类后去重、过滤、补充）；构造「一问一答」形式的客服对话数据（也可以调用其他大模型通过 PROMPT 批量构造）。
- **选基础模型**：考虑参数量与各项评测分数——参数越大通常越「聪明」，但推理越慢、显存越贵，最好挑几个候选做实测对比。
- **微调方式**：多数情况直接用 LoRA 微调出 Adapter 参数即可，不必全参微调。

> 微调的三个前提，缺一不可：**有足够多的高质量样本、任务稳定、并且已经用 Prompt / RAG 试过不够用**。数据只有几十条时，微调通常不如把例子写进提示词。

### 6.5 渐进式接入路径与总结

| 步骤 | 做什么 | 判断是否继续下一步 |
| --- | --- | --- |
| 第一步：PROMPT | 编写提示词、建立基本调用逻辑、测试效果 | 效果不达标，说明缺知识或缺格式约束 |
| 第二步：RAG | 用向量库把业务知识检索进提示词；若已有充足训练数据，可跳过直接进第三步 | 知识够了但仍不稳定、风格不对 |
| 第三步：Fine-tuning | 用高质量业务数据微调，提升准确性与推理速度 | —— |

**为什么是这个顺序**：Prompt 一天就能验证；RAG 一周能上线，知识更新只改文档；微调周期以周计，且数据质量决定上限。倒过来做，很容易花两个月训出一个「还不如改提示词」的模型。

原文的结论同样适用：三种方式各有效果与适用场景，最佳实践是**渐进式接入**（PROMPT → RAG → Fine-tuning），先低成本验证，再逐步加码。

## 七、Java 工程落地：Spring AI 与 Spring AI Alibaba

前面讲的是「怎么问」，这一章讲「怎么用 Java 问」。Spring 官方有 **Spring AI**，阿里在其上做了 **Spring AI Alibaba**（深度集成阿里云百炼平台）。两者都是「把模型调用封装成 Spring 风格的 Bean」，写法和你熟悉的 `JdbcTemplate`、`RestTemplate` 一个套路。本章还包含 AI 网关（Higress）做多模型切换与降级的做法。

> **版本说明**：本章所有依赖坐标都在 2026 年 11 月对照官方文档核对过。Spring AI 在 2025 年 5 月发布 1.0 GA，此后 starter 命名从 `spring-ai-xxx-spring-boot-starter` 改为 `spring-ai-starter-model-xxx`；Spring AI Alibaba 也进入 1.0 GA（文档版本 1.0.0.2），依赖从 `spring-ai-alibaba-starter` 变为 `spring-ai-alibaba-starter-dashscope`。原文使用的是 M5.1 时期的旧坐标，下文已更正并保留说明。

### 7.1 Spring AI 与 Spring AI Alibaba 是什么

- **Spring AI**：Spring 官方社区维护的开源框架，2024 年 5 月发布首个 Milestone，2025 年 5 月 1.0 GA。它把模型通信（ChatModel）、提示词（Prompt）、RAG、记忆（ChatMemory）、工具调用（Tool）、MCP 等能力抽象成 Spring 风格 API，与 Spring Boot 生态无缝集成。
- **Spring AI Alibaba**：基于 Spring AI 构建，深度集成阿里云百炼与通义系列模型，并额外提供 **Graph** 多智能体框架（可理解为 Java 版的 LangGraph）。

核心组件只有两个，先记住它们的分工：

| 组件 | 职责 | 类比 |
| --- | --- | --- |
| `ChatModel` | 最底层的模型调用：发 `Prompt`，收 `ChatResponse` | `JdbcTemplate`，直接操作 |
| `ChatClient` | 面向业务的 Fluent API：拼提示词、挂 Advisor（记忆 / RAG / 工具） | 你写的 Service 层，组装调用 |

`ChatClient` 天生支持流式与同步两种编程模型：`call()` + `content()` 拿字符串，`stream()` 拿 `Flux<String>`。有一点容易踩坑——**`call()` 本身不发请求**，真正的调用发生在 `content()` / `chatResponse()` 被调用的那一刻。

### 7.2 最小可用：用 OpenAI 兼容接口接任意模型

只要模型服务提供 **OpenAI 兼容接口**（DeepSeek、Ollama、vLLM、Higress 都提供），Spring AI 就能用同一套代码接入。

```xml
<!-- Spring AI 1.0 GA 起的坐标；1.0 之前的旧名为 spring-ai-openai-spring-boot-starter -->
<dependency>
  <groupId>org.springframework.ai</groupId>
  <artifactId>spring-ai-starter-model-openai</artifactId>
</dependency>
```

```yaml
spring:
  ai:
    openai:
      # 指向任意 OpenAI 兼容服务：DeepSeek、Ollama(http://localhost:11434)、vLLM、Higress 网关
      base-url: https://api.deepseek.com
      api-key: ${AI_API_KEY}
      chat:
        options:
          model: deepseek-flash
```

```java
@RestController
public class ChatController {
    private final ChatClient chatClient;

    public ChatController(ChatClient.Builder builder) {
        this.chatClient = builder.build();
    }

    @GetMapping("/chat")
    public String chat(@RequestParam("input") String input) {
        return chatClient.prompt().user(input).call().content();
    }
}
```

这就是「SpringBoot 快速整合大模型」的全部内容——**一个依赖、两行配置、三行代码**。换成 DeepSeek、Ollama 或自建 vLLM，只改 `base-url` 和 `model`。

### 7.5 用百炼 0 代码搭一个 RAG 应用，再接入 SpringBoot

阿里云百炼是可视化智能体开发平台，提供智能体、工作流、智能体编排三种模式，支持知识库检索、联网搜索等能力。下面的流程是「**先用平台零代码把 RAG 跑通，再让普通 Spring Boot 服务去调它**」。

**1. 先复习 RAG 的两个关键过程**

- **建立索引**：把私有文档（PDF / Word 等）提取文字、切成小块（chunk，避免超过提示词长度限制）、向量化后存入向量库。
- **检索与生成**：用户提问后，从向量库检索相关 chunk，拼进提示词，模型结合参考信息作答。

**2. 开通百炼**：进入百炼控制台（首次开通通常有免费额度），在「模型体验 > 文本模型 > 文本对话」里选一个通义千问模型试问一句。正式搭建前先测一个「模型一定答不上来」的问题，例如「西红市实验十小一年二班的班主任是谁？」——学校是虚构的，属于典型的私有知识问题。

**3. 创建知识库**：①上传示例知识文件到「数据管理」；②「本地上传」后等待解析（可刷新页面）；③在「数据应用-知识索引」里「创建知识库」，命名如「学校信息库」，其余默认（**相似度阈值**越高越精确但可能漏召，越低召回多但可能引入干扰，建议先用默认）；④「选择文件」选中文档，「数据处理」选「智能切分」；⑤状态变为「解析完成」即成功，可「查看切片」。

**4. 创建 RAG 应用**：「应用中心-我的应用」→「新增应用 > 直接创建」；填应用名称、选通义千问系列模型、打开「知识检索增强」（Prompt 栏会自动填充）、选择刚建的知识库。

**5. 测试**：右侧体验窗切到「发布版」，再问一次那个虚构学校的问题，开启知识检索增强后应该能答上来。

**6. 发布**：点右上角「发布」，之后就能通过 API 与该智能体应用对话。

**7. SpringBoot 接入**：加依赖 `com.alibaba.cloud.ai:spring-ai-alibaba-starter:${spring-ai-alibaba.version}`（此处对应 M 版本时期的坐标；1.0 GA 用 BOM + `spring-ai-alibaba-starter-dashscope`），然后配置应用标识与 Key：

```yaml
spring:
  ai:
    dashscope:
      agent:
        app-id: put-your-app-id-here
        api-key: ${AI_DASHSCOPE_API_KEY}
```

| 配置项 | 是否必填 | 说明 |
| --- | --- | --- |
| `api-key` | 必填 | 访问百炼服务的 Key |
| `app-id` | 必填 | 每个百炼应用都有唯一 id |
| `workspace-id` | 选填 | 默认用默认业务空间；在独立业务空间创建的应用需指定 |

之后用 `DashScopeAgent` 调用该应用即可（具体 API 随版本变化，参考官方文档的 agent 示例）。

### 7.6 用 Higress AI 网关做多模型切换与降级

**为什么需要网关**：①同时对接多个模型满足不同场景；②单模型故障时快速回退，保障业务连续性；③Multi-Agent 场景下多模型协同。Higress 的 AI 网关支持多模型服务，具备消费者鉴权、模型自动切换等能力。

> 类比：这就是**模型层的 Nginx + Sentinel**——统一入口、按规则路由、带鉴权与降级。

## 八、MCP 与 Agent：让模型会「用工具」

模型只能「说」，不能「查」。想让它知道现在几点、今天股价、你的订单状态，就得给它配工具。**MCP（Model Context Protocol，模型上下文协议）** 就是这件事的标准化方案。这一章先讲清 MCP 的架构，再用 Windsurf + firecrawl 复刻一个「Manus 式」的自动调研流程。

### 8.1 为什么需要 MCP

对接大模型时经常遇到一类问题：模型无法直接回答「现在几点」「明天气温」「我的订单到哪了」——因为它无法访问超出训练数据时间范围的信息，也不被允许随便访问你的系统。过去每个工具都要为每个 AI 工具单独写一遍集成代码，**N 个模型 × M 个工具 = N×M 份适配**。

MCP 做的是**把接口标准化**：工具方按协议实现一次「MCP Server」，任何支持 MCP 的客户端（AI 工具）都能直接用。适配量从 N×M 降到 N+M。

> 生活化比喻：MCP 是 AI 世界的 **USB 接口标准**。以前每个外设配一根专用线，现在统一成 USB-C，插上就能用。

### 8.2 MCP 的架构

MCP 采用**客户端-服务器架构**：

| 角色 | 职责 |
| --- | --- |
| MCP 主机（Host） | 发起请求的 LLM 应用，如 Claude Desktop、IDE 或 AI 编程工具 |
| MCP 客户端（Client） | 主机内部组件，与某个 MCP Server 保持 1:1 连接 |
| MCP 服务器（Server） | 向客户端提供上下文、工具（tools）与提示词（prompts） |
| 本地资源 | 本机上可供 Server 安全访问的资源（文件、数据库） |
| 远程资源 | Server 可连接的远程资源（如外部 API） |

两个实现细节值得记住：

- **传输方式**：本地 Server 一般走 **STDIO**（标准输入输出，一个 Server 服务一个客户端）；远程 Server 走 **Streamable HTTP**（一个 Server 服务多个客户端）。
- **消息格式**：数据层用 **JSON-RPC 2.0**，请求 / 响应 + 通知（notifications）。

**工作流程**：大模型识别到「这不是我原生能力能答的」请求时，MCP 客户端把请求路由到对应工具模块，工具执行完把结构化结果返回给模型，模型再继续生成。

一句话总结：**MCP 是大模型的能力扩展插件平台**——开发者不必为每个需求重写集成，一次开发、全局复用。

### 8.3 用 Windsurf + firecrawl 复刻 Manus 效果

Manus 值得学的三点：①显式列出计划，逐步执行并同步进度；②信息采集结合 AI 搜索与浏览器视觉识别；③用可视化方式输出结果。用「AI 开发工具 + MCP 服务」就能复刻。

**AI 开发工具**：Windsurf、Cursor 等（原文写作时 Trae 尚不支持，是否支持请以当前版本为准）。

**1. Windsurf 配置规则（Rules）**

新建一个工作空间文件夹；右下角「Windsurf - Settings」→「Memories and Rules」→ Manage，打开自动化效果；在 Edit workspace rules 里设置当前工作区规则，系统会打开 `.windsurfrules` 文件（**每次执行都会固定发给模型**）。

可以把它理解成「**项目级的 system prompt**」——相当于给这个工作区常驻一份编码规范。

```json
{
  "rules": [
    "Speak in Chinese",
    "You are an assistant. When you get a task, do it step by step. Generate a todo.md and update it when you finish a step.",
    "If you get a data analysis task, use Python-based data science",
    "Use Python 3.12 as the primary programming language",
    "Use NumPy for numerical computing and array operations",
    "Use Pandas for data manipulation and analysis",
    "Use uv for environment and package management",
    "Use Dash for web based report",
    "Generate the web based report in a separate file, pretty, modern and interactive",
    "Run a web server and give me the URL",
    "Use Website Preview and firecrawl to get web content",
    "Use a separate file to store project summary",
    "Use a separate file to store todo list",
    "Use a separate directory to store all files from one task",
    "Store all process data in files under the task directory"
  ]
}
```

规则逐条解释：说中文；接任务先整理 `todo.md` 存步骤、逐步执行且每步更新；数据分析任务用 Python；约定 Python 版本与常用库；用 `uv` 管理虚拟环境（用 conda 则相应替换）；以 Web 页面方式做可视化输出；每个任务用独立目录存数据与结果；用 firecrawl 抓取网页内容。

**2. 配置 firecrawl-mcp-server**

firecrawl 是一个「AI 友好」的爬虫：读取指定 URL 内容并返回模型易读的 Markdown 等格式。可以用它的云服务，也可以本地部署。MCP 配置如下（Windows 版本，其他平台替换 `command` / `args`）：

```json
{
  "mcpServers": {
    "firecrawl-mcp-server": {
      "command": "cmd",
      "args": ["/c", "npx", "-y", "firecrawl-mcp"],
      "env": {
        "FIRECRAWL_API_URL": "http://localhost:3002",
        "FIRECRAWL_RETRY_MAX_ATTEMPTS": "5",
        "FIRECRAWL_RETRY_INITIAL_DELAY": "2000",
        "FIRECRAWL_RETRY_MAX_DELAY": "30000",
        "FIRECRAWL_RETRY_BACKOFF_FACTOR": "3",
        "FIRECRAWL_CREDIT_WARNING_THRESHOLD": "2000",
        "FIRECRAWL_CREDIT_CRITICAL_THRESHOLD": "500"
      },
      "disabled": false,
      "autoApprove": []
    }
  }
}
```

注意 `FIRECRAWL_*` 这几个环境变量控制的是**重试与额度告警**：最大重试 5 次、初始延迟 2 秒、最大延迟 30 秒、退避系数 3、额度告警阈值 2000 / 500。这套参数和你在 Java 里配 `RetryTemplate` 的思路一样。

**3. 验证**：输入提示词「阿里巴巴集团发展史及当前集团公司结构」，在 Windsurf 的 Cascade 模式里选一个强推理模型执行。执行期间它会自己解决虚拟环境、依赖、代码报错等问题。其他工具（如 Cursor）也能用同一套流程。

**4. 本地 Docker 部署 firecrawl**

```bash
git clone https://github.com/mendableai/firecrawl.git
cd firecrawl
docker compose build
docker compose up -d
docker compose logs -f          # 没有报错红字即部署成功
curl -X GET http://localhost:3002/test   # 返回 Hello World 说明服务正常
```

> 想接入 MCP 生态里的其他服务（数据库、文件系统、浏览器），思路完全一样：拿到它的 Server 启动命令或 URL，写进客户端的 `mcpServers` 配置即可。

## 九、用自然语言查数据库：SQLChat + Ollama + one-api

业务同事问「上个月销售额最高的产品是什么」，你得写 SQL、导数据、做图。这一章用三个开源工具把这套流程变成「打字提问 → 自动出 SQL → 直接看结果」。

### 9.1 问题与技术栈

传统数据分析里 SQL 是门槛：非技术同事要么找开发，要么找 BI。**自然语言查询数据库（NLQ-to-SQL）** 让用户直接问，系统自动生成 SQL 并返回结果。

| 组件 | 作用 | 类比 |
| --- | --- | --- |
| **SQLChat** | 基于 Web 的自然语言转 SQL 工具，支持 MySQL、PostgreSQL 等；接收问题 → 调模型生成 SQL → 执行并展示结果 | 前端 UI + 调度器 |
| **Ollama** | 本地运行大模型的开源框架，支持 Llama、Mistral、CodeLlama 等，无需云端 | 本地「模型运行时」，像 `docker run` 模型 |
| **one-api** | 开源 API 管理平台，聚合 OpenAI、Azure、Ollama 等多种模型服务，提供统一接口与权限控制 | 模型侧的反向代理 + 账号体系 |

选它们的原因：SQLChat 轻量、支持私有化部署、可自定义提示词；Ollama 支持量化（如 4-bit），能显著降低硬件门槛；one-api 负责把不同厂商的模型统一成 OpenAI 格式，还能统计用量、控制额度。

### 9.2 部署 Ollama 并加载模型

部署前准备：Docker + MySQL（示例用 Windows 桌面版 Docker，MySQL 8.0 跑在宿主机）。

- 到 Ollama 官网（`ollama.com`）下载对应系统安装包；装完访问 `localhost:11434` 能看到提示信息就说明服务起来了。
- 命令行拉模型，例如 `ollama run sqlcoder`（专用于 text-to-SQL 的模型）；支持哪些模型见官网模型库。Ollama 默认没有 Web 界面，靠命令行用。
- 常用命令：

```bash
ollama run llama3:8b-text     # 运行指定模型（首次会自动下载）
ollama list                   # 查看本地已有模型
ollama ps                     # 查看正在运行的模型
ollama rm llama3:8b-text      # 删除本地模型
```

> 提示：Ollama 默认上下文窗口为 4096 token。做 NLQ-to-SQL 时提示词里要带表结构说明，很容易超；建议用 `OLLAMA_CONTEXT_LENGTH` 调大，否则表结构会被截断，生成的 SQL 就会「缺列少表」。

### 9.3 部署 one-api 并配置模型渠道

用 Docker 启动（示例连宿主机的 MySQL）：

```powershell
# 使用 MySQL 时在命令里加 -e SQL_DSN="root:pwd@tcp(host.docker.internal:3306)/oneapi"
# docker 访问宿主机 MySQL 需把 localhost 改为 host.docker.internal
docker run --name one-api -d --restart always -p 3000:3000 -e SQL_DSN="root:1qaz@WSX@tcp(host.docker.internal:3306)/oneapi" -e TZ=Asia/Shanghai -v /home/ubuntu/data/one-api:/data justsong/one-api
```

访问 `localhost:3000`，默认账号密码 `root` / `123456`（**登录后第一件事就是改密码**）。然后配置模型渠道：

- **Ollama 本地模型**：模型重定向填 `{"gpt-3.5-turbo": "deepseek-r1:1.5b"}`。因为 SQLChat 不支持选模型，所以用 `gpt-3.5-turbo` 这个「壳名字」跳到自定义模型；模型名要填「全限定名 + gpt-3.5-turbo」，代理填 `host.docker.internal:11434`。
- **第三方平台模型**（如硅基流动）：重定向填 `{"gpt-3.5-turbo": "Qwen/Qwen2.5-32B-Instruct"}`，模型名填平台上可用的模型全限定名 + `gpt-3.5-turbo`；非本地模型不需要填代理。
- **生成令牌**：配好渠道后生成 API Key，这个 Key 也能直接给 IDEA 等工具用。

> 「模型重定向」这个设计很像 Java 里的**别名映射**：对外暴露统一的名字（`gpt-3.5-turbo`），内部指向实际实现，前端不用改代码就能换模型。

### 9.4 部署 SQLChat

```powershell
# OPENAI_API_KEY: one-api 生成的令牌
# OPENAI_API_ENDPOINT: one-api 地址，如 http://host.docker.internal:3000/v1（务必带 /v1）
docker run --name sqlchat -d --hostname host --restart always -p 3761:3000 -e NEXTAUTH_SECRET=hjisabfia -e OPENAI_API_KEY=sk-xxx -e OPENAI_API_ENDPOINT=http://host.docker.internal:3000/v1 -e NEXT_PUBLIC_ALLOW_SELF_OPENAI_KEY=true sqlchat/sqlchat
```

使用：打开页面 → 左下角设置改为中文 → 配置 MySQL 连接 → 直接输入自然语言提问。至此整套链路打通，不会 SQL 的同事也能自己查数。

**已知限制**：受 token 长度限制（这类方案的通病），表多的时候要按需勾选表；提示词里能看到详细表说明，前期把表结构整理好，后续使用会很顺。

### 9.5 准备示例数据与校验 SQL

```sql
-- 订单主表
CREATE TABLE orders (
  order_id INT AUTO_INCREMENT COMMENT '订单ID（自增主键）',
  user_id INT NOT NULL COMMENT '用户ID（关联用户表）',
  order_date DATE NOT NULL COMMENT '订单创建日期',
  total_amount DECIMAL(10,2) NOT NULL COMMENT '订单总金额',
  PRIMARY KEY (order_id)
);

-- 订单详情表
CREATE TABLE order_details (
  detail_id INT AUTO_INCREMENT COMMENT '详情ID（自增主键）',
  order_id INT NOT NULL COMMENT '订单ID（逻辑关联 orders.order_id）',
  product_id INT NOT NULL COMMENT '商品ID（关联商品表）',
  quantity INT NOT NULL COMMENT '购买数量',
  price DECIMAL(10,2) NOT NULL COMMENT '商品单价（交易快照）',
  PRIMARY KEY (detail_id)
);

-- 各插入 10 条 2024-01 的订单与明细数据
CREATE INDEX idx_order_id ON order_details(order_id);
CREATE INDEX idx_user_id ON orders(user_id);
```

一句「查一下订单主表金额和明细汇总对不上的单子」，SqlChat 会生成类似下面的校验 SQL：

```sql
SELECT o.order_id, o.total_amount, SUM(od.quantity * od.price) AS detail_total
FROM orders o JOIN order_details od ON o.order_id = od.order_id
GROUP BY o.order_id, o.total_amount
HAVING o.total_amount != detail_total;
```

> 这段 SQL 本身也是个好习惯：**汇总字段和明细不一致是最常见的脏数据来源**，把它做成定时任务，比事后排查便宜得多。

Continue 是开源的 AI 代码助手插件，支持 VS Code 与 JetBrains 系列 IDE，能实时给出补全建议，也能连接多种模型。

## 十一、本地部署与私有化

把模型跑在自己机器上有三个理由：**数据不外传、没有排队限流、断网也能用**。代价是显存。这一章用 Ollama 走一遍完整流程，并给出真实的硬件门槛。

### 11.1 DeepSeek-R1 本地部署（Ollama 五步）

**步骤一：安装 Ollama**——到 Ollama 官网（`ollama.com`）下载安装包，双击安装即可。

![1738743300127-433b94b7-4509-4f69-bb6f-f7ebb5d66b53.png](images/1738743300127-433b94b7-4509-4f69-bb6f-f7ebb5d66b53-140597.png)

**步骤二：选择模型**——在 Ollama 官网搜索 `deepseek-r1`，选版本。数字越大参数越多、效果越好，但对机器要求越高：配置一般选 `1.5b`（15 亿参数，最轻量），配置好可选 `7b` 以上。

> **补充说明**：Ollama 上的 `deepseek-r1` 除了 1.5b / 7b / 8b / 14b / 32b / 70b / 671b 这些尺寸标签，还提供 `-qwen-distill-`、`-llama-distill-` 之类标签，含义是「基于 Qwen 或 Llama 底座蒸馏出来的小模型」。真正的 671B 满血版需要数百 GB 内存/显存，个人电脑基本跑不动；能跑的通常是蒸馏小模型。

**步骤三：复制安装命令**——例如 `ollama run deepseek-r1:1.5b`。


## 十二、用 AI 准备 Java 面试

面试准备最痛苦的不是不会，而是**不知道自己哪里不会**。让模型扮演面试官，按你的简历提问，能很快暴露盲区。这一章给出一次完整的模拟面试复盘，以及分模块的复习清单。

### 12.1 一次完整的模拟面试

准备一份简历（PDF 或截图），提示词：

```text
现在你是大厂 Java 技术专家，请根据我的简历给我做一个完整的模拟面试，
我的求职目标是大厂的高级工程师。
```

![1738833245286-baa670fc-66ee-4ac7-bd49-36880392bef4.png](images/1738833245286-baa670fc-66ee-4ac7-bd49-36880392bef4-089895.png)

假设简历写的是「9 年 Java 开发、3 年大型系统架构设计、2 年团队管理，负责高并发社区电商平台」，它会设计出覆盖五个方面的面试：

#### 一、技术深度考察

1. **Java 基础与 JVM**：`volatile` 的作用与使用场景；线上服务频繁 Full GC 如何排查优化（结合 JVM 内存模型与 GC 算法）；举例说明实际优化过的案例（堆大小、GC 策略调整）。
2. **并发编程与框架源码**：Netty 的 Reactor 线程模型、如何实现零拷贝；对比 Dubbo 与 Spring Cloud 的服务治理机制（负载均衡、熔断降级）；Dubbo 调用超时如何结合源码定位。
3. **分布式事务**：以支付场景说明 TCC 事务与可靠消息最终一致性的适用场景及实现细节；TCC 中 Confirm 阶段失败如何保证一致性。

#### 二、系统设计能力

1. **高并发架构**：日活 300 万、峰值并发 10 万的电商平台，如何设计秒杀系统（流量削峰如队列 / 令牌桶、库存扣减的原子性——Redis + Lua 还是数据库乐观锁、如何防超卖）。
2. **分布式系统**：解释基于 Elasticsearch + Kafka 自研 Trace 系统的核心设计（日志采集、链路追踪、性能统计）；ES 集群写入延迟高如何优化。
3. **数据库与缓存**：单表 10 亿级如何设计分片策略；Redis 集群数据倾斜（某节点负载过高）如何排查解决。

#### 三、项目经验与问题解决

1. **项目深挖**：商品资料专项中旧模型的痛点与新模型的设计（DDD 应用）；会员端接口变慢的优化案例中，本地缓存如何保证与数据库一致。
2. **技术难点与决策**：MySQL 主库 CPU 打高时如何分析慢查询（Explain、索引优化）；公共 Redis 迁移后如何验证数据完整性与一致性。

#### 四、行为面试与软技能

## 十三、附：自己搭一个《我的世界》Java 版服务器

这章和 AI 无关，但和 Java 有关——它是最容易上手的一次「跑一个 JVM 服务、改配置文件、开端口、排查连不上」的完整练习。用本地 Windows 机器搭 Java 版 MC 服务器，再用内网穿透工具（如 cpolar）突破局域网限制实现公网联机，不需要公网 IP，也不用改路由器。

> 有服务器之后有个好处：即使所有玩家下线，「世界」依旧在运行——相当于一个常驻的 JVM 进程。

### 13.1 下载服务端

按需要选版本（以下为项目名称，下载地址请到各自官网获取）：

1. **官方版**：Minecraft 官网的 Java 版服务端下载页。
2. **Forge 版**：带模组加载能力的服务端。
3. **Spigot 版**：常用插件服务端。
4. **Fabric 版**：轻量模组加载器。

也可使用第三方镜像站下载（地址略）。

![1696592234024-cbdf7dd0-12ce-452a-8ad9-0cde999c5e34.png](images/1696592234024-cbdf7dd0-12ce-452a-8ad9-0cde999c5e34-867192.png)

### 13.2 运行服务端

把服务端 jar 放进一个空目录，在该目录下执行：

```bash
java -Xmx1500M -Xms512M -jar server.jar nogui
```

这就是最朴素的 JVM 启动参数：`-Xms` 初始堆、`-Xmx` 最大堆。1500M 只够几个人的小服，人多或加载区块多时要往上调。

第一次启动会在目录里生成一堆文件，其中包括 `eula.txt`。打开它，把 `eula=false` 改为 `eula=true`（表示同意最终用户许可协议），保存。

![1696592480341-3fe4861f-7560-4da1-b334-07ea58c54f58.png](images/1696592480341-3fe4861f-7560-4da1-b334-07ea58c54f58-496273.png)

![1696592511324-8afac221-5258-4fe6-b12b-fd532ce7d926.png](images/1696592511324-8afac221-5258-4fe6-b12b-fd532ce7d926-513683.png)

再打开 `server.properties`（UTF-8 编码的 `key=value` 文本，语法和 Java 的 `Properties` 一脉相承），按需修改：

```properties
# 关闭正版验证，让未购买正版的客户端也能连（仅限私人小服，公网开放有风险）
online-mode=false
# 服务端端口，Java 版默认 25565
server-port=25565
# 世界文件夹名，也是存档目录名
level-name=world
```

改完保存，再执行一次启动命令。**注意：`server.properties` 的修改必须重启服务端才生效**——它不会热加载。

![1696592621733-ec01f350-81b5-4323-a5a6-ca2221f5082c.png](images/1696592621733-ec01f350-81b5-4323-a5a6-ca2221f5082c-202224.png)

### 13.3 客户端与常见问题

客户端推荐官方启动器或 HMCL 启动器；如果服务端已就绪、端口也放行了却连不上，优先换这两个启动器再试。

![1696592662044-4cab116e-2411-49c7-ac22-f6821658ce92.png](images/1696592662044-4cab116e-2411-49c7-ac22-f6821658ce92-989534.png)

**常见问题**：

| 现象 | 原因 | 解决 |
| --- | --- | --- |
| 登入失败：无效会话（请尝试重启游戏及启动器） | 客户端未使用正版账号登录 | 用正版账号登录，或在服务端把 `online-mode` 改为 `false` |
| 想换地图存档 | 世界目录名不匹配 | 把 `.minecraft/saves` 里的地图改名为 `world`，上传替换服务端目录下的 `world` 后重启；或上传后改 `server.properties` 的 `level-name` |
| 改了配置没反应 | `server.properties` 不热加载 | 改完重启服务端 |

> `server.properties` 各字段的完整说明以 Minecraft Wiki 为准；默认值在不同版本间略有差异（例如 Java 版 `server-port` 默认 25565、`online-mode` 默认 `true`）。
